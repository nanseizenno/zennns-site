## 複数の PCN はどのように状態遷移前制御ネットワークを形成するのか？

一つの PCN（Pre-Control Node / 前制御ノード）は、一つの明確な目標状態入口に対応する。

複雑なエンジニアリングシステムには、複数の目標状態入口が同時に存在し、それらは連続、並列、分岐、循環といった形を取ることがある。

一つの PCN は、一つの目標状態入口における局所的な前制御判定と制御を担当する。現在の入口で選択された制御経路が実際に実行されると、実行結果が生じ、さらに実際のエンジニアリング状態が変化する。

その状態変化によって新しいエンジニアリング状態事実が生じ、それが別の目標状態入口の関連入力となって、実際にその判定環境を変化させる場合、複数の PCN 間にエンジニアリング上の依存関係が成立する。

これらの目標状態入口、それぞれに対応する PCN、そして実際の状態変化によって成立する依存関係から構成される構造を **PCN ネットワーク（PCN Network）** と呼ぶ。

PCN ネットワークは、次のように定義できる。

> **複数の目標状態入口とそれぞれに対応する PCN が、実行結果によって生じる実際の状態更新と、その状態更新が他の目標状態入口の判定環境へ与える影響関係によって接続された、状態遷移前制御ネットワーク。**

PCN 間の依存関係を成立させるのは、実行後の状態更新によって生じた実際のエンジニアリング状態事実である。前段の PCN で生成された CAE-SDB 判定結果は、その PCN 自身の状態遷移判定履歴に保持され、そのまま次の PCN へ判定結果として引き渡されるわけではない。

PCN ネットワークの基本的な実行関係は、次のように整理できる。

```text
PCN-A
→ 実行結果
→ 状態更新
→ エンジニアリング状態事実を更新
→ 他の目標状態入口の判定環境に影響
→ PCN-B が自身の状態マッピングと判定を再実行
```

ここでは、ある PCN の実行結果から別の目標状態入口へ、実際の状態変化がどのように影響するかを示すため、矢印表現を用いている。

*図 1：PCN ネットワークの全体構造。複数の目標状態入口と対応する PCN は、実際の状態更新と状態遷移上の依存関係によって接続される。各 PCN は自身の目標状態入口に対応した局所的な判定の意味を保持し、状態遷移判定履歴によって追跡可能な運転履歴を記録する。*

## 1. PCN ネットワークのノードと基本対象

PCN ネットワークのノードとなるのは、独立して設計・判定・制御・記録する価値を持つ目標状態入口と、それに対応する PCN である。

たとえば、次のような関係がある。

| 状態遷移 | 対応する PCN |
|---|---|
| ロボット待機 → 把持段階 | 把持前 PCN |
| 配置完了 → 圧入段階 | 圧入前 PCN |
| 検査待ち → 検査段階 | 検査前 PCN |
| タスク生成済み → 実行状態 | タスク実行前 PCN |
| AGV 到着 → ステーション受入状態 | ステーション受入前 PCN |
| 保全解除 → 自動運転復帰 | 自動運転復帰前 PCN |

設備、PLC、ロボットコントローラ、MES、WCS、品質システム、その他のエンジニアリングシステムは、各 PCN が目標状態入口を判定するために必要な状態情報を提供できる。

PCN の設定単位は目標状態入口によって決まり、設備台数、コントローラ台数、システム名称との間に固定的な対応関係はない。

したがって、一台の複雑な設備の内部に複数の PCN を設定できる。異なる設備間でも、実際の状態変化によって PCN 間の依存関係が成立し得る。MES / WCS、設備、品質、保全、人による操作をまたぐ状態遷移についても、それぞれに対応する PCN を設定できる。

複数の PCN がネットワーク上の関係を構成するのは、目標状態入口間に実際の状態変化による依存関係が存在する場合である。

## 2. 状態事実は安定して保持し、状態遷移上の役割は具体的な目標状態入口に結び付ける

PCN ネットワークで共有の基礎となるのは、実際のエンジニアリング状態事実である。

設備、コントローラ、上位システムは、まず自身が確定できる客観的な運転状態を提供する。

たとえば、

```text
PROCESS_COMPLETE
RUN_READY
STATUS_VALID
品質承認状態
資源占有状態
区域許可状態
下流側の受入状態
タスク状態
```

などである。

これらの状態事実そのものに、あらかじめ C、A、E の役割を固定する必要はない。

C / A / E は、ある状態が現在の目標状態入口に対して担う状態遷移上の役割を表す。各 PCN は、設計または設定段階で、自身が担当する目標状態入口に基づいて関連状態の C / A / E 状態マッピングをあらかじめ定義する。

たとえば、下流設備の受入状態は、上流設備が搬送段階へ移行しようとする場合、E：Execution Chain / 実行チェーン状態に関係する状態として扱い、目標段階へ移行した後に実行チェーンを継続できるかを判定するために使用できる。

同じ状態事実であっても、別の目標状態入口ではエンジニアリング上の役割が異なる場合があり、その場合は別の PCN で異なる役割として定義できる。

ある状態が明確な移行許可を表している場合には、対応する目標状態入口で A：Authority / 許可状態として扱うことができる。

したがって、

> **状態事実そのものの基本意味は安定して保持し、C / A / E の役割は具体的な目標状態入口によって決まる。**

異なる PCN が同じ状態オブジェクトを参照する場合でも、それぞれが自身に定義された状態マッピングを適用する。

実行時には、現在影響を受けている目標状態入口に対して最新状態を読み取り、その PCN に適用される S / D / B 判定を実行する。

## 3. PCN 間のエンジニアリング依存関係はどのように成立するか

PCN ネットワークにおける接続は、設備の物理接続、通信接続、工程順序、システム所属だけを理由として自動的に成立するものではない。

直接的な PCN 間のエンジニアリング依存関係が成立するには、次の過程が必要である。

1. PCN-A が、選択済みの制御経路を実行する。
2. 実行結果によって実際の状態更新（State Update）が生じる。
3. 状態更新によって、エンジニアリング状態事実が新たに生じる、または既存の状態事実が更新される。
4. その状態事実が、PCN-B に対応する目標状態入口の関連入力となる。
5. その変化が、実際に PCN-B の判定環境を変化させる。

これらの条件が成立したとき、PCN-A と PCN-B の間に直接的なエンジニアリング依存関係が成立する。

ここでいう **状態更新（State Update）** とは、選択された制御経路を実行した結果として生じる、実際のエンジニアリング状態の変化を指す。

したがって、

> **PCN ネットワークの接続基盤は、実際の状態変化が他の目標状態入口へ与える影響関係である。**

設備が物理的に接続されていること、通信接続されていること、工程順序が前後していること、同じ設備・生産ラインに属していること、同じ資源を共有していること、統計的に同時発生が多いことだけでは、直接的な PCN 間のエンジニアリング依存関係を成立させるには不十分である。

状態更新の内容は、実際のエンジニアリング対象によって異なる。

たとえば、

- 状態進行
- 許可状態の変化
- 資源状態の変化
- 実行チェーン状態の変化
- タスク状態の変化
- 対象 / サイクル状態の変化
- その他のエンジニアリング状態変化

などがある。

これらは、まず実際のエンジニアリング状態更新として現れ、その後、他の目標状態入口へ影響を与えるかどうかによって PCN 間の依存関係が成立するかを判断する。

たとえば、把持動作が完了して「把持完了」という新しいエンジニアリング状態事実が生じ、それが「配置段階へ移行する」ための関連入力となる場合、配置前 PCN は自身の目標状態入口に基づいて現在状態を読み取り、あらためて判定する。

区域許可、品質承認状態、資源占有、バッファ容量、下流側の受入状態、結果の書き戻し状態などが実際に変化した場合も、更新後の状態事実が別の目標状態入口の判定環境に影響すれば、対応する PCN 間の依存関係が成立し得る。

代替経路、戻し経路、異常処理経路が新しい目標状態に対応する場合には、新しい目標状態入口として独立して前制御判定を行う。

## 4. 各 PCN は局所的な判定の意味を保持し、状態遷移判定履歴によってシステムレベルの関係を追跡する

PCN ネットワークでは、各 PCN が自身の局所的な判定の意味を保持する。

たとえば、PCN-A で `A-D` が生成された場合、それは PCN-A に対応する目標状態入口において、ある許可状態に動的時系列有効性の問題があることを表す。

その後、PCN-A の実行によって実際の状態変化が生じ、それが PCN-B に影響したとしても、PCN-B が `A-D` という判定ラベルをそのまま引き継ぐわけではない。

PCN-B は、更新後のエンジニアリング状態事実を読み取り、自身に定義された C / A / E 状態マッピングを適用し、現在状態に基づいて必要な S / D / B 判定を実行して、自身の CAE-SDB 判定結果を生成する。

その理由は、

> **C / A / E は、状態が具体的な目標状態入口に対して担う局所的な状態遷移上の役割だからである。**

したがって、PCN 間で受け渡されるのは、実際の状態事実と、それを当該目標状態入口で解釈するために必要な関連情報である。

一つの目標状態入口に対する1回の判定について、PCN は状態遷移判定履歴（PCN Trace）を記録する。

代表的な記録内容には、次のものが含まれる。

- 現在状態
- 目標状態
- 目標状態入口
- 関連状態
- C / A / E 状態マッピング
- S / D / B 判定
- CAE-SDB 判定結果
- 制御調停結果
- 複数経路制御結果
- 実行結果
- 時間情報
- 履歴 ID

単一の状態遷移判定履歴は、

> **この目標状態入口で、なぜ現在の判定結果と制御結果が得られたのか**

を説明するために使用できる。

複数の状態遷移判定履歴を実際の状態遷移上の依存関係と対応付けることで、さらに次の内容を追跡できる。

- ある状態事実が、どの上流側の実行結果によって生じたか
- その状態が、どの目標状態入口へ影響したか
- 下流 PCN が、どのような新しい判定結果を生成したか
- その後、さらにどのような新しい状態変化が生じたか

PCN ネットワークの実際の構造は、連続、並列、分岐、循環、複数システムにまたがる構成など、さまざまな形を取ることができる。

一つの状態更新が実際に複数の目標状態入口へ影響する場合には、複数のエンジニアリング依存関係が成立する。

状態タイプの関係には循環が存在する場合もある。

```text
A → B → C → A
```

一方、実際の運転における状態インスタンスは、時間方向に継続して生成される。

```text
A₁ → B₁ → C₁ → A₂
```

A₁ と A₂ は同じ状態タイプ A に属していても、異なる運転インスタンスである。

再加工、戻し、復帰、再投入などの工程経路によって状態タイプ上の循環が存在していても、運転履歴は時間方向に連続して記録される。

## 5. PCN ネットワークのエンジニアリング形態と境界

PCN ネットワークは、異なるエンジニアリング階層に存在し得る。

### 自動化実行ユニット

一つの自動化実行ユニットの内部にも、把持、配置、その後の実行段階など、複数の主要な目標状態入口を設定できる。

前段階の実行が完了すると、新しいエンジニアリング状態事実が生じる。その状態事実が後続の目標状態入口の判定環境に影響する場合、対応する PCN 間にエンジニアリング依存関係が成立する。

### MES / WCS と複数設備の協調

MES / WCS と複数設備が協調する場合、目標状態入口は複数の設備やシステムに分散して存在することが多い。

タスク生成、タスク実行、ステーション受入、引渡しなど、それぞれが明確な目標状態入口となり得る。

タスク、資源、経路、ステーション、許可、実行チェーンなどの状態が実際に更新され、その更新が別の目標状態入口に影響した場合に、PCN ネットワーク上の直接依存関係が成立する。

### 製造 DX と複数システムにまたがる状態遷移

設備、人、MES、品質システム、保全システムの間にも、多くの明確な状態遷移入口が存在する。

たとえば、

- 品質状態更新後に次工程へ移行する
- 保全状態更新後に自動運転へ復帰する
- 作業指示やレシピ状態更新後に新しい生産状態へ移行する

といった場合である。

PCN ネットワークを構成するために、これらのシステムを一つの中央状態システムへ統合する必要はない。

各 PCN は、自身の目標状態入口を基準として関連状態を読み取り、判定を実行し、制御結果を確定する。

異なる PCN は、PLC / HMI、産業用コントローラ、エッジコントローラ、WCS、MES、ソフトウェアサービスなど、異なる位置に配置できる。また、すべての PCN を一つの中央コントローラで統一的に実行する必要もない。

PCN ネットワークが扱うエンジニアリング対象は、目標状態入口間に実際に成立する状態変化による依存関係であり、設備トポロジ、通信トポロジ、通常の生産フロー図そのものではない。

直接的なエンジニアリング依存関係が成立するかどうかを判断するには、次の四点を確認する。

1. PCN-A の実行結果によって実際の状態更新が生じたか。
2. その状態更新によってエンジニアリング状態事実が新たに生じる、または既存の状態事実が更新されたか。
3. その状態事実が PCN-B の関連入力となったか。
4. PCN-B に対応する目標状態入口の判定環境を実際に変化させたか。

これらの関係が成立した場合に、直接的な PCN 間の依存関係を設定する。

PCN ネットワークは、ノード数や接続数を最大化することを目的としない。

より重要なのは、

> **できるだけ簡潔な関係構造で、実際のシステムにおいて状態遷移の判定、制御、伝達、追跡にエンジニアリング上の意味を持つ依存関係を保持すること。**

である。

具体的な実行ライフサイクル、PCN 間通信プロトコル、同期方式、状態更新のデータ構造、完全なインターフェース定義、完全な制御調停ルール、その他の内部実装機構については、本公開ノートでは扱わない。

## まとめ

一つの PCN は、一つの明確な目標状態入口に対応する。

複数の PCN 間に直接的なエンジニアリング依存関係が成立するのは、実行結果によって実際の状態更新が生じ、その更新が他の目標状態入口の判定環境をさらに変化させる場合である。

PCN 間の依存関係を成立させるのは、更新後のエンジニアリング状態事実である。C / A / E や CAE-SDB といった局所的な状態遷移上の意味は、それぞれ具体的な目標状態入口に結び付いており、各 PCN が自身に定義された関係に基づいて状態マッピングと判定をあらためて実行する。

上流 PCN の CAE-SDB 判定結果は、その PCN 自身の状態遷移判定履歴に保持され、下流 PCN の判定結果として直接引き継がれるわけではない。

複数の目標状態入口と、それらの間に成立するエンジニアリング依存関係が連続的に接続されることで、PCN ネットワークが構成される。

したがって、PCN ネットワークは次のようにまとめられる。

> **複数の目標状態入口とそれぞれに対応する PCN をノードとし、実行結果によって生じる実際の状態更新が他の目標状態入口へ与える現実の影響関係を接続基盤として、連続する状態遷移関係を組織・追跡・分析するためのエンジニアリングネットワーク。**

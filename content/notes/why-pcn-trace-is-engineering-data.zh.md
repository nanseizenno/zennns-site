## 为什么 PCN Trace 是一种新的工程数据？

基础概念可参见：

- [Concepts｜核心概念](/zh/concepts/)
- [TPCA / PCN 状态迁移前置控制架构｜白皮书](/zh/whitepaper/)
- [为什么 PCN 是 TPCA 的最小工程节点？](/zh/notes/pcn-minimum-engineering-unit/)
- [为什么状态迁移条件必须显式化？](/zh/notes/explicit-state-transition-conditions/)
- [为什么 OEE 之后还需要 PCN？](/zh/notes/why-oee-pcn/)
- [TPCA 的状态迁移单向性——为什么真实工程系统不存在状态回退？](/zh/notes/tpca-unidirectional-state-transition/)

制造现场已经存在大量数据。

PLC 保存状态和报警，MES 保存生产履历，WCS 保存任务和调度记录，设备平台保存温度、电流、位置、节拍和运行时间。

PCN 并不是因为现场“没有数据”才增加另一套数据。

它关注的是另一种记录对象：

> **一次目标状态迁移为什么被允许、等待、阻断或分流。**

PCN 在每一次状态迁移前置判定中，把当前状态、目标状态、相关输入、C / A / E 状态映射、S / D / B 判定、CAE-SDB 判定结果、控制仲裁、多路径控制、执行结果和时间信息关联起来，形成一条完整的判定履历。

本文将这种记录称为 **PCN Trace**。

其中的设备状态、时间戳、许可、报警、任务和路径状态，本来就可能存在于 PLC、MES、WCS 或其他系统中。

PCN Trace 的不同之处在于：

> **它把一次状态迁移判定本身作为一个完整的工程数据对象。**

同时，PCN Trace 记录的不是脱离时间的静态状态名称。

对于实际运行状态，即使后续再次出现与历史状态相同的工程内容，由于时间位置已经不同，也属于新的状态实例。

因此，PCN Trace 还承担一个基本作用：

> **区分“状态内容相同”与“实际状态实例相同”。**

---

## 1. 传统制造数据主要记录“发生了什么”

制造现场常见数据大致包括以下几类。

### 设备状态数据

- 运行；
- 停机；
- Ready；
- 位置；
- 转速；
- 温度；
- 电流；
- 压力；
- 能耗。

### 生产数据

- 产量；
- 良率；
- 节拍；
- OEE；
- 不良数量；
- 停机时间；
- 损失时间。

### 事件和报警履历

- 报警发生；
- 报警复位；
- 设备启动；
- 设备停止；
- 工序开始；
- 工序结束；
- 任务完成；
- 任务失败。

### MES / WCS 运行记录

- 任务生成；
- 任务分配；
- Waiting；
- Blocked；
- Pending；
- 资源占用；
- 路径状态；
- 站点状态。

这些数据都非常重要。

问题在于，它们通常不是围绕**一次明确的目标状态迁移判定**组织的。

例如，现场可能已经知道：

```text
机器人 Ready = TRUE
安全回路 = TRUE
视觉结果 = OK
下游 Ready = FALSE
机器人未动作
```

这些状态能够说明当时发生了什么。

但如果要继续回答：

> 为什么当时没有进入抓取阶段？

仍然需要重新恢复：

- 当时准备进入哪个目标状态；
- 哪些输入属于条件；
- 哪些输入属于许可；
- 哪些输入属于执行链；
- 当前状态是否仍然有效；
- 是否已经进入控制边界；
- 多个判定结果同时存在时，为什么最终选择了这条控制路径。

PCN Trace 的区别在于：

> **这些信息从一开始就被组织为同一次状态迁移判定的数据。**

此外，同一个状态内容可能在不同时间再次出现。

例如：

```text
Robot Position = Home
Mode = Auto
Ready = TRUE
```

既可能表示任务开始前的状态，也可能表示设备完成一次运行、异常处置或重新投入以后再次形成的状态。

状态内容相同，并不代表两次实际状态实例相同。

因此，仅保存状态值本身，还不足以完整描述状态迁移历史。

## 2. PCN Trace 记录的是一次完整的状态迁移判定

PCN 对应一个明确的目标状态入口：

```text
当前状态 → PCN → 目标状态
```

PCN 在系统进入目标状态之前，对与本次迁移相关的多源状态进行整理和判定：

```text
当前状态
→ 目标状态
→ PCN
→ 多源状态信号
→ C / A / E 状态映射
→ S / D / B 判定
→ CAE-SDB 判定结果
→ 控制仲裁
→ 多路径控制
→ PCN Trace
```

一条 PCN Trace 可以关联：

| 内容 | 工程意义 |
|---|---|
| PCN | 哪一个状态迁移入口 |
| 当前状态 | 系统当时处于什么状态 |
| 目标状态 | 系统准备进入哪里 |
| 关键输入状态 | 本次迁移使用了哪些状态 |
| 时间信息 | 本次状态、判定与执行发生在什么时间位置 |
| C / A / E 状态映射 | 各输入在本次迁移中的工程作用 |
| S / D / B 判定 | 各变量域从哪些性质进行判定 |
| CAE-SDB 判定结果 | 本次前置判定形成了什么结果 |
| 控制仲裁结果 | 多个结果如何形成最终控制方向 |
| 多路径控制结果 | 最终进入哪一条控制路径 |
| 执行结果 | 控制路径执行以后发生了什么 |
| Trace ID | 将上述信息绑定为同一次判定履历 |

例如：

```text
PCN： 抓取入口

当前状态： 等待抓取

目标状态： 进入抓取阶段

时间信息： T₂

CAE-SDB 判定结果： C-D

原因： 视觉结果已超出有效时间

控制仲裁结果： 本次抓取不放行

多路径控制： 重识别 / 回流

执行结果： 工件进入返回路径

Trace ID： PCN-XXXX-XXXX
```

重点不在字段名称，而在于：

> **输入、判定、仲裁、控制、执行结果和时间位置属于同一次状态迁移。**

## 3. 它与普通报警履历的区别，是“记录单位”不同

普通报警履历通常以事件为中心：

```text
10:15:02  视觉结果超时
10:15:03  机器人等待
10:15:04  输送带运行
10:15:06  视觉结果更新
10:15:07  机器人启动
```

这些记录没有问题。

但工程师如果要回答：

> 为什么 10:15:03 没有进入抓取阶段？

仍然需要把多个系统中的事件重新拼接起来。

PCN Trace 的记录单位不同。

它记录的是：

> **某个 PCN 在某一次“当前状态 → 目标状态”迁移入口上的完整判定。**

因此，PCN Trace 可以直接按照以下对象进行统计和比较：

- PCN；
- 目标状态；
- 状态迁移发生时间；
- C / A / E 变量域；
- S / D / B 判定性质；
- CAE-SDB 判定结果；
- 控制路径；
- 执行结果。

时间信息的作用也不仅是给日志排序。

它还用于区分不同的实际状态实例。

例如：

```text
A： Home / Auto / Ready
T₁
```

经过一系列实际状态迁移以后，又出现：

```text
C： Home / Auto / Ready
T₃
```

虽然：

```text
X_A = X_C
```

但：

```text
T_A ≠ T_C
```

因此 A 与 C 属于不同的状态实例。

PCN Trace 保存的正是这些实际发生的状态迁移判定，而不是只保存一个可以重复出现的状态名称。

## 4. PCN Trace 可以直接形成工程改善对象

传统现场数据从发现异常到形成改善，通常还需要工程师完成一系列恢复和解释工作：

```text
发现异常
→ 找到相关设备
→ 查报警
→ 查 PLC
→ 查机器人 / 视觉 / MES / WCS
→ 恢复当时状态
→ 判断为什么没有进入下一阶段
→ 找到改善位置
```

很多时候，真正消耗时间的不是“没有数据”，而是：

> **数据存在，但一次状态迁移为什么没有成立，需要重新还原。**

PCN Trace 在生成时已经绑定：

```text
哪个 PCN
哪个当前状态
哪个目标状态
本次状态和判定发生在什么时间位置
哪个变量域
哪种判定性质
形成了什么 CAE-SDB 判定结果
经过什么控制仲裁
最终走了哪条控制路径
执行结果如何
```

因此，长期积累以后，可以直接观察：

| Trace 中反复出现的模式 | 可以优先检查的工程方向 |
|---|---|
| C-S 集中出现 | 条件信号、接口或映射关系是否完整 |
| C-D 长期出现 | 数据刷新、同步和时间有效性是否合理 |
| C-B 高频出现 | 条件边界与现场波动是否匹配 |
| A-S 集中出现 | 许可来源和接口定义是否完整 |
| A-D 反复出现 | 许可刷新、同步或撤销过程是否稳定 |
| A-B 高频出现 | 许可边界、资源锁或关键约束是否合理 |
| E-S 集中出现 | 下游、回退、异常路径或回写链路是否完整 |
| E-D 长期阻塞 | 执行链、下游承接或协同节拍是否存在问题 |
| E-B 高频出现 | 等待、协调、降级或备用路径边界是否需要调整 |
| 某控制路径频繁触发但后续效果有限 | 对应控制策略是否需要重新设计 |

PCN Trace 不替代工程师判断。

它把改善对象进一步收敛到：

> **哪个状态迁移入口、哪个变量域、哪一种判定性质长期存在问题。**

## 5. 改善以后，可以继续用同一类 Trace 比较

PCN Trace 的另一个价值，是改善前后的数据结构可以保持一致。

例如，某个状态迁移入口长期出现：

```text
C-D 视觉结果失效或不同步
```

工程师修改了视觉结果刷新方式、同步方式或有效性判定以后，可以继续观察同一个 PCN：

- C-D 出现频率是否下降；
- 控制路径分布是否发生变化；
- 重识别或回流次数是否减少；
- 是否出现新的判定问题；
- 执行结果是否发生变化。

同样，如果某个 E 域问题长期出现，也可以在补充执行链、回退路径或下游协调以后，继续用后续 Trace 比较。

由此形成：

```text
PCN 运行
    ↓
PCN Trace
    ↓
聚合与比较
    ↓
发现状态迁移薄弱点
    ↓
工程改善
    ↓
规则 / 配置 / 系统设计更新
    ↓
重新运行
    ↓
新的 PCN Trace
    ↓
改善前后比较
```

这里需要注意：

> **改善前后的状态类型可以相同，但对应的实际状态实例和 Trace 不会相同。**

例如系统经过修改以后再次进入：

```text
WAIT → EXECUTE
```

这不是回到历史上的某一次 WAIT 或 EXECUTE，而是在新的时间位置形成新的状态迁移实例。

因此，PCN Trace 不只是运行日志。

它也是状态迁移改善前后的统一观察接口。

## 6. PCN Trace 使状态迁移本身成为可管理对象

复杂自动化系统中的状态迁移条件，长期分散存在于：

- PLC 程序；
- SFC；
- Interlock；
- 机器人程序；
- 安全逻辑；
- MES / WCS 流程；
- 工程师经验；
- 调试记录；
- 操作规程。

这些机制本身没有问题。

但当现场出现：

> 为什么没有进入下一步？

工程师往往需要跨多个系统重新解释。

PCN 将一个明确的状态迁移入口作为工程对象以后，Trace 可以持续回答：

- 哪些状态迁移入口最容易出现问题；
- 哪些迁移长期处于等待；
- 哪些问题集中在 C；
- 哪些问题集中在 A；
- 哪些问题集中在 E；
- 哪些属于结构问题；
- 哪些属于动态时序问题；
- 哪些经常进入控制边界；
- 哪些控制路径实际有效；
- 哪些问题经过修改以后仍然反复出现。

同时，PCN Trace 保留状态迁移的时间位置。

因此，对于：

```text
Rollback
Recovery
Return
Reset
复归
回流
重新投入
```

等现场常用工程术语，Trace 记录的仍然是：

```text
Current State → New Target State
```

新的 Target State 可以与历史状态具有相同或相似的工程状态内容，但它发生在新的时间位置，因此属于新的状态实例。

从这个角度看，PCN Trace 管理的并不是单纯的设备数据。

它记录的是：

> **状态迁移前置判定在实际运行历史中的表现。**

## 7. 它与制造 DX 的关系

制造 DX 已经大量使用设备数据、生产数据和事件数据：

```text
设备 / 生产数据
→ 可视化
→ 分析
→ 改善
```

PCN Trace 增加的是另一条数据链：

```text
状态迁移前置判定
→ PCN Trace
→ 状态迁移模式分析
→ 工程改善
→ 重新运行
→ Trace 比较
```

两类数据关注对象不同。

| 项目 | 设备 / 生产数据 | PCN Trace |
|---|---|---|
| 主要记录对象 | 设备、过程、任务、生产结果 | 一次目标状态迁移判定 |
| 主要回答 | 发生了什么 | 为什么本次迁移被允许、等待、阻断或分流 |
| 数据组织中心 | 设备、时间、任务、工单、事件 | PCN + 当前状态 + 目标状态 + 时间位置 |
| 主要分析对象 | 稼动、性能、质量、异常、产量 | C / A / E、S / D / B、判定结果、控制仲裁、控制路径 |
| 主要改善方向 | 设备、工艺、保全、生产过程 | 状态迁移条件、许可、执行链和控制路径 |
| 改善验证 | OEE、节拍、产量、报警、质量等 | 后续 Trace 中判定与执行结果的变化 |

设备数据能够说明物理系统发生了什么。

生产数据能够说明生产结果如何。

PCN Trace 则补充：

> **系统在某一个状态迁移入口为什么形成了这样的控制结果，以及这一次判定处于哪一个实际运行位置。**

## 8. 对 PLC / HMI、MES / WCS 和制造企业的价值

### 对 PLC / HMI

传统 PLC / HMI 已经能够显示：

- 信号状态；
- Ready；
- Interlock；
- Alarm；
- 顺序状态；
- 设备状态。

PCN Trace 可以在这些数据之上增加：

- 当前状态；
- 目标状态；
- 时间信息；
- CAE-SDB 判定结果；
- 控制仲裁结果；
- 多路径控制结果；
- Trace ID。

这样，HMI 不只是显示：

```text
CONDITION NOT READY
```

还可以进一步定位：

> **哪一个目标阶段没有成立，以及这一次前置判定为什么没有放行。**

### 对 MES / WCS

MES / WCS 已经拥有大量：

- 任务；
- 车辆；
- 站点；
- 路径；
- 资源；
- Waiting；
- Blocked；
- Pending。

PCN Trace 可以进一步把这些状态组织到具体状态迁移判定中。

系统不仅看到：

```text
WAITING
BLOCKED
PENDING
```

还可以继续关联：

```text
哪个 PCN
哪个目标状态
本次判定发生在什么时间位置
哪个变量域出现问题
属于什么判定性质
形成了什么 CAE-SDB 判定结果
最终进入什么控制路径
```

这为 MES / WCS 的协同停滞分析提供了一种统一的状态迁移判定数据结构。

### 对制造企业

对于制造企业，PCN Trace 还可以让生产技术、设备、电气、机器人、MES / WCS、安全和生产部门围绕同一次判定事件进行复盘。

讨论对象由：

> “PLC 没问题。”
>
> “机器人是 Ready 的。”
>
> “MES 已经下任务了。”
>
> “下游没有报警。”

转变为：

> **这一次状态迁移在哪一个变量域、哪一种判定性质上没有成立，最终为什么进入了这条控制路径。**

这也是 PCN Trace 作为工程数据的直接价值。

## 小结

制造现场并不缺数据。

设备数据记录设备状态。

生产数据记录生产结果。

报警和事件数据记录什么时候发生了什么。

PCN Trace 增加的是另一种记录对象：

> **一次完整的状态迁移前置判定。**

它把：

```text
当前状态
→ 目标状态
→ C / A / E 状态映射
→ S / D / B 判定
→ CAE-SDB 判定结果
→ 控制仲裁
→ 多路径控制
→ 执行结果
→ 时间信息
```

绑定到同一次 Trace 中。

时间信息使内容相同但发生在不同时间位置的状态能够被区分为不同状态实例。

因此，“新的工程数据”并不是指这些原始状态过去不存在，而是：

> **状态迁移判定本身被作为一个可以持续记录、比较、统计和改善的完整工程数据对象来管理。**

设备数据描述系统正在发生什么。

生产数据描述系统生产出了什么。

**PCN Trace 描述系统为什么允许、等待、阻断或分流这一次状态迁移，以及这一次判定在实际运行历史中的位置。**

这就是它与普通设备日志、报警履历和生产数据最主要的区别。

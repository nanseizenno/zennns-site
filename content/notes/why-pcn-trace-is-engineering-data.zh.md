## 为什么 PCN Trace 是一种新的工程数据？

基础概念可参见：

- [Concepts｜核心概念](/zh/concepts/)
- [TPCA / PCN 状态迁移前置控制架构｜白皮书](/zh/whitepaper/)
- [为什么 PCN 是 TPCA 的最小工程节点？](/zh/notes/pcn-minimum-engineering-unit/)
- [为什么状态迁移条件必须显式化？](/zh/notes/explicit-state-transition-conditions/)
- [为什么 OEE 之后还需要 PCN？](/zh/notes/why-oee-pcn/)
- [TPCA 的状态迁移单向性——为什么真实工程系统不存在状态回退？](/zh/notes/tpca-unidirectional-state-transition/)

制造现场已经积累了大量数据。

PLC 保存状态和报警，MES 保存生产履历，WCS 保存任务和调度记录，设备平台保存温度、电流、位置、节拍和运行时间。

这些数据大多围绕设备、任务、工单、报警或事件组织。

PCN Trace 增加的是另一种工程数据组织对象：

> **一次明确的 Target State Entry，为什么被允许、等待、阻断或分流。**

这里所说的“新的工程数据”，并不是指创造新的传感器数据、设备状态或时间戳类型。PCN Trace 使用的很多原始状态，本来就已经存在于 PLC、MES、WCS、机器人、视觉系统或其他工程系统中。

它增加的是一种新的组织方式：

> **把一次状态迁移判定本身作为完整的工程数据对象。**

在每一次状态迁移前置判定中，PCN 将当前状态、目标状态、相关输入、C / A / E 状态映射、S / D / B 判定、CAE-SDB 判定结果、控制仲裁、多路径控制、实际执行结果和时间信息关联起来，形成一条完整的状态迁移判定履历。

本文将这种履历称为 **PCN Trace**。

PCN Trace 不只是保存“发生了什么”，还保留：

> **为什么形成这个判定，为什么选择这条控制路径，以及最终实际发生了什么。**

## 1. PCN Trace 与传统工程数据的区别

制造现场常见数据主要包括以下几类。

### 设备状态数据

- 运行；
- 停机；
- Ready；
- 位置；
- 转速；
- 温度；
- 电流；
- 压力；
- 能耗。

### 生产数据

- 产量；
- 良率；
- 节拍；
- OEE；
- 不良数量；
- 停机时间；
- 损失时间。

### 事件和报警履历

- 报警发生；
- 报警复位；
- 设备启动；
- 设备停止；
- 工序开始；
- 工序结束；
- 任务完成；
- 任务失败。

### MES / WCS 运行记录

- 任务生成；
- 任务分配；
- Waiting；
- Blocked；
- Pending；
- 资源占用；
- 路径状态；
- 站点状态。

这些数据能够说明设备、任务和过程在某一时刻处于什么状态。

例如，现场可能已经保存：

```text
机器人 Ready = TRUE
安全回路 = TRUE
视觉结果 = OK
下游 Ready = FALSE
机器人未动作
```

这些状态能够说明当时各系统分别发生了什么。

但如果工程师进一步问：

> 为什么当时没有进入抓取阶段？

还需要恢复本次状态迁移判定的上下文：

- 当时准备进入哪个目标状态；
- 哪些输入属于条件；
- 哪些输入属于许可；
- 哪些输入属于执行链；
- 各状态当时是否仍然有效；
- 各状态是否处于预定义边界内；
- 同时存在多个判定结果时，控制仲裁如何形成最终控制方向；
- 最终选择并执行了哪一条控制路径。

普通日志可以帮助工程师事后还原这些关系。

PCN Trace 则在判定发生时，就围绕同一个 Target State Entry 组织这些信息。

因此，两者的主要区别不是“有没有数据”，而是：

```text
传统数据：
围绕设备、事件、任务、工单记录

PCN Trace：
围绕一次完整的状态迁移判定记录
```

## 2. PCN Trace 记录什么

PCN 对应一个明确的目标状态入口：

```text
当前状态
→ Target State Entry / PCN
→ 目标状态
```

在系统进入目标状态之前，PCN 对与本次迁移相关的多源状态进行整理和判定：

```text
当前状态
→ 目标状态
→ Target State Entry / PCN
→ 多源状态信号
→ C / A / E 状态映射
→ S / D / B 判定
→ CAE-SDB 判定结果
→ 控制仲裁
→ 多路径控制
→ 实际执行结果
→ PCN Trace
```

其中：

- C / A / E 表示状态在本次目标迁移中的功能角色；
- S / D / B 表示对这些状态进行验证时采用的判定性质；
- CAE-SDB Result 表示前置判定形成的结构化结果；
- Arbitration 根据判定结果、关键许可、控制约束和优先级形成最终控制方向；
- Multipath Control 表示 PCN 输出的控制路径；
- 实际执行结果记录控制路径执行后形成的现场结果；
- 时间信息用于保留状态、判定、控制和执行发生的实际时间位置。

一条 PCN Trace 可以关联：

| 内容 | 工程意义 |
| --- | --- |
| PCN | 哪一个状态迁移入口 |
| 当前状态 | 系统当时处于什么状态 |
| 目标状态 | 系统准备进入哪里 |
| 关键输入状态 | 本次迁移使用了哪些状态 |
| 时间信息 | 本次状态、判定、控制与执行处于什么时间位置 |
| C / A / E 状态映射 | 各输入在本次迁移中的工程作用 |
| S / D / B 判定 | 各变量域从哪些性质进行验证 |
| CAE-SDB 判定结果 | 本次前置判定形成了什么结果 |
| 控制仲裁结果 | 多个判定结果如何形成最终控制方向 |
| 多路径控制结果 | PCN 最终选择哪一条控制路径 |
| 执行结果 | 控制路径执行以后形成了什么现场结果 |
| Trace ID | 将上述信息绑定为同一次判定履历 |

例如：

```text
PCN：抓取入口

当前状态：等待抓取

目标状态：进入抓取阶段

时间信息：T₂

CAE-SDB 判定结果：C-D

原因：视觉结果已超出有效时间

控制仲裁结果：本次抓取不放行，选择回流路径

多路径控制：回流

执行结果：工件进入返回路径

Trace ID：PCN-XXXX-XXXX
```

这里最重要的不是多记录几个字段，而是保持以下关系：

```text
判定依据
→ CAE-SDB 判定
→ 控制仲裁
→ 控制路径
→ 实际执行结果
```

这些内容共同属于同一次 Target State Entry。

本文公开到 PCN Trace 的工程组成与作用层级。

实际产品中的内部请求标识、运行生命周期、详细字段结构、版本关系、存储结构、索引方式和回放机制，属于 PCN Runtime 与 Trace Schema 的内部实现范围。

## 3. 为什么同一种状态也需要形成新的 Trace

同一种工程状态内容可以在系统运行过程中多次出现。

例如：

```text
Robot Position = Home
Mode = Auto
Ready = TRUE
```

它可能出现在任务开始前，也可能出现在一次运行完成、异常处置、返工、回流或重新投入以后。

两次记录的状态内容可以完全相同，但它们处于不同的时间位置，也具有不同的迁移历史。

因此：

```text
状态内容相同
≠
同一次运行事实
```

PCN Trace 分别保留每一次实际发生的状态迁移判定。

例如：

```text
T₁：
Home / Auto / Ready
→ PCN-A
→ 进入执行

T₃：
Home / Auto / Ready
→ PCN-A
→ 再次进入执行
```

T₁ 与 T₃ 中的状态内容可以相同，但属于两个不同的运行位置。

对于返工、回流、复归、补偿、重新投入等工程路径也是一样。系统重新出现某个历史状态类型，不代表重新激活过去的运行事实，而是形成新的状态迁移履历。

因此，PCN Trace 管理的是：

> **状态迁移前置判定在实际运行历史中的连续表现。**

## 4. PCN Trace 如何形成工程改善闭环

很多制造现场并不缺数据。

真正耗费时间的是：

> **一次状态迁移为什么没有成立，需要工程师从多个系统的记录中重新恢复。**

传统排查过程常常类似：

```text
发现异常
→ 查报警
→ 查 PLC
→ 查机器人 / 视觉 / MES / WCS
→ 对照时间
→ 恢复当时状态
→ 判断为什么没有进入下一阶段
→ 找到改善位置
```

PCN Trace 在生成时已经把一次状态迁移的关键上下文绑定起来。

长期积累以后，可以直接统计：

| Trace 中反复出现的模式 | 可以优先检查的工程方向 |
| --- | --- |
| C-S 集中出现 | 条件信号、接口、映射关系及对象定义是否完整 |
| C-D 长期出现 | 数据刷新、同步、时间有效性和置信度是否合理 |
| C-B 高频出现 | 条件阈值、置信度、位置偏差等边界设定是否合理 |
| A-S 集中出现 | 许可来源、权限接口和资源许可结构是否完整 |
| A-D 反复出现 | 许可刷新、同步、撤销和状态切换过程是否稳定 |
| A-B 高频出现 | 许可状态对应的允许范围、时间窗口和关键约束边界是否合理 |
| E-S 集中出现 | 下游、替代路径、回退路径、异常路径和回写链路是否完整 |
| E-D 长期出现 | 执行链、下游承接、资源状态和协同时序是否稳定 |
| E-B 高频出现 | 容量、等待窗口、资源可用范围等执行链边界是否合理 |
| 某一控制路径长期高频触发 | 控制策略、优先级或替代路径设计是否需要复核 |
| 某控制路径高频触发且实际结果长期不理想 | 控制路径与现场结果之间的匹配关系是否需要调整 |

这样，工程改善可以进一步收敛到：

> **哪个 Target State Entry、哪个变量域、哪一种判定性质、哪一条控制路径长期存在问题。**

改善以后，可以继续使用同一类 Trace 比较。

例如某个 PCN 长期出现：

```text
C-D：视觉结果失效或不同步
```

工程师修改视觉结果刷新方式、同步方式或有效性规则以后，可以继续观察：

- C-D 出现频率是否下降；
- CAE-SDB Result 分布是否变化；
- 控制仲裁结果是否变化；
- 重识别、回流等控制路径是否减少；
- 是否出现新的边界问题；
- 实际执行结果是否改善。

于是形成：

```text
PCN 运行
    ↓
PCN Trace
    ↓
聚合与比较
    ↓
发现状态迁移薄弱点
    ↓
工程改善
    ↓
规则 / 配置 / 系统设计更新
    ↓
重新运行
    ↓
新的 PCN Trace
    ↓
改善前后比较
```

PCN Trace 因此不仅用于事后排查，也可以成为状态迁移设计和控制策略持续改善的数据基础。

## 5. PCN Trace 对 PLC / HMI、MES / WCS 和制造 DX 的价值

### 对 PLC / HMI

传统 PLC / HMI 已经能够显示：

- 信号状态；
- Ready；
- Interlock；
- Alarm；
- 顺序状态；
- 设备状态。

PCN Trace 可以进一步关联：

- 当前状态；
- 目标状态；
- Target State Entry；
- 时间信息；
- CAE-SDB 判定结果；
- 控制仲裁结果；
- 多路径控制结果；
- 实际执行结果；
- Trace ID。

这样，HMI 可以从：

```text
CONDITION NOT READY
```

进一步展开为：

> **哪一个目标阶段没有成立、具体落在哪一个 CAE-SDB 判定位置、最终为什么采用当前控制路径。**

### 对 MES / WCS

MES / WCS 已经拥有大量任务、车辆、站点、路径、资源和 Waiting / Blocked / Pending 状态。

PCN Trace 可以把这些状态继续组织到具体的状态迁移判定中，使系统能够关联：

```text
哪个 PCN
哪个 Target State Entry
哪个目标状态
本次判定发生在什么时间位置
哪个变量域出现问题
属于什么判定性质
形成了什么 CAE-SDB 判定结果
经过什么控制仲裁
最终进入什么控制路径
执行结果如何
```

这为 MES / WCS 的协同停滞分析增加统一的状态迁移判定数据结构。

### 对制造 DX

制造 DX 已经大量使用设备数据、生产数据和事件数据：

```text
设备 / 生产数据
→ 可视化
→ 分析
→ 改善
```

PCN Trace 增加的是另一条数据链：

```text
状态迁移前置判定
→ PCN Trace
→ 状态迁移模式分析
→ 工程改善
→ 重新运行
→ Trace 比较
```

两类数据服务于不同的工程对象。

| 项目 | 设备 / 生产数据 | PCN Trace |
| --- | --- | --- |
| 主要记录对象 | 设备、过程、任务、生产结果 | 一次目标状态迁移判定 |
| 主要回答 | 系统发生了什么 | 本次迁移为什么被允许、等待、阻断或分流 |
| 数据组织中心 | 设备、时间、任务、工单、事件 | PCN + Target State Entry + 当前状态 + 目标状态 + 时间位置 |
| 主要分析对象 | 稼动、性能、质量、异常、产量 | C / A / E、S / D / B、判定结果、仲裁结果、控制路径、执行结果 |
| 主要改善方向 | 设备、工艺、保全、生产过程 | 状态迁移条件、许可、执行链、边界设定和控制路径 |
| 改善验证 | OEE、节拍、产量、报警、质量等 | 后续 Trace 中判定、控制与执行结果的变化 |

PCN Trace 使状态迁移本身进入可以统计、比较和改善的数据体系。

## 6. 小结

制造现场已经拥有大量设备数据、生产数据、任务数据、报警数据和事件数据。

PCN Trace 增加的是另一种工程记录对象：

> **一次完整的状态迁移前置判定。**

它围绕明确的 Target State Entry，将：

```text
当前状态
→ 目标状态
→ C / A / E 状态映射
→ S / D / B 判定
→ CAE-SDB 判定结果
→ 控制仲裁
→ 多路径控制
→ 实际执行结果
→ 时间信息
```

绑定到同一次 Trace 中。

其中：

- C / A / E 描述状态在本次迁移中的功能角色；
- S / D / B 描述状态验证所关注的性质；
- B 判断相关状态是否处于预先定义的允许范围、阈值或控制边界之内；
- Arbitration 决定多个判定结果之间的控制优先关系；
- Multipath Control 给出最终控制路径；
- 执行结果记录控制路径实际执行后的现场结果；
- 时间信息保留本次运行事实在状态迁移历史中的位置。

本文所称“新的工程数据”，指的是：

> **状态迁移判定本身成为可以持续记录、比较、统计和改善的完整工程数据对象。**

设备数据描述系统当前和历史运行状态。

生产数据描述生产过程和生产结果。

PCN Trace 描述：

> **系统在某一次明确的 Target State Entry 上，为什么形成当前判定、经过怎样的控制仲裁、采用哪条控制路径，以及最终形成什么执行结果。**

因此，PCN Trace 的核心价值并不是“多记录一些数据”，而是：

> **把判定依据、判定结果、控制选择和实际结果保持在同一个状态迁移语义链中。**

这使一次状态迁移前置判定能够成为可追溯、可比较、可统计和可改善的工程数据对象。

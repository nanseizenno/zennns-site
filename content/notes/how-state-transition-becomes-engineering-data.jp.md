製造・自動化システムには、すでに多くのデータが存在している。

PLC には I/O、ステップ、インターロック、アラームがあり、ロボットコントローラには Ready、運転状態、動作結果がある。MES / WCS にはタスク、製造指図、資源、経路、ステーション状態がある。安全システム、画像認識システム、検査装置、人による確認、上位システムも、それぞれ固有の状態と記録を持っている。

ただし、これらのデータが存在しているだけで、一回の状態遷移を表すデータが整理されているとは限らない。

たとえば、システムが「待機段階」から「把持段階」へ移行しようとしているとする。

その時点では、ワーク、画像認識、位置、安全許可、区域許可、Robot Ready、ハンド状態、下流側の受入状態など、複数の状態が同時に存在している可能性がある。これらは異なるシステムから取得され、エンジニアリング上の役割もそれぞれ異なる。

必要なのは、

> **この一回の状態遷移で、どの状態を確認するのか。それぞれがどの役割を持ち、どの判定を受け、最終的になぜその制御経路が選ばれたのかを説明できること。**

である。

TPCA / PCN では、明確な **目標状態入口（Target State Entry）** をエンジニアリング対象として定め、分散している状態を同一の判定・制御・履歴として整理する。

関連する対象には、関連状態、C / A / E 状態マッピング、S / D / B 判定、CAE-SDB 判定結果、時間情報 T、制御調停、複数経路制御、実行結果、状態遷移判定履歴が含まれる。

データ表現という観点では、この一連の処理によって、

> **現実世界で発生する一回の状態遷移を、明確なエンジニアリング上の意味を持ち、長期的に記録・分析できるデータとして残す。**

ことを目指す。

---

## 1. データが存在することと、状態遷移データとして整理されていることは同じではない

現場データは通常、設備、システム、インターフェースごとに生成される。

たとえば、

```text
PLC：Step = 35
Robot：Ready = TRUE
Vision：認識結果あり
Safety：許可状態あり
Downstream：受入状態あり
```

といったデータである。

これらはいずれも実際の現場データである。

しかし、これらだけでは、システムが現在どの目標状態へ移行しようとしているのかは分からない。

また、ある Ready が今回の状態遷移でどの役割を持つのか、なぜ最終的に待機、移行許可、戻し、あるいは別の制御経路が選ばれたのかも、そのままでは説明できない。

状態値そのものには、状態遷移を判断するためのコンテキストが含まれていないからである。

同じ状態でも、目標状態入口が変われば、エンジニアリング上の意味が変わることがある。

たとえば、

`Robot Ready = TRUE`

という状態は、「把持段階へ移行する」入口では、把持実行チェーンに関係する状態の一つとして扱われる可能性がある。

一方、「異常退避段階へ移行する」入口では、同じ Ready 状態でも、関係する状態や判定条件が異なる可能性がある。

したがって、状態遷移データを既存のフィールド名だけで構成することはできない。

まず、現在状態または現在段階、目標状態または目標段階、そして対応する目標状態入口を明確にする必要がある。

そのうえで、その入口に直接関係する状態を選ぶ。

目標状態入口は、今回の状態遷移でどこまでを観測対象とするかを決める基準になる。

> **目標状態入口は、今回の状態遷移で観測・整理するデータの対象範囲を定める。**

この範囲が明確になって初めて、PLC、ロボット、MES / WCS、安全システム、画像認識システム、その他のインターフェースから取得されたデータを、一つのエンジニアリング対象として関連付けることができる。

したがって、データを集める前に、まず **どの状態遷移を観測するのか** を決める必要がある。

---

## 2. CAE-SDB：異種状態を共通の状態遷移判定構造で整理する

CAE-SDB は、明確な目標状態入口を基準として、異なるシステムから取得された状態を、共通の状態遷移判定構造に基づいて整理する。

現場の関連状態は、センサ、画像認識システム、ロボット、安全システム、MES、資源管理、人による確認、下流設備、通信インターフェースなど、さまざまな場所から取得される。

取得元、データ型、名称の付け方も異なる。

CAE-SDB では、主に次の二点を整理する。

> **この状態は、今回の状態遷移でどのような役割を持つのか。**

> **この状態を、どのような性質から判定するのか。**

第一の軸は C / A / E 状態マッピングである。

- **C = Condition / 条件状態**：目標状態へ移行するために必要な条件が成立しているか
- **A = Authority / 許可状態**：現在、目標状態への移行が許可されているか
- **E = Execution Chain / 実行チェーン状態**：目標状態へ移行した後、実行チェーンを継続できるか

この状態マッピングによって、異なるシステムから取得された状態を、今回の状態遷移におけるエンジニアリング上の役割として整理する。

第二の軸は S / D / B 判定である。

- **S = Structure / 構造完全性**：判定に必要な構造が定義・接続され、観測可能になっているか
- **D = Dynamics / 動的時系列有効性**：現在の状態を、今回の状態遷移に対する有効な判定根拠として使用できるか
- **B = Boundary / 制御境界**：関連状態が、現在の目標状態入口に対してあらかじめ定義された許容範囲または制御境界内にあるかを判定する。閾値、公差、容量、時間窓、回数、信頼度、偏差などを判定条件として利用できる

この二つの軸を組み合わせて、CAE-SDB の判定関係を構成する。

たとえば、ある把持入口で、下流設備が引き続きワークを受け入れられるかを確認する必要があるとする。

現在読み取られている下流側の受入状態は `FALSE` で、最後の更新から 12.8 秒が経過している。一方、あらかじめ定義された有効時間窓は 5.0 秒である。

`FALSE` という値だけでは、現在読み取られている状態値しか分からない。

それが直前に更新された有効な `FALSE` なのか、長時間更新されていない古い状態なのかは判断できない。

この下流側の受入状態を現在の目標状態入口で E：実行チェーン状態に関係する状態として定義し、動的有効性の判定規則を設定しておけば、D：動的時系列有効性の判定を行うことができる。

最後の更新から 12.8 秒が経過し、5.0 秒の有効時間窓を超えているため、この状態は動的時系列有効性のタイムアウトとして判定される。

ここで記録するのは、単なる `FALSE` ではない。

> **この実行チェーン関連状態が、今回の目標状態入口において動的時系列上の有効性を失っているという判定事実である。**

この例からも、**状態値と状態の有効性は別の問題** であることが分かる。

また、ある状態現象が存在するだけで、S / D / B の判定結果が成立するわけではない。

対応する判定規則が定義され、現在の入力に判定根拠があり、実際に判定処理を行った後に、CAE-SDB 判定結果が生成される。

したがって、

> **CAE-SDB は、同一の目標状態入口に関連する異種状態を、共通の状態遷移判定構造に基づいて整理する。**

---

## 3. 判定結果は、制御と実行結果まで接続する必要がある

CAE-SDB 判定結果は、状態遷移データの終点ではない。

たとえば、

`E-D = TIMEOUT`

という判定結果が生成されたとする。

これは、現在の実行チェーンに関係する状態に、動的時系列上の有効性問題があることを示している。

しかし、この結果だけでは、次に何を実行するかまでは決まらない。

待機を継続するのか、状態を再取得するのか、別の候補経路へ切り替えるのか、人による確認へ移行するのか、現在の目標状態入口への移行を禁止するのか。

これらは、CAE-SDB 判定結果の後段で決定する。

そのため、CAE-SDB 判定結果と時間情報 T は、制御調停へ渡される。

制御調停では、現在の目標状態入口の移行要件、重要な許可、安全制約、CAE-SDB 判定結果、あらかじめ定義された制御規則などを基に、制御上の優先関係を整理する。

その結果として、複数経路制御を構成する。

実際の制御経路には、移行許可、待機、再認識、戻し、異常系への分岐、代替経路、人による確認、移行禁止、安全ロックなどがある。

制御経路を決定した後には、実際の実行結果を取得する必要がある。

「移行許可」は、今回の前制御判定と制御調停によって、現在の目標状態への移行を許可する制御結果が確定したことを意味する。

ただし、実際に目標状態へ移行できたかどうかは、後続の実行フィードバックで確認する必要がある。

したがって、一回の記録には少なくとも、CAE-SDB 判定結果、時間情報 T、制御調停結果、複数経路制御、実行結果を含める必要がある。

> **状態遷移データには、「なぜその判定になったのか」だけでなく、「どの制御が選ばれ、実際に何が起きたのか」まで含める必要がある。**

---

## 4. 状態遷移判定履歴：一つの目標状態入口に対する1回の判定を単位として状態遷移事実を保存する

判定、制御、実行が完了すると、PCN は対応する **状態遷移判定履歴（PCN Trace）** を記録できる。

状態遷移判定履歴は、一つの目標状態入口に対する1回の判定を単位として、その時点の現在状態、目標状態、関連状態、時間情報を、CAE-SDB 判定、制御選択、実際の実行結果と関連付ける。

状態遷移判定履歴と一般的な運転ログの違いは、記録するフィールド数ではない。

> **データを整理する単位そのものが異なる。**

一般的な運転ログでは、信号変化、イベント、アラーム、動作、タスク状態変化などを単位として記録することが多い。

たとえば、

```text
10:32:15 Robot Ready OFF
10:32:16 Downstream Busy
10:32:17 Step 35 Waiting
10:32:20 Alarm 102
```

といった記録である。

これらのログから、現場で何が起きたかは確認できる。

しかし、一回の状態遷移がなぜ成立しなかったのかを理解するには、工程技術者が各記録の関係をあらためて組み直す必要がある。

状態遷移判定履歴では、データの整理単位を、一つの明確な目標状態入口に対する1回の判定に置く。

同じ入口について、

- どの目標状態へ移行しようとしていたか
- その時点でどの状態を参照したか
- それぞれの状態がどの役割を持っていたか
- どの判定を行ったか
- どの CAE-SDB 判定結果が生成されたか
- どの制御経路を選択したか
- 実際の実行結果はどうだったか

を、一つの状態遷移履歴として記録できる。

ここで CAE-SDB は重要な役割を持つ。

C / A / E 状態マッピングと S / D / B 判定がなければ、状態遷移判定履歴も、大量の状態値とイベントをもう一度まとめただけのデータになる可能性がある。

CAE-SDB によって、同一の目標状態入口に関連する異種状態を、共通の状態遷移判定構造に基づいて整理できる。

したがって、

> **状態遷移判定履歴は、元の運転データを単純に蓄積したものではなく、一つの明確な目標状態入口に対する判定、制御、実行結果を関連付けて記録した構造化履歴である。**

この履歴は、次のような用途に利用できる。

- 現場での事後確認
- 問題追跡
- 状態遷移設計のレビュー
- プロジェクト引継ぎ
- 高頻度問題の統計
- 異なる制御経路の結果比較
- 長期履歴分析
- 工程改善

## 5. 状態遷移判定履歴から分析と改善へ

状態遷移判定履歴が蓄積された後に、具体的な問題に応じて分析方法を選ぶ。

状態遷移判定履歴が長期的に蓄積されれば、まずルール、統計、傾向比較などによって、次のような内容を確認できる。

- どの目標状態入口で待機が発生しやすいか
- どの入口で C-D が繰り返し発生しているか
- 重要な許可に関係する A 判定が、どの入口で頻繁に不成立になっているか
- どの実行チェーンで E-D が集中しているか
- 異なる制御経路の後に、どのような実行結果の差があるか

最初に確認すべきなのは、

> **どの状態遷移入口で、類似した問題が繰り返し発生しているか。**

である。

複数の状態遷移判定履歴を横断して比較したり、自然言語で説明したり、パターン整理やレポート生成を行う場合には、大規模言語モデルやその他の分析ツールを利用することもできる。

大規模言語モデルは、履歴比較、パターン整理、改善候補の整理、事後確認レポートの生成などを支援できる。

ここで利用するのは、TPCA / PCN によってすでに整理・蓄積された構造化状態遷移履歴である。

大規模言語モデルの出力を、現場の状態遷移許可そのものとして直接使用するものではない。

実際の工程変更は、設備、工程、安全、生産、保全などの要求を踏まえて、工程技術者が確認する。

改善を実施した後、システムは新しい状態遷移判定履歴を記録する。

その結果、改善前後の運転状態を比較できるようになる。

状態遷移履歴の価値は、過去を説明することだけではない。

状態遷移判定履歴が長期的かつ安定して蓄積されれば、工程改善の前後を比較するための基盤にもなる。

ここでも順序は変わらない。

> **まず何を見るかを決める。次に、どのように見るかを決める。その後で、どの方法を使って分析するかを決める。**

アルゴリズムを利用しても、状態遷移対象やデータ表現の定義そのものが不要になるわけではない。

データ構造を整理する段階で重要な状態遷移関係が失われていれば、後段で統計、機械学習、大規模言語モデルを適用しても、失われたエンジニアリング上の関係を確実に復元できるとは限らない。

## まとめ

現実世界で発生する一回の状態遷移は、そのままでは必ずしも分析可能なエンジニアリングデータとして整理されているとは限らない。

TPCA / PCN では、目標状態入口によって観測する状態遷移を定め、CAE-SDB によって関連状態のエンジニアリング上の役割と判定性質を整理する。

さらに、制御調停、複数経路制御、実行結果によって、判定を制御選択と実際の結果へ接続し、状態遷移判定履歴によって、その全体を比較・追跡・事後確認可能な状態遷移履歴として記録する。

CAE-SDB の役割は、単に 3 × 3 の判定座標を生成することだけではない。

より重要なのは、

> **同一の目標状態入口に関連する異種状態を共通の状態遷移判定構造に基づいて整理し、状態取得、前制御判定、制御選択、実際の結果、長期履歴を、同じ目標状態入口を中心として連続的に関連付けられるようにすることである。**

状態遷移判定履歴における本質的な変化も、記録フィールドが増えることではない。

> **データの整理単位を、分散した信号・イベント・アラームから、一つの明確な目標状態入口に対する1回の判定へ変更することである。**

その後に利用するルール、統計、大規模言語モデル、その他の分析方法は、すでに整理・蓄積された状態遷移データの上に適用される。

本稿では TPCA / PCN の完全な方法論全体は扱わず、一回の状態遷移がどのように分析可能なエンジニアリングデータとして整理されるかに焦点を当てた。

# TPCA / PCN 适用场景分析

TPCA / CAE-SDB 处理的问题是：

> 技术系统准备进入一个明确的目标状态、目标执行路径或目标物理执行阶段之前，如何基于多源状态信号完成结构化前置判定，并形成对应控制路径。

PCN 是 TPCA 的最小工程单元。

判断一个对象是否适合进入 PCN，不应首先看它属于设备、人、软件、MES、WCS 还是其他系统，而应先看它能否进入这样一条完整工程链：

```text
Current State
→ Target State
→ PCN
→ Multi-source State Signals
→ C/A/E Mapping
→ S/D/B Evaluation
→ CAE-SDB Result
→ Arbitration
→ Multipath Control
→ PCN Trace
```

因此：

> **能用 C/A/E 解释，不等于应该纳入 PCN。**

真正适合 PCN 的对象，必须能够成为一次明确状态迁移判定中的工程状态。

---

## 1. 一个状态进入 PCN 判定链的四个基本条件

某个状态、信号或人工输入要成为 PCN 的有效判定要素，至少应满足四个基本条件。

| 层级  | 条件               | 判断重点                 |
| --- | ---------------- | -------------------- |
| 基础层 | 能被系统采集或记录        | 当前状态是否可读、可记录、可追溯     |
| 变量层 | 能映射到 C / A / E   | 它在本次目标状态迁移中承担什么作用    |
| 判定层 | 能参与 S / D / B 判定 | 能否判断结构完整性、动态有效性或控制边界 |
| 控制层 | 能影响状态迁移结果        | 状态变化是否可能改变最终控制路径     |

这四个条件不是为了给现场所有数据重新分类。

它们的作用是判断：

> **某个状态是否真正参与目标状态进入前的工程判定。**

例如：

仅仅能够采集温度，不代表温度一定属于某个 PCN。

只有当温度状态与某个明确 Target State 的进入要求有关，并被映射到 C、A 或 E，进一步参与 S、D 或 B 判定，同时可能影响该次状态迁移的控制结果时，它才成为该 PCN 的有效输入。

同样：

* 只能采集，但与目标状态进入无关，只是普通数据；
* 能映射，但不存在实际判定规则，只是状态描述；
* 能判定，但结果完全不影响状态迁移，只是辅助观察信息。

完整 PCN 在此基础上还应形成：

```text
CAE-SDB Result
→ Arbitration
→ Multipath Control
→ PCN Trace
```

也就是说，状态进入判定链以后，本次判定最终还必须能够被控制和记录。

---

## 2. 哪些对象通常不应纳入 PCN

以下信息通常不应直接作为 PCN 主线判定要素：

* 无法由系统采集或可靠记录；
* 只能依赖口头沟通、个人记忆或事后询问；
* 与某个明确 Target State 没有直接关系；
* 无法说明其属于 C、A 还是 E；
* 无法形成可重复的 S、D、B 判定规则；
* 即使状态变化，也不影响最终状态迁移；
* 只是背景信息、统计信息或说明性数据；
* 核心问题主要来自组织关系、部门协调、主观意愿或责任分配。

需要注意：

> **TPCA / PCN 并不排除“人”。**

它排除的是：

> **无法转化为可靠技术状态的人类组织行为。**

例如操作员通过 HMI 明确按下“确认”，这是系统可以记录的状态。

但“操作员实际上是否放心”“某部门是否真正愿意推进”“负责人心里是否支持”，则不是可靠的工程状态。

这两类信息不能混为一谈。

## 3. 人参与的生产 DX 场景如何判断

生产 DX、组装线、质量流转、设备复归和异常处理过程中，经常必须有人参与。

判断人的动作能否纳入 PCN，关键不在于动作是不是由人完成，而在于：

> **这个人的动作是否已经被系统化为明确状态。**

例如：

| 人的动作                | 在 PCN 中可能承担的工程角色          |
| ------------------- | ------------------------- |
| 操作员在 HMI 确认工件已放置    | C：人工确认后的对象条件              |
| 操作员扫码确认工件 ID        | C：对象识别条件                  |
| 质检员输入首件 OK          | C：质量状态，或 A：质量放行许可，取决于系统定义 |
| 班组长执行批次放行           | A：人工 / 上位许可               |
| 保全人员完成点检并解除设备限制     | A：保全许可                    |
| 工程师确认异常复归           | A：人工复归许可                  |
| 操作员对边界异常进行人工确认      | 人工确认结果可作为 A 输入参与后续状态迁移判定  |
| 作业员执行系统已经输出的回流或隔离操作 | 属于控制路径执行结果，而不是 B 本身       |

最后两项尤其需要区分。

按照当前 CAE-SDB 定义：

> **B = Boundary，是边界判定。**

例如系统发现：

```text
C-B:
识别置信度进入人工确认边界
```

这只是一个 CAE-SDB Result。

系统可能同时还有其他结果，例如：

```text
A:
安全许可成立

E:
回流路径可用
```

完整结果经过 Arbitration 后，才可能形成：

```text
Control:
MANUAL_CONFIRM
```

然后操作员作出确认，其结果再成为后续判定的人工许可状态。

因此不能简单写成：

> “人工确认 = B”

或者：

> “回流、隔离 = B”。

B 是判定性质，人工确认、回流、隔离是最终可能形成的控制路径或路径执行动作。

## 4. 组装线中的具体例子

以一个人工参与的组装单元为例。

```text
Current State:
上一工序完成 / 等待进入下一工序

Target State:
进入检测、下一组装工序或包装阶段

PCN:
设置在目标工序进入前
```

PCN 可以读取：

| 信号来源  | 代表状态               |
| ----- | ------------------ |
| HMI   | 操作员确认、人工许可、异常确认结果  |
| 扫码系统  | 工件 ID、部品 ID、工序通行记录 |
| 质量系统  | 首件结果、检测结果、质量放行     |
| MES   | 工单、批次、工序许可         |
| 设备控制器 | Ready、治具、夹具、传感器状态  |
| 安全系统  | 安全门、光栅、急停、区域许可     |
| 保全系统  | 点检完成、保全解除、复归确认     |
| 下游工位  | 接收许可、缓存容量、设备状态     |

这些状态再根据本次 Target State 的要求映射到 C/A/E。

### C：Condition

例如：

* 工件 ID 正确；
* 部品到位；
* 前工序完成；
* 参数匹配；
* 检测结果有效。

### A：Authority

例如：

* 质量放行；
* MES 工序许可；
* 安全许可；
* 保全解除；
* 必要人工确认。

关键 A 不成立时，即使 C 和 E 满足，也不得进入目标状态。

### E：Execution Chain

例如：

* 下游可以承接；
* 检测设备可用；
* 包装路径可接续；
* 回流路径可用；
* 异常隔离路径可用；
* 结果回写链路可用。

E 不等于某台设备 Ready。

Ready 只可能是 E 的其中一个输入。

---

一次实际判定可能是：

```text
Current State:
Assembly Completed

Target State:
Quality Inspection

CAE-SDB Result:
C     = satisfied
A-D   = quality authorization not refreshed
E     = available

Arbitration:
关键质量许可状态无法证明当前有效

Multipath Control:
WAIT / MANUAL_CONFIRM

PCN Trace:
记录本次输入、判定、仲裁和最终路径
```

另一次可能是：

```text
C:
工件 ID 与工单不一致

A:
许可成立

E:
下游可承接

CAE-SDB Result:
C-D abnormal

Arbitration:
目标对象身份当前不可确认

Multipath Control:
RE-SCAN
```

这时人的扫码行为仍然属于系统化的 C 状态获取过程，而不是组织管理行为。

## 5. 为什么很多组织管理问题可以解释，却不适合作为 PCN 主线

C/A/E 本身具有较高的抽象解释能力。

因此审批、会议、采购、项目管理等活动，也可以表面拆成：

| C / A / E | 表面对应          |
| --------- | ------------- |
| C         | 资料是否齐全、条件是否成立 |
| A         | 是否获得审批或授权     |
| E         | 批准以后是否能够执行    |

这说明 C/A/E 可以帮助描述某些判断结构。

但：

> **可以描述，不意味着适合作为 PCN 工程对象。**

很多组织管理问题的核心状态并不是稳定的技术状态。

例如：

* “资料是否足够充分”；
* “风险是否可以接受”；
* “当前是否适合推进”；
* “部门是否愿意配合”；
* “负责人是否真正认可”；
* “实际资源是否能够调出来”。

这些条件往往受到：

* 人的判断；
* 隐性资源；
* 部门利益；
* 风险偏好；
* 责任关系；
* 未公开信息；
* 临时优先级变化；

影响。

即使给这些内容强行赋予 C、A、E 标签，也未必能够形成：

```text
可观测状态
→ 可重复判定
→ CAE-SDB Result
→ Arbitration
→ Multipath Control
→ Trace
```

因此这类问题更适合由 BPM、工作流、项目管理、组织设计或管理制度处理。

TPCA / PCN 的主线仍应保持在：

> **可观测、可判定、可控制、可记录的技术系统状态迁移。**

## 6. 哪些场景优先适合 PCN

### 高适配场景

| 场景               | 适合原因                       |
| ---------------- | -------------------------- |
| 自动化执行单元进入下一物理阶段  | Current / Target、信号和控制路径明确 |
| 机器人抓取、压装、检测、搬送交接 | 目标物理执行阶段明确，多源状态可观测         |
| MES / WCS 协同停滞   | 任务、许可、资源、主体和执行链可以形成结构诊断    |
| AGV / AMR 群控     | 群体状态、任务、路径、许可和下游承接可记录      |
| 设备复归前确认          | 安全、保全、复归和后续执行链存在明确约束       |
| 质量流转             | 质量条件、质量许可、下游路径和异常路径可追溯     |
| 人机协同生产单元         | 人工动作已经通过 HMI、扫码、质量系统等系统化   |
| AI / 工具调用前置控制    | 请求条件、授权和目标执行链可以数字化判定       |

这些场景的共同点不是行业相同。

共同点是：

> **都存在明确状态迁移入口。**

---

### 通常不应作为 PCN 主线的场景

| 场景       | 主要原因                                 |
| -------- | ------------------------------------ |
| 普通行政审批   | 核心通常是工作流和组织权限管理                      |
| 普通会议决策   | 关键条件依赖人的判断和隐性信息                      |
| 人事和组织管理  | 主要问题不是技术状态迁移                         |
| 普通项目管理   | 大量状态来自组织协调、责任和主观判断                   |
| 单纯统计报表   | 只观察，不参与状态迁移控制                        |
| 普通趋势监控   | 如果结果不参与 Target State 判定，就不是 PCN 核心输入 |
| 单纯 BI 分析 | 主要输出是分析结果，不是运行时控制路径                  |

这里的“不适合”并不是逻辑上的绝对禁止。

例如一个 CI / CD 系统，如果讨论的是一般 DevOps 管理流程，并没有必要使用 TPCA。

但如果问题具体变成：

```text
Current State:
Build Completed

Target State:
Production Deployment

Deployment Gate:
明确的安全、授权、测试、资源和回退状态
```

而这些状态可以数字化判定，并直接控制：

```text
ALLOW
WAIT
DEGRADE
ROLLBACK
PROHIBIT
```

那么它事实上已经变成一个明确的数字状态迁移入口，此时就存在使用 PCN 思路的可能。

因此真正的边界不是行业名称。

而是：

> **是否能够形成一个真实的、可运行的状态迁移前置控制节点。**

## 7. 一个更严格的适用性判断方法

面对一个新的应用对象，可以先问六个问题：

### 1. Current State 是什么？

如果连当前状态都无法明确，暂时不适合建立 PCN。

### 2. Target State 是什么？

PCN 必须对应一个明确目标状态、目标执行路径或目标物理执行阶段。

### 3. PCN 设置在哪里？

必须能够指出：

> 在进入 Target State 之前，哪个位置需要做前置判定？

### 4. 相关状态能否形成 C/A/E？

能够说明：

* 哪些是 Condition；
* 哪些是 Authority；
* 哪些是 Execution Chain。

### 5. 是否能够进行 S/D/B 判定？

不仅知道当前值，还能够判断：

* 结构是否完整；
* 动态状态是否有效；
* 是否进入预定义控制边界。

### 6. 判定结果是否真正影响系统行为？

如果最终仍然只能生成一份分析报告，而不会影响：

* Allow；
* Wait；
* Retry；
* Return；
* Degrade；
* Manual Confirm；
* Prohibit；
* Safety Lock；
* 其他实际路径；

那么它更像分析系统，而不是完整 PCN。

一个完整 PCN 最终还应把：

```text
Input
→ CAE-SDB Result
→ Arbitration
→ Multipath Control
→ Execution Result
```

组织进 PCN Trace。

## 小结

TPCA / PCN 的适用范围，不应按照行业名称、设备类型或者“有没有人参与”来划分。

真正的判断对象是：

> **一个明确的状态迁移入口能否被工程化。**

某个状态进入 PCN 判定链，至少应满足：

* 能被系统采集或记录；
* 能映射到 C/A/E；
* 能参与 S/D/B 判定；
* 能影响状态迁移控制结果。

完整 PCN 则进一步形成：

```text
Current State
→ Target State
→ PCN
→ C/A/E Mapping
→ S/D/B Evaluation
→ CAE-SDB Result
→ Arbitration
→ Multipath Control
→ PCN Trace
```

TPCA / PCN 不排除人。

它排除的是无法转化为可靠工程状态的人类组织行为。

人的扫码、HMI 确认、质量放行、保全解除，只要已经成为系统可读状态，就可以进入 PCN。

人的真实意愿、部门关系、风险态度和未公开判断，则不适合作为 PCN 的核心状态。

因此，TPCA / PCN 的边界可以归结为一句话：

> **能解释，不等于应该纳入；能形成可观测、可判定、可控制、可追溯的目标状态迁移入口，才真正具有 PCN 的工程价值。**

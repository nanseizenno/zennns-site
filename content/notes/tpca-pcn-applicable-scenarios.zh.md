# TPCA / PCN 适用场景分析

TPCA / PCN 的核心命题是：

> **一次明确的目标状态入口，应当成为可以被独立设计、判定、控制和记录的工程对象。**

因此，判断一个场景是否适合使用 TPCA / PCN，不应首先看它属于设备、软件、MES、WCS、人机协同还是其他系统。

核心判断是：

> **这个场景中是否存在一个明确的目标状态入口，并且这个入口能够被工程化。**

PCN 是部署在目标状态入口前的前置控制节点。

它不是为了给所有数据重新分类，也不是为了把所有业务流程都改造成 PCN。

真正需要判断的是： **哪些状态迁移入口值得被独立设计、判定、控制和记录。**

---

## 1. 什么样的目标状态入口适合设置 PCN

一个场景适合设置 PCN，通常应同时具备以下几个特征。

### 目标状态明确

能够明确说明：

```text
当前状态 → 目标状态
```

例如：

- 等待抓取 → 进入抓取阶段；
- 任务已分配 → 开始搬送；
- 保全解除 → 重新投入自动运行；
- 质量确认完成 → 进入下一生产阶段。

如果目标状态本身无法明确，PCN 就缺少稳定的工程对象。

### 相关状态可以被系统获取

与本次状态迁移有关的关键状态，需要能够被系统读取、记录或可靠确认。

这些状态可以来自：

- PLC；
- 机器人控制器；
- 安全系统；
- MES / WCS；
- 视觉系统；
- 质量系统；
- HMI；
- 扫码系统；
- 其他设备或软件接口。

状态来源可以不同，但必须能够参与实际工程判断。

### 判定结果会影响系统行为

如果分析结果只用于事后报告，而不会影响状态迁移是否继续，那么它更接近分析系统，而不是完整 PCN。

PCN 关注的是：  **一次状态迁移判断最终能否影响实际控制结果。**

例如：

- 允许进入；
- 继续等待；
- 重新确认；
- 转入替代路径；
- 禁止进入；
- 人工确认。

### 判定过程可以形成履历

一次状态迁移为什么成立或没有成立，应当能够被记录和追溯。

这也是 PCN Trace 的基本价值。

因此，适合 PCN 的场景通常同时具备：

> **明确目标状态 + 可观测状态 + 可执行判定 + 可追溯履历。**

## 2. 哪些场景通常具有较高适配性

### 自动化执行单元

例如：

- 机器人抓取；
- 检测；
- 压装；
- 搬送交接；
- 上下料；
- 正常路径与异常路径切换。

这类场景通常具有明确的当前状态、目标状态和物理执行边界。

> **目标物理执行阶段进入前，是典型的 PCN 设置位置。**

相关案例：

[自动化执行单元前置判定案例](/zh/cases/automation-execution-unit-pre-control/)

---

### MES / WCS 与多设备协同

例如：

- AGV / AMR 群控；
- 任务执行；
- 资源使用；
- 路径与站点协调；
- 下游承接；
- 协同停滞恢复。

这类场景的特点是：

> 单个设备或系统可能都没有明显故障，但多个状态共同决定一次协同状态迁移。

如果能够明确目标协同状态，并把与本次迁移有关的任务、许可、资源和执行状态组织起来，就具备较高 PCN 适配性。

相关案例：

[MES / WCS 协同停滞诊断模块案例](/zh/cases/collaborative-stagnation-diagnosis/)

---

### 生产 DX 与跨系统状态迁移

例如：

- 质量放行；
- 工序切换；
- 异常复归；
- 保全解除后的重新投入；
- 人工确认后的自动恢复；
- MES、质量、设备与下游之间的状态切换。

这类场景经常已经拥有大量数据，但“下一阶段是否可以开始”的判断仍然分散在多个系统和人员之间。

如果人的动作已经通过 HMI、扫码、质量系统或其他接口转化为可记录状态，也可以成为状态迁移判断的一部分。

相关案例：

[生产 DX 状态迁移条件设计与履历分析案例](/zh/cases/production-dx-state-transition/)

---

### 数字系统中的明确执行入口

TPCA / PCN 的工程对象并不限于物理设备。

如果数字系统中存在明确的：

```text
当前状态 → 目标执行状态
```

并且进入该状态之前需要检查可观测条件、许可和执行可用性，也可能适合使用 PCN 思路。

例如：

- 高成本服务调用；
- 工具调用；
- API 执行；
- 自动化发布入口；
- 其他明确的数字执行路径。

这里的关键仍然不是“是不是软件系统”，而是：

> **是否存在一个真实、可运行、可控制的目标状态入口。**

---

## 3. 人参与，并不意味着不能使用 PCN

TPCA / PCN 不排除人的参与。

关键区别是： **人的动作是否已经被系统化为明确状态。**

例如：

- HMI 人工确认；
- 扫码结果；
- 质量放行；
- 保全解除；
- 工程师复归确认。

这些动作一旦成为系统可读取、可记录的状态，就可以参与后续状态迁移判断。

但下面这些内容通常不适合作为 PCN 核心状态：

- 某个人是否“觉得可以”；
- 某部门是否愿意推进；
- 负责人是否真正认可；
- 隐性资源是否可能协调出来；
- 未被系统记录的临时判断。

这些问题更接近组织管理、工作流或项目管理，而不是技术系统状态迁移。

因此：

> **TPCA / PCN 不排除人，但要求进入判定链的信息能够转化为可靠工程状态。**

---

## 4. 哪些场景通常不应作为 PCN 主线

以下场景通常不适合直接作为 PCN 的主要工程对象：

- 普通行政审批；
- 普通会议决策；
- 人事与组织管理；
- 主要依赖主观判断的项目管理；
- 单纯统计报表；
- 不参与状态迁移控制的趋势监视；
- 只生成分析结果、不影响系统行为的 BI 场景。

原因并不是这些问题不能被 C / A / E 描述。

而是： **能够描述，不等于已经形成可运行的状态迁移工程对象。**

如果核心状态主要来自人的主观判断、组织关系、临时协调或未公开信息，就很难形成稳定的工程判定与控制闭环。

---

## 5. 一个简化的适用性判断

面对新的应用对象，可以先回答四个问题。

### 1. 当前状态和目标状态是否明确？

如果无法明确：

```text
当前状态 → 目标状态
```

就很难建立 PCN。

### 2. 与本次状态迁移有关的关键状态是否可观测？

这些状态必须能够被系统读取、记录或可靠确认。

### 3. 判定结果是否会影响目标状态进入？

如果结果只用于解释，而不影响实际状态迁移，就不属于完整的前置控制节点。

### 4. 这次判断能否形成可追溯履历？

如果输入、判定、控制和执行结果能够围绕同一次状态迁移形成记录，就具备进一步工程化的基础。

可以简化为：

```text
目标状态明确
→ 状态可观测
→ 判定影响控制
→ 结果可追溯
```

满足这些条件后，再进一步通过 C / A / E、S / D / B、控制仲裁和多路径控制完成具体 PCN 设计。

完整定义可参见：

[Concepts｜核心概念](/zh/concepts/)

## 6. 适用边界的核心不是行业，而是工程对象

TPCA / PCN 的适用范围不应按照行业名称、设备类型或“有没有人参与”来划分。

真正需要判断的是：**一个明确的目标状态入口能否被工程化。**

自动化执行单元、MES / WCS 协同和生产 DX 看起来属于不同层级，但它们都可能存在同一种工程对象：

> **系统准备进入一个明确目标状态之前，需要对多个相关状态形成前置判断。**

相反，即使某个场景可以用 C / A / E 进行概念解释，如果它不能形成稳定、可观测、可执行和可追溯的状态迁移入口，就不应为了套用 TPCA / PCN 而强行建立 PCN。

---

## 工程结论

TPCA / PCN 的适用边界可以归结为一句话：

> **一次明确的目标状态入口，只有在能够被观测、判定、控制和记录时，才真正具有被工程对象化的价值。**

因此，PCN 的选择原则不是：

> “这个系统有没有很多状态？”
> “这个问题能不能用 C / A / E 描述？”

而是：

> **这里是否存在一个值得被独立设计、判定、控制和记录的目标状态入口？**

如果答案是肯定的，就存在设置 PCN 的工程基础。

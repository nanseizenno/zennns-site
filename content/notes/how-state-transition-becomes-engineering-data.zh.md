制造和自动化系统中并不缺少数据。

PLC 有 I/O、步序、联锁和报警，机器人控制器有 Ready、运行状态和动作结果，MES / WCS 有任务、工单、资源、路径和站点状态。安全系统、视觉系统、检测设备、人工确认和上位系统，也分别保存自己的状态和记录。

但这些数据同时存在，并不代表系统已经形成对一次状态迁移的完整数据表示。

例如，系统准备从“等待阶段”进入“抓取阶段”时，现场可能同时存在工件、视觉、位置、安全许可、区域许可、Robot Ready、夹爪以及下游接收等状态。这些数据来自不同系统。

真正需要回答的是：这一次状态迁移需要观察哪些状态，它们分别承担什么作用，需要进行什么判定，最终为什么选择某一条控制路径。

TPCA / PCN 以明确的目标状态入口（Target State Entry）为工程对象，将这些分散状态组织到同一次判定、控制和履历中。

基本对象包括相关状态、C / A / E Mapping、S / D / B Evaluation、CAE-SDB Result、时间信息 T、Arbitration、Multipath Control、Execution Result 和 PCN Trace。

从数据表示的角度看，这一过程的目的就是：

> **把现实中的一次状态迁移整理成具有明确工程语义、可以长期记录和分析的数据。**

---

## 1. 有了数据，不等于形成了状态迁移数据

现场数据通常按照设备、系统或接口分别产生。

例如：

```text
PLC：Step = 35
Robot：Ready = TRUE
Vision：识别结果已生成
Safety：许可状态已返回
Downstream：接收状态已返回
```

这些都是真实数据，但仅凭这些数据，还不能直接说明系统当前准备进入什么目标状态，也不能说明某个 Ready 在这一次迁移中承担什么作用，更不能直接解释为什么最终选择等待、允许进入、回流或其他路径。

状态值本身不包含完整的状态迁移上下文。

同一个状态在不同 Target State Entry 中，也可能具有不同工程意义。例如 `Robot Ready = TRUE`，在“进入抓取阶段”前可能参与当前抓取执行链的判定；在“进入异常退避阶段”前，同一个 Ready 对应的状态关系和判定要求可能不同。

因此，建立状态迁移数据时，首先要明确当前状态、目标状态和对应的 Target State Entry，再确定与这一次入口直接相关的状态。

Target State Entry 在这里确定了本次状态迁移的数据观察边界。

边界明确以后，来自 PLC、机器人、MES / WCS、安全系统、视觉系统和其他接口的数据，才能围绕同一个工程对象建立关系。

所以，数据采集之前，先要明确准备观察哪一次状态迁移。

---

## 2. CAE-SDB：为异构状态建立统一的状态迁移判定语义

CAE-SDB 围绕明确的 Target State Entry，为当前入口相关、来自不同系统的状态建立统一的状态迁移判定语义。

现场状态可能来自传感器、视觉系统、机器人、安全系统、MES、资源管理、人工确认、下游设备和通信接口等。这些状态的来源、数据类型和命名方式都可能不同。

CAE-SDB 主要处理两个问题：

> **这个状态在本次状态迁移中承担什么作用？应从什么性质判定这个状态？**

第一层是 C / A / E Mapping：

- **C = Condition**：进入目标状态所需条件是否具备；
- **A = Authority**：当前是否允许进入目标状态；
- **E = Execution Chain**：进入目标状态以后，当前执行链是否能够继续接续。

这一层确定相关状态在本次状态迁移中的工程作用。

第二层是 S / D / B Evaluation：

- **S = Structure**：判定所依赖的结构是否已经定义、接入并可观测；
- **D = Dynamics**：当前状态是否仍然能够作为本次状态迁移的有效依据；
- **B = Boundary**：相关状态是否仍处于预先定义的允许边界内。

两层组合后形成 C / A / E 与 S / D / B 的双轴判定关系。

例如，某个抓取入口需要确认下游是否能够继续承接。系统当前读取到的下游接收状态为 FALSE，距离最近一次更新已经过去 12.8 秒，而预先定义的有效窗口为 5.0 秒。

单独看这个 FALSE，只能确认当前读取到的状态值。它可能是刚刚更新的有效状态，也可能是长时间没有刷新的旧状态。

如果该下游状态在当前抓取入口中被定义为 E，并且已经配置动态有效性规则，就需要接受 D 判定。由于状态已经 12.8 秒未刷新，超过 5.0 秒有效窗口，因此形成动态时序有效性超时的判定结果。

这时记录的已经不只是一个 FALSE，而是：

> **该 E 类状态在本次 Target State Entry 中的动态时序有效性判定事实。**

状态值与状态有效性是两个不同的问题。

同样，存在某种状态现象，也不代表已经形成某个 S / D / B 判定结果。只有对应规则已经定义、当前输入具备判定依据，并完成实际判定后，才能形成相应的 CAE-SDB Result。

因此，CAE-SDB 的作用是为同一 Target State Entry 下的异构状态建立统一的状态迁移判定语义。

---

## 3. 判定结果还需要连接控制和执行结果

CAE-SDB Result 不是状态迁移数据链的终点。

例如形成 `E-D = TIMEOUT`，说明当前执行链相关状态存在动态时序有效性问题，但还不能直接决定下一步应该等待、重新获取状态、转向其他候选路径、人工确认，还是禁止进入当前 Target State Entry。

CAE-SDB Result 和时间信息 T 需要进入控制仲裁。

控制仲裁根据当前 Target State Entry 的进入要求、关键许可、安全约束、判定结果和预先定义的控制规则，处理多个结果之间的控制关系，再形成多路径控制。

实际控制路径可以包括允许进入、等待、重识别、回流、异常分流、备用路径、人工确认、禁止进入或安全锁定等。

控制路径形成以后，还需要保留实际执行结果。

“允许进入”表示本次前置判定和控制仲裁允许当前目标状态入口继续，但目标状态是否实际成立，还需要结合后续执行反馈确认。

因此，一次完整记录至少需要保留 CAE-SDB Result、时间信息 T、控制仲裁结果、多路径控制和执行结果。

> **状态迁移数据既要记录为什么这样判断，也要记录选择了什么控制，以及实际发生了什么。**

---

## 4. PCN Trace：以一次 Target State Entry 为单位保存迁移事实

完成判定、控制和执行以后，PCN 可以形成对应的 PCN Trace。

围绕一次 Target State Entry，PCN Trace 将当前状态、目标状态、相关状态和时间信息，与 CAE-SDB 判定、控制选择和实际执行结果建立关联。

PCN Trace 与普通运行日志的主要差异，不在于增加多少字段，而在于数据组织单位不同。

普通运行日志通常以信号变化、事件、报警、动作或任务状态变化作为记录单位。例如：

```text
10:32:15 Robot Ready OFF
10:32:16 Downstream Busy
10:32:17 Step 35 Waiting
10:32:20 Alarm 102
```

这些记录能够说明现场发生了什么。

但如果要判断一次状态迁移为什么没有成立，工程师仍然需要重新建立这些记录之间的关系。

PCN Trace 则以一次明确的 Target State Entry 作为数据组织单位。

围绕同一个入口，可以记录：

- 准备进入什么目标状态；
- 当时依据哪些状态；
- 这些状态承担什么功能角色；
- 执行了什么判定；
- 形成了什么 CAE-SDB Result；
- 选择了什么控制路径；
- 实际执行结果是什么。

CAE-SDB 在这里提供统一的状态迁移判定语义。

如果缺少 C / A / E Mapping 和 S / D / B Evaluation，PCN Trace 仍可能只是大量状态值和事件的重新汇总。

因此：

> **PCN Trace 保存的是围绕一次明确 Target State Entry 形成的结构化状态迁移履历。**

这种履历可以用于现场复盘、问题追溯、状态迁移设计审核、项目交接、高频问题统计、不同控制路径结果比较、长期履历分析和工程改善。

---

## 5. 从 Trace 到分析与改善

形成 PCN Trace 以后，再根据问题选择分析方法。

长期积累后，可以先通过规则、统计和趋势比较，观察：

- 哪些 Target State Entry 更容易进入等待；
- 哪些入口反复出现 C-D；
- 哪些关键许可相关的 A 判定经常不成立；
- 哪些执行链长期集中出现 E-D；
- 不同控制路径对应的后续执行结果有什么差异。

这些分析首先用于识别：

> **哪些状态迁移入口反复出现相似问题。**

需要跨 Trace 比较、自然语言解释、模式归纳或报告生成时，也可以使用大语言模型或其他分析工具。

大语言模型可以辅助履历比较、模式汇总、改善候选整理和复盘报告生成。它使用的是已经通过 TPCA / PCN 形成的结构化状态迁移履历，不作为现场状态迁移许可的直接来源。

工程修改仍由工程师根据设备、工艺、安全、生产和维护要求确认。

改善实施以后，系统继续形成新的 PCN Trace，再比较修改前后的运行情况。

因此，状态迁移履历的价值不只在于解释过去，也可以作为后续工程改善的比较基础。

这里的顺序很明确：

> **先决定看什么，再决定怎么看，最后才选择分析方法。**

算法不能替代状态迁移对象和数据表示的定义。如果数据结构形成之前已经丢失关键状态迁移关系，后续统计、机器学习或大语言模型也无法可靠恢复这些工程事实。

---

## 结语

一次真实状态迁移不会自动形成可分析的工程数据。

在 TPCA / PCN 中，Target State Entry 确定观察哪一次状态迁移；CAE-SDB 组织相关状态的功能角色和判定性质；控制仲裁、多路径控制和执行结果把判定连接到实际控制和执行；PCN Trace 将这些信息保存为可以比较、追溯和复盘的状态迁移履历。

CAE-SDB 的作用不只在于形成一个 3 × 3 判定结果。它还为同一 Target State Entry 下的异构状态建立统一的状态迁移判定语义，使状态获取、前置判定、控制选择、执行结果和长期履历能够在同一个工程对象下连续组织。

PCN Trace 的核心变化也不在于增加多少字段，而在于：

> **把数据组织单位从分散的信号、事件和报警，转向一次明确的 Target State Entry。**

后续使用规则、统计、大语言模型或其他分析方法，都建立在已经形成的状态迁移数据之上。

本文不讨论 TPCA / PCN 的完整方法论，只说明一次状态迁移如何形成可分析的工程数据。

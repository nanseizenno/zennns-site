## 为什么 OEE 之后还需要 PCN？

基础概念可参见：

- [Concepts｜核心概念](/zh/concepts/)
- [TPCA / PCN 状态迁移前置控制架构｜白皮书](/zh/whitepaper/)
- [为什么 PCN 是 TPCA 的最小工程节点？](/zh/notes/pcn-minimum-engineering-unit/)
- [为什么状态迁移条件必须显式化？](/zh/notes/explicit-state-transition-conditions/)

OEE、设备稼动数据、报警履历和保全数据，是制造现场数字化的重要基础。

它们能够帮助现场判断：

- 设备有没有运行；
- 停了多久；
- 性能有没有下降；
- 不良有没有增加；
- 生产损失出现在哪里；
- 某项改善以后运行绩效有没有变化。

但复杂自动化系统中还经常出现另一类问题：

> **设备没有明显故障，系统却进不了下一步。**

例如：

- 机器人 Ready，但抓取没有开始；
- 任务已经存在，但执行路径没有成立；
- 上游已经完成，下游暂时无法承接；
- MES、WCS、PLC、机器人都有状态记录，但系统长期处于 Waiting；
- 单体设备没有明显报警，但某个关键阶段始终不能进入。

这类问题关注的已经不只是运行绩效，而是：

> **某一次具体的状态迁移为什么没有成立。**

这正是 PCN 所处理的对象。

---

## 1. OEE 关注运行绩效，PCN 关注状态迁移入口

OEE 主要用于观察生产设备、生产单元或生产过程的运行绩效及其损失。

典型关注内容包括：

- 时间开动率；
- 性能效率；
- 良品率；
- 停机损失；
- 性能损失；
- 质量损失；
- 节拍变化；
- 产量变化。

它适合回答：

> 运行效率怎么样？

> 损失出现在哪里？

> 哪一段时间性能下降？

> 某项改善以后生产绩效有没有变化？

PCN 关注的对象不同。

PCN 对应一个明确的状态迁移入口：

```text
当前状态
→ PCN
→ 目标状态
```

它要回答的是：

- 当前系统准备进入哪个目标状态；
- 进入该状态所需要的条件是否成立；
- 必要许可是否成立；
- 进入以后执行链能否继续接续；
- 当前状态是否存在结构、动态或控制边界问题；
- 多个判定结果同时存在时，应进入哪一条控制路径；
- 本次判定与执行结果如何形成履历。

因此，更准确的区别是：

> **OEE 主要观察运行绩效和损失。**

> **PCN 主要处理一次明确的状态迁移是否能够成立。**

---

## 2. 复杂自动化系统的问题经常出现在“状态之间”

复杂设备和自动化生产线并不是只有“运行”和“停止”两个状态。

一台设备内部就可能存在：

```text
待机 → 自动运行
原点复归 → 自动运行
上料完成 → 加工
加工完成 → 检测
检测完成 → 排出
异常停止 → 复归
换型完成 → 批量生产
```

多设备系统中还会出现：

```text
识别完成 → 抓取
放置完成 → 压装
检测完成 → 分流
包装完成 → 码垛
码垛完成 → 入库交接
任务生成 → 任务派发
AGV 到站 → 站点交接
人工确认 → 自动恢复
```

这些都是明确的状态迁移入口。

系统不能进入下一步时，原因可能来自不同位置。

例如机器人已经 Ready，但：

- 工件识别结果已经过期；
- 安全区域许可没有成立；
- 上位系统尚未放行；
- 下游投放位置无法承接；
- 返回路径不可用；
- 某个关键状态正在切换；
- 必要信号虽然存在，但没有形成有效映射。

这些问题未必首先表现为 OEE 中的某一项损失类型。

它们首先表现为：

> **本次目标状态进入所需要的结构没有完整成立。**

因此，只看设备运行结果，可以知道最终停了多久，却未必能够直接回答：

> **为什么当时没有进入下一阶段？**

## 3. PCN 把一次状态迁移展开为可判定的工程结构

PCN 设置在目标状态进入前。

其基本处理链为：

```text
当前状态
→ 目标状态
→ PCN
→ 多源状态信号
→ C/A/E 状态映射
→ S/D/B 判定
→ CAE-SDB 判定结果
→ 控制仲裁
→ 多路径控制
→ PCN Trace
```

C / A / E 分别表示条件、许可和执行链三个状态变量域。

S / D / B 分别表示结构完整性、动态时序有效性和控制边界三类判定性质。

同一次状态迁移可以形成多个 CAE-SDB 判定结果。

这些结果经过控制仲裁以后，形成最终多路径控制。

因此，PCN 不是再增加一个新的 Ready、Interlock 或报警点，而是把一次明确状态迁移所需要的：

> **输入、语义、判定、仲裁、控制和履历**

组织在同一个工程节点中。

## 4. OEE 与 PCN 记录的是不同层面的工程事实

两者可以作如下比较：

| 项目 | OEE / 设备与生产数据 | PCN |
|---|---|---|
| 核心对象 | 运行绩效、生产结果和损失 | 一次明确的状态迁移入口 |
| 典型问题 | 效率怎么样、损失在哪里 | 为什么本次不能进入目标状态 |
| 主要数据 | 稼动、性能、质量、停机、节拍、产量 | 当前状态、目标状态、判定结果、控制结果、Trace |
| 时间位置 | 对运行过程和结果持续统计 | 在目标状态进入前进行判定 |
| 主要作用 | 发现绩效损失及其变化 | 判断状态迁移是否成立并选择控制路径 |
| 改善对象 | 设备、工艺、生产过程、运行损失 | 状态迁移条件、许可、执行链和控制路径 |

例如，OEE 或其他生产数据发现：

> 某设备在一个班次内发生了较长的等待损失。

如果同时存在 PCN Trace，就可以继续定位到：

```text
PCN-07

当前状态：
检测完成

目标状态：
工件排出

CAE-SDB 判定结果：
E-D

原因：
下游状态未刷新

控制仲裁：
暂不进入排出阶段

控制结果：
等待

执行结果：
下游状态同步后恢复
```

这时：

> **“发生了等待损失”**

与：

> **“为什么这次没有进入下一状态”**

就能够被连接起来。

因此：

> **OEE 描述运行绩效和损失，PCN Trace 描述其中一次具体状态迁移为什么没有成立。**

二者是互补关系。

## 5. 单台复杂设备内部同样可能需要 PCN

PCN 并不只用于 MES、WCS 或多设备系统。

只要自动化对象内部存在关键状态迁移入口，就可以设置 PCN。

例如：

```text
待机
→ 自动运行
```

进入自动运行之前，可能需要同时确认：

- 原点复归是否完成；
- 工件是否到位；
- 夹具是否锁紧；
- 安全许可是否成立；
- 工艺参数是否有效；
- 下游是否可承接；
- 异常复归是否完成；
- 结果回写链路是否可用。

这些信息原本可能分别存在于：

- PLC；
- 安全 PLC；
- 机器人控制器；
- 视觉系统；
- HMI；
- 上位系统；
- Interlock；
- 顺序控制逻辑。

传统控制逻辑本身可以完成动作控制。

PCN 进一步把：

```text
待机 → 自动运行
```

明确成一个可以持续判定和记录的状态迁移入口。

现场不再只有：

```text
AUTO START NG
```

还可以进一步看到：

- 当前状态；
- 目标状态；
- CAE-SDB 判定结果；
- 控制仲裁结果；
- 多路径控制结果；
- Trace ID。

这对复杂设备的调试、维护、复盘和模板复用具有直接工程意义。

## 6. 多系统联动会进一步放大这种差异

当 MES、WCS、PLC、机器人、AGV、视觉、安全系统和人工确认同时参与一个制造流程时，状态迁移条件会分布在不同系统中。

例如：

```text
MES 产生任务
→ WCS 是否允许派发
→ 车辆是否可以进入执行
→ 路径资源是否可用
→ AGV 是否到达
→ 站点是否允许交接
→ 下游是否能够承接
→ 结果是否正确回写
```

任何一个环节不成立，都可能造成整体流程停滞。

但单独查看某一个系统时：

- MES 可能显示任务已经存在；
- WCS 可能没有报警；
- AGV 可能在线；
- PLC 可能正常；
- 站点也可能处于 Ready。

问题仍然存在，因为：

> **单个系统状态成立，不等于整个目标状态迁移成立。**

PCN 的作用，就是在明确的状态迁移入口，把这些分散状态组织到同一次判定中。

多个 PCN 按状态迁移关系连接以后，可以进一步形成 PCN 网络。

相关说明可参见：

[多个 PCN 如何形成状态迁移前置控制网络？](/zh/notes/pcn-network-structure/)

## 7. OEE 与 PCN 服务于不同的改善问题

OEE 可以告诉现场：

- 哪一段生产过程效率下降；
- 损失持续了多久；
- 时间开动率、性能效率或良品率发生了什么变化；
- 改善前后整体运行绩效如何变化。

PCN 可以进一步回答：

- 哪一个状态迁移入口没有成立；
- 问题出现在 C、A 还是 E；
- 属于 S、D 还是 B；
- 当时形成了什么 CAE-SDB 判定结果；
- 为什么最终选择这条控制路径；
- 同一个 PCN 是否反复出现相似问题。

因此可以形成这样的分析关系：

```text
OEE / 生产绩效数据
        ↓
发现绩效损失
        ↓
关联相关状态迁移区间
        ↓
PCN Trace
        ↓
CAE-SDB 判定结果
        ↓
控制仲裁 / 多路径控制
        ↓
定位状态迁移设计薄弱点
```

PCN 不负责重新计算 OEE。

OEE 也不承担 PCN 的前置控制功能。

两者可以在实际改善过程中形成上下游关系。

---

## 8. PCN 增加的是“状态迁移判定数据”

PCN 的价值并不只体现在减少报警或缩短排查时间。

更根本的变化是：

> **把原本隐含在程序、接口、许可、设备联动和工程师经验中的状态迁移判断，变成显式、可记录的工程对象。**

对于一个关键状态迁移入口，可以明确记录：

```text
当前状态
目标状态
关键输入状态
C/A/E 状态映射
S/D/B 判定
CAE-SDB 判定结果
控制仲裁结果
多路径控制结果
执行结果
PCN Trace
```

这样，状态迁移不再只存在于 PLC 梯形图、Interlock、MES 流程、WCS 调度或调试工程师经验中。

它开始具备：

- 可定义；
- 可判定；
- 可记录；
- 可比较；
- 可追溯；
- 可复盘；

的工程属性。

实际部署时，也没有必要对所有普通动作设置 PCN。

更适合优先选择：

- 关键设备联动入口；
- 高频 Waiting 节点；
- 上下游承接节点；
- 资源锁节点；
- 关键许可节点；
- 自动 / 人工切换节点；
- 异常恢复节点；
- 经常依赖经验排查的状态迁移入口。

## 小结

OEE 之后还需要 PCN，并不是因为 OEE 不够先进，也不是因为设备数据没有价值。

两者处理的是不同工程对象。

> **OEE 主要描述运行绩效和损失。**

> **PCN 主要处理一次明确的目标状态迁移为什么能够成立，或者为什么没有成立。**

当生产效率下降时，OEE 可以帮助发现损失。

当现场继续追问：

> 为什么这个阶段没有进入？

> 为什么设备都正常，系统还是 Waiting？

> 为什么有任务却没有执行？

> 为什么最终进入等待，而不是其他控制路径？

这时需要观察的是状态迁移入口本身。

PCN 将这个入口组织为：

```text
当前状态
→ 目标状态
→ C/A/E 状态映射
→ S/D/B 判定
→ CAE-SDB 判定结果
→ 控制仲裁
→ 多路径控制
→ PCN Trace
```

因此，OEE 与 PCN 的关系可以概括为：

> **OEE 让现场看见运行绩效和损失。**

> **PCN 让现场看见一次状态迁移为什么成立，或者为什么没有成立。**

二者结合以后，制造系统不仅能够回答：

> **运行得怎么样？**

还可以进一步回答：

> **为什么系统当时没有进入下一状态？**

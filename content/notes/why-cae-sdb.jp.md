## なぜ CAE-SDB なのか

TPCA / PCN では、システムが現在状態（Current State）から目標状態（Target State）へ進む際、目標状態入口（Target State Entry）の前で状態を整理し、必要な判定を行う。

この時点では、設備の Ready、画像認識結果、安全許可、タスク状態、サービス状態、データベース状態など、複数の情報がすでに存在している場合が多い。実際の状態遷移では、これらを個別に確認するだけでは不十分であり、今回の 目標状態入口 に関係する状態として整理する必要がある。

CAE-SDB は、その整理と判定を二つの軸で行う。

```text
C / A / E：状態が今回の状態遷移で担う役割

S / D / B：その状態に対して適用する判定特性
```

現在の定義は次の通りである。

```text
C = Condition         条件状態
A = Authority         許可状態
E = Execution Chain   実行チェーン状態

S = Structure         構造完全性
D = Dynamics          動的時系列有効性
B = Boundary          制御境界
```

C / A / E は状態変数領域であり、S / D / B はそれらの状態に適用する判定特性である。両者を組み合わせることで、目標状態入口 前の状態関係を構造化して扱う。

---

## 1. C / A / E：状態遷移における役割

PCN は、目標状態入口に関係する複数系統の状態信号を、今回の状態遷移での役割に応じて、C：条件状態、A：許可状態、E：実行チェーン状態に整理する。

```text
C：目標状態 へ進むための条件
A：目標状態 への進入を許可する状態
E：目標状態 へ進入した後の実行チェーン状態
```

機能上の位置関係は、次のように整理できる。

```text
進入前                目標状態入口                進入後
  │                           │                           │
  C                           A                           E
条件状態                     許可状態                 実行チェーン状態
```

C、A、E はいずれも目標状態入口の前に PCN へ入力し、判定する。E では、目標状態へ進入した後に必要となる実行チェーンを、進入前に確認する。

### 1.1 C：Condition

C は、目標状態 へ進入するために必要な事実条件を表す。

代表例を以下に示す。

* ワークが存在している。
* 対象、位置または姿勢が要求条件を満たしている。
* 認識結果が取得されている。
* リクエストパラメータが揃っている。
* 前工程または前段の業務状態が完了している。
* 必要なデータが存在している。

### 1.2 A：Authority

A は、システムとして 目標状態 への進入が許可されている状態を表す。

代表例を以下に示す。

* 安全許可。
* エリア許可。
* 上位システムからの許可。
* 資源ロック。
* 承認状態。
* ユーザーまたはテナントの権限。
* 予算に関する許可。

重要な A は、独立した必要制約となる。重要な許可が成立していない場合、C と E が成立していても、現在の 目標状態 への進入は許可されない。

### 1.3 E：Execution Chain

E は、目標状態 へ進入した後、その段階を完了するために必要な実行チェーンの状態を表す。

例えば、

```text
Robot Ready = TRUE
```

という状態は、ロボット本体が Ready 状態にあることを示す。一方、実際の実行では、グリッパ、下流受入、異常処理、結果の書き戻しなども関係する。これらを含めて後続処理が継続できるかを確認するのが E である。

同様に、

```text
Service Healthy = TRUE
```

という状態だけでは、データベース、メッセージキュー、下流 API、Callback、業務結果の書き戻しまでを含む一連の処理が継続できるとは判断できない。

E には、本体装置、エンドエフェクタ、下流受入、代替経路、退避経路、異常処理経路、結果アップロード、書き戻し経路など、後続の実行に関係する状態が含まれる。

このように、C / A / E は、異なる設備やシステムに分散している状態を、今回の状態遷移における役割に基づいて整理する。

## 2. S / D / B：状態に対する判定特性

C / A / E へのマッピング後は、各状態に対して必要な S / D / B 判定を行う。

例えば、

```text
VisionOK = TRUE
```

という状態を判定に使用する場合、値そのものに加えて、信号構造、現在の有効性、制御境界との関係を確認する。

代表的な確認内容は次の通りである。

* 必要な信号およびインターフェースが定義され、接続されているか。
* 認識結果が現在の対象に対応しているか。
* 認識結果がタイムアウトしていないか。
* 現在値が事前に定義された制御境界内にあるか。

S、D、B の基本的な役割は次の通りである。

```text
S：判定に必要な構造を確認する。
D：現在の状態が判定に使用できるかを確認する。
B：現在の状態が制御境界内にあるかを確認する。
```

### 2.1 S：Structure

S は、今回の状態遷移判定に必要なエンジニアリング構造の完全性を判定する。

主な確認対象は次の通りである。

* 信号またはフィールドが定義されているか。
* インターフェースが接続されているか。
* マッピング関係が設定されているか。
* 許可元が明確であるか。
* 実行チェーンの関係が定義されているか。
* 必要な対象を観測できるか。

自動化システムでは、I/O 設定、変数定義、通信マッピング、設備パラメータなどが対象となる。

ソフトウェアシステムでは、Schema、Contract、Configuration、Dependency Definition、Permission Mapping などとして実装される場合がある。

### 2.2 D：Dynamics

D は、運転中の関連状態が現在も有効であり、今回の 目標状態入口の判定根拠として使用できるかを判定する。

主な確認対象は次の通りである。

* タイムアウトしていないか。
* 長時間更新されていない状態ではないか。
* チャタリングが発生していないか。
* 状態間に競合または同期ずれが発生していないか。
* 許可がすでに取り消されていないか。
* キャッシュまたは Token が期限切れになっていないか。
* 対象のバージョンが変化していないか。

実装には、Timer、Timeout、Timestamp、Heartbeat、Debounce、Freshness、Version Check、Synchronization など、既存の機構を使用できる。

```text
状態値が存在していても、現在の判定に使用できるとは限らない。
```

### 2.3 B：Boundary

B は、関連状態が事前に定義された許容範囲、しきい値または制御境界内にあるかを判定する。

境界判定に使用する代表的なパラメータには、次のようなものがある。

```text
Min / Max
Threshold
Tolerance
Range
Time Window
Quota
Capacity
Rate Limit
Retry Limit
```

例えば、ある寸法の許容範囲を次のように定義する。

```text
19.90 mm ～ 20.10 mm
```

この場合の判定例は次の通りである。

```text
20.06 mm → 許容範囲内
20.18 mm → 許容範囲外
```

B は制御境界に関する判定を担当する。判定後にどの制御経路を選択するかは、他の CAE-SDB 判定結果 を含む判定結果全体を 制御優先度調停 で処理したうえで決定する。

S、D、B は三つの判定特性であり、PCN ランタイム の処理順序を規定するものではない。実際の処理順序、ショートサーキット条件、実装方法はエンジニアリングルールによって決定される。

## 3. C / A / E と S / D / B の組合せ

C / A / E で状態の役割を整理した後、その状態に必要な S / D / B 判定を適用する。

例えば、画像認識結果を現在のワークがピック条件を満たすことの根拠として使用する場合、その状態は C にマッピングされる。

この認識結果に D 判定を適用し、タイムアウトが確認された場合、次の CAE-SDB 判定結果 を形成できる。

```text
C-D
```

この結果は、今回の 目標状態入口 に必要な条件状態に動的時系列有効性の問題があることを示す。

その他の例を以下に示す。

```text
A-D
今回の状態遷移に必要な許可状態について、動的な失効が確認された。

E-B
今回の状態遷移に必要な実行チェーン状態が、事前に定義された受入境界を外れている。

C-S
今回の状態遷移に必要な条件状態について、必要な構造定義または接続が不足している。
```

CAE-SDB 判定結果は、対応する S、D、B の判定を実際に行い、その結果が得られた場合に形成する。

現場で観測された現象のみを根拠として、C-S、A-D、E-B などの結果を直接付与することはしない。

CAE-SDB は、一回の明確な目標状態入口に関係する状態と判定の関係を表す。

## 4. 既存のエンジニアリング機構との関係

CAE-SDB で利用する基礎的な判定機構の多くは、すでに自動化システムやソフトウェアシステムで使用されている。

PLC または自動化制御システムでは、例えば次のような機構がある。

```text
S：信号定義、インターフェースマッピング、設定確認
D：チャタリング除去、タイムアウト、時間ウィンドウ、ハートビート、安定性判定
B：上下限、範囲、しきい値、許容ウィンドウ
```

業務システムまたはバックエンドサービスでは、例えば次のような機構がある。

```text
S：Schema、Contract、Dependency、Permission Mapping
D：TTL、Timeout、Heartbeat、Version、Freshness
B：Rate Limit、Quota、Amount Limit、Capacity、Retry Limit
```

PCN は、これらの既存機構を 目標状態入口 単位で整理し、状態遷移判定に使用する。

整理対象は次の通りである。

```text
現在状態は何か。

目標状態は何か。

今回の 目標状態入口 に関係する状態は何か。

各状態は C / A / E のどの役割を担うか。

どの状態に対して S / D / B のどの判定が必要か。

CAE-SDB 判定結果 と時間情報 T を 制御優先度調停 へどのように渡すか。

現在の 目標状態入口 に対して、どの 複数経路制御 を出力できるか。

判定根拠と制御結果をどのように PCN 状態遷移判定履歴 として記録するか。
```

基本的な処理関係は次の通りである。

```text
現在状態
     ↓
目標状態
     ↓
目標状態入口 / PCN
     ↓
C / A / E 状態マッピング
     ↓
S / D / B 判定
     ↓
CAE-SDB 判定結果 + T
     ↓
制御優先度調停
     ↓
複数経路制御
     ↓
PCN 状態遷移判定履歴
```

設備プログラム、インターフェース設定、既存の制御ロジック、エンジニアリング経験などに分散している判定関係を、この処理単位に合わせて整理することで、目標状態入口 ごとの判定内容と制御結果を記録できる。

## 5. CAE-SDB の適用対象

CAE-SDB は、PLC を含む自動化システムだけでなく、明確な 目標状態入口 を持つ他のエンジニアリングシステムにも適用できる。

適用候補となる基本条件を以下に示す。

```text
明確な 現在状態
明確な 目標状態入口
観測可能な状態遷移関連情報
目標状態 へ入る前の判定要求
事前に定義可能な後続制御経路
```

### 5.1 自動化実行ユニット

例えば、次のような状態遷移を対象とする。

```text
Waiting Stage → Pick Stage

C：対象の存在、位置・姿勢が要求条件を満たしている
A：安全許可、エリア許可、上位システムからの許可
E：ロボット、グリッパ、および関連する実行チェーンの状態
```

### 5.2 業務システム

例えば、次のような状態遷移を対象とする。

```text
注文提出待ち → 正式提出

C：パラメータが揃っている、業務対象が存在する、前段処理が完了している
A：ユーザー権限、承認、予算に関する許可
E：データベース書込み、在庫サービス、メッセージ発行などの実行チェーン状態
```

### 5.3 API または AI ツール呼出し

例えば、次のような状態を対象とする。

```text
C：リクエスト対象が明確、パラメータが揃っている、必要なコンテキストが存在する
A：ネットワークアクセス、ナレッジベース、ツール、テナントに対する認可が成立している
E：モデル、ツールチェーン、対象 API、応答経路が利用可能である
```

各分野では、それぞれの既存機構を利用して S / D / B の判定を実装できる。

CAE-SDB は、明確な 目標状態入口 を基準として、状態変数領域と判定特性の関係を整理する構造である。実装先のコントローラやソフトウェアプラットフォームは限定しない。

## 6. CAE-SDB 判定結果、制御優先度調停、複数経路制御

C / A / E に対する S / D / B 判定 の結果として CAE-SDB 判定結果 が形成される。

CAE-SDB 判定結果は構造化判定結果として制御優先度調停に入力する。制御優先度調停では判定結果と制御制約を処理し、その結果に基づいて複数経路制御を決定する。

```text
CAE-SDB 判定結果 + T
        ↓
   制御優先度調停
        ↓
 複数経路制御
        ↓
    PCN 状態遷移判定履歴
```

一回の 目標状態入口 において、複数の CAE-SDB 判定結果 が同時に形成される場合がある。

制御優先度調停 では、重要な許可、安全上の制約、制御優先度、境界ルール、選択可能な候補経路などを考慮し、制御上の優先関係を処理する。

代表的な 複数経路制御 には、次のようなものがある。

```text
移行許可
待機
再認識
再サンプリング
再試行
戻し処理
下流調整
資源解放
縮退実行
人工確認
移行禁止
安全ロック
異常隔離
```

同じ CAE-SDB 判定結果でも、対象となる目標状態入口、安全上の制約、制御ルールに応じて選択する制御経路は変わる。

```text
C-D ≠ WAIT
E-B ≠ RETURN
A-S ≠ SAFETY LOCK
```

同一の CAE-SDB 判定結果 であっても、目標状態入口、安全上の制約、制御ルールが異なれば、選択される制御経路が変わる場合がある。

移行許可、移行禁止、その他の複数経路制御は、対象となる明確な目標状態入口に対して形成する。

代替経路、退避経路、戻し経路は、それぞれ対応する後続の目標状態または目標実行経路の候補として扱う。現在の目標状態入口に対する E は、現在の目標状態へ進入した後に必要となる実行チェーンを対象として判定する。移行許可は、その目標状態入口に対する判定結果と制御優先度調停の結果に基づいて決定する。

PCN 状態遷移判定履歴 には、今回の状態遷移に関する主要な判定情報と制御情報を記録する。

代表的な記録内容は次の通りである。

* 現在状態。
* 目標状態。
* 判定に使用した状態および時間情報 T。
* C / A / E 状態マッピング。
* S / D / B 判定。
* CAE-SDB 判定結果。
* 制御優先度調停結果。
* 複数経路制御。
* 実行結果。

これらの記録は、現場での問題追跡、プロジェクト引継ぎ、ルールレビュー、バージョン比較、後続のエンジニアリング改善に利用できる。

## 7. 現時点の検証範囲

CAE-SDB は、現在の TPCA / PCN において 目標状態入口 前の判定に使用するエンジニアリング構造である。

現段階では、C / A / E または S / D / B があらゆるエンジニアリングシステムを完全に表現できることを数学的に証明したものではない。

今後の検証では、次の点を継続して確認する。

```text
C / A / E 以外に、
明確な 目標状態入口 に不可欠な独立した状態遷移上の役割が存在するか。

S / D / B 以外に、
状態遷移に関係する状態を判定するうえで不可欠な独立した判定特性が存在するか。
```

異なる業界、設備、システムへ適用した際、現在の構造では自然に扱えない対象が継続して確認された場合、その対象を個別に検証する。

現段階での主な検証対象は次の通りである。

```text
C / A / E が 目標状態入口 に必要な状態遷移上の役割を安定して整理できるか。

S / D / B が各分野ですでに使用されている状態判定機構を安定して整理できるか。

CAE-SDB が 制御優先度調停、複数経路制御、PCN 状態遷移判定履歴 を継続して支えられるか。
```

## なぜ CAE-SDB なのか？

TPCA / PCN において、CAE-SDB は、明確な Target State Entry の前に行う構造化判定に使用する。

既存の概念定義では、次のように定義している。

- C = Condition
- A = Authority
- E = Execution Chain
- S = Structure
- D = Dynamics
- B = Boundary

ただし、六つの定義を示すだけでは、さらに基本的な問いには答えられない。

> **なぜ C / A / E なのか。なぜ S / D / B なのか。**

CAE-SDB は、3 × 3 の分類表を作るために六つのラベルを組み合わせたものではない。

CAE-SDB には、役割の異なる二つの分析軸がある。

```text
CAE — Transition Role Axis
状態遷移における機能役割軸

SDB — State Validation Axis
状態検証軸
```

二つの軸は、それぞれ異なる問いを扱う。

---

## 1. CAE：Target State Entry における三つの遷移機能役割

Target State が明確になった後、1 回の状態遷移では、まず次の三つの基本的なエンジニアリング上の問いに答える必要がある。

```text
C：必要な条件はそろっているか？

A：進入が許可されているか？

E：進入後も実行を継続できるか？
```

Target State Entry との関係は、次のように表せる。

```text
進入前                Target State Entry                進入後
  │                           │                           │
  C                           A                           E
Condition                 Authority                Execution Chain
```

ここで示す「進入前―入口―進入後」は、C / A / E が担うエンジニアリング上の機能位置を示すものである。

E を Target State へ進入した後に判定するという意味ではない。

> **C、A、E は、いずれも Target State Entry の前に PCN で前判定する。**

### C：必要な条件はそろっているか？

C は、Target State へ進む前に必要となる現場条件、対象条件、認識条件、データ条件、タスク条件、パラメータ条件などが成立しているかを扱う。

例えば、次のような状態である。

```text
ワークは存在しているか？
認識結果は成立しているか？
位置は適正か？
必要なパラメータはそろっているか？
タスクデータは完全か？
```

C が扱うのは、

> **Target State へ進むために必要な事実条件がそろっているか。**

という問いである。

### A：進入が許可されているか？

C が成立していても、それだけで Target State への進入が許可されるとは限らない。

さらに、例えば次の状態を確認する必要がある。

```text
安全許可は成立しているか？
上位システムから許可されているか？
対象エリアへの進入は許可されているか？
リソースロックは取得されているか？
人による確認が必要か？
相手機器から許可されているか？
```

したがって、A が扱うのは、

> **現在のシステムが Target State への進入を許可されているか。**

という問いである。

重要な A：Authority は、独立した必要条件となり得る。

例えば、

```text
C = 成立
E = 成立
```

であっても、重要な A：Authority が成立していなければ、

```text
A = 不成立
```

Target State へ進入してはならない。

### E：進入後も実行を継続できるか？

Condition と Authority が成立していても、さらに確認すべき事項がある。

> **Target State へ進んだ後、後続の Execution Chain を継続できるか。**

E：Execution Chain は、単一設備の Ready と同一ではない。

例えば、次のような状態が関係する。

```text
本体設備
エンドエフェクタ
下流受入
代替経路
戻り経路
異常排出経路
結果アップロードまたは書戻し経路
```

したがって、

```text
C：必要な条件はそろっているか？
A：進入が許可されているか？
E：進入後も実行を継続できるか？
```

は、1 回の状態遷移における異なるエンジニアリング上の機能役割を示す。

CAE の目的は、「ロボット信号」「PLC 信号」「MES 信号」のように、信号の取得元で状態を分類することではない。

判定対象は、

> **この状態が、本 Target State Entry においてどの遷移機能役割を担うか。**

である。

## 2. SDB：関連状態をどの性質から判定するか

ある状態を C、A、E のいずれかへマッピングした時点で明確になるのは、

> **その状態が本状態遷移でどの機能役割を担うか。**

という点である。

その後、関連状態そのものについて、さらに次の事項を判定する必要がある。

- その状態を判定するために必要なエンジニアリング構造が確立されているか。
- 現在取得している状態が、本 Target State Entry に対して現在も有効か。
- 現在状態が、事前に定義された境界に対してどの位置にあるか。

このために使用する第二の分析軸が SDB である。

```text
S：必要な構造は確立されているか？

D：現在状態は有効か？

B：現在状態は規定境界内にあるか？
```

### S：必要な構造は確立されているか？

S = Structure。

S は、関連する対象、信号、インターフェース、マッピング関係、許可元、役割、Execution Chain の境界が定義・接続され、観測可能であるかを判定する。

例えば、次の事項を確認する。

```text
必要な信号は定義されているか？
インターフェースは接続されているか？
マッピング関係は明確か？
許可元は明確か？
役割関係は明確か？
Execution Chain の境界は定義されているか？
必要な状態を観測できるか？
```

これらの基礎構造が存在しない、または不完全である場合、後続の状態判定には信頼できるエンジニアリング上の基盤がない。

したがって、S：Structure が扱うのは、

> **判定に必要なエンジニアリング構造が確立されているか。**

という問いである。

---

### D：現在状態は有効か？

必要な構造が確立されていても、次の問題が残る。

> **現在取得している状態は、本 Target State Entry に対して現在も有効か。**

例えば、

```text
Robot Ready = TRUE
```

という状態変数が存在していても、その値をそのまま現在有効な判定根拠として使用できるとは限らない。

さらに、次のような状態を確認する必要がある。

```text
タイムアウトしていないか？
更新されているか？
チャタリングしていないか？
状態が競合していないか？
遅延していないか？
複数の状態源が同期しているか？
信頼度は現在も有効か？
許可が直前に取り消されていないか？
```

したがって、

```text
状態が存在する ≠ 現在有効な状態である
```

D = Dynamics が扱うのは、

> **時間経過および状態変化を考慮したとき、現在状態が本 Target State Entry の判定根拠として現在も有効か。**

という問いである。

---

### B：現在状態は規定境界内にあるか？

必要なエンジニアリング構造が確立され、現在有効な状態を取得できた後、さらに確認すべき事項がある。

> **現在状態が、事前に定義された許容範囲、制限値、または制御境界に対してどの位置にあるか。**

これを判定するのが B = Boundary である。

例えば、寸法の許容範囲が、

```text
19.90 mm ～ 20.10 mm
```

であり、現在の測定値が、

```text
20.06 mm
```

である場合、B：Boundary では、

```text
20.06 mm が規定境界内にあるか？
```

を判定する。

同じ考え方は、例えば次の状態にも適用できる。

```text
温度範囲
圧力範囲
バッファ容量
負荷率
距離
速度
許可エリア
許可レベル
状態集合
その他の事前定義されたエンジニアリング境界
```

したがって、B：Boundary は Wait、Return、Manual Confirm、Safety Lock などの制御経路を示すものではない。

これらは後段の制御経路である。

B：Boundary が扱うのは、

> **現在有効な状態と、事前に定義された境界との位置関係を判定すること。**

である。

---

## 3. CAE と SDB は異なる次元の分析軸である

以上から、CAE と SDB が扱う対象は異なる。

CAE が扱うのは、

> **関連状態が、本状態遷移でどの機能役割を担うか。**

という問いである。

SDB が扱うのは、

> **その状態について、必要な構造、現在の有効性、境界との関係をどのように判定するか。**

という問いである。

CAE は、次のように整理できる。

```text
CAE — Transition Role Axis

C：必要な条件はそろっているか？
A：進入が許可されているか？
E：進入後も実行を継続できるか？
```

SDB は、次のように整理できる。

```text
SDB — State Validation Axis

S：必要な構造は確立されているか？
D：現在状態は有効か？
B：現在状態は規定境界内にあるか？
```

したがって、CAE と SDB は二つの重複した状態分類ではなく、異なる次元を持つ二つの分析軸である。

全体関係は、次のように表せる。

```text
Target State Entry
        │
        ▼
本状態遷移に関係する状態を識別
        │
        ▼
CAE：遷移機能役割をマッピング
        │
        ├── C：必要な条件はそろっているか？
        ├── A：進入が許可されているか？
        └── E：進入後も実行を継続できるか？
                  │
                  ▼
SDB：関連状態の性質を判定
                  │
        ├── S：必要な構造は確立されているか？
        ├── D：現在状態は有効か？
        └── B：現在状態は規定境界内にあるか？
                  │
                  ▼
            CAE-SDB Result
```

簡潔に表すと、

> **CAE は「その状態が本状態遷移でどの役割を担うか」を示す。**

> **SDB は「その状態について、構造、現在の有効性、境界との関係を判定する」。**

という関係である。

## 4. 簡単なエンジニアリング例

自動化設備が加工段階へ進む前に、ワーク寸法を確認する場合を例とする。

まず、C：Condition に関係する状態変数がある。

```text
C 状態変数： Workpiece_Dimension
```

この状態変数が持つエンジニアリング上の役割は、

> **ワーク寸法が、加工段階へ進む前に確認すべき Condition に属する。**

という点である。

その後、S / D / B の各判定性質から評価する。

### C-S：Structure

```text
測定対象は明確か？
寸法検出センサは接続されているか？
信号アドレスは正しいか？
単位は統一されているか？
測定値と現在のワークが正しく関連付けられているか？
```

### C-D：Dynamics

```text
この寸法値は現在のワークの測定値か？
測定結果は更新されているか？
データはタイムアウトしていないか？
ワーク移動後に旧測定値が失効しているか？
```

### C-B：Boundary

例えば、許容寸法が、

```text
19.90 mm ～ 20.10 mm
```

と定義されている場合、現在有効な測定値がこの範囲内にあるかを判定する。

```text
20.06 mm → 規定境界内

20.18 mm → 規定境界外
```

ここで、

```text
C
```

は、「ワーク寸法」が本 Target State Entry において Condition の機能役割を担うことを示す。

一方、

```text
S / D / B
```

は、それぞれ次の事項を判定する。

```text
この寸法状態を判定するために必要な構造は確立されているか？

現在取得している寸法値は、現在も有効か？

現在有効な寸法値は、規定境界内にあるか？
```

このように、二つの分析軸を明確に区別できる。

同じ考え方は、A：Authority と E：Execution Chain にも適用できる。

例えば、A：Authority では次のように整理できる。

```text
A：
特定の安全許可は、Target State への進入に必要な Authority である。

A-S：
許可元、インターフェース、認可関係は確立されているか？

A-D：
許可は現在も有効か？

A-B：
現在の許可状態または認可レベルは、進入を許可する規定境界内にあるか？
```

E：Execution Chain では、例えば次のように整理できる。

```text
E：
下流受入能力は、Target State へ進んだ後に Execution Chain を継続できるかを判断するための状態である。

E-S：
下流受入チェーンおよび関連インターフェースは定義されているか？

E-D：
現在の下流能力状態は、現在も有効か？

E-B：
現在の容量、負荷、位置などの状態は、受入可能な規定境界内にあるか？
```

## 5. CAE-SDB Result は終点ではない

CAE-SDB の目的は、新しい異常分類表を作ることではない。

CAE-SDB による構造化判定は、

```text
CAE-SDB Result
```

を形成し、その結果はさらに次の処理へ進む。

```text
CAE-SDB Result
        ↓
   Arbitration
        ↓
Multipath Control
```

Arbitration は、重要な Authority、制御制約、複数の CAE-SDB Result の間にある制御上の優先関係を処理する。

Multipath Control は、その結果に基づいて最終的なエンジニアリング制御出力を形成する。

代表的な制御経路には、例えば次のものがある。

```text
Allow
Wait
Recheck
Retry
Return
Degrade
Manual Confirm
Prohibit
Safety Lock
その他の事前定義された経路
```

したがって、

> **S / D / B は制御動作ではない。**

特に、B：Boundary は境界判定を示すものであり、Wait、Return、Manual Confirm などの具体的な制御経路を示すものではない。

CAE-SDB が提供するのは、

> **Arbitration へ入力する前の構造化判定基盤である。**

## 6. 現在の理論境界と今後の検証

本稿で説明するのは、現在の CAE-SDB における基礎構造の解釈である。

この構造について、数学的に、

```text
すべてのエンジニアリングシステムにおいて、
CAE と SDB に拡張の余地が存在しない。
```

ことを証明したわけではない。

検証対象は、より厳密には、明確に定義された 1 回の Target State Entry の作用範囲に限定する必要がある。

### CAE 第四変数の反例探索

確認すべきなのは、

> **C / A / E のいずれにも還元できず、かつ明確な Target State Entry に不可欠な第四の遷移機能役割 X が存在するか。**

という点である。

すなわち、

```text
X ≠ C
X ≠ A
X ≠ E
```

であり、かつ既存定義を変更して C / A / E のいずれかへ強制的に含めることができない X を探索する。

### SDB 第四判定性質の反例探索

同様に確認すべきなのは、

> **本状態遷移の判定対象として取り込まれた関連状態について、S / D / B のいずれにも還元できず、かつ不可欠な第四の独立した判定性質 P が存在するか。**

という点である。

すなわち、

```text
P ≠ S
P ≠ D
P ≠ B
```

となる独立した判定性質を探索する。

検証の目的は、現在の CAE-SDB 構造を維持することではない。

> **現在の定義では説明できない現実のエンジニアリング対象を積極的に探索すること。**

が目的である。

今後、業界、設備、システムをまたいだ事例検証において、現在の定義では自然に表現できない独立した機能役割または判定性質が繰り返し確認された場合は、新たな理論課題として扱う必要がある。

## 小結

CAE-SDB は、異なる次元を持つ二つの分析軸として整理できる。

### CAE — Transition Role Axis

```text
C：必要な条件はそろっているか？
A：進入が許可されているか？
E：進入後も実行を継続できるか？
```

Target State Entry を中心とした機能位置は、次のように表せる。

```text
進入前 → Target State Entry → 進入後
```

ただし、C、A、E は、いずれも Target State Entry の前に PCN で前判定する。

### SDB — State Validation Axis

```text
S：必要な構造は確立されているか？
D：現在状態は有効か？
B：現在状態は規定境界内にあるか？
```

全体関係は、次のように整理できる。

```text
Target State Entry
        ↓
関連状態を識別
        ↓
Transition Role
C / A / E
        ↓
State Validation
S / D / B
        ↓
CAE-SDB Result
        ↓
Arbitration
        ↓
Multipath Control
```

CAE-SDB の目的は、新しい状態ラベルを増やすことではない。

対象とするのは、

> **明確な Target State Entry に対して、関連状態が状態遷移で担う機能役割を識別し、それぞれの状態について、構造完全性、動的時系列有効性、事前定義された境界との位置関係を判定すること。**

である。

CAE-SDB Result は、その後 Arbitration と Multipath Control へ接続される。

これにより、状態遷移前に取得する複数ソース状態の判定と、後続の制御経路との関係を明確にできる。

## なぜ CAE-SDB なのか？

**CAE-SDB は、TPCA / PCN において、目標状態入口前の複雑な状態を構造化して判定するための中核分析法である。**

製造・自動化システムにおける一つの状態遷移は、設備状態、安全許可、画像認識結果、タスク状態、下流受入状態、上位システム状態など、複数の要素に同時に左右される。

これらの状態は異なる設備やシステムから取得される。一つの明確な状態遷移として扱うには、少なくとも次の二つを分けて考える必要がある。

- その状態が今回の状態遷移で、どのようなエンジニアリング上の役割を担うか。
- 現在、その状態をどのような性質から判定する必要があるか。

CAE-SDB では、前者を C / A / E、後者を S / D / B として整理する。

```text
C = Condition         条件状態
A = Authority         許可状態
E = Execution Chain   実行チェーン状態

S = Structure         構造完全性
D = Dynamics          動的時系列有効性
B = Boundary          制御境界
```

二つの軸を組み合わせることで、**C / A / E × S / D / B** の構造化判定関係として整理できる。

これにより、「どの状態変数領域に対して、どの性質の判定を行っているか」を明確にできる。

CAE-SDB の判定結果は、その後の制御調停へ渡され、複数経路制御、実行結果、PCN の状態遷移判定履歴へ接続される。

---

## 1. なぜ二つの軸が必要なのか

TPCA / PCN では、システムが現在状態から目標状態へ移行する際、その直前で前制御判定を行う位置を**目標状態入口**として扱う。

たとえば、ロボットが把持段階へ移行しようとしている場合、現場には次のような状態が同時に存在する。

```text
画像認識結果 = 成立
安全許可 = 成立
ロボット準備状態 = 成立
下流受入状態 = 受入可能
```

いずれも現在の目標状態入口に関係する状態であるが、エンジニアリング上の役割は同じではない。

画像認識結果は把持条件に関係する。安全許可は、現在その状態遷移を許可できるかに関係する。ロボット準備状態や下流受入状態は、目標状態へ移行した後に必要な実行チェーンを継続できるかに関係する。

さらに、状態が存在しているだけでは、現在の判定に使用できるとは限らない。

たとえば、次の点を確認する必要がある。

- 必要な信号、インターフェース、マッピング関係が定義されているか。
- その状態が現在の対象物、現在のサイクルに対応しているか。
- 状態が有効時間内にあるか。
- 関連する数値が許容範囲内にあるか。

したがって、

> **その状態が今回の状態遷移でどのような役割を持つか**

という問題と、

> **現在、その状態をどの性質から判定する必要があるか**

という問題は、別の軸として扱う必要がある。

CAE-SDB では、前者を C / A / E、後者を S / D / B として分離する。

---

## 2. C / A / E：状態遷移における役割

C / A / E は、各状態が現在の目標状態入口に対して担うエンジニアリング上の役割によって区分する。

| 条件の役割 | 許可の役割 | 実行チェーン継続の役割 |
|---|---|---|
| **C = Condition** | **A = Authority** | **E = Execution Chain** |
| 条件状態 | 許可状態 | 実行チェーン状態 |
| 目標状態へ移行するために必要な条件 | 目標状態への移行に必要な許可 | 現在の目標状態入口に関係する実行チェーンの継続状態 |
| **条件は成立しているか？** | **現在、移行を許可できるか？** | **移行後、必要な実行チェーンを継続できるか？** |

C / A / E は、いずれも実際に目標状態へ移行する前に PCN が取得・判定する。

三者の違いは、判定の時間順序ではなく、**今回の状態遷移において何を意味する状態か**という役割の違いにある。

### 2.1 なぜ C / A / E を分けるのか

条件、許可、実行チェーン継続状態を区別しない場合、性質の異なる問題がすべて「条件未成立」や「移行不可」といった一つの結果に圧縮されやすい。

その結果、現場では「何が足りないのか」が分からず、確認対象を再び設備、PLC、上位システム、下流設備へ横断して探すことになる。

#### C と A：条件が成立していても、移行許可が得られているとは限らない

ある自動化実行ユニットが、ワークを次の加工段階へ移行させようとしているとする。

```text
ワーク存在 = 成立
ワーク位置 = 規定内
前工程検査 = 完了

対象ステーションの資源ロック = 未取得
上位システムからの許可 = 未成立
```

ワーク自体は、次工程へ進むための条件を満たしている。

一方で、現在の目標状態入口に必要な許可は成立していない。

```text
C = 成立
A = 不成立
```

C と A を区別しなければ、資源ロックや上位許可の問題まで「条件未成立」として扱われる。

その場合、現場ではワーク位置や前工程検査を確認し続ける可能性があるが、実際に今回の状態遷移を止めているのは許可状態である。

> **条件が成立していても、現在の移行許可が成立しているとは限らない。**

A には、安全システム、上位システム、区域制御、資源管理、相手機器、人による確認、権限管理など、さまざまな許可元が存在し得る。

重要な A は独立した必要制約となる。C と E が成立していても、重要な許可が成立していなければ、現在の目標状態入口では移行を許可しない。

#### A と E：許可されていても、移行後の実行チェーンが継続できるとは限らない

同じ自動化実行ユニットで、次の状態を考える。

```text
対象ステーションの資源ロック = 取得済み
上位システムからの許可 = 成立

下流側の受入状態 = 不可
必要な結果の書き戻し経路 = 利用不可
```

現在の目標状態へ移行するための許可は成立している。

一方、目標状態へ移行した後に必要な実行チェーンは継続できない。

```text
A = 成立
E = 不成立
```

A と E を区別しなければ、「許可された」ことがそのまま「移行後も実行可能」と解釈されやすくなる。

> **移行が許可されていても、その後の実行チェーンが継続できるとは限らない。**

A は、現在その目標状態への移行を許可できるかを扱う。

E は、現在の目標状態入口に結び付いた実行チェーンが、移行後も継続できるかを扱う。

#### C と E：移行条件が成立していても、実行チェーンが継続可能とは限らない

たとえば、

```text
ワーク存在 = 成立
ワーク位置 = 規定内
前工程検査 = 完了

下流ステーション = 満杯
バッファ空き = 不足
後続設備 = 受入不可
```

という状態では、現在の目標状態へ移行するためのワーク条件や前工程条件は成立している。

一方、移行後の実行チェーンは継続できない。

```text
C = 成立
E = 不成立
```

> **移行条件が成立していても、移行後の実行チェーンが継続可能とは限らない。**

C は、目標状態へ移行するために必要な条件を扱う。

E は、現在の目標状態入口に結び付いた実行チェーンの継続状態を扱う。

### 2.2 C / A / E を分けることで何が残るのか

一つの「目標状態へ移行できない」という結果を、C / A / E によって次のように区別できる。

```text
C 不成立：
目標状態へ移行するための条件が成立していない

A 不成立：
条件は成立していても、現在の移行許可が成立していない

E 不成立：
条件や許可は成立していても、移行後の実行チェーンを継続できない
```

これにより、状態遷移に関する三つの異なるエンジニアリング意味を保持できる。

```text
移行に必要な条件
        ↓
C：条件は成立しているか？

移行許可
        ↓
A：現在、移行を許可できるか？

移行後の実行チェーン継続要件
        ↓
E：必要な実行チェーンを継続できるか？
```

C / A / E は、すべて目標状態入口前に PCN が取得・判定する。

ここでの違いは判定時刻ではなく、各状態が今回の状態遷移で担うエンジニアリング上の役割にある。

その後、C / A / E の各状態に対して S / D / B 判定を行う。

| **S = Structure** | **D = Dynamics** | **B = Boundary** |
|---|---|---|
| 構造完全性 | 動的時系列有効性 | 制御境界 |

CAE-SDB の第一軸が答える問いは、

> **この状態は、今回の状態遷移でどのようなエンジニアリング上の役割を持つか。**

第二軸が答える問いは、

> **現在、この状態をどの性質から判定する必要があるか。**

である。

現在状態、目標状態、時間情報、状態識別子、判定結果、制御結果は、それぞれ独立したエンジニアリング上の意味を持ち、C / A / E の状態変数領域には含めない。

### 2.3 C：Condition｜条件状態

C は、目標状態へ移行する前に成立している必要がある条件状態を表す。

自動化実行ユニットでは、ワークが存在しているか、対象物の位置や姿勢が要求を満たしているか、画像認識や検査結果が取得済みか、前工程が完了しているかといった状態が C に該当し得る。

デジタルシステムであれば、要求パラメータや必要データがそろっているかといった状態も、同じ条件状態として扱える。

C が答える問いは、

> **現在、この目標状態へ移行するための条件がそろっているか。**

である。

### 2.4 A：Authority｜許可状態

A は、システムが現在その目標状態へ移行することを許可されているかを表す。

安全許可、区域許可、上位システム許可、相手機器からの許可、資源ロック、ユーザー権限、人による確認などが A に該当し得る。

重要な A は独立した必要制約となる。

重要な許可が成立していない場合、C と E が成立していても、現在の目標状態入口では移行を許可しない。

A が答える問いは、

> **現在、この目標状態への移行を許可できるか。**

である。

### 2.5 E：Execution Chain｜実行チェーン状態

E は、現在の目標状態入口に結び付いた、目標状態へ移行した後の実行チェーンが継続可能な状態にあるかを表す。

たとえば、ロボットが把持段階へ移行する場合、ロボット本体の実行能力、実行機構の状態、現在の把持処理に必要な下流受入状態、結果の送信経路・書き戻し経路などが E の関連状態になり得る。

戻し、異常排出、代替経路などが現在の目標状態に必要な実行チェーンに含まれない場合、それらを現在の入口における E の成立根拠には用いない。

それらは後続の複数経路制御における候補となり得る。実際にその経路に対応する目標状態へ移行する場合は、新しい目標状態入口としてあらためて判定する。

ロボット準備状態は E の一つの入力となり得るが、E が扱うのは単一設備の Ready ではなく、現在の目標状態入口に結び付いた実行チェーン全体の継続性である。

E が答える問いは、

> **現在の目標状態へ移行した後、その入口に結び付いた必要な実行チェーンを継続できるか。**

である。

## 3. S / D / B：状態に対する判定性質

C / A / E の状態マッピングを行った後、PCN は現在の目標状態入口に対して定義済みの判定規則に基づき、関連状態に S / D / B 判定を適用する。

三つの判定性質は、それぞれ構造完全性、動的時系列有効性、制御境界を扱う。

| **判定性質** | **基本的な問い** |
|---|---|
| S：Structure | 判定に必要な構造が定義・接続され、観測可能になっているか |
| D：Dynamics | 現在の状態を今回の状態遷移の有効な判定根拠として使用できるか |
| B：Boundary | 現在の状態が、あらかじめ定義された許容境界内にあるか |

### 3.1 S：Structure｜構造完全性

S は、今回の状態遷移判定に必要なエンジニアリング構造が成立しているかを確認する。

ここでいう構造には、必要な信号とインターフェース、対象と状態のマッピング関係、許可元、関連経路、実行チェーン境界、必要状態の可観測性などが含まれる。

ある状態が現場では実際に存在していても、判定側でその信号が定義されていない、インターフェースが接続されていない、現在の対象や目標状態入口との関係が確認できない場合、今回の判定に必要な構造は成立していない。

S が答える問いは、

> **今回の判定に必要な構造が、定義・接続され、観測可能になっているか。**

である。

### 3.2 D：Dynamics｜動的時系列有効性

D は、すでに取得されている状態を、現在の目標状態入口に対する有効な判定根拠として使用できるかを確認する。

工程状態には、時間や運転サイクルに関係する性質がある。

一度取得した状態であっても、タイムアウト、未更新、通信遅延、システム間の非同期、許可撤回、状態切替などによって、現在の判定には使えなくなることがある。

たとえば、

```text
画像認識結果 = 成立
```

という状態が残っていても、それが前のワークに対する結果であれば、現在の把持入口には使用できない。

D が答える問いは、

> **この状態を、現在の目標状態入口に対する有効な判定根拠として使用できるか。**

である。

### 3.3 B：Boundary｜制御境界

B は、関連状態が現在の目標状態入口に対してあらかじめ定義された制御境界のどこに位置するかを確認する。

制御境界は、数値範囲、閾値、公差、容量、時間窓、待機時間上限、許容継続時間、回数上限、信頼度、偏差などのエンジニアリングパラメータによって定義できる。

たとえば、ある寸法の許容範囲が、

```text
19.90 mm ～ 20.10 mm
```

と定義されている場合、20.06 mm は許容範囲内であり、20.18 mm は現在の制御境界を超えている。

また、不完全確定または境界状態にある場合、B の判定結果は後続の制御調停に渡され、待機、再確認、再試行、縮退、移行禁止、人による確認、安全ロック、異常隔離などの制御経路を選択するための判定根拠となる。

B は制御動作そのものを表すものではなく、現在の状態がどの制御境界にあるかを判定する性質である。

B が答える問いは、

> **この状態は、現在の目標状態入口に対して定義されたどの制御境界にあるか。**

である。

D と B は、異なる性質を扱う。

| **判定** | **主な確認対象** |
|---|---|
| D | 状態を現在の判定根拠として使用できるか |
| B | 有効な状態または工程量が、定義された許容境界内にあるか |

たとえば、画像認識結果が前のワークに対応している場合は D の問題である。

現在ワークの画像認識結果ではあるが、その位置偏差が許容値を超えている場合は B の問題である。

時間情報についても、D と B の両方に関係する場合がある。

状態の更新時刻、データの新鮮度、有効期限、システム間同期などを使って「この状態を現在の判定に使えるか」を確認する場合は D である。

一方、待機時間上限、工程上の許容継続時間、再試行可能な時間範囲など、あらかじめ定義した時間境界に対して確認する場合は B である。

```text
画像認識結果が有効期限を超過
→ D：現在の判定根拠としての時系列有効性を失っている

待機継続時間が許容上限を超過
→ B：現在の待機状態が定義された制御境界を超えている
```

## 4. C / A / E と S / D / B の組合せ

二つの軸を組み合わせることで、CAE-SDB の二軸判定構造として整理できる。

| **状態変数領域** | **S：構造完全性** | **D：動的時系列有効性** | **B：制御境界** |
|---|---|---|---|
| C：条件状態 | C-S | C-D | C-B |
| A：許可状態 | A-S | A-D | A-B |
| E：実行チェーン状態 | E-S | E-D | E-B |

各座標は、ある状態変数領域に対して、どの性質の判定を行うかを表す。

対応する判定規則が定義され、現在の入力に判定根拠があり、実際の判定が完了した場合に、その CAE-SDB Result を生成する。

たとえば、

- **C-D**：条件状態に対する動的時系列有効性の判定
- **A-D**：許可状態に対する動的時系列有効性の判定
- **E-B**：実行チェーン状態に対する制御境界の判定
- **C-S**：条件状態に必要な構造完全性の判定

として整理できる。

同じ状態変数領域に複数の判定性質を適用することもできる。

たとえば、画像認識結果を C にマッピングした場合、

- **C-S**：認識結果インターフェースや対象との対応関係が定義されているか
- **C-D**：認識結果が現在のワークに対応し、有効時間内にあるか
- **C-B**：信頼度や位置偏差が許容範囲内にあるか

をそれぞれ判定できる。

同じ判定性質を、異なる状態変数領域に適用することもできる。

```text
C-D：画像認識結果が期限切れ
A-D：許可が撤回されている
E-D：下流状態が長時間更新されていない
```

CAE-SDB Result は、対応する判定規則が定義され、現在の入力に判定根拠があり、実際の判定処理が完了した場合に生成される。

**時間情報（T）** は、関連状態および判定結果とともに保持する。

T は状態遷移判定における時間情報の記録・関連付けに使用するが、CAE-SDB に追加される第三の分析軸ではない。

---

## 5. CAE-SDB Result の位置

CAE-SDB は、現在の目標状態入口に関係する状態を C / A / E と S / D / B の二軸で整理し、一つまたは複数の構造化判定結果を生成する。

一つの目標状態入口に対する1回の判定では、C-D、A-B、E-D など、複数の CAE-SDB Result が同時に生成されることもある。

これらの判定結果は時間情報 T とともに制御調停へ渡される。

制御調停では、CAE-SDB Result、重要な許可、あらかじめ定義された制御制約などをもとに制御方向を整理し、その後に複数経路制御を構成する。

具体的な制御経路、実行結果、履歴記録は後段の制御処理と PCN の状態遷移判定履歴で扱う。

CAE-SDB Result と具体的な制御動作は、固定的な一対一対応を持たない。

---

## 6. 適用範囲とエンジニアリング上の前提

CAE-SDB の直接的な適用対象は、明確な状態遷移関係を持つエンジニアリングシステムである。

適用時には、まず次の内容を明確にする。

- システムが現在どの状態または段階にあるか
- 次にどの目標状態または段階へ移行しようとしているか
- 目標状態入口がどこにあるか
- どの状態が今回の状態遷移に直接関係するか

そのうえで、各状態が現在の目標状態入口で担う役割に応じて C / A / E 状態マッピングを定義し、実際のエンジニアリング要件に基づいて必要な S / D / B 判定を適用する。

対象設備、制御プラットフォーム、業種、信号名称が異なっていても、この二軸構造自体は共通に利用できる。

一方、具体的な状態マッピング、判定規則、時間条件、許容範囲、制御境界は、対象となるシステムに応じて定義する必要がある。

CAE-SDB は、**目標状態入口を基準として状態遷移判定を構造化するための二軸分析法**である。

   *Statecharts: A Visual Formalism for Complex Systems.*

   DOI: 10.1016/0167-6423(87)90035-9  
   https://www.sciencedirect.com/science/article/pii/0167642387900359

   **参照理由：**  
   複雑システムにおける状態および状態遷移の構造化表現に関する代表的研究であり、状態遷移モデリングの既存理論背景を確認するために参照する。

   *OPC Unified Architecture — Part 4: Services.*

3. **LAMPORT L.**  
   *Time, Clocks, and the Ordering of Events in a Distributed System.*

   **参照理由：**  
   分散システムにおけるイベント順序と時間関係を扱った代表的研究であり、複数システムの状態が同一の目標状態入口判定に関与する場合の時系列問題を理解するために参照する。

これらの資料は、CAE-SDB が扱う問題に既存のエンジニアリング上の基盤があることを確認するためのものである。

CAE-SDB の二軸構造そのものは、TPCA / PCN において目標状態入口前の判定を構造化するための分析法である。

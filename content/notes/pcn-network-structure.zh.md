## 多个 PCN 如何形成状态迁移前置控制网络？

一个 PCN（Pre-Control Node / 前置控制节点）对应一个明确的目标状态入口。

复杂工程系统中通常同时存在多个目标状态入口。这些入口可以连续、并行、分支或循环存在。

单个 PCN 负责一个目标状态入口上的局部前置判定与控制。当前入口的控制路径实际执行后，会形成执行结果，并进一步造成实际工程状态发生变化。

当这些状态变化形成新的工程状态事实，并成为其他目标状态入口的相关输入、实际改变其判定环境时，多个 PCN 之间形成工程依赖关系。

由这些目标状态入口、对应 PCN 以及实际状态迁移依赖关系构成的结构，称为 **PCN Network**。

PCN Network 可以定义为：

> **由多个目标状态入口及其对应 PCN，通过执行结果形成的实际状态更新及其对其他目标状态入口判定环境产生的影响关系连接而成的状态迁移前置控制网络。**

其基本运行关系可以表示为：

```text
PCN-A
    ↓
执行结果
    ↓
实际状态更新
    ↓
形成 / 更新工程状态事实
    ↓
成为其他目标状态入口的相关输入
    ↓
影响该入口的判定环境
    ↓
PCN-B
    ↓
调用 PCN-B 预先定义的 C / A / E 状态映射关系
    ↓
基于当前状态执行 S / D / B 判定
    ↓
形成新的判定与控制结果
```

这里传播的是实际工程状态变化及其形成的状态事实，不是前一个 PCN 的 CAE-SDB 判定标签。

## 1. PCN Network 的节点与基本对象

PCN Network 的节点对象，是具有独立设计、判定、控制和记录价值的目标状态入口及其对应 PCN。

例如：

| 状态迁移 | 对应 PCN |
|---|---|
| 机器人等待 → 抓取阶段 | 抓取前 PCN |
| 放置完成 → 压装阶段 | 压装前 PCN |
| 待检测 → 检测阶段 | 检测前 PCN |
| 任务已生成 → 执行状态 | 任务执行前 PCN |
| AGV 到站 → 站点接收状态 | 站点接收前 PCN |
| 保全解除 → 自动运行恢复 | 自动运行恢复前 PCN |

设备、PLC、机器人控制器、MES、WCS、质量系统以及其他工程系统，可以为各 PCN 提供目标状态入口判定所需要的状态信息。

PCN 的设置单位由目标状态入口决定，而不是由设备数量、控制器数量或系统名称决定。

因此，一台复杂设备内部可以存在多个 PCN；不同设备之间也可以通过实际状态迁移形成 PCN 依赖；跨 MES / WCS、设备、质量、保全和人工操作的状态迁移，同样可以分别形成对应 PCN。

PCN Network 不是设备数量增加以后自动形成的网络。

只有当多个目标状态入口之间存在实际状态迁移影响关系时，才形成相应的 Network 关系。

## 2. 状态事实保持稳定，迁移语义绑定具体目标状态入口

PCN Network 中传播和共享的基础，是实际工程状态事实。

设备、控制器和上位系统应优先提供自身能够确认的客观运行状态，例如：

```text
PROCESS_COMPLETE
RUN_READY
STATUS_VALID
质量放行状态
资源占用状态
区域许可状态
下游接收状态
任务状态
```

这些状态事实本身不预先固定为 C、A 或 E。

C / A / E 表示某一状态相对于当前目标状态入口所承担的状态迁移功能角色。

其基本关系为：

```text
状态事实
    ×
目标状态入口
    ↓
该 PCN 中预先定义的 C / A / E 状态映射关系
```

例如，某个下游设备的接收状态，在上游设备准备进入搬送阶段时，可以作为与 E：Execution Chain 有关的状态，用于判断进入目标阶段后执行链是否能够继续接续。

同一个状态事实进入另一个目标状态入口以后，如果其工程作用发生变化，则可以在另一个 PCN 的预定义状态映射关系中承担不同角色。

如果某一状态表示明确的进入许可，则可以在相应目标状态入口中作为 A：Authority。

因此：

> **状态事实的基础语义保持稳定，C / A / E 角色由具体目标状态入口决定。**

不同 PCN 可以引用同一个状态对象，但分别按照各自预先定义的状态映射关系进行判定。

运行时不是重新推导状态属于 C、A 还是 E，而是根据当前受影响的目标状态入口，调用对应 PCN 已经定义的状态映射关系，并基于当前状态重新执行判定。

## 3. PCN 工程依赖如何形成

PCN Network 中的连接，不根据设备物理连接、通信连接、流程先后关系或系统归属自动建立。

一个直接 PCN 工程依赖关系的基本形成过程为：

```text
PCN-A
    ↓
执行选定控制路径
    ↓
Execution Result
    ↓
形成实际 State Update
    ↓
形成 / 更新工程状态事实
    ↓
该状态事实成为 PCN-B 对应 Target State Entry 的相关输入
    ↓
实际改变 PCN-B 的判定环境
    ↓
形成 PCN-A → PCN-B 的工程依赖关系
```

本文中的 **状态更新（State Update）**，表示已选控制路径执行后，执行结果对实际工程状态形成的更新。

因此：

> **PCN Network 的连接基础是实际状态影响关系。**

以下关系本身不足以直接形成 PCN 工程依赖：

```text
设备物理连接
通信连接
流程上的前后顺序
属于同一设备
属于同一生产线
共享某个资源
统计上经常同时发生
```

只有当实际状态变化进入另一个目标状态入口的判定环境以后，才形成相应的工程依赖。

State Update 的具体内容取决于实际工程对象，可以涉及：

```text
状态推进
许可状态变化
资源状态变化
执行链状态变化
任务状态变化
对象 / 周期状态变化
其他工程状态变化
```

这些变化本身不是不同类型的 Network Edge。

它们首先表现为实际工程状态更新，再根据是否影响其他目标状态入口决定是否形成 PCN Dependency。

例如：

```text
等待抓取
→ 抓取前 PCN
→ 抓取执行
→ 抓取完成
```

`抓取完成` 是前一个执行过程形成的新的工程状态事实。

如果该状态成为“进入放置阶段”的相关输入，则：

```text
抓取完成
→ 放置前 Target State Entry
→ 放置前 PCN
```

后续 PCN 再按照自身目标状态入口进行判定。

同样，区域许可、质量放行、资源占用、Buffer 容量、下游接收、结果回写等状态发生实际变化以后，如果这些更新后的状态事实成为其他目标状态入口的相关输入，也可以形成相应的 PCN Dependency。

替代路径、回流路径或异常处理路径如果对应新的目标状态，应在新的 Target State Entry 下独立进行前置判定。

## 4. 各 PCN 保持局部判定语义，并通过 Trace 形成系统级关联

PCN Network 中，一个重要原则是：

> **上游 PCN 的 CAE-SDB 判定结果不直接作为下游 PCN 的 CAE-SDB 判定结果。**

例如：

```text
PCN-A
A-D
```

表示某个许可状态在 PCN-A 的目标状态入口中形成了 A-D 判定结果。

如果 PCN-A 后续执行形成新的实际状态变化，该状态进入 PCN-B 时，PCN-B 不继承 `A-D` 这一标签。

其基本过程为：

```text
PCN-A
    ↓
CAE-SDB Result
    ↓
控制仲裁
    ↓
多路径控制
    ↓
Execution Result
    ↓
State Update
    ↓
更新后的工程状态事实
    ↓
PCN-B Related State
    ↓
调用 PCN-B 预先定义的 C / A / E 状态映射关系
    ↓
基于当前状态执行 S / D / B 判定
    ↓
形成 PCN-B 自己的 CAE-SDB Result
```

原因在于：

> **C / A / E 是状态相对于具体 Target State Entry 的局部迁移功能角色。**

因此，PCN Network 传播的是实际状态事实及其必要上下文，而不是把一个节点已经形成的局部判定语义直接复制到另一个节点。

单个 PCN 会形成一次目标状态入口对应的 PCN Trace，代表性内容包括：

- 当前状态；
- 目标状态；
- 目标状态入口；
- 相关状态；
- C / A / E 状态映射关系；
- S / D / B 判定；
- CAE-SDB 判定结果；
- 控制仲裁结果；
- 多路径控制结果；
- 执行结果；
- 时间信息；
- Trace ID。

单个 PCN Trace 回答的是：

> **这一目标状态入口为什么形成当前判定和控制结果。**

当多个 PCN 的 Trace 再与实际状态迁移依赖对应起来后，可以进一步回答：

```text
这个状态从哪里产生？
↓
哪个上游执行结果形成了它？
↓
它影响了哪个目标状态入口？
↓
下游 PCN 形成了什么新的判定结果？
↓
这个结果继续形成了什么新的状态变化？
```

PCN Network 的实际结构可以是连续、并行、分支、循环或跨系统结构。

例如连续关系：

```text
PCN-A
→ State Update
→ PCN-B
→ State Update
→ PCN-C
```

也可以形成分支：

```text
             → PCN-B
State Update
             → PCN-C
```

同一个状态更新如果实际影响多个目标状态入口，可以形成相应的多个工程依赖关系。

状态类型也可以形成循环：

```text
A → B → C → A
```

但实际运行中的状态实例仍然沿时间方向继续生成：

```text
A₁ → B₁ → C₁ → A₂
```

A₁ 与 A₂ 属于同一状态类型，但属于不同的运行实例。

返工、回流、恢复、重新投入等工艺路径可以形成状态类型上的循环，运行履历仍然保持时间方向上的连续性。

关于这一点，可参见：

- [TPCA 的状态迁移单向性——为什么真实工程系统不存在状态回退？](/zh/notes/tpca-unidirectional-state-transition/)
- [为什么 PCN Trace 是一种新的工程数据？](/zh/notes/why-pcn-trace-is-engineering-data/)

## 5. PCN Network 的工程形态与边界

PCN Network 可以存在于不同工程层级。

### 自动化执行单元

一个自动化执行单元内部可以存在多个主要目标状态入口：

```text
等待
→ 抓取前 PCN
→ 抓取

抓取完成
→ 放置前 PCN
→ 放置

放置完成
→ 后续阶段 PCN
→ 后续执行
```

这里真正连接前后 PCN 的，是前一个执行阶段结束以后形成的新状态事实，以及这些状态事实对后续 Target State Entry 的影响。

### MES / WCS 与多设备协同

MES / WCS 与多设备协同时，目标状态入口往往分布在不同设备和系统中：

```text
任务生成
→ 任务执行前 PCN
→ 执行

执行结果
→ 任务 / 主体 / 资源状态更新
→ 站点接收前 PCN
→ 交接

交接结果
→ 新状态更新
→ 后续 PCN
```

任务、资源、路径、站点、许可和执行链等状态，只有在发生实际更新并进一步影响其他目标状态入口时，才形成相应的 PCN Network 关系。

### 制造 DX 与跨系统状态迁移

设备、人员、MES、质量系统和保全系统之间也存在大量明确的状态迁移入口：

```text
质量状态更新
→ 下一工序前 PCN
→ 工序进入

保全状态更新
→ 自动运行恢复前 PCN
→ 运行恢复

工单 / 配方状态更新
→ 目标生产状态前 PCN
→ 新生产状态
```

PCN Network 不要求把这些系统统一成一个新的中央状态系统，而是围绕每一个明确 Target State Entry，识别哪些实际状态更新正在影响当前迁移判定。

不同 PCN 可以部署在 PLC / HMI、工业控制器、边缘控制器、WCS、MES 或软件服务等不同位置。

PCN Network 不要求所有 PCN 由一个中央控制器统一执行，也不表示必须建立一个全局状态机。

PCN Network 也不是设备拓扑图、通信网络图或普通生产流程图。

判断是否形成直接工程依赖，需要继续确认：

```text
PCN-A 的执行结果
↓
是否形成实际 State Update
↓
该 State Update 是否形成 / 改变某项工程状态事实
↓
该状态事实是否成为 PCN-B 的相关输入
↓
是否实际改变 PCN-B 的 Target State Entry 判定环境
```

只有这一关系成立时，才需要建立相应的直接 PCN Dependency。

因此，PCN Network 不追求节点和连接数量最大化。

更合理的目标是：

> **以尽可能简洁的关系结构，保留真实系统中对状态迁移判定、控制、传播和追溯具有工程意义的依赖关系。**

具体运行生命周期、节点间通信协议、同步方式、State Update 数据结构、完整接口定义、完整控制仲裁规则以及其他内部实现机制，属于工程实现内容，本公开札记不展开。

## 总结

一个 PCN 对应一个明确的目标状态入口。

多个 PCN 并不是因为处于同一设备、同一生产线、同一系统或共享资源，就自动形成 PCN Network。

PCN Network 的基本运行关系为：

```text
PCN-A
↓
Execution Result
↓
State Update
↓
更新后的工程状态事实
↓
影响其他 Target State Entry
↓
PCN-B
↓
调用自身预先定义的 C / A / E 状态映射关系
↓
重新执行适用的 S / D / B 判定
↓
形成新的判定与控制结果
```

其中：

> **状态事实可以跨 PCN 传播和共享，但 C / A / E 与 CAE-SDB 等局部迁移语义始终绑定具体 Target State Entry。**

上游 PCN 的 CAE-SDB 判定结果保留在自身状态迁移判定履历中，不直接作为下游 PCN 的判定结果。

当一个 PCN 的执行结果形成实际状态更新，并进一步改变另一个目标状态入口的判定环境时，两个 PCN 之间形成工程依赖关系。

多个这样的目标状态入口和工程依赖关系持续连接以后，形成 PCN Network。

因此，PCN Network 可以概括为：

> **以多个目标状态入口及其对应 PCN 为节点，以执行结果形成的实际状态更新对其他目标状态入口产生的真实影响关系为连接基础，用于组织、追溯和分析连续状态迁移关系的工程网络。**

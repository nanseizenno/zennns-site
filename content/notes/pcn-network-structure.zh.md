# 从一个 PCN 到 PCN Network

TPCA / PCN 的核心命题是：

> **一次明确的目标状态入口，应当成为可以被独立设计、判定、控制和记录的工程对象。**

一个 PCN 对应一个明确的目标状态入口。

复杂工程系统中通常不只有一个这样的入口。

当多个 PCN 按实际状态迁移关系连接起来，就可以进一步形成 **PCN Network**。

PCN Network 关注的是：

> **复杂工程系统中，哪些关键目标状态入口需要被独立设计，以及这些入口之间存在怎样的状态迁移关系。**

## 1. PCN Network 的节点不是设备，而是目标状态入口

在传统设备结构图中，节点通常是：

- PLC；
- 机器人；
- 输送机；
- 工位；
- AGV；
- MES / WCS；
- 其他设备或系统。

PCN Network 的节点不是这些设备本身。

它的节点是：

> **需要被独立设计的关键目标状态入口。**

例如：

| 状态迁移 | PCN |
|---|---|
| 机器人等待 → 进入抓取阶段 | 抓取前 PCN |
| 放置完成 → 进入压装阶段 | 压装前 PCN |
| 待检测 → 进入检测阶段 | 检测前 PCN |
| 任务已生成 → 进入执行状态 | 任务执行前 PCN |
| AGV 到站 → 进入站点承接状态 | 站点承接前 PCN |
| 保全解除 → 恢复自动运行 | 自动复归前 PCN |

因此：

- 一台复杂设备内部可以存在多个 PCN；
- 一条产线可以围绕多个关键状态迁移入口设置 PCN；
- MES / WCS 与现场设备之间也可以形成 PCN；
- 人工确认、质量放行或设备复归，只要形成明确目标状态入口，也可以进入 PCN Network。

PCN Network 应理解为：

> **目标状态入口之间的工程关系网络。**

---

## 2. “这里需要增加一个 PCN 点”是什么意思？

工程师讨论复杂自动化、产线、物流路径或 MES / WCS 联动时，经常会发现某个位置：

- 不是单一 Ready 能决定；
- 需要多个系统共同判断；
- 存在关键许可；
- 进入以后还要确认下游能否接续；
- 不能进入时可能存在不同处理路径；
- 问题发生以后还需要能够追溯。

这时可以说：

> **这里需要增加一个 PCN 点。**

这句话真正表达的是：

> **这里存在一个重要目标状态入口，需要被独立设计、判定、控制和记录。**

因此，“PCN 点”是一种工程讨论语言。

它把讨论对象从缺少某个信号，提升到：

> **这一次状态迁移本身是否已经被完整设计。**

---

## 3. 哪些位置值得设置 PCN？

并不是每一个动作都需要独立 PCN。

是否值得设置，可以先看四个问题：

1. 当前状态和目标状态是否明确？
2. 进入目标状态前，是否需要多个相关状态共同判断？
3. 判定结果是否会影响实际状态迁移或控制路径？
4. 这次判断是否值得形成可追溯履历？

如果这些条件成立，这个入口就具有较强的 PCN 设置价值。

例如包装前，如果系统不仅需要确认包装设备 Ready，还需要同时考虑：

- 待包装对象；
- 包装材料；
- 必要许可；
- 下游承接；
- 异常处理能力；

那么“进入包装阶段”就比某一个局部动作更适合作为 PCN 工程对象。

关于更完整的适用边界，可参见：

[TPCA / PCN 适用场景分析](/zh/notes/tpca-pcn-applicable-scenarios/)

## 4. 多个 PCN 如何形成关系

多个 PCN 之间的连接，不是人为画一张网络图以后强行关联。

连接应来自实际状态迁移关系。

例如：

```text
等待抓取
→ 抓取前 PCN
→ 抓取完成

抓取完成
→ 投放前 PCN
→ 投放完成

投放完成
→ 下一阶段 PCN
→ 后续执行
```

这里每一个 PCN 都有自己的目标状态入口。

前一个状态迁移完成以后，系统进入新的状态，随后可能进入下一个 PCN。

因此 PCN Network 的基本关系可以理解为：

> **状态推进形成节点之间的连接。**

除此之外，不同 PCN 之间还可能存在：

- 许可依赖；
- 资源依赖；
- 下游承接关系；
- 状态回写关系；
- 其他与目标状态进入有关的工程约束。

但这些关系最终都应回到：

> **它们是否影响另一个目标状态入口的判定。**

---

## 5. PCN Network 不等于集中式控制

多个 PCN 形成网络以后，并不意味着所有判断都必须集中到一个中央控制器。

每个 PCN 仍然围绕自己的目标状态入口完成前置判定。

可以是：

```text
PCN A
→ 状态迁移
→ PCN B
→ 状态迁移
→ PCN C
```

也可以存在并行、分支或相互依赖的 PCN。

> **PCN Network 描述的是状态迁移工程关系，不规定系统必须采用集中式或分布式控制架构。**

实际运行中，PCN 可以存在于：

- PLC / HMI；
- 边缘控制器；
- WCS；
- MES；
- 软件服务；
- 其他合适的工程位置。

具体 Runtime、接口、同步和部署机制不属于本公开札记范围。

---

## 6. PCN Network 与 PCN Trace

单个 PCN 可以记录一次目标状态入口的判定与执行履历。

多个 PCN 长期运行后，可以进一步形成系统级状态迁移履历。

这使工程师能够观察：

- 哪些目标状态入口频繁无法成立；
- 哪些节点经常受到关键许可阻断；
- 哪些执行链接续问题反复出现；
- 哪些状态迁移长期处于 Waiting；
- 哪些控制路径经常被触发；
- 某个工程修改以后，相关状态迁移表现是否发生变化。

因此，PCN Network 的价值是：

> **系统开始拥有一套以关键状态迁移入口为中心的运行结构和履历视图。**

关于 PCN Trace，可参见：

[为什么 PCN Trace 是一种新的工程数据？](/zh/notes/why-pcn-trace-is-engineering-data/)

## 7. 三类典型网络形态

PCN Network 可以出现在不同工程层级。

### 自动化执行单元

例如：

```text
等待
→ 抓取前 PCN
→ 抓取

抓取完成
→ 投放前 PCN
→ 投放

投放完成
→ 后续阶段 PCN
```

一个自动化单元内部就可能形成多个关键 PCN。

---

### MES / WCS 与多设备协同

例如：

```text
任务生成
→ 任务执行前 PCN
→ 执行

到达站点
→ 站点承接前 PCN
→ 交接

执行完成
→ 结果回写前 PCN
→ 完成
```

PCN 可以跨越任务、资源、路径、站点和下游状态。

---

### 生产 DX 与跨系统状态迁移

例如：

```text
质量确认
→ 下一工序前 PCN
→ 工序进入

保全解除
→ 自动复归前 PCN
→ 恢复运行

异常处理完成
→ 再投入前 PCN
→ 重新执行
```

这些 PCN 可以跨越设备、人员、MES、质量和保全系统。

共同点仍然不是系统类型相同，而是：

> **存在明确、值得独立管理的目标状态入口。**

---

## 工程结论

单个 PCN 对应一个明确的目标状态入口。

多个 PCN 按实际状态迁移关系连接以后，可以进一步形成 PCN Network。

PCN Network 不是设备连接图，也不是中央控制系统。

它表达的是：

> **复杂工程系统中，关键目标状态入口之间的工程关系。**

因此：

> **“这里需要增加一个 PCN 点”**

可以作为一种面向复杂工程系统设计的工程语言。

它真正表达的是：

> **“这里存在一个重要目标状态入口，需要被独立设计、判定、控制和记录。”**

当多个这样的入口被持续识别、设计和连接以后，TPCA 才从单个 PCN 进一步扩展为系统级状态迁移前置控制架构。

## なぜ PCN Trace は新しいエンジニアリングデータなのか？

製造現場には、すでに大量のデータが蓄積されている。

PLC は設備状態やアラームを記録し、MES は生産履歴を保持する。WCS にはタスクや配車・搬送の履歴が残り、設備監視基盤では温度、電流、位置、サイクルタイム、稼働時間などが継続的に収集されている。

これらのデータは通常、設備、タスク、製造指図、アラーム、イベントなどを単位として整理される。

PCN Trace（状態遷移判定履歴）は、そこに別のデータ組織単位を加える。

> **一回の目標状態入口に対して行われた状態遷移判定である。**

一つの明確な目標状態入口に対して、PCN Trace は、その判定に使用した関連状態、C / A / E Mapping、S / D / B Evaluation、CAE-SDB Result、制御優先度調停の結果、複数経路制御、実行結果、時間情報 T を相互に関連付ける。

基本関係は次のとおりである。

```text
関連状態
→ C / A / E Mapping
→ S / D / B Evaluation
→ CAE-SDB Result + T
→ 制御優先度調停
→ 複数経路制御
→ 実行結果
→ PCN Trace
```

CAE-SDB は、同一の目標状態入口に関連しながら、異なる設備やシステムから取得された状態に対して、共通の状態遷移判定上の意味付けを行う。

PCN Trace は、その判定結果を制御選択と実行結果まで結び付け、一回の状態遷移として記録する。

本稿でいう「新しいエンジニアリングデータ」とは、履歴記録そのものが新しいという意味ではない。また、新しいセンサデータ形式を追加するという意味でもない。

重要なのは、

> **一回の目標状態入口における判定、制御、実行の一連の過程を、継続的に記録・比較・統計・分析できるデータ対象として扱うことである。**

## 1. PCN Trace と従来の工程データの違い

製造現場で一般的に扱われるデータには、設備状態、生産・品質実績、アラーム・イベント履歴、MES / WCS の運用履歴などがある。

設備側では、運転・停止、Ready、位置、回転数、温度、電流、圧力、消費電力などが記録される。生産側では、出来高、良品率、サイクルタイム、OEE、不良数、停止時間などが管理される。イベント系では、アラーム発生・復帰、設備起動・停止、工程開始・完了、タスク完了・失敗などが記録される。MES / WCS では、タスク生成・割当て、Waiting、Blocked、Pending、資源占有、搬送経路、ステーション状態などが履歴として残る。

これらのデータから、ある時点で設備やタスクがどのような状態にあったかを確認することはできる。

たとえば、次のような履歴が残っていたとする。

```text
Robot Ready = TRUE
安全許可 = TRUE
画像認識結果 = OK
下流 Ready = FALSE
ロボット動作なし
```

これにより、各システムの局所状態は確認できる。

しかし、さらに、

> **なぜ、その時点で把持段階へ進入しなかったのか。**

を説明しようとすると、これらの状態値だけでは不十分である。

どの目標状態へ進もうとしていたのか、その目標状態入口にどの状態が関係していたのか、それぞれの状態がどの役割を担っていたのか、どのような判定が行われ、なぜ現在の制御経路が選択されたのか、そして実行後に何が起きたのかを再構成する必要がある。

PCN Trace は、これらを一回の目標状態入口という共通の状態遷移コンテキストにまとめる。

したがって、PCN Trace と一般的な運転ログの最も大きな違いは、記録項目の多さではない。

> **データを組織する単位が異なる。**

その違いは、次のように整理できる。

```text
信号 / イベントを中心とした記録
        ↓
一回の状態遷移を中心とした記録
```

従来の設備・生産データでは、設備、イベント、タスク、製造指図などが主要な記録単位となる。一方、PCN Trace では、一回の目標状態入口に対する状態遷移判定そのものが記録単位となる。

そのため PCN Trace は、

> **本判定で何を参照し、どのような判定が成立し、なぜその制御経路を選択し、実際の結果がどうなったか。**

という問いに対して、状態遷移単位で追跡できる構造を持つ。

## 2. PCN Trace が記録する情報

一つの PCN は、一つの明確な目標状態入口に対応する。

基本関係は次のとおりである。

```text
現在状態
    ↓
目標状態入口 / PCN
    ↓
目標状態
```

PCN は目標状態へ進入する前に関連状態を取得し、状態遷移に必要な判定と制御を実行する。

```text
関連状態
→ C / A / E Mapping
→ S / D / B Evaluation
→ CAE-SDB Result + T
→ 制御優先度調停
→ 複数経路制御
→ 実行結果
→ PCN Trace
```

一条の PCN Trace には、現在状態、目標状態、判定に使用した関連状態、CAE-SDB 判定結果、制御選択、実行結果、時間情報などが、一回の目標状態入口を基準として関連付けられる。

たとえば「把持段階への進入」という目標状態入口であれば、その時点で参照した画像認識結果、安全許可、Robot Ready、下流受入状態などと、それらから形成された CAE-SDB 判定結果、制御優先度調停後に選択された経路、実行後の結果を同一の履歴に関連付ける。

PCN Trace において重要なのは、

```text
入力状態
→ 判定結果
→ 制御選択
→ 実行結果
```

という因果関係そのものを、一回の状態遷移として保持することである。

### 2.1 CAE-SDB が PCN Trace に与える判定上の意味

PCN Trace は、PLC、ロボット、MES / WCS、安全システム、下流設備などの状態を単純に再収集したログではない。

同一の目標状態入口に関係する状態は、まず C / A / E Mapping によって、本状態遷移における機能役割へ整理される。

```text
C = Condition
目標状態へ進入するための条件

A = Authority
目標状態への進入許可

E = Execution Chain
目標状態へ進入した後の実行チェーン継続性
```

その後、各状態に対して、あらかじめ定義された S / D / B の判定を行う。

```text
S = Structure
判定に必要な構造が成立しているか

D = Dynamics
現在の状態を判定根拠として使用できるか

B = Boundary
状態が定義済みの制御境界内にあるか
```

この処理により、PCN Trace では単なる状態値ではなく、

```text
どの目標状態入口に対して
↓
どの状態が判定に参加し
↓
どの機能役割を担い
↓
どの判定が行われ
↓
どの CAE-SDB Result が形成され
↓
どの制御経路が選択され
↓
最終的にどの実行結果となったか
```

を一つの状態遷移履歴として関連付けられる。

CAE-SDB は、異なる情報源から取得された状態に対して、同一の目標状態入口を基準とした共通の判定上の意味付けを与える。

PCN Trace は、その意味付けを制御選択と実行結果まで保持する。

この構造がなければ、Trace は大量の状態値、イベント、アラームを再度まとめただけの履歴へ戻ってしまう。

したがって、

> **CAE-SDB は、PCN Trace が状態遷移判定履歴として成立するための判定意味の基盤となる。**

本稿では、PCN Trace の基本構成と工程上の役割までを公開対象とする。詳細なフィールド構成、保存方式、索引、バージョン管理、再生機構などは、具体的な製品実装の範囲に含まれる。

## 3. PCN Trace を蓄積すると何が見えるのか

PCN Trace を継続的に蓄積すると、目標状態入口ごとに判定結果、制御結果、実行結果を統計・比較できるようになる。

たとえば、ある入口で C-D が繰り返し発生している場合、条件状態に関係するデータ更新、同期、時間有効性に問題が集中している可能性を確認できる。A-D が多い場合には、許可の更新、撤回、状態切替の時系列を確認できる。E-D が継続して発生する場合には、下流受入、資源状態、システム間同期など、実行チェーン側の問題を調べることができる。

重要なのは、単一信号の異常件数を数えることではない。

同種の状態遷移において、どの判定結果が繰り返し発生し、どの制御経路が選択され、その結果として何が起きたのかを比較することである。

改善後も同じ PCN の Trace を継続して記録すれば、改善前後で判定結果、制御経路、実行結果がどのように変化したかを比較できる。

```text
PCN 運転
    ↓
PCN Trace
    ↓
統計・比較
    ↓
状態遷移上の改善対象を特定
    ↓
工程変更
    ↓
再運転
    ↓
新しい PCN Trace
    ↓
改善前後の比較
```

このため PCN Trace は、事後のトラブル追跡だけでなく、継続的な工程改善の比較基盤としても利用できる。

Trace の蓄積量や対象問題に応じて、ルール判定、統計、傾向分析、大規模言語モデルなど、複数の分析手法を組み合わせることもできる。

ただし、工程変更そのものは、設備、工程、安全、生産、保全などの要求を踏まえて工程技術者が確認する。

基本的な改善ループは次のようになる。

```text
PCN Trace
    ↓
分析
    ↓
改善候補
    ↓
工程技術者による確認
    ↓
工程変更
    ↓
再運転
    ↓
新しい PCN Trace
    ↓
改善前後の比較
```

PCN Trace は、まず「何を状態遷移として観測・記録するか」を明確にする。その後に、実際の課題に応じた分析方法を選択する。

## 4. PLC / HMI、MES / WCS、製造DX における PCN Trace の利用

### 4.1 PLC / HMI

PLC / HMI は、従来から信号状態、Ready、Interlock、Alarm、シーケンス状態、設備状態などを表示・記録している。

PCN Trace を加えることで、それらの情報を、現在状態、目標状態、目標状態入口、時間情報 T、CAE-SDB 判定結果、制御優先度調停結果、複数経路制御、実行結果、Trace ID とともに、一回の状態遷移として表示できる。

たとえば HMI 上では、次のような情報を同一の状態遷移として示すことができる。

```text
目標状態：把持段階

CAE-SDB Result：C-D

判定内容：画像認識結果が有効時間を超過

制御優先度調停結果：再認識を優先

複数経路制御：再認識
```

これにより、現場では「現在どの目標状態へ進めないのか」「どの判定位置で問題が生じているのか」「なぜ現在の制御経路が選択されているのか」を一つの画面や履歴で確認できる。

### 4.2 MES / WCS

MES / WCS は、タスク、車両、ステーション、搬送経路、共有資源、Waiting、Blocked、Pending など、多くの運用情報をすでに保持している。

PCN Trace を用いると、これらの状態を具体的な目標状態入口へ関連付け、一回の状態遷移として記録できる。

たとえば協調停滞を分析する場合、単に「タスクが Waiting だった」ことだけを見るのではなく、その Waiting がどの目標状態入口で発生したのか、どの条件や許可が判定に関与したのか、実行チェーンのどの状態が進入を妨げていたのか、どの CAE-SDB Result が形成され、どの制御経路が選択され、最終的な実行結果がどうなったのかまで確認できる。

このように、MES / WCS が持つタスク・資源データと、具体的な状態遷移判定履歴を対応付けることができる。

### 4.3 製造DX

製造DX では、設備データ、生産データ、イベントデータを用いた可視化、分析、改善が広く行われている。

しかし、データを集める前に、

> **どの工程現象を観測し、その関係をどのようなデータ構造として残すか。**

を定義する必要がある。

状態遷移を対象とする場合、まず目標状態入口によって観測対象を明確にする。

次に CAE-SDB が、その入口に関連する異種状態へ共通の状態遷移判定上の意味付けを行う。

PCN Trace は、その判定、制御、実行結果を継続的な状態遷移履歴として記録する。

```text
目標状態入口
↓
関連状態
↓
CAE-SDB
↓
制御優先度調停 / 複数経路制御
↓
実行結果
↓
PCN Trace
↓
分析・改善
```

PCN Trace が追加するのは、「状態遷移判定」という新たな分析単位である。

設備・生産データとの違いは、次のように整理できる。

| 項目 | 設備・生産データ | PCN Trace |
|---|---|---|
| 主な記録対象 | 設備、工程、タスク、生産結果 | 一回の目標状態入口に対する状態遷移判定 |
| 主な確認内容 | 何が発生したか | 何を根拠に判定し、どの制御を選択し、結果がどうなったか |
| データ組織単位 | 設備、時刻、タスク、製造指図、イベント | PCN、目標状態入口、現在状態、目標状態、T |
| 主な分析対象 | 稼働、性能、品質、異常、出来高 | C / A / E、S / D / B、CAE-SDB Result、制御優先度調停、複数経路制御、実行結果 |
| 主な改善対象 | 設備、工程、保全、生産プロセス | 状態遷移条件、許可、実行チェーン、制御境界、制御経路 |
| 改善確認 | OEE、サイクルタイム、出来高、アラーム、品質 | 改善後 Trace における判定、制御、実行結果の変化 |

このように、製造DX におけるデータ対象を、設備や生産実績だけでなく、状態遷移そのものへ拡張できる。

### 4.4 PCN Network との組合せ

単一の PCN Trace は、一回の目標状態入口に対する状態遷移判定履歴を記録する。

複数の PCN に蓄積された Trace を関連付けることで、複数入口にまたがる状態遷移関係や依存関係を分析することもできる。

## まとめ

製造現場では、設備データ、生産データ、タスクデータ、アラームデータ、イベントデータがすでに継続的に記録されている。

PCN Trace の特徴は、それらの情報を一回の明確な目標状態入口へ戻し、次の関係として組織化する点にある。

```text
関連状態
→ C / A / E Mapping
→ S / D / B Evaluation
→ CAE-SDB Result + T
→ 制御優先度調停
→ 複数経路制御
→ 実行結果
→ PCN Trace
```

PCN Trace における本質的な変化は、分散した設備状態、イベント、アラームを単純に追加保存することではない。

**データの組織単位を、一回の明確な目標状態入口に対する状態遷移判定へ変更することである。**

CAE-SDB は、その目標状態入口に関連する異種状態へ共通の状態遷移判定上の意味付けを行う。

したがって、本稿でいう「新しいエンジニアリングデータ」とは、

> **一回の目標状態入口に対応する状態遷移判定を、継続的に記録・比較・統計・分析可能なデータ対象として扱うことである。**

PCN Trace により、本判定でどの状態を利用したか、それぞれがどの機能役割を担ったか、どの CAE-SDB 判定結果が形成されたか、どのような制御優先度調停を経て、どの制御経路が選択され、最終的にどの実行結果となったかを一連の履歴として確認できる。

長期的に蓄積すれば、目標状態入口ごとの反復問題、判定結果の分布、制御経路の選択傾向、実行結果、工程変更前後の差異を比較できる。

必要に応じて、ルール、統計、傾向分析、大規模言語モデルなどの分析手法を適用し、新たな PCN Trace によって改善前後の変化を確認することもできる。

> **PCN Trace の価値は、記録項目を増やすことではなく、判定根拠、判定結果、制御選択、実行結果を同一の状態遷移コンテキストに保持することにある。**

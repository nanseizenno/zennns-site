## なぜ PCN は TPCA の最小エンジニアリングノードなのか？

TPCA は、明確な **Target State Entry（目標状態入口）** を基準として、状態遷移前の判定と制御を構造化するアーキテクチャである。

実際のエンジニアリングシステムでは、「次の状態へ移行する」という処理自体は、PLC のシーケンス、状態マシン、MES / WCS の業務フロー、ロボットプログラム、設備間のハンドシェイクなど、既存の仕組みですでに実装されていることが多い。

一方、ある状態遷移について、

- どの条件を確認するのか
- どの許可が必要なのか
- 移行後の実行チェーンが継続できるか
- どの制御経路を選択するのか
- 実行後に実際に何が起きたのか

といった関係は、複数の設備、プログラム、制御層、上位システムに分散している。

そこで最初に明確にする必要があるのは、

> **システムが現在どの状態から、どの目標状態へ移行しようとしており、その前制御判定をどこで行うか。**

という点である。

TPCA では、その位置を **Target State Entry（目標状態入口）** とし、独立して設計・判定・制御・記録できる状態遷移上のエンジニアリング対象として扱う。

PCN（Pre-Control Node / 前制御ノード）は、具体的な Target State Entry に対して配置するエンジニアリング実装単位であり、その入口の直前で前制御を担当する。

一つの PCN は、一つの明確な Target State Entry に対応し、今回の状態遷移に関係する状態、構造化判定、制御選択、実行結果、状態遷移判定履歴を同じエンジニアリング文脈の中で扱う。

実行時には、あらかじめ定義した関係に基づいて関連状態を取得し、

```text
C / A / E Mapping
→ S / D / B Evaluation
→ CAE-SDB Result
→ 制御調停
→ 複数経路制御
→ Execution Result
→ PCN Trace
```

までを一つの状態遷移単位としてつなぐ。

ここで、

```text
C = Condition         条件状態
A = Authority         許可状態
E = Execution Chain   実行チェーン状態

S = Structure         構造完全性
D = Dynamics          動的時系列有効性
B = Boundary          制御境界
```

を表す。

PCN を「最小エンジニアリングノード」と呼ぶときの「最小」は、ハードウェアの大きさ、ソフトウェア規模、信号数を意味しない。

> **一つの明確な Target State Entry を基準として、状態入力、構造化判定、制御選択、実行結果、状態遷移判定履歴までを独立して保持できる最小のエンジニアリング責任単位**

という意味である。

## 1. 一つの PCN は、一つの明確な Target State Entry に対応する

一つの状態遷移を独立したエンジニアリング対象として扱うには、まず Current State、Target State、そして両者の間にある Target State Entry を明確にする必要がある。

同じ設備やシステムであっても、連続する複数の状態や実行段階を持つ。

それぞれの目標状態では、必要な条件、許可、実行チェーン、制御経路が異なるため、今回どの目標状態へ移行しようとしているのかを先に特定しなければ、判定対象は定まらない。

たとえば、ロボットが待機状態から把持段階へ移行しようとしている場合、今回の対象は「把持段階への移行入口」である。

把持動作を開始する前には、たとえば次のような状態を確認する。

- ワーク状態
- 画像認識結果
- ロボット状態
- 安全許可
- 上位システム許可
- 下流側の受入状態

これらの状態を、今回の把持入口という一つの状態遷移文脈に関連付ける。

Target State Entry は、そのためのエンジニアリング上の基準点となる。

一つの Target State Entry を明確にすると、次の内容を定義できる。

- 現在どの状態または段階から移行するか
- 次にどの目標状態または段階へ移行するか
- どの状態が今回の状態遷移に直接関係するか
- どの条件が成立する必要があるか
- どの許可が成立する必要があるか
- 移行後にどの実行チェーンが継続できる必要があるか
- 現在の入口から選択可能な制御経路は何か
- 今回の判定、制御、実行結果をどの履歴単位で記録するか

PCN は、この入口の直前に配置し、対応する前制御判定と制御を担当する。

複雑な設備やシステムでは、通常、複数の Target State Entry が存在する。

そのため、同一設備内、設備間、複数システム間のいずれでも、実際の状態遷移構造に応じて複数の PCN を配置できる。

PCN の単位は、設備台数や PLC 台数では決まらない。

**独立して判定・制御・記録すべき状態遷移入口がどこにあるか**によって決まる。

Target State Entry は管理対象となる状態遷移入口であり、PCN はその直前で前制御責任を担うエンジニアリングノードである。

両者は一対一に対応するが、同じエンジニアリング対象ではない。

## 2. 一つの PCN が保持するエンジニアリング関係

Current State と Target State は、今回の状態遷移の文脈を定める。

PCN は、その間にある明確な Target State Entry を基準として、今回の状態遷移に直接関係する情報と処理を、一つのエンジニアリング責任範囲にまとめる。

| PCN に関係する対象 | 役割 |
|---|---|
| Target State Entry | 今回の PCN が担当する状態遷移入口を明確にする |
| Related States | 今回の状態遷移に直接関係する多源状態を取得する |
| CAE-SDB | 現在の Target State Entry に対する構造化判定結果を生成する |
| 制御調停 / 複数経路制御 | 判定結果と制御制約に基づいて制御経路を決定する |
| Execution Result | 制御経路を実行した後に実際に生じた結果を取得する |
| PCN Trace | 今回の判定、制御、実行結果を同一の状態遷移履歴として記録する |

これらを同じ Target State Entry に結び付けることで、初めて一つの状態遷移を一つのエンジニアリングプロセスとして説明できる。

同じ状態信号、同じ許可状態、同じ設備 Ready であっても、異なる Target State Entry では役割が変わる場合がある。

したがって、その状態が今回の状態遷移でどのような意味を持つかは、状態名だけでは決まらず、対象となる Target State Entry との関係で決まる。

PCN ごとに入力数、判定規則、制御経路、実装規模が異なっていても問題はない。

共通して必要なのは、

> **一つの Target State Entry に対して、状態入力、判定、制御、実行結果、履歴の関係を一貫して保持すること**

である。

## 3. 「最小エンジニアリングノード」の意味

PCN の「最小」は、状態遷移に対するエンジニアリング責任の境界を表す。

一つの現場信号は、ある局所状態を表す。

Ready は、その設備やシステムであらかじめ定義された準備状態を表す。

Interlock や Permissive は、状態遷移に関係する一部の制約や許可を表す。

一つの CAE-SDB Result は、一つの構造化判定結果を表す。

一つの制御出力は、現在選択された制御経路または制御処理を表す。

いずれも、一つの状態遷移に必要なエンジニアリング情報の一部である。

しかし、それぞれ単独では、

> **今回の Target State Entry について、何を根拠として判定し、どの判定結果が生成され、どの制御を選択し、実際に何が起きたのか。**

という一連の関係を説明できない。

この問いに答えるには、

```text
関連状態
→ 構造化判定
→ 制御選択
→ 実行結果
→ 状態遷移判定履歴
```

を、同じ Target State Entry に関連付けて保持する必要がある。

PCN が担うのは、このエンジニアリング責任である。

複数の Target State Entry を一つの責任単位にまとめ過ぎると、どの判定や制御がどの状態遷移に対するものかが曖昧になる。

反対に、単一信号、単一判定、単一制御出力まで細分化すると、一つの状態遷移全体を独立して保持できなくなる。

したがって、PCN の「最小」は次のように定義できる。

> **一つの明確な Target State Entry を基準として、状態入力、構造化判定、制御選択、実行結果、状態遷移判定履歴の関係を保持できる最小のエンジニアリング責任ノード。**

ここでいう「最小」は、入力点数、判定規則数、プログラム容量などの固定値ではない。

一つ下の単位まで分解すると、状態遷移全体のエンジニアリング文脈を独立して保持できなくなる。

一つ上の単位へまとめると、複数の異なる状態遷移責任が同じノードに混在する。

この境界が、PCN の最小性を決める。

## 4. 分散した状態を同じ Target State Entry に関連付ける

複雑な自動化システムでは、一つの状態遷移に必要な情報が、複数の設備やシステムに分散している。

たとえば、ロボットが把持段階へ移行する場合、関連状態は次のような場所に存在し得る。

- 画像認識システム
- ロボットコントローラ
- PLC
- 安全システム
- 搬送設備
- 下流設備
- 上位システム

これらの状態を PCN のために一か所へ集約して保存する必要はない。

また、既存システムのデータ管理方式を変更する必要もない。

設計段階で必要なのは、

- どの状態が現在の Target State Entry に直接関係するか
- 各状態が今回の状態遷移でどのようなエンジニアリング上の役割を担うか

を定義することである。

PCN は実行時に、その定義に基づいて必要な状態を取得し、C / A / E Mapping と S / D / B Evaluation を行い、CAE-SDB Result を生成する。

ここでは、次の二つを分けて考える。

```text
状態がどこに存在するか

と

今回の状態遷移で、
なぜその状態を使うのか
```

たとえば、Robot Ready はロボット制御側で従来どおり管理してよい。

PCN が確認するのは、その Ready が現在の Target State Entry に関係する状態か、そして今回の状態遷移でどのような役割を担うかである。

そのため PCN は、すべての現場情報を集約する中央ノードではない。

現在の Target State Entry に直接関係する状態だけを取得し、その状態遷移に必要な判定と制御の責任範囲を明確にする。

- [自動化実行ユニット前判定事例](/jp/cases/automation-execution-unit-pre-control/)

## 5. PCN はエンジニアリング責任ノードであり、実装形式を限定しない

PCN は、特定の PLC ファンクションブロック、コントローラ、ソフトウェアモジュール、製品形式を指すものではない。

PCN が定義するのは、状態遷移前制御における**エンジニアリング責任の境界**である。

具体的な実装方式は、Target State Entry が存在するシステム階層、既存の制御アーキテクチャ、現場要件によって異なる。

PCN は、例えば次の環境に実装できる。

- PLC
- 産業用コントローラ
- エッジシステム
- MES / WCS のソフトウェア機能
- その他の制御・情報システム

また、ロボット、安全システム、画像認識システム、下流設備、上位システムなど、既存の制御対象と必要な状態・制御関係を接続することもできる。

実装形式が異なっていても、一つの PCN が担う基本責任は変わらない。

- 一つの明確な Target State Entry に対応する
- 今回の状態遷移に必要な関連状態を取得する
- 前制御判定と制御を実行する
- Execution Result を取得する
- 対応する PCN Trace を記録する

ある実装が PCN に該当するかを判断するうえで重要なのは、その実装が何で作られているかではない。

> **一つの明確な Target State Entry に対して、状態遷移前制御のエンジニアリング責任を一貫して担っているか。**

が判断基準となる。

## まとめ

複雑なエンジニアリングシステムにおける一つの状態遷移では、複数の設備やシステムに分散した条件、許可、実行チェーン状態、制御関係を扱う必要がある。

Target State Entry は、それらを一つの具体的な状態遷移へ結び付ける基準点となり、その入口を独立して設計・判定・制御・記録できるエンジニアリング対象として扱えるようにする。

PCN（Pre-Control Node / 前制御ノード）は、TPCA がこの Target State Entry に対して設定するエンジニアリング実装単位である。

一つの PCN は、一つの明確な Target State Entry に対応し、同じ責任範囲の中で、

- 関連状態
- CAE-SDB 判定
- 制御調停
- 複数経路制御
- 実行結果
- PCN Trace

を一貫して扱う。

したがって、PCN における「最小エンジニアリングノード」とは、

> **一つの明確な Target State Entry を基準として、状態入力、構造化判定、制御選択、実行結果、状態遷移判定履歴の関係を保持できる最小のエンジニアリング責任ノード**

を意味する。

PCN をこの単位で設計することで、TPCA の状態遷移前制御を、個別設備、自動化実行ユニット、MES / WCS、その他のシステム階層に存在する具体的な Target State Entry へ展開できる。

## 为什么状态迁移条件必须显式化？

复杂自动化现场经常出现以下现象：

- 设备没有报警，但系统无法进入下一阶段；
- PLC 中大部分条件已经成立，执行机构仍未动作；
- MES 中存在任务，WCS 中也有记录，但现场持续 Waiting；
- 上游已经完成，下游暂时无法承接；
- 新增工位、接口或控制对象以后，原本稳定的单元开始反复等待。

这些现象具有一个共同特征：

> **各局部系统均具有状态，但一次明确的目标状态入口为什么没有成立，相关判断关系并未被完整表达。**

问题通常不在于现场缺少信号。

PLC 有状态位，机器人有 Ready，视觉系统有 OK / NG，安全系统有许可，MES 有任务，WCS 有调度记录，HMI 也有报警和状态画面。

更需要明确的是：

> **系统从当前状态进入目标状态之前，究竟依赖哪些状态，这些状态在本次目标状态入口中形成什么工程关系，以及本次判定发生在什么时间位置。**

如果这些判断长期分散在程序、接口、画面和工程师经验中，状态迁移就容易依赖少数熟悉系统的人进行解释和维护。

这正是状态迁移条件需要显式化的原因。

## 1. 隐含判断越多，系统越依赖少数熟悉人员

简单设备的状态迁移通常比较直接。

例如：

```text
启动请求
+ 安全条件成立
+ 设备 Ready
→ 动作开始
```

复杂自动化系统则不同。

一个自动化单元内部可能包含：

- 待机；
- 原点复归；
- 上料；
- 定位；
- 加工；
- 检测；
- 排出；
- 异常处理；
- 换型；
- 重新投入。

一条生产线还可能同时连接：

- PLC；
- 机器人；
- 视觉系统；
- 安全系统；
- HMI；
- MES；
- WCS；
- AGV / AMR；
- 检测设备；
- 包装设备；
- 码垛设备；
- 仓储交接；
- 人工确认。

在这种系统中，“能否进入下一阶段”往往同时依赖多个状态。

例如：

- 工件是否存在；
- 位置和姿态是否满足要求；
- 识别结果是否仍然有效；
- 安全许可是否成立；
- 上位系统是否放行；
- 资源锁是否释放；
- 下游是否能够承接；
- 回流或异常路径是否可用；
- 结果是否能够回写；
- 必要人工确认是否完成。

即使这些关系没有被单独整理出来，系统仍然可以依赖 PLC、Interlock、程序分支、接口约定和人工经验运行。

但随着设备改造、换型、扩线、系统升级和人员更替，隐含判断会逐渐转化为维护负担。

现场开始反复出现：

```text
Ready，但不动作
Waiting，但不知道在等什么
任务存在，但没有进入执行
没有报警，但流程停在当前阶段
```

这时，真正困难的往往不是找到某一个信号，而是重新还原：

> **当初为什么这样设计这一次状态迁移。**

## 2. 显式化的对象不是更多信号，而是状态迁移关系

状态迁移条件显式化，不等于继续增加传感器、状态位或数据采集量。

复杂现场通常已经具有大量状态。

例如：

```text
Robot Ready
Vision OK
Safety Permission
MES Task
WCS Status
Downstream Ready
```

这些信息都具有明确作用。

但：

```text
Robot Ready = TRUE
```

与：

```text
机器人当前是否可以进入抓取阶段
```

并不是同一个工程问题。

后一个问题还可能需要同时判断：

- 工件是否存在；
- 视觉结果是否有效；
- 位置是否满足抓取要求；
- 安全许可是否成立；
- 路径是否可达；
- 夹爪是否可用；
- 正常投放位是否能够承接；
- 回流路径是否可用；
- 异常分流路径是否可用；
- 结果回写链路是否能够继续。

因此，需要显式化的不是某个孤立信号，而是：

> **围绕一个明确的目标状态入口，本次状态迁移真正依赖哪些状态，以及这些状态之间形成什么判定关系。**

PCN 将这些分散状态组织到同一个目标状态入口：

```text
当前状态
→ 目标状态
→ PCN
→ C / A / E 状态映射
→ S / D / B 判定
→ CAE-SDB Result + T
→ Arbitration
→ Multipath Control
→ PCN Trace
```

其中，T 表示与本次状态和判定结果一起保留的时间信息，用于标识本次状态与判定所处的时间位置，并支持动态时序有效性判断和 PCN Trace。

这样，原本“存在于程序中的判断”才进一步成为“工程上可见的状态迁移结构”。

## 3. 工程讨论会从“补信号”转向“设计目标状态入口”

状态迁移条件没有被显式化时，现场改善经常采用局部补充方式：

> 这里增加一个传感器。  
> 这里增加一个 Interlock。  
> 这里增加一个报警。  
> HMI 再显示一个状态。  
> 这里等待 MES 放行。  
> 这里增加人工确认。  
> 程序中再增加一个判断。

这些措施本身并没有问题。

问题在于，如果每次修改只针对局部信号或局部功能，系统会逐步积累大量分散判断。

当目标状态入口被显式化以后，讨论对象会发生变化：

> 当前状态是什么？

> 目标状态是什么？

> 哪些状态与本次目标状态入口直接相关？

> 哪些状态属于 C？

> 哪些 A 构成必要许可？

> 进入以后 E 是否能够继续接续？

> 需要进行哪些 S / D / B 判定？

> 本次状态和判定对应的时间信息是什么？

> 多个判定结果同时存在时，如何进行控制仲裁？

> 最终应进入哪个目标状态或目标执行路径？

> 本次判定是否需要形成 PCN Trace？

工程讨论因此由：

> “还缺哪个信号？”

转变为：

> **“这个目标状态入口应该如何设计？”**

这是状态迁移条件显式化最直接的工程意义之一。

## 4. 工程经验可以从个人检查逻辑转化为可维护结构

有经验的工程师处理现场问题时，通常已经在脑中形成较稳定的检查顺序。

例如，看到机器人不抓取时，往往会依次检查：

- 工件；
- 视觉；
- 路径；
- 安全；
- 夹爪；
- 下游；
- 回流；
- 回写。

看到 AGV 无法进入站点时，会检查：

- 任务；
- 路径；
- 资源锁；
- 站点状态；
- 区域许可；
- 下游承接。

看到设备无法重新投入自动运行时，会检查：

- 异常是否解除；
- 原点状态；
- 安全许可；
- 模式状态；
- 保全解除；
- 后续执行链。

这些经验具有较高工程价值。

但如果相关判断仅存在于个人经验中，就难以：

- 交接给新工程师；
- 在不同项目之间复用；
- 与系统集成商形成统一接口语言；
- 在 HMI、MES 或其他系统中统一表达；
- 形成长期判定数据；
- 比较改善前后的变化。

PCN 的作用之一，就是将这类隐含检查结构落到明确的目标状态入口上。

于是，工程经验可以逐步转化为：

```text
PCN
+ 目标状态
+ 相关状态
+ C / A / E 状态映射
+ S / D / B 判定
+ CAE-SDB Result + T
+ 控制路径
+ PCN Trace
```

工程经验由个人知识逐步转化为可以维护、交接和复用的工程资产。

## 5. 不显式化，并不会减少系统复杂度

复杂系统中的状态迁移关系本来就客观存在。

随着设备和系统增加，还会继续增加：

- 状态；
- 接口；
- 许可；
- 下游承接；
- 回流路径；
- 回退路径；
- 异常路径；
- 人工确认；
- 系统间同步；
- 数据回写。

如果不对这些关系进行显式组织，复杂度并不会消失。

它只会转移到其他位置：

- PLC 梯形图深处；
- 机器人程序分支；
- HMI 模糊提示；
- MES / WCS 接口逻辑；
- 调试工程师经验；
- 设备厂家之间的接口约定；
- 跨部门排查过程；
- 故障发生后的人工日志拼接。

“回流”“回退”“复归”“重新投入”等现场工程名称可以继续保留。

但从 TPCA 的状态迁移视角看，这些路径实际都表示：

```text
Current State → New Target State / Target Path
```

即使新的目标状态与历史某一状态具有相同或相似的工程内容，由于其时间位置和迁移历史不同，仍然属于新的状态实例。

因此，状态迁移条件显式化并不是额外制造复杂度。

它的作用是：

> **将已经存在的复杂关系放到能够被明确观察、设计和管理的位置。**

只有在这些关系被显式表达以后，才可能进一步进行：

- 分层；
- 审核；
- 标准化；
- 模板化；
- 记录；
- 改善。

## 6. 目标状态入口可以成为独立工程对象

状态迁移条件被显式化以后，“进入下一状态”就不再只是程序中的一段隐含逻辑。

它可以被独立设计。

例如：

```text
当前状态： 识别完成 / 等待抓取

目标状态： 进入抓取阶段
```

围绕这一目标状态入口，工程师可以继续定义：

- PCN 设置位置；
- 本次迁移需要读取哪些状态；
- 哪些状态映射到 C；
- 哪些状态映射到 A；
- 哪些状态映射到 E；
- 需要进行哪些 S / D / B 判定；
- 本次状态和判定对应的时间信息 T；
- 可以形成哪些目标状态或目标执行路径；
- 需要记录哪些 PCN Trace 信息。

这样，一次目标状态进入开始具备明确的工程属性。

### 可设计

在设计阶段明确目标状态入口所需要的状态和关系，而不是在调试阶段持续补充条件。

### 可检查

能够检查关键许可、下游承接、回流或回退路径、状态有效性等关系是否遗漏。

### 可记录

每次判定可以形成包含时间信息 T 的统一 PCN Trace。

### 可复用

同类设备、同类工位和相似目标状态入口可以复用已有结构或模板。

### 可改善

可以比较哪些目标状态入口长期无法成立、哪些许可频繁阻断、哪些执行链经常无法接续，以及工程修改前后的 Trace 如何变化。

状态迁移因此从：

> 隐含控制逻辑

逐步转化为：

> **可管理的工程结构。**

---

## 7. 显式化为跨系统状态建立共同工程上下文

复杂制造系统中的状态往往分布在不同层级。

例如，一次物料交接可能同时涉及：

```text
MES
→ WCS
→ AGV
→ PLC
→ 站点设备
→ 下游工位
```

每个系统都可以维护自己的状态。

但如果没有明确的目标状态入口，这些状态很难自然形成同一个判定对象。

PCN 提供了一个共同的工程位置：

> **所有与本次目标状态进入有关的状态，在同一个 PCN 中获得共同的工程上下文。**

例如：

- MES 的任务状态可以作为本次迁移的条件或许可输入；
- WCS 的资源状态可以参与许可或执行链判定；
- AGV 状态可以参与执行链接续判断；
- PLC 和安全系统可以提供现场状态与许可；
- 下游工位可以提供承接状态；
- 人工确认可以作为系统化许可输入；
- 时间信息 T 可以关联各状态的发生顺序和当前有效性；
- 最终判定可以形成统一的 PCN Trace。

这也是状态迁移条件显式化对于生产 DX 的工程意义之一。

生产 DX 不只是将更多设备数据接入平台。

更重要的是：

> **使原本分散在人员、设备、系统和流程之间的状态迁移条件获得共同的工程语义、时间位置和判定上下文。**

## 小结

现代自动化系统通常并不缺少状态。

更难处理的是：

> **决定一次目标状态进入能否成立的判断关系，长期分散在不同程序、设备、系统和工程师经验中。**

这些关系长期保持隐含状态时，系统会越来越依赖熟悉现场的人员，项目之间也难以形成稳定复用。

PCN 将一个明确的目标状态入口作为工程对象，并把与本次状态迁移有关的状态组织为：

```text
当前状态
→ 目标状态
→ PCN
→ C / A / E 状态映射
→ S / D / B 判定
→ CAE-SDB Result + T
→ Arbitration
→ Multipath Control
→ PCN Trace
```

其中，T 与本次状态和判定结果一起保留，用于标识实际发生的时间位置。

因此，即使后续状态再次出现与历史状态相同的工程内容，也仍然属于新的状态实例。

由此，状态迁移条件可以进一步实现：

- 可设计；
- 可检查；
- 可记录；
- 可复用；
- 可改善。

因此，状态迁移条件显式化的目的，不是增加更多状态，也不是增加更多控制逻辑。

而是：

> **将已经存在但长期隐含的状态迁移判断，转化为可以被工程化设计、管理和持续改善的对象。**

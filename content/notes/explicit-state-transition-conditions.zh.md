## 为什么状态迁移条件必须显式化？

自动化现场经常出现一类问题：

- 设备没有报警，但系统不进入下一步；
- PLC 里大部分条件已经成立，执行机构仍然不动作；
- MES 有任务，WCS 有记录，现场却一直 Waiting；
- 上游已经完成，下游暂时不能承接；
- 新增一个工位或接口以后，原本稳定的单元开始反复等待。

这些现象有一个共同特点：

> 每个局部系统都有状态，但一次具体状态迁移为什么没有成立，并没有被完整表达出来。

问题通常不是现场没有信号。

PLC 有状态位，机器人有 Ready，视觉有 OK / NG，安全系统有许可，MES 有任务，WCS 有调度记录，HMI 也有报警和状态画面。

真正缺少的往往是：

> **从 Current State 进入 Target State 之前，到底需要哪些状态共同成立，以及这些状态之间是什么关系。**

如果这些条件长期分散在程序、接口、画面和工程师经验中，状态迁移就只能依赖“知道这套系统的人”来解释。

这就是状态迁移条件需要显式化的原因。

## 1. 隐含条件越多，系统越依赖“知道的人”

简单设备的状态迁移通常比较直接：

```text
启动请求
+ 安全条件成立
+ 设备 Ready
→ 动作开始
```

复杂自动化系统则不同。

一个自动化单元内部可能已经包含：

- 待机；
- 原点复归；
- 上料；
- 定位；
- 加工；
- 检测；
- 排出；
- 异常复归；
- 换型；
- 自动恢复。

一条生产线还可能连接：

- PLC；
- 机器人；
- 视觉系统；
- 安全系统；
- HMI；
- MES；
- WCS；
- AGV / AMR；
- 检测设备；
- 包装设备；
- 码垛设备；
- 仓储交接；
- 人工确认。

这时，“能不能进入下一阶段”往往同时依赖多个状态。

例如：

- 工件是否存在；
- 位置和姿态是否满足；
- 识别结果是否仍然有效；
- 安全许可是否成立；
- 上位系统是否放行；
- 资源锁是否释放；
- 下游是否能够承接；
- 回流或异常路径是否可用；
- 结果是否能够回写；
- 必要人工确认是否完成。

这些条件即使没有被整理出来，系统仍然可以通过 PLC、Interlock、程序分支和人工经验运行。

但随着设备改造、换型、扩线、系统升级和人员更替，隐藏条件会逐渐成为维护成本。

现场开始出现：

```text
Ready 了，但不动作
Waiting 了，但不知道在等什么
任务存在，但没有进入执行
没有报警，但流程停在当前阶段
```

这时真正困难的不是找到某一个信号，而是重新恢复：

> **当初为什么这样设计这次状态迁移。**

---

## 2. 显式化的不是“更多信号”，而是“状态迁移结构”

状态迁移条件显式化，不等于继续增加传感器或增加数据采集量。

现场通常已经有大量状态。

例如：

```text
Robot Ready
Vision OK
Safety Permission
MES Task
WCS Status
Downstream Ready
```

这些都是有效信息。

但：

```text
Robot Ready = TRUE
```

和：

```text
机器人现在是否可以进入抓取阶段
```

不是同一个问题。

后者可能还需要同时确认：

- 工件存在；
- 视觉结果有效；
- 位置满足抓取要求；
- 安全许可成立；
- 路径可达；
- 夹爪可用；
- 正常投放位可以承接；
- 回流路径可用；
- 异常分流路径可用；
- 结果回写链路可用。

因此需要显式化的是：

> **围绕一个明确 Target State Entry，本次迁移真正依赖哪些状态。**

PCN 将这些分散状态围绕同一次迁移组织起来：

```text
Current State
→ Target State
→ Multi-source State Signals
→ C/A/E Mapping
→ S/D/B Evaluation
→ CAE-SDB Result
→ Arbitration
→ Multipath Control
→ PCN Trace
```

这样，状态迁移条件才从“程序里存在”进一步变成“工程上可见”。

---

## 3. 工程讨论会从“补信号”变成“设计入口”

状态迁移条件没有被显式化时，现场改善经常采用局部补丁方式：

> 这里加一个传感器。  
> 这里加一个 Interlock。  
> 这里增加一个报警。  
> HMI 再显示一个状态。  
> 这里等 MES 放行。  
> 这里增加人工确认。  
> 程序里再补一个判断。

这些措施本身并没有问题。

问题是，如果每一次修改都只围绕局部状态进行，系统会逐渐形成大量分散判断。

而把状态迁移入口显式化以后，讨论方式会发生变化：

> 当前状态是什么？

> Target State 是什么？

> 进入 Target State 前需要哪些 C？

> 哪些 A 是必须成立的许可？

> 进入以后 E 是否能够接续？

> 当前有哪些结构、动态或边界判定需要执行？

> 多个判定结果同时存在时如何形成最终控制路径？

> 这次判定是否需要留下 Trace？

讨论对象由：

> “还缺哪个信号？”

变成：

> **“这个状态迁移入口应该怎样设计？”**

这才是显式化最直接的工程意义。

## 4. 工程经验可以从个人检查表变成结构

有经验的工程师处理现场问题时，通常已经在脑中形成一套检查顺序。

看到机器人不抓，会自然检查：

- 工件；
- 视觉；
- 路径；
- 安全；
- 夹爪；
- 下游；
- 回流；
- 回写。

看到 AGV 不进入站点，会检查：

- 任务；
- 路径；
- 资源锁；
- 站点状态；
- 区域许可；
- 下游承接。

看到设备不能自动复归，会检查：

- 异常解除；
- 原点状态；
- 安全许可；
- 模式状态；
- 保全解除；
- 后续执行链。

这些经验非常有价值。

但如果只存在于人的脑中，就很难：

- 交给新人；
- 跨项目复用；
- 与系统集成商共享；
- 在 HMI 或 MES 中统一表达；
- 形成长期数据；
- 比较改善前后的变化。

PCN 的作用之一，就是把这类隐含检查结构落到明确状态迁移入口上。

于是经验可以逐步转化为：

```text
PCN
+ Target State
+ Required States
+ C/A/E Mapping
+ S/D/B Evaluation
+ Control Paths
+ Trace
```

工程经验不再只属于某个熟悉现场的人，而开始成为可以维护的工程资产。

## 5. 不显式化，复杂度也不会消失

复杂系统的状态迁移关系本来就存在。

设备增加以后，会增加：

- 状态；
- 接口；
- 许可；
- 下游承接；
- 回退路径；
- 异常路径；
- 人工确认；
- 系统间同步；
- 数据回写。

不把这些关系整理出来，并不会让系统变简单。

复杂度只会转移到其他地方：

- PLC 梯形图深处；
- 机器人程序分支；
- HMI 模糊提示；
- MES / WCS 接口逻辑；
- 调试工程师经验；
- 设备厂家之间的接口约定；
- 跨部门排查过程；
- 故障发生后的人工日志拼接。

因此，状态迁移条件显式化并不是额外制造复杂度。

它做的是：

> **把已经存在的复杂度放到一个可以被工程师看见和管理的位置。**

只有被看见以后，复杂度才能进一步被：

- 分层；
- 审核；
- 标准化；
- 模板化；
- 记录；
- 改善。

## 6. 状态迁移本身可以成为工程对象

当状态迁移条件显式化以后，“进入下一状态”就不再只是程序中的一段逻辑。

它可以被单独设计。

例如：

```text
Current State:
识别完成 / 等待抓取

Target State:
机器人抓取
```

工程师可以继续定义：

- PCN 设置在哪里；
- 本次迁移需要读取哪些状态；
- 哪些状态属于 C；
- 哪些属于 A；
- 哪些属于 E；
- 需要执行哪些 S/D/B 判定；
- 可以形成哪些控制路径；
- 需要记录哪些 Trace。

于是，一次状态迁移开始具备几个工程属性。

### 可设计

在设计阶段就明确 Target State Entry 需要什么，而不是调试时不断补条件。

### 可检查

能够检查关键许可、下游承接、回退路径、状态有效性是否遗漏。

### 可记录

每次判定可以留下统一的 PCN Trace。

### 可复用

同类设备、同类工位和相似状态迁移可以复用已有模板。

### 可改善

可以比较哪些入口长期失败、哪些许可频繁阻断、哪些执行链经常无法接续，以及工程修改前后 Trace 如何变化。

这使状态迁移从：

> 隐含控制逻辑

逐步变成：

> **可管理的工程结构。**

---

## 7. 显式化以后，设备、系统和数据才容易连接起来

复杂制造系统的问题往往不是某一个系统完全没有状态，而是状态分布在不同层级。

例如一次物料交接可能同时涉及：

```text
MES
→ WCS
→ AGV
→ PLC
→ 站点设备
→ 下游工位
```

每个系统都可能保存自己的状态。

但如果没有明确 Target State Entry，这些状态很难自然形成同一个判定对象。

PCN 提供了一个连接位置：

> **所有与当前 Target State 有关的状态，在这里获得共同的工程上下文。**

于是：

- MES 的任务状态可以成为本次迁移的条件或许可输入；
- WCS 的资源状态可以参与许可或执行链判定；
- AGV 状态可以参与执行链接续判断；
- PLC 和安全系统提供现场状态与许可；
- 下游工位提供承接状态；
- 人工确认可以作为系统化许可输入；
- 最终判定形成统一 Trace。

这也是状态迁移条件显式化对生产 DX 的意义。

DX 不只是把更多设备数据送进平台。

更重要的是：

> **让原本分散在人员、设备、系统和流程之间的状态迁移条件具有共同的工程结构。**

---

## 小结

现代自动化系统并不缺少状态。

真正困难的是：

> **决定一次状态迁移能否成立的条件，往往分散在不同程序、设备、系统和工程师经验中。**

这些条件长期保持隐含状态时，系统会越来越依赖熟悉现场的人，项目之间也难以复用。

PCN 将一个明确的 Current State → Target State 入口作为工程对象，把与本次迁移有关的状态组织为：

```text
Current State
→ Target State
→ PCN
→ C/A/E Mapping
→ S/D/B Evaluation
→ CAE-SDB Result
→ Arbitration
→ Multipath Control
→ PCN Trace
```

这样，状态迁移条件才能进一步做到：

- 可设计；
- 可检查；
- 可记录；
- 可复用；
- 可改善。

因此，状态迁移条件显式化的目的，不是增加更多状态或更多控制逻辑。

而是：

> **把已经存在但长期隐含的状态迁移判断，变成可以被工程化管理的对象。**

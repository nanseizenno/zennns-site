# 为什么智能算法越来越强，生产线的底层控制仍然需要确定性判定？

机器视觉、优化算法、预测模型和强化学习正在不断提高系统识别、预测和决策的能力。

视觉系统可以判断工件的位置和姿态，优化算法可以寻找更优路径，预测模型可以提前发现异常趋势，强化学习可以从长期结果中寻找更好的行动策略。

但回到生产线真正执行动作的瞬间，控制系统面对的仍然是另一类问题：

```text
机器人现在能不能开始抓取？

工件现在能不能放行？

AGV 现在能不能进入这个区域？

设备现在能不能重新进入自动运行？

下一工序现在能不能开始？
```

这些问题最终必须形成明确的控制结果：

```text
允许 / 不允许
进入 / 保持
执行 / 禁止
```

本文所说的“确定性判定”，特指在一个具体状态迁移入口，最终形成明确、可执行、可复核的进入、保持或禁止结果。

上游的识别、预测、估计和优化过程仍然可以采用概率模型、统计模型或学习算法。

因此，一个更加基础的问题逐渐显现出来：

> **智能算法越来越擅长回答“什么更可能、更优”；而在具体物理状态迁移入口，控制系统最终仍必须回答“现在能不能执行”。**

从“更可能、更优”到“现在允许执行”，中间存在一个天然的状态迁移工程问题。

---

## 1. 为什么智能算法越来越强，底层控制仍然需要确定性判定？

### 1.1 算法输出与状态迁移控制结果具有不同语义

智能算法可以形成：

```text
预测（Prediction）
识别（Recognition）
置信度（Confidence）
推荐（Recommendation）
优化结果（Optimization Result）
```

控制系统还需要进一步形成：

```text
状态迁移控制结果
```

例如视觉系统已经可靠识别工件，机器人开始抓取之前仍可能需要确认：

- 当前工件是否仍位于有效抓取区域；
- 识别结果是否仍然有效；
- 机器人是否处于正确模式；
- 安全区域许可是否成立；
- 夹具和执行机构是否可用；
- 下游是否能够承接；
- 当前任务是否仍然有效。

所以真正的问题已经从“识别准不准”进一步进入：

> **当前这一组状态是否足以支持一次物理状态迁移。**

### 1.2 物理执行具有不可忽略的动作后果

软件计算可以重新执行，优化结果可以重新计算，预测值也可以在新的数据到达后更新。

生产线中的物理执行会直接改变现实状态。

机器人伸手以后，工件位置发生变化。

输送线放行以后，工件进入下一个区域。

断路器动作以后，供电结构发生改变。

AGV 进入共享路径以后，其他车辆的可用路径随之变化。

因此，物理执行之前的控制判定需要具有明确的工程责任边界。

### 1.3 状态还具有时间有效性

控制系统使用的状态并不是永久有效的。

例如：

```text
Robot Ready = TRUE
```

只能说明某个时刻机器人处于已定义的准备状态。

实际进入下一阶段时，还需要考虑：

```text
超时（Timeout）
状态陈旧（Stale）
延迟（Delay）
状态不同步（Unsynchronized）
许可撤回（Revoked）
切换中（Switching）
```

也就是说：

> **状态值存在，只说明系统获得过这个状态；状态是否仍能作为本次状态迁移的有效依据，还需要进一步判定。**

状态是否仍然有效，只是状态迁移判定中的一个问题。进一步还需要明确：

> **当前这次状态迁移到底应该观察哪些状态。**

---

## 2. 从“推荐下一步”到“允许下一步”，中间还缺什么？

假设一个路径优化算法已经计算出：

```text
路径 B = 当前最优路径
```

对于路径优化算法而言，这个结果已经完成了自己的主要任务。

但真实控制系统还必须继续判断：

```text
路径 B 当前是否开放？

共享资源是否已经被占用？

交通许可是否成立？

目标站点是否可以接收？

当前车辆状态是否允许进入？

进入以后后续路径能否继续？
```

因此：

> **“推荐下一步”和“允许下一步”属于两个不同的工程阶段。**

这种问题在控制理论中具有明确的研究基础。

离散事件系统（Discrete Event Systems）研究由离散事件驱动的系统行为；监督控制（Supervisory Control）进一步研究如何根据控制规范，对系统中的可控事件进行限制，使系统行为满足给定的控制要求。

在生产系统中，大量关键动作本身就可以理解为离散事件：

```text
启动（Start）
进入（Enter）
放行（Release）
转移（Transfer）
接收（Accept）
恢复（Recover）
切换（Switch）
```

系统需要根据当前状态和控制约束决定这些事件是否可以发生。

监督控制理论由此提供了一个重要基础：

> **“下一步是否允许发生”本身就是正式的控制问题。**

落到复杂生产线以后，进一步的问题变成：

> **形成这次判断所依据的状态，到底应该如何选择和组织？**

---

## 3. 真正更上游的问题：算法到底看到了什么？

一个算法能够判断什么，首先取决于它获得了什么表示。

假设视觉与机器人系统已经获得：

```text
视觉识别结果 = OK
置信度 = 98%
机器人 Ready = TRUE
```

如果当前系统没有同时表示：

```text
安全许可（Safety Permission）
生产许可（Production Permission）
下游承接状态（Downstream Acceptance）
视觉结果时间有效性（Vision Result Age）
工件位置边界（Workpiece Position Boundary）
执行链状态（Execution Chain State）
```

那么后续算法能够处理的问题空间，从一开始就已经缺失了这些工程关系。

强化学习领域同样长期关注状态表示（State Representation）。

面对复杂或高维观测空间，系统需要从原始观测中形成能够支持后续决策的有效状态表示。状态表示的质量会进一步影响学习效率、泛化能力以及最终策略表现。

深度学习可以参与这种表示学习，但任务所需要的信息是否得到充分保留，仍然是后续判断和决策能够达到什么能力的重要前提。

这个问题在复杂工程系统中更加明显。

生产线真实世界可能拥有：

```text
数千个设备 Tag
数百个状态变量
多个任务系统
多个资源状态
多种安全与许可状态
```

但对于：

> “机器人现在是否可以进入抓取阶段？”

真正相关的状态只是其中一部分。

对于：

> “AGV 现在是否可以进入某个站点？”

相关状态集合又会发生变化。

因此，状态不能只按照“来自哪台设备”组织。

它还需要围绕：

> **当前准备发生哪一次状态迁移**

重新建立上下文。

这可以表示为：

```text
现实系统
↓
对象选择
↓
状态表示（State Representation）
↓
面向本次状态迁移的上下文组织
↓
算法
↓
判断 / 决策
```

这里形成一个重要的方法论关系：

> **先决定看什么，再决定怎么看，最后才决定使用什么算法。**

如果“看什么”没有定义清楚，后续算法只能在已经获得的表示范围内继续处理变量、规则、异常和约束。

> **算法能力不仅受到模型本身约束，也受到状态表示以及状态迁移上下文组织的上游约束。**

对于复杂自动化系统，一个值得被独立定义的工程对象，就是：

> **一次明确的状态迁移入口。**

在 TPCA / PCN 中，将这样一个明确的迁移入口定义为：

> **目标状态入口（Target State Entry）。**

---

## 4. TPCA / PCN 如何围绕 Target State Entry 组织状态迁移？

TPCA / PCN 将一个明确的目标状态入口（Target State Entry）作为可以独立设计、判定、控制和记录的工程对象。

基本关系为：

```text
当前状态（Current State）
↓
PCN 前置判定
↓
目标状态入口（Target State Entry）
↓
目标状态（Target State）
```

PCN（Pre-Control Node / 前置控制节点）对应一个明确的目标状态入口，并部署在该入口之前，负责围绕本次状态迁移组织相关工程信息。

其核心过程可以概括成三个问题。

### 4.1 先决定看什么

第一步先明确：

```text
当前状态（Current State）
目标状态（Target State）
目标状态入口（Target State Entry）
相关状态（Relevant State）
```

然后根据这些状态在当前目标状态入口中承担的工程作用，将其映射为：

```text
C = Condition（条件状态）
A = Authority（许可状态）
E = Execution Chain（执行链状态）
```

C 表示进入目标状态所需要的条件状态。

A 表示进入目标状态所需的许可状态，包括安全许可、上位许可、区域许可、人工确认、权限、资源锁和对方设备许可等；其中关键 A 可以构成独立必要约束。

E 表示进入目标状态以后相关执行链是否能够继续接续，包括本体设备、末端执行机构、下游承接、替代路径、回退路径、异常排出以及结果上传或回写链路等状态。

例如在机器人准备进入抓取阶段时：

```text
工件位置
→ C

区域进入许可
→ A

下游接收状态
→ E
```

同一个状态对象在另一个目标状态入口中，可以承担不同的工程角色。

因此，状态的工程意义由：

```text
状态对象
×
目标状态入口
```

共同决定。

### 4.2 再决定怎么看

相关状态确定以后，还需要判断这些状态当前是否能够作为本次状态迁移的有效依据。

TPCA / PCN 从三个判定性质进行评价：

```text
S = Structure（结构完整性）
D = Dynamics（动态时序有效性）
B = Boundary（控制边界）
```

其中：

- S 关注必要的信号、接口、映射关系、许可来源、路径和执行链边界是否已经定义、接入并可观测；
- D 关注状态是否存在超时、未刷新、不同步、抖动、延迟、许可撤销或状态切换等动态时序有效性问题；
- B 关注相关状态是否处于预先定义的阈值、允许范围、容量、时间窗口、次数、置信度或偏差边界之内。

因此形成：

```text
C / A / E
×
S / D / B
```

的 CAE-SDB Matrix（CAE-SDB 矩阵）。

这一步回答的是：

> **已经找到的相关状态，在当前这个状态迁移时刻，是否仍然构成有效的工程依据。**

### 4.3 最后决定当前允许怎么走

多个状态及其判定结果可能同时存在。

例如：

```text
视觉结果仍然有效
+
机器人 Ready
+
安全许可成立
+
下游暂时无法接收
```

控制系统需要进一步处理这些判定结果之间的优先关系。

因此形成：

```text
CAE-SDB 判定结果
↓
控制仲裁（Arbitration）
↓
多路径控制（Multipath Control）
```

最终控制结果可以包括：

```text
允许进入（Allow）
等待（Wait）
重试（Retry）
重新识别（Re-identify）
重新定位（Re-position）
回流（Return）
替代路径（Alternative Path）
人工确认（Manual Confirm）
禁止进入（Prohibit）
安全锁定（Safety Lock）
```

实际执行以后，本次输入、判定、控制路径和执行结果（Execution Result）可以进一步形成 PCN Trace。

一次状态迁移由此形成完整的工程上下文：

```text
当前状态
↓
目标状态与目标状态入口确定
↓
相关状态
↓
PCN 前置判定
↓
C / A / E
×
S / D / B
↓
CAE-SDB 判定结果
↓
控制仲裁
↓
多路径控制
↓
被选定路径对应的目标状态入口
↓
实际执行
↓
PCN Trace
```

TPCA / PCN 在这里承担的核心作用，是先把一次状态迁移的问题空间组织清楚。

确定性控制、优化算法和学习算法，都可以在这一问题空间中承担适合自身能力的位置。

## 5. 从单个入口到多主体协同系统

前面的机器人抓取案例对应一个自动化执行单元中的目标状态入口。

当系统进一步扩展到 AGV / AMR 群控、MES / WCS 协同以及多设备自动化时，问题会从一个入口扩展到多个相互影响的入口。

例如：

```text
任务（Task）
车辆（Vehicle）
交通状态（Traffic）
资源（Resource）
站点（Station）
充电状态（Charge）
许可（Permit）
↓
多个目标状态入口
↓ 各自对应
多个 PCN
↓ 连接关系
PCN Network
```

此时，一个主体的状态迁移还可能改变其他主体后续可以进入的状态。

例如：

```text
AGV-A 改道
↓
共享路径占用变化
↓
AGV-B 等待
↓
Station-C 接收延迟
↓
后续任务重新分配
```

在单个自动化执行单元中，工程重点通常集中在：

> **设备在什么条件下能够进入下一执行阶段。**

进入多主体协同系统以后，系统还需要持续处理：

> **多个主体什么时候、在什么条件和许可下、通过哪条合法路径进入下一状态。**

随着自动化系统进一步向多主体协同和无人化方向发展，状态迁移问题也会从单点控制逐步扩展为系统级状态迁移网络问题。

---

## 总结

智能算法越来越擅长识别、预测和优化，而生产线的物理状态迁移入口仍然必须明确回答：

> **现在能不能执行？**

在两者之间，真正需要被工程化的，是当前状态迁移到底应该观察哪些状态、这些状态是否仍然有效，以及当前允许进入哪条控制路径。

> **TPCA / PCN 的定位，就是围绕明确的目标状态入口，把这一状态迁移问题组织成可设计、可判定、可控制和可记录的工程结构。**

随着自动化从单个设备进一步发展到多主体协同，这一问题也会从单个入口扩展到多个入口之间的状态迁移网络。

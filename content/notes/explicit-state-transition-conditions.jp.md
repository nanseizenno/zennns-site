## なぜ状態遷移条件を明示する必要があるのか？

複雑な自動化現場では、次のような状態が発生することがある。

- 設備にアラームはないが、次の段階へ進まない。
- PLC 内では多くの条件が成立しているが、アクチュエータが動作しない。
- MES にタスクがあり、WCS にも記録があるが、現場では Waiting が継続している。
- 上流工程は完了しているが、下流が一時的に受け入れられない。
- ステーション、インターフェース、制御対象などを追加した後、従来安定していたユニットで待機が繰り返し発生する。

これらの状態では、各システムが個別の状態を保持していても、明確な Target State Entry に対して、どの状態がどのような関係で判定に使われているかが十分に整理されていない場合がある。

現場には、すでに多くの状態情報が存在する。

PLC には状態ビットがあり、ロボットには Ready、画像認識システムには OK / NG、安全システムには許可、MES にはタスク、WCS にはスケジューリング記録がある。HMI にもアラームや状態表示が存在する。

状態遷移を判定するためには、これらの状態を今回の Target State Entry に対応付けて整理する必要がある。

確認対象は、例えば次の通りである。

- Current State は何か。
- Target State は何か。
- 今回の Target State Entry に関係する状態は何か。
- 各状態は C / A / E のどの状態変数領域に属するか。
- どの S / D / B 判定が必要か。
- 状態および判定はどの時間位置にあるか。
- 複数の判定結果を Arbitration でどのように処理するか。
- 今回の Target State Entry に対してどの Multipath Control を形成するか。
- 判定と実行結果をどのように PCN Trace として記録するか。

これらの関係がプログラム、インターフェース、画面、エンジニアの経験に分散している場合、状態遷移の設計意図や判定根拠を確認する際に、複数の情報を再構成する必要がある。

状態遷移条件を明示する目的は、この判定関係を Target State Entry 単位でエンジニアリング対象として整理することである。

## 1. 暗黙の判定関係が増えるほど、システム理解が特定の担当者に集中しやすい

単純な設備では、状態遷移条件を比較的少ない状態で構成できる。

例えば、

```text
起動要求
+ 安全条件成立
+ 設備 Ready
→ 動作開始
```

という関係である。

複雑な自動化システムでは、1 つのユニット内部に多数の工程段階が存在する。

例えば、

- 待機
- 原点復帰
- 搬入
- 位置決め
- 加工
- 検査
- 排出
- 異常処理
- 段取り替え
- 再投入

などである。

さらに、生産ラインでは複数の設備・システムが連携する。

- PLC
- ロボット
- 画像認識システム
- 安全システム
- HMI
- MES
- WCS
- AGV / AMR
- 検査設備
- 包装設備
- パレタイズ設備
- 倉庫引渡し
- 手動確認

このようなシステムでは、一回の Target State Entry に複数の状態が関係する。

代表例は次の通りである。

- ワークが存在するか。
- 位置と姿勢が要求条件を満たしているか。
- 認識結果が今回の判定に使用できるか。
- 安全許可が成立しているか。
- 上位システムからの許可が成立しているか。
- 資源ロック状態が今回の進入を許可しているか。
- 下流が受入可能か。
- 回流経路や異常処理経路が今回の実行チェーンに含まれている場合、その状態はどうなっているか。
- 結果書戻しが可能か。
- 必要な手動確認が完了しているか。

これらの関係は、PLC、Interlock、プログラム分岐、インターフェース仕様、運用手順などによって実装できる。

一方、状態遷移の判定関係が複数の場所へ分散すると、設備改造、段取り変更、ライン拡張、システム更新、担当者変更の際に、設計意図の確認に必要な範囲が広がる。

現場では、例えば次のような状態として現れる。

```text
Ready だが動作しない
Waiting が継続している
タスクはあるが実行へ進まない
アラームはないが現在段階から進まない
```

この場合、確認対象は個別の信号だけではなく、

> **今回の Target State Entry が、どの状態と判定関係によって構成されているか。**

である。

## 2. 明示する対象は信号数ではなく状態遷移関係である

状態遷移条件の明示では、既存の状態情報を Target State Entry に対応付けて整理する。

複雑な現場には、すでに多数の状態が存在する。

例えば、

```text
Robot Ready
Vision OK
Safety Permission
MES Task
WCS Status
Downstream Ready
```

などである。

Robot Ready は、ロボット本体の運転準備状態を示す。

一方、ロボットがピックアップ段階へ入る Target State Entry では、例えば次の状態も関係する。

- ワーク存在状態
- 画像認識結果
- 位置・姿勢状態
- 安全許可
- ロボット経路状態
- グリッパ状態
- 正常配置先の受入状態
- 今回の実行チェーンに含まれる回流経路や異常分流経路の状態
- 結果書戻し状態

したがって、明示する対象は、

> **一回の明確な Target State Entry に対して、どの状態を判定に使用し、それぞれをどの状態変数領域と判定性質で扱うか。**

という関係である。

PCN では、分散した状態を次の処理関係に整理する。

```text
Current State
→ Target State
→ PCN
→ C / A / E Mapping
→ S / D / B Evaluation
→ CAE-SDB Result + T
→ Arbitration
→ Multipath Control
→ PCN Trace
```

時間情報 T は、状態および判定とともに保持し、状態の前後関係、D の判定、PCN Trace に使用する。

この構造により、プログラムや複数システムに分散している状態遷移判定を、明確な Target State Entry に対応するエンジニアリング構造として扱うことができる。

---

## 3. エンジニアリング上の検討単位を Target State Entry に移す

状態遷移条件が複数の場所に分散している場合、現場改善では個別の信号や機能単位で修正が行われることがある。

例えば、

> センサを追加する。  
> Interlock を追加する。  
> アラームを追加する。  
> HMI に状態表示を追加する。  
> MES の許可待ちを追加する。  
> 手動確認を追加する。  
> プログラムに判定条件を追加する。

これらは、それぞれ具体的な工程目的に基づいて実装される。

Target State Entry を明示した場合、検討対象を次の単位で整理できる。

> Current State は何か。

> Target State は何か。

> 今回の Target State Entry に直接関係する状態は何か。

> どの状態を C にマッピングするか。

> どの A が Target State Entry に対する必要許可となるか。

> E に含める実行チェーンをどこまで定義するか。

> どの状態に対して S / D / B Evaluation を行うか。

> 状態および判定に対応する時間情報 T は何か。

> 複数の CAE-SDB Result を Arbitration でどのように処理するか。

> 今回の Target State Entry に対してどの Multipath Control を形成するか。

> どの情報を PCN Trace に記録するか。

このように、検討単位を個別の信号から Target State Entry へ移すことで、

> **「この Target State Entry をどのように設計するか」**

という形で状態遷移条件を整理できる。

## 4. エンジニアの確認手順を保守可能な構造へ整理する

経験を持つエンジニアは、現場問題に対して一定の確認手順を持っている場合がある。

例えばロボットがピックアップしない場合、次のような項目を確認する。

- ワーク
- 画像認識
- 経路
- 安全許可
- グリッパ
- 下流受入
- 回流経路
- 結果書戻し

AGV がステーションへ進入できない場合は、例えば次の項目を確認する。

- タスク
- 経路
- 資源ロック
- ステーション状態
- エリア許可
- 下流受入

設備を自動運転へ再投入する場合は、例えば次の状態を確認する。

- 異常処理状態
- 原点状態
- 安全許可
- 運転モード
- 保全状態
- 後続実行チェーン

これらの確認関係を Target State Entry に対応付けることで、個人の確認手順をエンジニアリング構造として整理できる。

例えば、次のように表せる。

```text
PCN
+ Target State
+ 関連状態
+ C / A / E Mapping
+ S / D / B Evaluation
+ CAE-SDB Result + T
+ Arbitration
+ Multipath Control
+ PCN Trace
```

この構造は、次の用途に利用できる。

- 新任エンジニアへの引継ぎ
- 同種設備への展開
- システムインテグレータとの設計確認
- HMI や MES / WCS での共通表示
- 長期的な判定履歴の蓄積
- 改善前後の比較

エンジニアの確認手順を明確な Target State Entry に対応付けることで、維持・更新・再利用しやすい構造として管理できる。

## 5. 状態遷移関係を明示することで複雑度の所在を確認できる

複雑なシステムでは、設備や連携先が増えるにつれて、状態遷移に関係する要素も増える。

例えば、

- 状態
- インターフェース
- 許可
- 下流受入
- 回流経路
- 回退経路
- 異常処理経路
- 手動確認
- システム間同期
- データ書戻し

などである。

これらの関係は、実装上さまざまな場所に配置される。

- PLC ラダープログラム
- ロボットプログラム
- HMI 表示
- MES / WCS インターフェースロジック
- 設備間インターフェース仕様
- 調整手順
- エンジニアの確認手順
- 問題発生時のログ照合

「回流」「回退」「復旧」「再投入」などの工程名称も、そのまま現場の Target State または目標実行経路として使用できる。

TPCA の実運転上の状態遷移は、次のように扱う。

```text
Current State → New Target State / Target Path
```

後続状態が過去の状態と同一または類似したエンジニアリング内容を持つ場合も、その時点で新しい状態インスタンスが形成される。

状態遷移条件を Target State Entry 単位で明示することで、既存の複雑な関係を、確認可能なエンジニアリング対象として整理できる。

その上で、次のような処理へ展開できる。

- 階層化
- 設計レビュー
- 標準化
- テンプレート化
- 履歴記録
- 改善

## 6. Target State Entry を独立したエンジニアリング対象として設計する

状態遷移条件を明示すると、Target State Entry を独立した設計対象として扱うことができる。

例えば、

```text
Current State：認識完了 / ピックアップ待ち

Target State：ピックアップ段階
```

という状態遷移を考える。

この Target State Entry に対して、次の事項を定義できる。

- PCN の配置位置
- 今回の状態遷移で取得する状態
- C にマッピングする状態
- A にマッピングする状態
- E にマッピングする状態
- 必要な S / D / B Evaluation
- 状態および判定に対応する時間情報 T
- Arbitration で扱う制御制約
- 候補となる Target State または目標実行経路
- PCN Trace に記録する情報

これにより、Target State Entry は次の観点から管理できる。

### 設計

設計段階で Target State Entry に必要な状態、判定、制御関係を定義する。

### 確認

必要な信号、許可元、実行チェーン、状態有効性、制御境界などを確認する。

### 記録

一回の Target State Entry に対する判定、時間情報 T、Arbitration Result、Multipath Control、実行結果を PCN Trace として記録する。

### 再利用

同種設備、同種ステーション、類似する Target State Entry に対して、既存の設計構造やテンプレートを利用する。

### 改善

どの Target State Entry で特定の CAE-SDB Result が頻発しているか、どの許可や実行チェーンが繰り返し影響しているか、改善前後で PCN Trace がどのように変化したかを比較する。

この構成により、状態遷移判定を継続的に管理できるエンジニアリング構造として扱うことができる。

## 7. 明示化により、複数システムの状態を同じ Target State Entry に対応付ける

複雑な製造システムでは、一回の状態遷移に関係する状態が複数のシステムに分散している。

例えば、物料引渡しでは次のようなシステムが関係する。

```text
MES
→ WCS
→ AGV
→ PLC
→ ステーション設備
→ 下流工程
```

各システムは、それぞれの役割に応じた状態を保持する。

明確な Target State Entry を設定すると、これらの状態を同じ判定対象として関連付けることができる。

例えば、

- MES のタスク状態を C または A に関係する状態として扱う。
- WCS の資源状態を A または E に関係する状態として扱う。
- AGV の実行状態を E に関係する状態として扱う。
- PLC と安全システムから現場状態や A に関係する許可状態を取得する。
- 下流ステーションから E に関係する受入状態を取得する。
- 手動確認を A に関係する状態として扱う。
- 時間情報 T により各状態の前後関係と D の判定を行う。
- CAE-SDB Result、Arbitration Result、Multipath Control、実行結果を PCN Trace に記録する。

このように、Target State Entry は複数システムに分散する状態を同じエンジニアリング文脈で扱うための共通位置となる。

生産 DX においても、設備データを収集するだけでなく、状態がどの Target State Entry に関係し、どの判定に使用されたかを関連付けることで、状態遷移条件を共通のエンジニアリング文脈で扱うことができる。

## まとめ

現代の自動化システムには、多数の状態情報が存在する。

状態遷移条件を明示する際に対象となるのは、

> **明確な Target State Entry に対して、どの状態を使用し、どの判定を行い、その結果をどの制御へ接続するか。**

という状態遷移関係である。

PCN は、Target State Entry をエンジニアリング対象として、次の処理関係を構成する。

```text
Current State
→ Target State
→ PCN
→ C / A / E Mapping
→ S / D / B Evaluation
→ CAE-SDB Result + T
→ Arbitration
→ Multipath Control
→ PCN Trace
```

時間情報 T は、状態および判定とともに保持し、状態の前後関係、D の判定、PCN Trace に使用する。

後続の運転で過去と同じ状態内容が現れた場合も、その時点で新しい状態インスタンスが形成される。

状態遷移条件を Target State Entry 単位で整理することにより、次の工程活動へ展開できる。

- 設計
- 確認
- 記録
- 再利用
- 改善

状態遷移条件の明示化は、既存の状態、許可、実行チェーン、時間情報、制御境界を、一回の Target State Entry に対応する判定・制御・履歴として整理するためのエンジニアリング手段である。

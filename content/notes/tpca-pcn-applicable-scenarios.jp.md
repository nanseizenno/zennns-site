# TPCA / PCN の適用シナリオ分析

TPCA / PCN の中核となる考え方は、次の通りである。

> **明確な Target State Entry は、それ自体を独立して設計・判定・制御・記録できるエンジニアリング対象として扱うべきである。**

したがって、ある場面が TPCA / PCN の適用対象となるかを判断する際は、設備、ソフトウェア、MES、WCS、人との協調などのシステム種別から判断するのではなく、まず Target State Entry を確認する。

基本となる確認事項は、次の通りである。

> **明確な Target State Entry が存在し、その入口をエンジニアリング対象として設計できるか。**

PCN は、明確な Target State Entry の前に配置する前制御ノードである。

すべてのデータを再分類したり、すべての業務フローを PCN に置き換えたりすることを目的とするものではない。

実際の適用では、

> **どの Target State Entry を独立して設計・判定・制御・記録する対象とするか。**

を選定する。

---

## 1. PCN の設定に適した Target State Entry

PCN の設定に適した場面では、通常、次の条件を確認できる。

### Target State が明確である

次の関係を明確にできることが基本となる。

```text
Current State → Target State
```

例えば、次のような状態遷移がある。

- ピックアップ待ち → ピックアップ段階
- タスク割当済み → 搬送開始
- 保全完了 → 自動運転への再投入
- 品質確認完了 → 次の生産段階

Target State が明確でなければ、PCN が対象とする Target State Entry も明確にならない。

### 関連状態をシステムで取得できる

今回の Target State Entry に関係する主要な状態は、システムから取得、記録、または確実に確認できる必要がある。

状態の取得元には、例えば次のものがある。

- PLC
- ロボットコントローラ
- 安全システム
- MES / WCS
- 画像認識システム
- 品質システム
- HMI
- バーコード読取システム
- その他の設備・ソフトウェアインターフェース

状態の取得元が異なっていても、今回の Target State Entry に対する実際の判定に使用できることが必要である。

### 判定結果がシステムの動作に反映される

判定結果が事後分析やレポートだけに使用され、Target State Entry の制御結果に反映されない場合、その機能は分析システムに近い。

PCN では、一回の状態遷移前判定が今回の Target State Entry に対する Multipath Control に接続される。

例えば、次のような制御出力がある。

- 進入許可
- 待機
- 再確認
- 代替経路への分岐
- 進入禁止
- 手動確認

### 判定履歴を形成できる

今回の Target State Entry に対して、どの状態を使用し、どのような判定を行い、どの制御結果となったかを記録できることが望ましい。

この履歴を PCN Trace として形成する。

したがって、PCN の適用に適した場面は、次の関係で整理できる。

> **明確な Target State + 観測可能な状態 + 制御に反映される判定 + 追跡可能な履歴**

---

## 2. 適用しやすい代表的な場面

### 自動化実行ユニット

代表的な対象には、次のようなものがある。

- ロボットピックアップ
- 検査
- 圧入
- 搬送引渡し
- 搬入・搬出
- 正常経路と異常経路の切替

このような場面では、Current State、Target State、物理実行段階の境界を比較的明確に設定できる。

> **目標物理実行段階へ入る前は、代表的な PCN の配置位置である。**

関連事例：

[自動化実行ユニット前判定事例](/jp/cases/automation-execution-unit-pre-control/)

---

### MES / WCS と複数設備の協調

代表的な対象には、次のようなものがある。

- AGV / AMR 群制御
- タスク実行
- 資源使用
- 経路・ステーション協調
- 下流受入
- 協調停滞からの後続状態遷移

このような場面では、個別の設備やシステムに明確な故障がなくても、複数の状態が一回の協調状態遷移を共同で決定する場合がある。

Target State を明確にし、今回の Target State Entry に関係するタスク、許可、資源、実行状態を取得できる場合、PCN の適用対象として整理できる。

関連事例：

[MES / WCS 協調停滞診断モジュール事例](/jp/cases/collaborative-stagnation-diagnosis/)

---

### 生産 DX とシステム間状態遷移

代表的な対象には、次のようなものがある。

- 品質放行
- 工程切替
- 異常処理後の状態遷移
- 保全完了後の再投入
- 手動確認後の自動運転再開
- MES、品質システム、設備、下流システム間の状態遷移

このような場面では、多数のデータが取得されていても、「次の段階へ入れるか」という判定が複数のシステムや担当者に分散している場合がある。

人による操作についても、HMI、バーコード読取、品質システム、その他のインターフェースを通じてシステムが読み取り・記録できる状態になっている場合は、Target State Entry の判定に使用できる。

関連事例：

[製造 DX 状態遷移条件設計・履歴分析事例](/jp/cases/production-dx-state-transition/)

---

### デジタルシステムにおける明確な実行入口

TPCA / PCN のエンジニアリング対象は、物理設備だけに限定されない。

デジタルシステムでも、次の関係を明確に設定できる場合がある。

```text
Current State → Target State
```

Target State へ入る前に、観測可能な Condition、Authority、Execution Chain に関係する状態を確認し、その判定結果によって実行経路を制御する場合は、PCN の適用対象として検討できる。

代表例は次の通りである。

- 高コストサービスの呼出し
- ツール呼出し
- API 実行
- 自動デプロイの実行入口
- その他の明確なデジタル実行経路

ここでも重要なのは、ソフトウェアシステムかどうかではなく、

> **実際に実行され、判定によって制御できる明確な Target State Entry が存在するか。**

という点である。

---

## 3. 人が関与する場面でも PCN を適用できる

TPCA / PCN は、人が関与するシステムを適用対象から除外するものではない。

重要なのは、人の操作や判断結果がシステム上の明確な状態として取得できるかである。

例えば、次のような状態がある。

- HMI での手動確認
- バーコード読取結果
- 品質放行
- 保全解除
- エンジニアによる復旧確認

これらがシステムから読み取り、記録できる状態として定義されている場合は、Target State Entry の判定に使用できる。

一方、次のような情報は、通常、PCN の中核となる状態には適しにくい。

- 担当者が感覚的に「進めてもよい」と判断しているか
- 部門が案件を進める意向を持っているか
- 責任者が実質的に賛同しているか
- 明示されていない資源を調整できる可能性があるか
- システムに記録されていない一時的な判断

これらは、技術システムの状態遷移よりも、組織運営、ワークフロー、プロジェクト管理に関係する。

したがって、

> **人が関与する情報を PCN の判定に使用する場合は、システムが取得・記録できる信頼可能なエンジニアリング状態として扱えることが基本となる。**

---

## 4. PCN の主要なエンジニアリング対象に適しにくい場面

次のような場面は、通常、PCN の主要なエンジニアリング対象には適しにくい。

- 一般的な社内承認
- 通常の会議による意思決定
- 人事・組織管理
- 主観的判断への依存が大きいプロジェクト管理
- 単純な統計レポート
- 状態遷移制御に関与しないトレンド監視
- 分析結果のみを生成し、システム動作に反映しない BI

これらの対象を C / A / E の観点から説明できる場合があっても、それだけで PCN のエンジニアリング対象になるわけではない。

主要な状態が、個人の主観、組織関係、一時的な調整、システムに記録されていない情報に依存する場合、安定した状態遷移前判定と Multipath Control を構成しにくい。

---

## 5. 適用性を確認するための簡易チェック

新しい対象に TPCA / PCN を適用する場合は、まず次の4点を確認できる。

### 1. Current State と Target State を明確にできるか

次の関係を明確にできない場合、PCN が対象とする Target State Entry を設定しにくい。

```text
Current State → Target State
```

### 2. 今回の状態遷移に関係する主要な状態を観測できるか

判定に使用する状態は、システムから読み取り、記録、または確実に確認できる必要がある。

### 3. 判定結果が Target State Entry の制御に反映されるか

判定結果が説明や分析にのみ使用され、実際の状態遷移に影響しない場合は、完全な PCN とは異なる。

### 4. 一回の判定を PCN Trace として記録できるか

今回の Target State Entry に対する入力状態、判定、時間情報 T、Arbitration Result、Multipath Control、実行結果を一連の履歴として記録できる場合、エンジニアリング対象として整理しやすい。

簡略化すると、次のように表せる。

```text
Target State が明確
→ 状態を観測可能
→ 判定が制御に反映
→ 結果を追跡可能
```

これらを確認した後、具体的な PCN では C / A / E Mapping、S / D / B Evaluation、CAE-SDB Result、Arbitration、Multipath Control、PCN Trace を設計する。

詳細な定義については、以下を参照。

[Concepts｜基本概念](/jp/concepts/)

## 6. 適用境界を決めるのは業界ではなくエンジニアリング対象である

TPCA / PCN の適用範囲は、業界名、設備種別、または人が関与するかどうかだけで決まるものではない。

確認すべき対象は、

> **明確な Target State Entry をエンジニアリング対象として設計できるか。**

という点である。

自動化実行ユニット、MES / WCS 協調、生産 DX は異なるシステム階層に属するが、いずれも次の共通構造を持つ場合がある。

> **システムが明確な Target State へ入る前に、複数の関連状態を用いて前判定を行う。**

一方、ある場面を C / A / E の概念で説明できたとしても、Target State Entry が安定して定義できず、状態を観測できない、制御結果に接続できない、または履歴を形成できない場合は、TPCA / PCN の主要な適用対象として扱うことは適切ではない。

---

## エンジニアリング上の結論

TPCA / PCN の適用境界は、次のように整理できる。

> **明確な Target State Entry が存在し、その入口を観測・判定・制御・記録できる場合、PCN としてエンジニアリング対象化する基盤がある。**

PCN の選定では、

> 「状態数が多いか。」

> 「C / A / E で説明できるか。」

だけではなく、

> **「独立して設計・判定・制御・記録する価値のある Target State Entry が存在するか。」**

を確認する。

この条件を満たす場合、その Target State Entry に PCN を配置し、具体的な状態遷移前制御を設計することができる。

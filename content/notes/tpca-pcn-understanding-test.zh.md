# 你真的理解 TPCA / PCN 了吗？

会解释下面这些术语，并不代表真正理解 TPCA / PCN：

```text
C = Condition
A = Authority
E = Execution Chain

S = Structure
D = Dynamics
B = Boundary
```

这些定义本身并不难记。

TPCA / PCN 更核心的问题是：

> **面对一个陌生工程系统，能不能识别出真正需要被独立设计的目标状态入口？**

进一步还需要判断：

- PCN 应该设置在哪里；
- 哪些状态真正与这次状态迁移有关；
- 为什么这一次可以进入，或者为什么还不能进入；
- 多个判定结果同时存在时，最终应该形成什么控制结论；
- 这次判定和执行结果能否形成可追溯履历。

下面十个问题，用来检查理解是否已经从“会背术语”进入“能识别和设计工程对象”。

---

## 1. 你能先找到目标状态入口吗？

给你一个简单流程：

```text
工件等待
→ 搬送取件
→ 到达检测位置
→ 开始检测
```

不要先做 C / A / E 分类。

先选择其中一次状态迁移，回答：

1. 当前状态是什么？
2. 目标状态是什么？
3. 目标状态入口在哪里？
4. 为什么这个入口值得被独立设计？
5. PCN 应该设置在什么位置？

如果连目标状态入口都无法明确，后面的结构化判定也就没有稳定对象。

---

## 2. Robot Ready = TRUE，为什么仍然不能抓？

一个机器人单元准备进入抓取阶段。

已知：

- Robot Ready = TRUE；
- 夹爪正常；
- 安全状态正常；
- 视觉结果有效；
- 但下游正常投放位已经无法承接。

请回答：

> 为什么不能写成 `Robot Ready = TRUE → Allow Pick`？

进一步说明：

- 当前状态是什么；
- 目标状态是什么；
- 为什么下游承接状态会影响这次状态迁移；
- PCN 应该在什么时候完成前置判定。

这个问题检验的是：

> **能否区分“局部 Ready”和“目标状态入口成立”。**

---

## 3. C 和 E 都成立，A 不成立，可以继续吗？

某个自动化单元准备进入下一物理执行阶段。

已知：

- 相关条件已经成立；
- 后续执行链可以接续；
- 但关键区域许可没有成立。

问题：

> 系统能不能因为“其他状态都正常”而继续进入目标阶段？

进一步回答：

> 为什么关键许可需要作为独立约束理解，而不能简单被其他条件抵消？

这个问题检验的是对 Authority 的理解。

---

## 4. 同一个视觉状态，为什么会出现不同性质的问题？

某个视觉结果出现三种情况：

A：

> 视觉结果接口没有被系统正确接入。

B：

> 识别结果曾经有效，但现在已经超过有效时间。

C：

> 当前结果仍然有效，但已经进入预设边界范围。

这三种情况表面上都可能表现为：

```text
Vision Not Available
```

请回答：

- 为什么它们不是同一种工程问题？
- 分别更接近 S、D、B 中哪一种判定性质？
- 为什么不能把 `Vision_Result` 固定定义成所谓“S 信号”“D 信号”或“B 信号”？

这个问题检验的是：

> **状态变量域与判定性质为什么必须分开。**

---

## 5. 所有主要设备都 Ready，为什么 E 仍然可能不成立？

请构造一个实际工程场景：

> 主要设备都显示 Ready，但系统仍然不能进入目标状态。

场景中至少考虑：

- 本体设备；
- 下游承接；
- 正常执行路径；
- 回退、异常或备用路径中的至少一种。

然后回答：

> 为什么 `Execution Chain` 不等于 `Equipment Ready`？

这个问题检验的是对执行链接续性的理解。

---

## 6. 得到一个 CAE-SDB Result，为什么还不能直接输出控制动作？

假设 PCN 得到：

```text
E-D
```

即执行链存在动态时序有效性问题。

为什么不能直接规定：

```text
E-D = WAIT
```

请考虑：

- 问题可能只是短时未刷新；
- 备用执行路径可能仍然可用；
- 同时可能存在关键许可阻断；
- 其他结果可能具有更高控制优先级。

然后回答：

> 为什么 CAE-SDB Result 与最终控制路径之间还需要控制仲裁？

这个问题检验的是：

> **判定结果和控制结果为什么不是机械的一一对应。**

---

## 7. 一台 AGV 停了很久，为什么不能直接判断“群控协同停滞”？

某台 AGV 在一个区域等待了较长时间。

问题：

> 这是否足以说明整个多主体系统已经发生协同停滞？

如果不能，还需要从哪些群体状态继续观察？

例如：

- 是否存在有效任务；
- 其他主体是否仍在正常执行；
- 资源和通行许可是否形成集中阻断；
- 下游是否仍然能够持续承接；
- 这种状态是否具有群体性和持续性。

这个问题检验的是：

> **能否区分单体运行现象与系统级状态迁移问题。**

---

## 8. Alarm Code + Timestamp，算不算 PCN Trace？

假设系统只记录：

```text
Alarm 1032
08:31:25
```

这是一条报警履历。

但它是不是完整的 PCN Trace？

为了重新解释一次状态迁移为什么没有成立，至少还需要知道什么？

例如：

- 当时系统处于什么状态；
- 准备进入什么目标状态；
- 哪些状态参与了本次判断；
- 形成了什么结构化判定结果；
- 最终形成了什么控制结论；
- 实际执行结果是什么。

这个问题检验的是：

> **能否区分“发生了什么”和“为什么这次状态迁移没有成立”。**

---

## 9. 哪些问题虽然能解释，却不一定适合设置 PCN？

下面这些对象都可能存在“条件、许可、执行”：

- 行政审批；
- 项目管理；
- 质量放行；
- 自动仓库交接；
- 设备保全复归；
- 软件发布入口。

请回答：

> 为什么“能够用 C / A / E 描述”并不等于“应该设置 PCN”？

进一步判断：

- 目标状态是否明确；
- 相关状态是否可观测；
- 判定结果是否真正影响系统行为；
- 本次判断能否形成可追溯履历。

这个问题检验的是对 TPCA / PCN 工程边界的理解。

相关说明：

[TPCA / PCN 适用场景分析](/zh/notes/tpca-pcn-applicable-scenarios/)

---

## 10. 不使用现成案例，你还能建立一个 PCN 吗？

为了检验方法是否能够迁移到新的工程对象，这一题不使用：

- 机器人抓取；
- AGV / AMR 群控；
- 已公开的生产 DX 案例。

请选择一个新的工程对象，例如：

- 电力顺控；
- 自动仓库交接；
- 包装线换型；
- 自动检测流程；
- 设备保全复归；
- 软件发布入口；
- 其他具有明确状态迁移入口的工程系统。

至少说明：

1. 当前状态；
2. 目标状态；
3. 目标状态入口；
4. PCN 设置位置；
5. 与本次迁移有关的代表性状态；
6. 一个结构完整性问题；
7. 一个动态时序有效性问题；
8. 一个控制边界问题；
9. 至少两种可能的控制结果；
10. 本次判断需要记录哪些基本履历。

最后回答：

> **为什么这里需要的是一个独立状态迁移工程对象，而不只是再增加一个 Interlock？**

---

## 怎么判断自己是真的理解，还是只会背术语？

如果只能回答：

```text
C 是 Condition
A 是 Authority
E 是 Execution Chain
```

这只是记住了定义。

如果能够判断某个问题属于：

```text
C-D
A-B
E-S
```

说明已经能够使用 CAE-SDB 的基本坐标。

但真正理解 TPCA / PCN，还需要再往上一层。

面对一个陌生工程系统，应该能够先完成：

```text
当前状态
→ 目标状态
→ 目标状态入口
→ PCN
```

然后再进一步组织：

```text
相关状态
→ C / A / E
→ S / D / B
→ CAE-SDB Result
→ 控制仲裁
→ 多路径控制
→ PCN Trace
```

也就是说：

> **真正理解 TPCA / PCN，不是先会分类状态，而是先能识别“哪一次状态迁移值得成为独立工程对象”。**

如果这一点成立，后面的结构化判定、控制和履历才有明确对象。

## TPCA / PCN 建立在什么工程基础上？

评价一种新的工程方法，不能简单以“其中是否包含已有概念”作为判断依据。

状态、状态迁移、Interlock、Ready、安全许可、超时、降级和备用路径等机制，早已存在于成熟的工业自动化系统中。IEC 61131-3、ISA-88、ISO 13849-1 以及 OPC UA 等标准或规范，也分别从程序组织、批过程控制、安全相关控制和状态信息模型等角度形成了成熟的工程基础。[1][2][3][4]

需要进一步讨论的是：

> **当这些机制已经广泛存在时，为什么复杂自动化系统仍然经常出现“局部状态正常，但目标状态仍无法进入”的问题？**

典型现象包括：

- 设备没有报警，但系统无法进入下一阶段；
- 机器人已经 Ready，但动作仍未开始；
- MES 中存在任务，WCS 中也有记录，但现场持续 Waiting；
- 各单体设备分别正常，但整体执行链无法继续接续；
- 某个状态刚刚仍然有效，短时间后已经不能继续作为放行依据；
- 安全许可、运行条件、下游状态和异常路径分散在不同程序与系统中，最终仍需工程师跨程序、日志和接口进行判断。

TPCA / PCN 关注的是：

> **当系统准备进入一个明确目标状态时，如何将原本分散的判断关系组织到同一个目标状态入口。**

从这一角度看，TPCA / PCN 建立在五个基础工程共识之上。

---

## 1. 工程控制不仅涉及状态，还涉及状态迁移

单个信号为 TRUE，并不能直接说明系统应当进入下一阶段。

例如，机器人 Ready 只能表示机器人当前具备某种局部运行条件。

它不能单独回答：

- 当前系统处于什么状态；
- 系统准备进入什么目标状态；
- 工件条件是否成立；
- 必要许可是否成立；
- 下游是否能够承接；
- 当前使用的相关状态是否仍然有效。

自动化控制中的关键对象并不只是某个离散信号，而是状态之间的迁移关系。

例如：

```text
当前状态 → 目标状态
```

因此，问题不仅是：

> 某个信号当前是什么值？

还包括：

> **为了从当前状态进入目标状态，需要哪些工程条件共同成立？**

SFC、状态机以及工业设备状态模型等既有方法，已经长期使用状态、步骤和迁移来组织控制逻辑。[1][2][4]

TPCA 进一步把分析位置收敛到一个明确的目标状态入口。

只有先确定：

```text
当前状态 → 目标状态
```

后续 C / A / E 状态映射和 S / D / B 判定才具有明确的工程对象。

## 2. 可执行性与进入许可需要区分

复杂工程系统中，“具备执行能力”和“被允许执行”并不是同一类判断。

机器人可能已经 Ready，夹爪状态正常，路径也可能具备执行条件。

但如果安全许可尚未成立、区域许可已经撤销或上位系统尚未放行，系统仍不得进入目标状态。

安全相关控制本身就是成熟且独立的工程领域。ISO 13849-1:2023 对执行安全功能的控制系统安全相关部分（SRP/CS）的设计与集成给出了方法、要求和指导。[3]

因此，TPCA 将目标状态进入前的相关状态进一步区分为不同变量域。

### C：Condition

C 表示进入目标状态前，与本次状态迁移有关的事实条件是否成立。

例如：

- 对象条件；
- 现场条件；
- 识别条件；
- 任务条件；
- 参数条件；
- 前序完成状态。

### A：Authority

A 表示系统当前是否被允许进入目标状态。

例如：

- 安全许可；
- 区域许可；
- 上位系统放行；
- 人工确认；
- 权限与授权；
- 资源锁；
- 对方设备许可。

关键 A 可以构成独立必要约束。

也就是说：

> **即使 C 已经成立，E 也具备接续条件，只要关键 A 不成立，系统仍不得进入目标状态。**

将 C 与 A 区分，并不是增加两个分类名称，而是避免把性质不同的问题统一压缩为：

```text
Condition = FALSE
```

## 3. 单体 Ready 不等于执行链成立

复杂自动化系统中，局部设备状态与整体执行链接续能力不是同一个工程对象。

例如：

- 机器人 Ready，不代表抓取后的工件已经具备可用投放位置；
- 压装设备 Ready，不代表搬送机构已经退出压装区域；
- 检测设备 Ready，不代表检测结果能够正常上传并继续进入后续流程；
- AGV Ready，不代表目标站点当前能够接收；
- 主设备 Ready，也不代表返回、异常分流或其他必要路径已经可用。

ISA-88 建立了批过程控制中的物理模型、功能关系和顺序控制等标准化框架，其相关技术报告还提供了机器与单元状态的实施示例。[2]

这些既有工程实践说明，单体设备状态与更高层级的过程、单元和执行关系需要分别描述。

TPCA 中：

> **E = Execution Chain，执行链状态。**

E 关注的是：

> **系统进入目标状态以后，后续执行链是否能够继续接续。**

代表性内容可以包括：

- 本体设备状态；
- 末端执行机构；
- 下游承接；
- 正常执行路径；
- 返回路径；
- 异常分流路径；
- 备用路径；
- 资源释放；
- 结果上传；
- 状态回写；
- 对方设备接收状态。

Ready 可以作为 E 的一个输入，但不能代表整个 E。

因此，复杂系统完全可能出现：

> **各单体设备均 Ready，但执行链仍然不能成立。**

## 4. 状态判断必须具有时间语义

工业现场中存在一类典型问题：

> **状态值本身没有错误，但其时序已经不再适用于当前状态迁移。**

例如：

- 视觉系统曾经输出 OK，但工件已经移动；
- 下游设备刚才处于 Ready，但当前状态已经变化；
- 资源锁曾经释放，但随后已经被其他主体重新占用；
- 上位许可曾经成立，但当前已经撤销。

因此：

> **TRUE 不等于当前仍然有效。**

一个状态能否用于本次目标状态进入判断，还需要结合其运行上下文判断：

- 状态何时产生；
- 是否持续刷新；
- 是否已经超时；
- 是否存在抖动；
- 多个相关状态是否同步；
- 是否存在冲突；
- 是否正在切换；
- 当前置信度是否仍满足要求。

TPCA 将这一类判定性质定义为：

> **D = Dynamics，动态时序有效性。**

同一个状态至少需要区分两个不同问题。

第一类问题是：

> **该状态是否已经定义、接入并能够被观测？**

这属于：

> **S = Structure，结构完整性。**

第二类问题是：

> **该状态当前是否仍然有效、同步和可信？**

这属于：

> **D = Dynamics，动态时序有效性。**

OPC UA 的状态机信息模型对 CurrentState、Transition、LastTransition 以及 Transition 的时间信息提供了显式表达。[4]

这说明在工业信息模型中，状态并不只是一个孤立值，还可以与迁移及时间信息共同描述。

TPCA 的 D 则进一步面向具体目标状态入口，判断相关状态当前能否继续作为本次状态迁移的有效依据。

## 5. 工程系统需要预先定义控制边界

很多工程状态并不能简单表示为 OK / NG。

例如：

- 视觉识别置信度接近正常放行范围边界；
- 位置偏差接近允许补偿范围；
- 下游暂时不能承接，但仍处于允许等待窗口；
- 某项许可正在切换，当前尚不能放行，但也不能直接判定为永久失效。

这些状态具有一个共同特征：

> **系统已经偏离正常进入条件，但尚未必达到必须直接终止或禁止进入的程度。**

因此，工程系统需要预先定义相应的控制边界。

例如：

- 哪些范围仍可继续观察；
- 哪些状态允许再次采样；
- 哪些状态允许重新确认；
- 何时达到重试上限；
- 何时进入降级候选范围；
- 哪些边界越过后不得进入目标状态；
- 哪些情况需要人工确认；
- 哪些情况需要进入更高等级控制约束。

TPCA 将这一类判定性质定义为：

> **B = Boundary，控制边界。**

例如：

- 视觉识别置信度接近预设边界，可以形成 C-B 判定；
- 某项许可达到预定义确认边界，可以形成 A-B 判定；
- 下游等待达到预定义时间边界，可以形成 E-B 判定。

B 判断的是：

> **某个 C、A 或 E 相关状态是否已经进入预先定义的控制边界。**

B 本身不是最终控制路径。

边界被触发以后，系统最终进入等待、重采样、回流、人工确认、降级或禁止进入等哪一条路径，仍需要结合完整判定结果进行控制仲裁。

## 6. TPCA / PCN 在这些工程基础上增加了什么？

前述五个基础分别观察，都不是陌生的工程概念。

- 状态机和 SFC 处理状态与迁移；
- PLC 和控制程序使用 Interlock；
- 安全相关控制具有独立的安全许可与约束；
- 工业系统长期存在时序、刷新、同步和有效性问题；
- 工程控制普遍存在等待、重试、降级、备用路径和禁止进入等控制策略。

TPCA / PCN 的重点不在于重新命名这些既有机制，而在于：

> **将它们围绕一次明确的目标状态入口重新组织为完整的前置判定与控制关系。**

这一目标状态入口由 PCN（Pre-Control Node，前置控制节点）承担具体工程组织。

基本处理链为：

```text
当前状态
→ 目标状态
→ PCN
→ C / A / E 状态映射
→ S / D / B 判定
→ CAE-SDB Result
→ Arbitration
→ Multipath Control
→ PCN Trace
```

其中：

**PCN** 回答：

> 在哪个目标状态入口进行本次前置判定？

**C / A / E** 回答：

> 哪些状态变量参与本次目标状态进入判断，它们分别承担什么工程作用？

**S / D / B** 回答：

> 从哪些判定性质分析这些状态？

**CAE-SDB Result** 表示：

> 本次目标状态入口形成了哪些结构化判定结果？

**Arbitration** 处理：

> 多个判定结果和控制约束同时存在时，如何确定控制优先关系？

**Multipath Control** 形成：

> 系统最终进入哪一条控制路径？

**PCN Trace** 记录：

> 本次判定依据了哪些状态，形成了什么判定和仲裁结果，以及最终输出了什么控制路径？

因此，TPCA / PCN 将一次目标状态进入组织为：

```text
目标状态入口
→ 状态组织
→ 结构化判定
→ 判定结果
→ 控制仲裁
→ 多路径控制
→ 判定履历
```

## 小结

TPCA / PCN 建立在成熟工业自动化机制已经广泛存在的工程基础之上。

其出发点不是否定状态机、PLC、Interlock、安全控制、MES / WCS 或其他既有技术，而是处理一个在复杂系统中仍然反复出现的问题：

> **当多个已有机制共同决定一次状态迁移时，如何围绕同一个目标状态入口形成明确的前置判定、控制输出和判定履历。**

因此，TPCA / PCN 将分析对象收敛到：

> **明确的目标状态入口。**

并通过：

```text
PCN
→ C / A / E 状态映射
→ S / D / B 判定
→ CAE-SDB Result
→ Arbitration
→ Multipath Control
→ PCN Trace
```

把一次目标状态进入转化为可设计、可判定、可控制、可记录和可复用的工程对象。

## 参考文献与外部依据

以下资料用于说明本文涉及的状态迁移、批过程控制、安全相关控制和状态信息模型等工程基础已经具有成熟的标准或规范背景。

这些资料用于说明 TPCA / PCN 所处的既有工程基础和技术边界，**不构成 TPCA / PCN 的理论来源说明，也不用于直接证明相关专利的新颖性或创造性。**

1. **PLCopen — IEC 61131-3**  
   PLCopen 对 IEC 61131-3 PLC 编程语言体系进行公开说明，其中 Sequential Function Chart（SFC）以步骤、迁移和动作组织顺序控制逻辑。  
   https://www.plcopen.org/standards/logic/iec-61131-3/

2. **ISA — ISA-88 Series of Standards: Batch Process Control**  
   ISA-88 为批过程控制提供术语、数据结构、物理模型和功能关系等标准化框架，并包含顺序控制、安全互锁等控制活动之间的关系；相关技术报告还提供机器与单元状态的实施示例。  
   https://www.isa.org/standards-and-publications/isa-standards/isa-88-standards

3. **ISO 13849-1:2023 — Safety of machinery — Safety-related parts of control systems — Part 1: General principles for design**  
   ISO 13849-1:2023 规定并提供执行安全功能的控制系统安全相关部分（SRP/CS）设计与集成的方法、要求、建议和指导。  
   https://www.iso.org/standard/73481.html

4. **OPC Foundation — OPC Unified Architecture, Part 16: State Machines**  
   OPC UA Part 16 对状态机、当前状态、状态迁移及相关状态变量进行规范化表达，其中 TransitionVariableType 还包含迁移发生时间相关信息。  
   https://reference.opcfoundation.org/specs/OPC-10000-16

## 一句话定义

TPCA / PCN 的核心命题是：

> **一次明确的目标状态入口，应当成为可以被独立设计、判定、控制和记录的工程对象。**

**TPCA（Transition Pre-Control Architecture）** 是状态迁移前置控制的总体架构。

**PCN（Pre-Control Node）** 是部署在具体目标状态入口前的前置控制节点，是这一工程对象在实际系统中的工程节点。

PCN 围绕一次明确的目标状态进入组织多源状态信号，进行 C / A / E 状态映射和 S / D / B 判定，形成 CAE-SDB Result，经控制仲裁后输出多路径控制，并通过 PCN Trace 记录本次判定与执行履历。

多个 PCN 按实际状态迁移关系以及必要的许可、资源和执行依赖关系连接后，可以进一步形成 PCN Network。

TPCA / PCN 主要回答以下问题：

- 为什么当前不能进入目标状态；
- 问题来自条件、许可还是执行链；
- 问题属于结构缺失、动态异常还是进入控制边界；
- 多个判定结果同时存在时如何形成最终控制结论；
- 下一步应进入哪一条控制路径；
- 本次判定、控制和执行结果如何记录与追溯。

## 执行摘要

制造现场已经具备 Ready、Interlock、Handshake、报警、状态码、MES 记录和 WCS 日志。

这些机制能够支撑设备运行，也能够记录大量状态。

在复杂系统中，仍然存在一个长期反复出现的工程问题：

> **当系统准备进入一个明确目标状态时，相关状态虽然分别存在，但本次目标状态入口为什么可以进入、等待、阻断或分流，仍未形成统一的工程对象。**

这些具体问题已经在 [工程问题](/zh/questions/) 中展开。

本文进一步归纳这些问题背后的共同结构：

> **一次明确的目标状态入口，应当成为可以被独立设计、判定、控制和记录的工程对象。**

![复杂工程系统中的共通状态迁移问题](/images/tpca/01-common-state-transition-problem.png)

图1：多个现场问题往往集中发生在系统准备进入目标状态之前。

TPCA 定义总体前置控制架构。

PCN 设置在明确的目标状态入口前，接收多源状态信号，完成 C / A / E 状态映射、S / D / B 判定和 CAE-SDB Result 生成，经控制仲裁后输出相应的多路径控制，并记录 PCN Trace。

其判定与控制主链可以概括为：

```text
当前状态
→ 目标状态
→ PCN
→ 多源状态信号
→ C / A / E 状态映射
→ S / D / B 判定
→ CAE-SDB Result + T
→ 控制仲裁
→ 多路径控制
→ PCN Trace
```

其中，T 表示与本次状态和判定一起保留的时间信息，用于状态先后关系、动态时序判定和 PCN Trace。

TPCA 同时认为，真实运行中的状态迁移始终沿时间方向发生。即使后续状态内容与历史状态相同，由于时间位置不同，仍属于新的状态实例。

这一点将在后文作为状态迁移单向性的补充说明展开。

# 第 1 章 工程问题

制造现场通常已经具备多种控制和记录机制。

PLC 有顺序控制、互锁和状态位。

机器人有 Ready、自动模式、报警和动作完成反馈。

视觉系统有 OK / NG、置信度、位置和姿态。

安全系统有安全门、光栅、急停和安全回路。

MES / WCS 有任务、工单、派单、执行状态和日志。

HMI / SCADA 有报警画面、设备状态和趋势记录。

这些机制能够支撑基础运行，但当系统不能进入下一状态时，相关结果通常被简化为：

```text
OK / NG
Ready / Not Ready
True / False
允许 / 不允许
报警 / 正常
Waiting / Pending / Blocked
```

这些结果能够阻止不满足条件的动作，但未必能够直接说明：

- 问题来自对象条件、许可状态还是执行链接续；
- 当前状态是结构缺失、动态失效还是进入控制边界；
- Ready 是否只代表本机就绪；
- 任务是否真正具备进入目标执行路径的条件；
- 某个报警是源头问题还是后续结果；
- 下一步应等待、重识别、回流、协调、降级、禁止，还是人工确认。

# 第 2 章 TPCA / PCN 的基本架构

## 2.1 TPCA 的定位

TPCA（Transition Pre-Control Architecture），即状态迁移前置控制架构。

TPCA 面向系统进入目标状态、目标执行路径或目标物理执行阶段之前的前置判定与多路径控制，并把明确的目标状态入口作为前置控制的基本工程对象。

目标状态可以是：

- 自动化执行单元的下一物理执行阶段；
- 机器人单元的抓取、放置、回流或异常分流阶段；
- 压装、检测、搬送交接等工艺阶段；
- AGV / AMR 群控系统恢复到可持续协同执行状态；
- MES / WCS 中的目标执行路径；
- 生产 DX 中人员、设备、系统和流程之间的关键状态切换；
- 数字调用系统中的目标执行路径。

TPCA 关注：

- 进入目标状态前，条件是否成立；
- 许可是否成立；
- 进入以后执行链是否能够接续；
- 当前判定结构是否完整；
- 当前状态是否仍然有效；
- 是否进入控制边界；
- 多个判定结果如何形成最终控制路径；
- 本次状态迁移如何形成可追溯履历。

TPCA 不要求替代既有 PLC、状态机、SFC、Interlock、安全系统、MES 或 WCS。

其作用是：

> **当多个已有机制共同决定一次目标状态进入时，围绕同一个目标状态入口形成明确的前置判定、控制和履历。**

## 2.2 PCN 与 CAE-SDB 的层级关系

PCN（Pre-Control Node），即前置控制节点。

PCN 是 TPCA 的最小工程节点。

PCN 部署在一个明确的目标状态入口前，围绕本次目标状态进入组织输入、判定、仲裁、控制和履历。

CAE-SDB 是 PCN 内部的结构化判定逻辑。

C / A / E 表示状态变量域：

- C = Condition，条件状态；
- A = Authority，许可状态；
- E = Execution Chain，执行链状态。

S / D / B 表示判定性质：

- S = Structure，结构完整性；
- D = Dynamics，动态时序有效性；
- B = Boundary，控制边界。

因此，当前层级关系为：

```text
TPCA
→ PCN
→ CAE-SDB
→ 控制仲裁
→ 多路径控制
→ PCN Trace
```

TPCA 定义总体架构。

PCN 承载一次具体目标状态入口的前置控制。

CAE-SDB 完成结构化判定。

控制仲裁处理多个判定结果与控制约束之间的优先关系。

多路径控制形成最终工程输出。

PCN Trace 记录本次状态迁移的判定与执行履历。

## 2.3 基本工程链条

TPCA / PCN 的基本工程链条如下：

```text
当前状态 / 当前阶段
→ 目标状态 / 目标阶段
→ PCN
→ 多源状态信号
→ C / A / E 状态映射
→ S / D / B 判定
→ CAE-SDB Result + T
→ 控制仲裁
→ 多路径控制
→ PCN Trace
→ 复盘、改善与再部署
```

![TPCA 的基本处理链条](/images/tpca/02-tpca-process-chain.png)

图2：TPCA 从当前状态、目标状态和多源状态出发，经 PCN 完成结构化判定、控制仲裁、多路径控制和判定履历记录。

在这条链中，False、NG、Not Ready、Pending 等结果不再作为判定终点。

系统继续判断：

- 问题属于哪个变量域；
- 属于哪种判定性质；
- 多个结果之间如何形成最终控制结论；
- 最终进入哪一条控制路径；
- 本次状态迁移如何形成可追溯履历。

## 2.4 状态迁移单向性

TPCA 面向真实运行中的状态迁移。

在实际工程系统中，状态迁移始终沿时间方向发生。

例如：

```text
A
→ B
→ C
```

如果 C 的工程状态内容与 A 相同，也不表示系统真正回到了 A。

原因是两者发生在不同时间。

因此：

> **状态内容可以再次相同，但状态实例已经不同。**

这意味着，工程中常用的：

- 回流；
- 回退；
- Return；
- Rollback；
- Recovery；
- 复归；
- 重新投入；

仍然可以作为控制路径或工程动作名称保留。

但从 TPCA 的状态迁移视角看，它们都属于：

```text
Current State
→ New Target State
```

新的目标状态可以与历史状态具有相同或相似的工程内容，但仍然是新的状态实例。

这一原则可以概括为：

> **状态类型可以循环，状态实例只能向前。**

状态迁移单向性并不改变 PCN、CAE-SDB、控制仲裁和多路径控制的基本结构。

它只是进一步说明：

> **TPCA 中所有实际控制最终都表现为从当前状态进入新的目标状态。**

详细讨论可参见：

[TPCA 的状态迁移单向性——为什么真实工程系统不存在状态回退？](/zh/notes/tpca-unidirectional-state-transition/)

# 第 3 章 PCN：状态迁移前置控制的最小工程节点

## 3.1 PCN 的定义

PCN 是部署在明确目标状态入口之前的前置控制节点。

一个 PCN 对应一个明确的目标状态入口。

其主要职责包括：

- 获取当前状态和目标状态；
- 读取与本次状态迁移相关的多源状态信号；
- 读取必要的时间、对象和版本信息；
- 对状态进行必要的标准化整理；
- 完成 C / A / E 状态映射；
- 完成 S / D / B 判定；
- 形成一个或多个 CAE-SDB Result；
- 对多个判定结果进行控制仲裁；
- 输出最终多路径控制；
- 记录 PCN Trace。

PCN 将 TPCA 从总体架构落实为可配置、可部署、可显示、可记录和可复盘的工程节点。

相关阅读：

[为什么 PCN 是 TPCA 的最小工程节点？](/zh/notes/pcn-minimum-engineering-unit/)

## 3.2 PCN 设置在什么位置

PCN 位于当前状态与目标状态之间：

```text
当前状态
→ PCN
→ 目标状态
```

![PCN 前置控制节点的位置与工作方式](/images/tpca/04-pcn-node-position.png)

图3：PCN 位于当前状态与目标状态之间，在进入目标状态之前完成状态组织、结构化判定、控制仲裁和控制路径输出。

在自动化执行单元中，PCN 可以设置在：

- 等待阶段 → 抓取阶段之前；
- 放置完成 → 压装阶段之前；
- 待检测 → 检测执行之前；
- 搬送待机 → 交接阶段之前；
- 正常路径、回流路径、异常分流路径切换之前。

在 MES / WCS 协同系统中，PCN 可以设置在：

- 任务进入执行路径之前；
- 区域放行之前；
- 站点承接之前；
- 主体进入有效执行状态之前；
- 群控系统恢复可持续协同执行状态之前。

在生产 DX 中，PCN 可以设置在人员、设备、系统和流程之间的关键状态切换入口。

PCN 的设置位置由目标状态入口决定，而不是由设备名称或系统类型决定。

## 3.3 PCN 的基本分析模板

一个 PCN 的工程描述至少应明确以下项目。

| 分析项 | 内容 |
|---|---|
| 当前状态 / 当前阶段 | 系统当前处于什么状态 |
| 目标状态 / 目标阶段 | 系统准备进入什么状态 |
| PCN 设置位置 | 前置控制节点位于哪个目标状态入口 |
| 触发时机 | 什么时候启动本次前置判定 |
| 多源状态信号 | 本次迁移需要读取哪些状态 |
| 时间 / 版本 / 对象信息 | 当前状态是否与本次对象、时序和版本对应 |
| C 条件状态 | 哪些状态用于判断进入条件 |
| A 许可状态 | 哪些状态用于判断是否允许进入 |
| E 执行链状态 | 哪些状态用于判断进入以后是否能够接续 |
| S 结构判定 | 所需信号、接口、映射、许可来源和执行链边界是否完整 |
| D 动态判定 | 当前状态是否有效、同步、未超时、可信 |
| B 控制边界 | 当前状态是否进入预设控制边界 |
| CAE-SDB Result | 本次判定形成了哪些结构化结果 |
| 时间信息 T | 标识本次状态与判定的时间位置 |
| 控制仲裁 | 多个结果如何形成最终控制结论 |
| 多路径控制 | 最终进入哪一条控制路径 |
| PCN Trace | 记录本次输入、判定、控制和执行结果 |

不同现场的设备、信号和接口可以不同，但 PCN 的基本工程结构保持一致。

PCN 不需要接收所有现场数据。

纳入 PCN 的状态应与本次目标状态进入直接相关，并能够参与 C / A / E 映射、S / D / B 判定或最终控制路径选择。

关于适用对象和工程边界，可参见：

[TPCA / PCN 适用场景分析](/zh/notes/tpca-pcn-applicable-scenarios/)

## 3.4 PCN 节点示例

以机器人由等待阶段进入抓取阶段为例。

当前阶段：机器人等待，主输送带输送工件，视觉系统完成识别。

目标阶段：机器人进入抓取阶段。

PCN 设置位置：抓取动作真正启动之前。

相关状态可以来自视觉系统、机器人控制器、安全系统、输送系统、下游投放位、返回路径、异常分流路径和上位系统。

C 条件状态可以包括：

- 工件是否存在；
- 位置是否合格；
- 姿态是否合格；
- 视觉结果是否有效。

A 许可状态可以包括：

- 安全许可；
- 区域许可；
- 上位生产许可；
- 本次动作许可；
- 必要人工确认。

E 执行链状态可以包括：

- 机器人路径是否可达；
- 夹爪是否可用；
- 正常投放位是否可承接；
- 返回路径是否可用；
- 异常分流路径是否可用；
- 回退路径是否存在；
- 结果是否能够回写。

这里继续保留“返回路径”“回流路径”“回退路径”等现场工程术语。

这些术语描述的是路径用途。

当系统实际进入这些路径时，在 TPCA 中仍然表现为：

```text
当前状态
→ 新的目标状态 / 目标执行路径
```

随后对相关状态进行 S / D / B 判定，形成 CAE-SDB Result，并经控制仲裁生成最终多路径控制。

## 3.5 多个 PCN 形成 PCN Network

单个 PCN 对应一个明确的目标状态入口。

复杂工程系统通常包含多个连续、并行或相互依赖的目标状态入口。

多个 PCN 按实际状态迁移关系以及许可、资源和执行依赖关系连接后，可以形成 PCN Network。

例如，在自动化执行单元中，可以存在：

```text
等待 → 抓取
抓取完成 → 搬送
搬送完成 → 投放
投放完成 → 后续处理
```

每一个关键入口都可以形成独立 PCN。

在 MES / WCS 协同系统中，也可以围绕任务执行、区域进入、站点承接、资源释放、下游接续和结果回写等目标状态入口形成多个 PCN。

PCN Network 描述的是目标状态入口及其工程关系。

其状态类型关系可以存在循环，但实际运行中的状态迁移仍然沿时间方向持续生成。

因此：

> **PCN Network 可以存在状态类型上的循环关系，实际状态实例不存在真正的状态回退。**

PCN Network 使工程师能够进一步观察：

- 哪些目标状态入口频繁出现问题；
- 哪些许可长期成为阻断点；
- 哪些执行链反复无法接续；
- 哪些控制路径经常触发；
- 哪些节点之间反复出现许可、资源或执行依赖；
- 哪些工程修改以后状态迁移表现发生变化。

[多个 PCN 如何形成状态迁移前置控制网络？](/zh/notes/pcn-network-structure/)

## 3.6 PCN 的部署方式

PCN 的部署不要求一次性重构既有控制系统。

实际部署可根据项目阶段逐步推进。

### 旁路诊断

读取历史日志、准实时状态或导出数据，形成结构化判定和履历，用于验证方法的分析价值。

### 结构化显示

将 PCN 判定结果用于 HMI、MES / WCS 页面、事件报告或复盘记录。

### 建议性控制

根据判定结果和控制仲裁，向工程师或上位系统提供建议控制路径。

### 工程嵌入

在符合安全、控制规范和验证要求的前提下，将部分 PCN 前置判定与控制逻辑嵌入 PLC / HMI、WCS、边缘控制器或软件平台。

不同部署方式可以对应不同项目阶段。

PCN 与既有 PLC、SFC、Interlock、安全系统、MES 和 WCS 形成工程分工，不替代这些成熟机制。

# 第 4 章 C / A / E 状态映射与 S / D / B 判定

## 4.1 C = Condition，条件状态

C 表示进入目标状态前，与本次目标状态进入相关的事实条件是否成立。

在自动化执行单元中，可以包括：

- 工件是否存在；
- 位置是否合格；
- 姿态是否合格；
- 视觉结果是否有效；
- 识别置信度是否满足；
- 前序动作是否完成；
- 工艺参数是否完整。

在 MES / WCS 协同系统中，可以包括：

- 任务是否存在；
- 任务目标是否明确；
- 物料需求是否有效；
- 目标站点是否定义；
- 缓存区是否可用；
- 订单、工艺和现场条件是否满足。

## 4.2 A = Authority，许可状态

A 表示系统是否允许进入目标状态。

可以包括：

- 安全许可；
- 区域许可；
- 上位系统放行；
- 人工确认；
- 资源锁；
- 任务分配许可；
- 对方设备接收许可；
- 权限或授权状态；
- 调度系统放行；
- 质量或工艺放行。

关键 A 可以构成独立必要约束。

关键许可不成立时，即使 C 和 E 均成立，也不得进入目标状态。

## 4.3 E = Execution Chain，执行链状态

E 表示进入目标状态以后，整个执行链是否能够继续接续。

E 的工程范围不等同于单体 Ready。

在自动化执行单元中，可以包括：

- 机器人路径是否可达；
- 夹爪、真空或治具是否可用；
- 下游放置位是否可承接；
- 返回路径是否可用；
- 异常分流路径是否可用；
- 回退路径是否存在；
- 结果上传或回写是否可继续。

在 AGV / AMR 群控系统中，可以包括：

- 主体是否能够执行任务；
- 路径是否可通行；
- 站点是否可承接；
- 共享资源是否可用；
- 能源补给是否影响执行能力；
- 下游是否能够继续承接；
- 结果状态是否能够回写。

“返回”“回流”“回退”等术语在 E 中表示后续执行链的工程路径。

这些路径在实际运行中仍属于新的目标状态或目标执行路径。

E 关注的是：

> **进入目标状态以后，后续执行链是否能够继续接续。**

## 4.4 S = Structure，结构完整性

S 判断目标状态进入所需要的结构是否已经定义、接入并可观测。

典型内容包括：

- 所需信号；
- 接口；
- 映射关系；
- 许可来源；
- 路径；
- 角色；
- 执行链边界。

例如：

- 视觉结果已经存在，但时间信息没有接入；
- 下游状态存在，但没有纳入目标状态进入判定；
- 资源锁存在，但来源和释放状态不可观测；
- 异常分流路径存在，但没有进入执行链定义。

## 4.5 D = Dynamics，动态时序有效性

D 判断相关状态在本次目标状态进入中是否仍然有效、同步和可信。

典型问题包括：

- 超时；
- 未刷新；
- 抖动；
- 冲突；
- 延迟；
- 不同步；
- 低置信度；
- 许可撤销；
- 状态切换；
- 对象或版本不一致。

例如：

- 视觉结果曾经成立，但已经超过有效时间；
- 下游 Ready 长时间未刷新；
- 上位许可在多个周期内反复成立和撤销；
- WCS 显示任务已经派发，但主体状态仍未进入执行。

D 判定可以使用时间戳、更新时间、序列、版本和对象关联等信息，判断某个 C、A 或 E 状态当前是否仍可作为本次目标状态进入的有效依据。

## 4.6 B = Boundary，控制边界

B 判断 C / A / E 相关状态是否已经进入预先定义的控制边界。

用于边界判定的工程参数可以包括：

- 时间窗口；
- 重试上限；
- 信号有效时间；
- 识别置信度范围；
- 位置和姿态偏差范围；
- 容量边界；
- 资源占用边界；
- 其他与目标状态进入相关的边界参数。

B 的具体判定边界由目标状态、风险等级、设备特性、工艺条件和控制策略决定。

B 本身不是控制路径。

达到某一边界以后，系统最终进入等待、重新采样、回流、人工确认、禁止进入或其他控制路径，需要结合完整判定结果继续进行控制仲裁。

## 4.7 时间信息 T

PCN 所使用的状态并非静态不变。

在进入目标状态之前，多源状态会持续更新。

例如：

| 时间点 | C 条件状态 | A 许可状态 | E 执行链状态 | 说明 |
|---|---|---|---|---|
| T0 | C(T0) | A(T0) | E(T0) | 当前采样 |
| T1 | C(T1) | A(T1) | E(T1) | 状态继续刷新 |
| T2 | C(T2) | A(T2) | E(T2) | 状态可能稳定、撤销、冲突或失效 |
| Tn | C(Tn) | A(Tn) | E(Tn) | 进入目标状态前的当前判定依据 |

现场经常出现：

- 视觉结果在 T0 有效，后续已经失效；
- 安全许可在 T0 成立，T1 被撤销；
- 下游 Ready 在 T0 成立，后续长期未刷新；
- 任务存在，但资源锁未释放；
- 主体处于自动模式，但有效执行能力持续下降。

因此，每次 CAE-SDB 判定同时保留对应的时间信息 T，用于：

- 标识本次状态与判定所处的时间位置；
- 判断状态的先后关系；
- 支持 D 的动态时序有效性判断；
- 形成 PCN Trace。

根据具体系统，T 可以对应：

- Timestamp；
- 更新时间；
- 事件时间；
- 序列时间；
- 批次时间；
- 其他足以确定状态先后关系的时间信息。

## 4.8 CAE-SDB 的组合关系

C / A / E 表示状态变量域。

S / D / B 表示判定性质。

两者组合形成 CAE-SDB 判定结构。

| 判定性质 / 状态变量域 | C 条件 | A 许可 | E 执行链 |
|---|---|---|---|
| S 结构完整性 | 条件状态所需信号、接口和映射是否完整 | 许可来源、接口和关系是否完整 | 下游、回退、异常路径和回写链路是否完整 |
| D 动态时序有效性 | 条件状态是否超时、抖动、冲突、未刷新 | 许可是否延迟、撤销、冲突、未同步 | 执行链是否阻塞、反馈超时、状态未刷新或切换中 |
| B 控制边界 | 条件状态是否进入预设边界 | 许可状态是否进入预设边界 | 执行链状态是否进入预设边界 |

![CAE-SDB 正交判定结构](/images/tpca/03-cae-sdb-matrix.png)

图4：C / A / E 表示状态变量域，S / D / B 表示判定性质，组合后形成 CAE-SDB Result。

CAE-SDB Result 不是最终控制动作。

同一次状态迁移可以形成多个判定结果。

这些结果经控制仲裁后，再形成最终多路径控制。

# 第 5 章 CAE-SDB Result、控制仲裁与多路径控制

## 5.1 从判定结果到控制路径

PCN 内部形成的控制链为：

```text
CAE-SDB Result + T
→ 控制仲裁
→ 多路径控制
→ 执行结果
→ PCN Trace
```

CAE-SDB Result 说明：

> **问题位于哪个状态变量域，以及属于什么判定性质。**

控制仲裁用于处理：

> **多个判定结果、关键许可和控制约束同时存在时，最终应形成什么控制结论。**

多路径控制将控制结论转化为实际工程路径。

代表性路径包括：

- 允许进入；
- 等待；
- 重识别；
- 重采样；
- 重定位；
- 回流；
- 返回；
- 回退路径；
- 异常分流；
- 下游协调；
- 资源释放；
- 任务重新分配；
- 降级执行；
- 备用路径；
- 禁止进入；
- 安全锁定；
- 人工确认；
- 异常隔离；
- 增强记录。

这些术语继续保留其现场工程含义。

从 TPCA 的状态迁移视角看，多路径控制的共同本质是：

> **根据当前判定结果，确定系统下一步应进入的目标状态或目标执行路径。**

因此，“回流”“返回”“回退”描述的是路径用途，不表示状态真正回到过去。

## 5.2 CAE-SDB Result

代表性判定结果包括：

| 判定结果 | 含义 |
|---|---|
| C-S | 条件域存在结构完整性问题 |
| C-D | 条件域存在动态时序有效性问题 |
| C-B | 条件域进入控制边界 |
| A-S | 许可域存在结构完整性问题 |
| A-D | 许可域存在动态时序有效性问题 |
| A-B | 许可域进入控制边界 |
| E-S | 执行链域存在结构完整性问题 |
| E-D | 执行链域存在动态时序有效性问题 |
| E-B | 执行链域进入控制边界 |

同一次目标状态进入判定中可以同时存在多个 CAE-SDB Result。

## 5.3 控制仲裁的基本原则

公开白皮书只说明控制仲裁的基本原则。

关键 A 可以构成独立必要约束。

关键许可不成立时，不允许进入目标状态。

关键结构缺失时，不能默认相关状态已经成立。

关键动态状态失效时，不能继续把已经超时、未刷新、冲突或不同步的状态作为放行依据。

当多个 CAE-SDB Result 同时存在时，需要经过控制仲裁，再生成最终多路径控制。

只有必要条件、关键许可和执行链接续均满足，并且不存在更高优先级的限制结果时，才允许进入目标状态。

当不能进入原目标状态时，控制仲裁可以根据完整判定结果选择等待、回流、重新识别、人工确认、安全状态或其他目标状态 / 目标执行路径。

完整仲裁规则、内部运行生命周期、配置结构和具体控制参数不属于本公开白皮书范围。

## 5.4 PCN Trace

PCN 在完成判定和控制的同时，可以形成 PCN Trace。

在公开层面，PCN Trace 可从以下内容理解：

| 记录内容 | 作用 |
|---|---|
| 当前状态 / 当前阶段 | 明确系统当时处于什么状态 |
| 目标状态 / 目标阶段 | 明确系统准备进入哪里 |
| 关键输入状态 | 记录与本次迁移直接相关的状态 |
| 时间信息 T | 记录本次状态与判定的时间位置 |
| 版本 / 对象信息 | 记录状态版本与对象关联 |
| C / A / E 状态映射 | 记录状态变量域 |
| S / D / B 判定 | 记录判定性质 |
| CAE-SDB Result | 记录结构化判定结果 |
| 控制仲裁结果 | 记录最终控制结论的形成结果 |
| 多路径控制 | 记录最终控制路径 |
| 执行结果 | 记录控制以后实际发生了什么 |
| Trace ID | 关联同一次状态迁移判定履历 |

PCN Trace 的价值不在于增加日志数量，而在于将一次状态迁移判定作为完整的工程数据对象记录下来。

它可以进一步区分：

- 状态内容相同但发生时间不同的状态；
- 相同 Ready 状态下不同的迁移历史；
- 同一状态类型经过不同路径形成的实际状态实例。

相关阅读：

[为什么 PCN Trace 是一种新的工程数据？](/zh/notes/why-pcn-trace-is-engineering-data/)

## 5.5 复盘与改善

PCN Trace 可以进一步用于观察：

- 哪些目标状态入口频繁出现问题；
- 哪些条件状态长期失效；
- 哪些许可经常阻断；
- 哪些执行链经常不能接续；
- 哪些动态问题长期反复；
- 哪些控制边界经常进入；
- 哪些控制路径经常触发；
- 哪些状态类型反复出现，但对应实际状态具有不同迁移历史；
- 某次工程修改以后，状态迁移表现发生了什么变化。

因此，TPCA / PCN 不仅服务于当前状态迁移控制，也可以为后续设计改善、设备复用、工程培训、项目交接和生产 DX 提供结构化履历。

AI 可以基于 PCN Trace 辅助开展履历比较、模式分析、候选改善方向整理和报告生成。

AI 分析不替代 PCN 或既有现场控制逻辑承担确定性控制职责。

## 6.1 自动化执行单元

自动化执行单元的典型对象包括：

- 机器人抓取；
- 压装；
- 检测；
- 搬送交接；
- 视觉识别输送线；
- 上下料单元；
- PLC / HMI 自动化单元。

典型问题包括：

- 机器人 Ready，但不能抓取；
- 视觉结果曾经 OK，但已经失效；
- 安全许可未成立；
- 压装头 Ready，但搬送机构未撤离；
- 检测设备 Ready，但结果回写链路不可用；
- 下游显示 Ready，但实际不能承接；
- 回流或异常路径存在，但没有进入目标阶段判定。

PCN 设置在目标物理执行阶段进入之前，对多源状态进行 C / A / E 映射和 S / D / B 判定，形成 CAE-SDB Result，经控制仲裁输出多路径控制。

在异常发生后，如果系统进入安全停止、退避、回流、重新识别或重新投入等路径，这些过程仍然按照新的目标状态入口继续组织。

## 6.2 MES / WCS 协同停滞

在 AGV / AMR、多设备协同、WCS、MES、缓存区、站点、共享资源和下游工位之间，单体设备正常并不代表群体能够持续执行。

典型问题包括：

- 任务存在，但主体没有有效执行；
- 多个主体长期处于 Waiting、Blocked、Idle、Pending；
- 主体集中等待共享资源；
- 资源锁未释放；
- 区域许可未成立；
- 下游站点不能承接；
- 能源补给集中导致可执行主体比例下降；
- MES / WCS 有记录，但现场仍需人工跨系统查日志。

群控协同层 PCN 汇总多源状态，进行 C / A / E 映射、S / D / B 判定，并结合群体指标进行停滞识别和结构分析。

代表性控制或诊断输出可以包括：

- 分配约束；
- 资源竞争；
- 能源偏在；
- 未确定状态；
- 等待；
- 任务重新分配；
- 资源释放；
- 路径或通行权协调；
- 限流；
- 下游协调；
- 人工确认；
- 增强记录。

## 6.3 生产 DX

生产 DX 通常从数据采集、可视化、报表和看板建设开始。

TPCA / PCN 在此基础上进一步关注：

> **这些数据如何参与一个明确目标状态入口的工程判定。**

例如：

- 人工确认完成后是否允许自动恢复；
- 工单切换后是否允许进入目标生产状态；
- 保全解除后是否允许重新投入；
- 质量放行后是否允许进入下一处理路径；
- 多系统状态是否已经形成可接续执行链。

这里的“恢复”“重新投入”等工程术语仍然保留。

从 TPCA 的状态迁移视角看，它们表示从当前状态进入新的目标状态。

PCN 可以把原本分散在设备、系统、人员和流程中的状态迁移条件显式化，并形成判定、控制和履历。

## 6.4 数字调用治理扩展

TPCA / PCN 也可以扩展到数字调用治理场景。

例如：

- AI 推理调用；
- 工具调用；
- 企业知识库访问；
- API 调用；
- 外部服务调用；
- 智能体调用链；
- 高成本模型调用。

请求已经生成，并不等于目标执行路径已经成立。

仍然需要判断：

- 请求条件是否满足；
- 权限、预算、租户授权或工具调用许可是否成立；
- 模型、工具链、接口服务或队列资源是否可执行；
- 最终应进入高成本路径、澄清路径、降级路径、等待路径还是阻断路径。

这一方向属于 TPCA / PCN 的扩展应用。

制造系统中的主要应用仍然是自动化执行单元前置控制、MES / WCS 协同停滞和生产 DX 跨系统状态迁移。

相关说明：

# 结语

复杂制造系统的问题并不只来自设备、信号和日志数量的增加。

随着系统复杂度提高，需要管理的目标状态入口也随之增加。

TPCA 定义状态迁移前置控制的总体架构。

PCN 设置在明确的目标状态入口之前，把与本次状态迁移相关的多源状态组织为 C / A / E 状态变量，通过 S / D / B 进行判定，形成 CAE-SDB Result，再经过控制仲裁输出最终多路径控制，并通过 PCN Trace 记录本次状态迁移履历。

因此，当前体系的核心关系可以概括为：

```text
TPCA = 状态迁移前置控制架构

PCN = 前置控制节点

CAE-SDB = PCN 内部结构化判定逻辑

T = 与状态和 CAE-SDB Result 一起保留的时间信息

控制仲裁 = 多判定结果与控制约束的控制结论形成过程

多路径控制 = 面向下一目标状态 / 目标执行路径的工程输出

PCN Trace = 状态迁移判定履历
```

TPCA / PCN 不替代 PLC、SFC、Interlock、安全系统、MES 或 WCS。

TPCA / PCN 补充的是：

> **一次明确的目标状态入口，应当成为可以被独立设计、判定、控制和记录的工程对象。**

围绕这一工程对象，TPCA / PCN 将原本分散的状态组织为可判定、可控制和可追溯的前置控制结构。

TPCA 同时保留状态与判定的时间信息。

因此，即使后续状态与历史状态具有相同工程内容，也仍然属于新的状态实例。

这使正常执行、回流、回退、复归、降级、异常处理和重新投入可以在不改变现场工程术语的前提下，被统一理解为：

```text
Current State
→ New Target State
```

单个 PCN 可以独立设计、部署和复盘。

多个 PCN 按实际状态迁移关系以及许可、资源和执行依赖关系连接后，可以进一步形成 PCN Network。

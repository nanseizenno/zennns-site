## 1. 現場問題

製造 DX プロジェクトでは、通常すでに大量の生産データや運転データを取得できる。

MES は作業指示、ロット、計画、生産実績を記録できる。品質システムは検査結果、品質判定、品質承認状態を記録できる。PLC や設備制御システムは、自動モード、設備 Ready、アラーム、Interlock、動作状態を提供できる。人員システムは、本人確認と権限を管理できる。保全システムは、修理、点検、復旧を記録できる。下流設備、搬送システム、バッファエリアも、受入、占有、運転状態を提供できる。

しかし、現場では依然として次のような問題が発生することがある。

- 前工程は完了しているが、次工程がなかなか開始されない；
- MES 上では作業指示が有効で、設備も Ready だが、現在の製品またはロットが次の段階へ進めない；
- 品質結果はすでに生成されているが、現在のロットが正式に品質承認されたかどうかを確認できない；
- 検査結果が NG でも、手直し、回流、廃棄処理、隔離工程へ接続できるかどうかをさらに判断する必要がある；
- 保全作業は完了しているが、設備を生産へ再投入できるかどうかを確認する必要がある；
- 作業指示は切り替わっているが、PLC レシピ、材料、品質結果、トレーサビリティ情報が完全には同期していない；
- 下流は受入可能と表示されているが、その状態が現在も有効かどうかをすぐに確認できない；
- 複数システムに状態記録が存在していても、現在対象をどの後続生産工程へ進めるべきか、依然として人が複数システムを横断してプログラム、状態、履歴を確認する必要がある。

問題は多くの場合、データが不足していることではなく、

> **現在対象がどの Current State からどの Target State へ進むのか、またその Target State Entry 前に必要な条件、許可、実行チェーンが、同じ Target State Entry を中心として統一されたエンジニアリング設計になっていないこと**

にある。

たとえば、

```text
MES 作業指示 = 有効
品質結果 = 合格
設備 = Ready
オペレータ = 確認済み
下流 = 受入可能
```

という局所状態がすべて同時に成立していたとしても、直接、

```text
現在対象の次生産工程への進入を許可
```

と結論付けることはできない。

さらに、次の事項を確認する必要がある。

- 品質結果が現在ロットに属しているか；
- 品質承認が成立しているか；
- 作業指示、レシピ、材料、設備モードが一致しているか；
- 保全解除が成立しているか；
- 人による確認が必要な権限を持っているか；
- 下流状態が現在も有効か；
- Target State へ進入した後、実行チェーン全体が継続して接続できるか；
- 本判定結果を追跡可能な状態遷移履歴として残せるか。

したがって、本事例では、

> **明確な生産 Target State Entry を中心として、複数システムに分散している状態を、判定・制御・記録可能な生産状態遷移のエンジニアリング構造として整理すること**

を対象とする。

## 2. 事例の位置付けと PCN の位置

本事例では、生産プロセスにおける複数システム横断の状態遷移を対象とする。

ある生産段階が完了した後、現在対象は複数の後続工程へ進む可能性がある。

```text
前工程完了 → 次生産工程

検査完了 → 手直し工程

検査完了 → 回流工程

検査完了 → 廃棄処理工程

検査完了 → 隔離工程

保全完了 → 自動生産へ再投入
```

これらの経路はいずれも、明確な生産状態遷移に対応する。

手直し、回流、廃棄処理、隔離、再投入などの名称は、そのまま現場におけるエンジニアリング上の意味を維持する。

TPCA の状態遷移視点では、これらはいずれも、

```text
Current State → New Target State / Target Path
```

を表す。

後続で過去と同じ、または類似したエンジニアリング状態内容が再び現れた場合でも、それは新しい状態インスタンスである。

ここで TPCA / PCN が対象とするのは、

> **Current State から Target State、目標実行経路、または目標生産段階へ進入する前に、必要な条件、許可、実行チェーンが成立しているか**

という問題である。

PCN は、明確な Target State Entry の前に配置する。

基本的なエンジニアリングチェーンは次の通りである。

```text
Current State
→ Target State
→ PCN
→ 複数ソース状態信号
→ C / A / E 状態マッピング
→ S / D / B 判定
→ CAE-SDB Result + T
→ Arbitration
→ Multipath Control
→ PCN Trace
```

たとえば、システムが「検査完了」の Current State にある場合、後続の Target State は、次生産工程、手直し工程、回流工程、廃棄処理工程、隔離工程などになり得る。

PCN は、現在対象、Target State、関連する複数ソース状態に基づいて前判定を行い、対応する生産経路の制御結果を形成する。

PCN の具体的な実装は、MES、製造実行ミドルウェア、産業用エッジシステム、PLC / HMI 協調モジュール、その他のソフトウェアコンポーネントで実現できる。

本事例では、具体的な配置プラットフォームは限定しない。

## 3. 複数ソース状態信号と C / A / E 状態マッピング

代表的な状態を以下に示す。

| 情報源 | 代表的な状態 |
|---|---|
| MES | 作業指示状態、ロット番号、製品型式、生産許可、レシピ番号 |
| 品質システム | 検査完了、品質結果、品質承認、手直し判定、廃棄判定、隔離状態 |
| PLC / 設備 | 自動モード、設備 Ready、現在工程段階、レシピ読込、動作完了、設備アラーム |
| 保全システム | 点検完了、修理完了、保全解除、再投入許可 |
| 人員 / 権限システム | オペレータ本人確認、資格、権限、人による確認 |
| 材料 / トレーサビリティシステム | 材料 ID、ロット関連付け、トレーサビリティ識別子、前工程結果との関連付け |
| 下流 / 搬送システム | 下流受入可能、バッファ容量、搬送可用、引渡し許可 |
| データインターフェース | 状態更新時刻、状態バージョン、シーケンス情報、書戻し完了、インターフェース利用可能、同期完了 |

これらの状態は、本 Target State Entry におけるエンジニアリング上の役割に基づいて C / A / E へマッピングされる。

| 変数領域 | 判定する問題 | 本事例における代表項目 |
|---|---|---|
| C：Condition | Target State へ進入するために必要な事実条件が成立しているか | 作業指示有効、ロット正しい、前工程完了、品質結果あり、材料とレシピ一致、トレーサビリティ関係有効 |
| A：Authority | システムとして Target State への進入が許可されているか | 品質正式承認、生産許可、保全解除、人員権限、人による確認、特別承認 |
| E：Execution Chain | Target State へ進入した後、実行チェーンが継続できるか | 設備実行、下流受入、搬送、バッファ、手直し、回流、廃棄処理、隔離、結果アップロード、トレーサビリティ書戻し |

C / A / E は、システムの情報源によって分類するのではなく、本状態遷移におけるエンジニアリング上の役割によって分類する。

同一システムが C、A、E に必要な状態を同時に提供する場合もある。同じ状態でも、Target State Entry が異なれば、異なるエンジニアリング上の役割を持つ場合がある。

### 品質結果と品質承認

たとえば、

```text
品質結果 = 合格
```

であり、Target State が「次生産工程」である場合、この結果は C における事実条件として扱うことができる。

一方、

```text
品質承認 = 承認済み
```

は、正式な許可が成立していることを表し、A に属する。

したがって、

> **品質結果が成立していることと、品質承認が成立していることは同じではない。**

### 品質 NG と Target State

たとえば、

```text
品質結果 = NG
```

であっても、そのエンジニアリング上の意味は具体的な Target State によって異なる。

Target State が「次の正常生産工程」である場合、品質 NG は関連する C 条件が成立していないことを意味し得る。

一方、Target State が「手直し工程」である場合、品質 NG は逆に手直し工程へ進入するために必要な C 条件の一つとなり得る。

同様に、回流、廃棄処理、隔離についても、それぞれ対応する Target State を中心として C / A / E を構成する必要がある。

したがって、

> **状態のエンジニアリング上の意味は、Current State、Target State、具体的な Target State Entry から切り離して単独では解釈できない。**

### 設備 Ready と実行チェーン

設備 Ready は、設備本体が局所的な運転条件を満たしていることを示すにすぎない。

下流が受入できない、搬送が利用できない、バッファが満杯、手直し工程へ接続できない、廃棄処理工程が利用できない、隔離場所が利用できない、結果書戻し経路が継続できない場合、E：Execution Chain が成立しているとはみなせない。

## 4. S / D / B 判定

C / A / E 状態マッピングを完了した後、PCN はさらに S / D / B の 3 つの判定性質から分析する。

| 判定性質 | 判定する問題 | 本事例における代表項目 |
|---|---|---|
| S：Structure | 必要な信号、インターフェース、マッピング関係、許可元、実行チェーン境界が定義・接続されているか | ロットと品質結果のマッピング、品質承認元、保全解除元、手直し / 回流 / 廃棄処理 / 隔離工程インターフェース |
| D：Dynamics | 現在状態が有効で、同期され、タイムアウトしておらず、取消されておらず、競合していないか | 作業指示切替、レシピ同期、許可取消、状態未更新、状態失効、バージョン不一致、インターフェース遅延 |
| B：Boundary | 現在状態が事前定義された制御境界に入っているか | 待ち時間、同期時間、人による確認の有効期限、バッファ容量、リトライ上限、手直し回数 |

### 状態値が成立していることと、現在も有効であることは同じではない

製造 DX では、複数ソース状態は通常異なるシステムから取得され、各システムの取得周期、更新時刻、状態保持方式は一致しない。

したがって、PCN は単に、

```text
品質結果 = 合格
下流 = 受入可能
保全解除 = 成立
人による確認 = 完了
```

という値を読み取るだけでは不十分である。

さらに、それらの状態が**現在対象および本 Target State Entry に対して現在も有効な状態であるか**を判断する必要がある。

たとえば、

```text
品質結果 = 合格
```

という状態であっても、その結果が現在製品または現在ロットに属しており、状態バージョン、更新時刻、有効範囲が本状態遷移の要求を満たしていることを確認できて初めて、現在の C 条件に対する有効な判定根拠として使用できる。

同様に、

```text
下流受入可能 = 成立
```

という状態でも、長時間更新されていない、または下流状態切替前に生成された値である場合、現在読取値が成立したままであっても、E：Execution Chain が現在も継続可能であると直接判断することはできない。

したがって、製造 DX では、

```text
状態値が成立 ≠ 状態が現在も有効
```

を区別する必要がある。

PCN による状態判定では、現在値だけでなく、対象関連付け、更新時刻、更新状態、状態バージョン、シーケンス情報、必要な有効時間範囲などを組み合わせ、現在の有効性を判断する。

これは、すべてのシステムに同一の Timestamp や更新周期を要求するものではない。

MES、品質システム、PLC、保全システム、人員システム、下流システムは、それぞれ異なるデータ更新方式を使用できる。エンジニアリング上必要なのは、

> **本 Target State Entry に関係する状態が、現在有効であるかを判断するために十分な時間的意味を持つこと**

である。

この時間的意味は、システムの特性に応じて、状態更新時刻、バージョン番号、シーケンス情報、ロット番号、イベント識別子、更新状態、その他の追跡可能な情報によって提供できる。

これらは D：Dynamics の動的時系列有効性判定に含まれる。

本事例では、各状態および CAE-SDB Result とともに対応する時間情報 **T** を保持する。

T は Timestamp、更新時刻、イベント時刻などで表すことができ、本状態および判定の時間位置を示し、状態間の前後関係、継続時間、動的時系列有効性判定、PCN Trace を支援する。

具体的な有効時間、更新周期、同期ウィンドウ、失効条件は、実際の生産システム、工程要求、制御要求に応じて設定する必要がある。

### C-S

品質結果は存在するが、

```text
品質結果 ↔ 現在ロット
```

の明確な関連付けが定義されていない。

この場合、C 領域における構造完全性の問題となる。

### C-D

MES はすでに新しい作業指示へ切り替わっているが、PLC はまだ前のレシピを使用している、または現在品質結果が前ロットに属している場合がある。

また、関連する状態値自体は存在していても、本 Target State Entry で許容される有効範囲をすでに超えている、または異なるシステム間で状態バージョンやシーケンス関係が一致していない場合もある。

この場合、条件情報は存在しているが、現在状態が同期していない、または動的時系列有効性が不足している。

### A-S

Target State への進入に品質承認、保全解除、特定人員による確認が必要であるにもかかわらず、システム上で明確な許可元が定義されていない。

この場合、A 領域における構造完全性の問題となる。

### A-D

品質許可は一度成立したが、その後取り消された、または保全解除状態が変化したにもかかわらず、関連システムに旧状態が残っている場合がある。

また、人による確認、生産許可、その他の認可状態がすでに有効範囲を超えているにもかかわらず、システムが成立値を保持している場合もある。

この場合、許可元自体は存在しているが、現在の許可状態に必要な動的時系列有効性が不足している。

### E-S

手直し、回流、廃棄処理、隔離、下流受入、結果書戻しなどの実行経路は生産プロセス内に存在しているが、それらに必要な信号、インターフェース、役割、実行チェーン境界が完全には定義されていない。

この場合、E 領域における構造完全性の問題となる。

### E-D

下流は受入可能と表示されているが、長時間更新されていない場合がある。また、手直し設備、搬送システム、廃棄処理設備、隔離エリア、結果書戻しインターフェースが、現在切替中、遅延、閉塞状態にある場合もある。

ある状態値が正常を示していても、その更新時刻、状態バージョン、シーケンス関係、関連コンテキストから本 Target State Entry に現在も適用可能であることを確認できない場合、その実行チェーンが現在有効であると直接判断してはならない。

この場合、実行チェーン自体は定義されているが、現在も安定して接続可能であることを確認できない。

### B に関する判定

生産プロセスでは、さらに次のような状態が発生することがある。

- 状態同期待ちが事前設定時間に到達；
- 人による確認が有効期限に到達；
- 再読込またはリトライが事前設定回数に到達；
- 下流バッファが容量境界に接近；
- 作業指示切替が長時間安定しない；
- ある許可が再確認条件に到達；
- 手直し回数が事前定義された制御境界に到達。

これらの判定は CAE-SDB Result を形成し、さらに Arbitration へ進む。

## 5. 生産状態遷移と Multipath Control

同一の Current State は、複数の候補 Target State または生産経路に対応することがある。

たとえば、検査工程完了後、対象によって次のような工程へ進むことができる。

```text
次生産工程
手直し工程
回流工程
廃棄処理工程
隔離工程
```

各候補 Target State へ進入する前に、PCN はそれぞれ対応する C / A / E を構成し、S / D / B 判定を行う。

### 次生産工程へ進入

```text
Current State：前工程完了

Target State：次生産工程
```

関連する状態には、たとえば次のものがある。

```text
作業指示有効
品質結果合格
品質承認成立
設備実行可能
下流受入可能
トレーサビリティ関係有効
```

進入条件を満たすと判定された場合、

```text
CAE-SDB Result + T → Arbitration → Multipath Control → 進入許可
```

となり、現在対象は次生産工程へ進入する。

### 品質承認状態が同期していない場合

```text
Current State：前工程完了

Target State：次生産工程

品質結果：合格
```

ここで、

```text
品質承認状態が未同期
下流状態が適時更新されていない
```

場合、たとえば、

```text
A-D + E-D
```

を形成し得る。

その後、

```text
CAE-SDB Result + T → Arbitration → 待機 / 状態再同期 / 再確認
```

となり、現在対象は一時的に Target State へ進入しない。

関連状態が更新された後、PCN は再度判定を行う。

### 手直し工程へ進入

```text
Current State：検査完了

品質結果：NG

Target State：手直し工程
```

PCN は、次の内容を判定する。

```text
C：現在製品、ロット、品質結果、手直し条件が成立しているか

A：手直し許可、品質許可、人員権限が成立しているか

E：手直し設備、搬送、バッファ、トレーサビリティ、結果書戻しが継続して接続可能か
```

進入条件を満たすと判定された場合、

```text
CAE-SDB Result + T → Arbitration → Multipath Control → 手直し工程へ進入
```

となる。

### 回流または廃棄処理工程へ進入

回流、廃棄処理などの経路も、それぞれの Target State Entry を中心として判定できる。

たとえば、

```text
Current State：検査完了

Target State：廃棄処理工程
```

の場合、PCN は次の内容を判定する。

```text
C：廃棄判定、製品 ID、ロット情報が成立しているか

A：廃棄処理許可が成立しているか

E：廃棄搬送、回収、数量計上、トレーサビリティ、結果書戻しが継続して接続可能か
```

進入条件を満たすと判定された場合、

```text
→ Multipath Control
→ 廃棄処理工程へ進入
```

となる。

手直し、回流、廃棄処理、隔離は、いずれも生産プロセス上の Target State または目標実行経路として扱うことができる。

TPCA の状態遷移視点では、これらはすべて Current State から新しい Target State または目標実行経路へ進むことを意味し、過去の状態インスタンスへ戻ることを意味しない。

## 6. 代表的判定、時間情報 T、制御経路、PCN Trace

本事例では、次のような代表的 CAE-SDB Result を形成できる。

| 判定座標 | 本事例における代表状態 |
|---|---|
| C-S | 現在ロットと品質結果、作業指示、レシピの関係が完全に定義されていない |
| C-D | 作業指示、ロット、レシピ、品質結果の切替が非同期、状態失効、バージョン不一致 |
| C-B | Condition 状態が事前定義された再確認または制御境界に到達 |
| A-S | 品質承認、保全解除、人による確認などの許可元が完全に定義されていない |
| A-D | 許可取消、遅延、未更新、有効範囲超過、複数システム間状態非同期 |
| A-B | 許可待ち、確認有効期限、人による確認が制御境界に到達 |
| E-S | 下流受入、手直し、回流、廃棄処理、隔離、結果書戻し経路が完全に定義されていない |
| E-D | 下流、搬送、手直し設備、廃棄処理、バッファ、インターフェース、書戻し状態が現在安定して接続できない、または関連状態が現在有効であることを確認できない |
| E-B | バッファ容量、待ち時間、手直し回数、実行チェーン状態が事前定義された制御境界に到達 |

各 CAE-SDB Result とともに、対応する時間情報 T を保持する。

CAE-SDB Result は Arbitration を経て Multipath Control を形成する。

代表的な制御出力には、次のようなものがある。

- 進入許可；
- 待機；
- 再読込；
- 再照合；
- 再確認；
- 状態再同期；
- 手直し；
- 回流；
- 廃棄処理；
- 異常分流；
- 下流調整；
- 資源解放；
- 縮退実行；
- 代替経路；
- 進入禁止；
- 安全ロック；
- 人による確認；
- 隔離；
- 強化記録。

たとえば、

```text
C-D

作業指示は切り替わっているが、PLC レシピがまだ同期していない
→ 再読込 / 同期待ち
```

また、

```text
C-D

品質結果は合格を示しているが、前ロットに属している、または本状態遷移で許容される有効範囲を超えている
→ 再読込 / 再照合 / Target State へ一時的に進入しない
```

あるいは、

```text
A-D

品質承認が取り消された、有効範囲を超えた、または複数システム間で非同期
→ 待機 / 再確認 / Target State へ一時的に進入しない
```

さらに、

```text
E-D

下流状態が未更新で、受入可能かどうかを確認できない
→ 更新待ち / 状態再同期
```

また、

```text
Target State：手直し工程

E-S：
手直し実行チェーンが完全に定義されていない
→ 手直し工程へ一時的に進入しない
→ 人による確認 / エンジニアリング確認
```

一方、

```text
Target State：廃棄処理工程

C / A / E がすべて成立
→ 廃棄処理工程への進入を許可
```

となる。

1 回の PCN 判定では、同時に対応する PCN Trace を形成する。

代表的な記録内容は次の通りである。

```text
Current State
Target State
主要入力状態
時間情報 T
C / A / E 状態マッピング
S / D / B 判定
CAE-SDB Result
Arbitration Result
Multipath Control
実行結果
Trace ID
```

必要に応じて、主要入力状態には次の情報も関連付けることができる。

```text
対象 / ロット情報
状態更新時刻
状態バージョン / シーケンス情報
関連イベントまたはトレーサビリティ識別子
```

これらの情報は、本判定が依拠した有効状態とそのコンテキストを明確にするために使用する。

たとえば、

```text
Current State：前工程完了

Target State：次生産工程

時間情報：T

CAE-SDB Result：A-D + E-D

エンジニアリング上の意味：
品質承認状態の再確認が必要 / 下流受入状態が適時更新されていない

Multipath Control：
状態再同期 / 再確認

実行結果：
Target State へは一時的に未進入
```

また、

```text
Current State：検査完了

Target State：手直し工程

時間情報：T

品質結果：NG

Multipath Control：
手直し工程への進入許可

実行結果：
現在対象が手直し工程へ進入
```

となる。

PCN Trace が重点的に記録するのは、

> **今回どの Target State へ進入しようとしていたのか、どの現在有効な状態に基づいて判定したのか、なぜその判定を形成したのか、そして最終的にどの生産経路へ進んだのか。**

という内容である。

## 7. 履歴振り返り、AI 補助分析、製造 DX における価値

複数の PCN が長期間運用されると、PCN Trace が継続的に蓄積される。

製造 DX では、設備効率、生産実績、品質結果、停止、アラーム、エネルギー消費、物流などの分析に加えて、さらに次のような分析が可能になる。

- どの Target State が頻繁に成立しないか；
- どの C 条件が長期的に状態遷移の阻害要因となっているか；
- どの A 許可が長期的に生産許可のボトルネックとなっているか；
- どの E 実行チェーンが頻繁に継続できないか；
- どの手直し、回流、廃棄処理経路が長期的に高頻度で利用されているか；
- どの S 構造問題が繰り返し発生しているか；
- どの D 動的問題が長期間存在しているか；
- どの B 制御境界が頻繁にトリガされているか；
- どの制御経路が頻繁に使用されているか；
- どのエンジニアリング改善後に、同一判定結果が明確に減少したか。

たとえば、A-S が長期的に高頻度で発生している場合、改善の重点は、許可元、責任役割、システムインターフェースの再整理にある可能性がある。

C-D、A-D、E-D が長期的に高頻度で発生している場合は、作業指示切替、状態更新、状態有効性、バージョン関係、インターフェース遅延、複数システム間同期メカニズムをさらに確認できる。

複数システムが同一の状態遷移判定に共同参加する場合、さらに重要なのは、

> **異なるシステム内の状態がそれぞれ正しくても、それらが同一の Target State Entry 判定において同時に有効であるとは限らない。**

という点である。

たとえば、MES、品質システム、PLC、下流システムが、それぞれ合理的な状態値を保持していたとしても、それらが異なる対象、異なるロット、異なる状態バージョン、異なる更新時間ウィンドウに由来している場合、単純に組み合わせて一つの有効な状態遷移根拠として使用することはできない。

手直し経路が長期的に高頻度で利用されている場合は、製品、設備、工程、品質履歴と組み合わせ、その発生条件をさらに分析できる。

特定の B 判定が長期間頻繁にトリガされる場合、現在の状態遷移条件、確認方式、制御境界が妥当かを再検討できる。

したがって、PCN Trace は事後追跡だけでなく、生産状態遷移設計を振り返るためのデータソースとしても利用できる。

手直し、回流、再投入などの経路についても、PCN Trace は、エンジニアリング上の状態内容が同じであっても、発生時間や遷移履歴が異なる状態インスタンスを区別できる。

### AI 補助分析

本事例では、AI は現場における確定的制御を担当せず、PCN Trace の補助分析に使用する。

AI の分析対象は、単独の設備状態、アラーム、生産結果、時系列データだけではなく、具体的な Target State Entry と結び付いた PCN Trace となる。

PCN Trace は、

```text
Current State
Target State
主要入力状態
時間情報 T
C / A / E 状態マッピング
S / D / B 判定
CAE-SDB Result
Arbitration Result
Multipath Control
実行結果
```

を、同一の状態遷移判定履歴の中に整理する。

そのため、AI はさらに、

```text
状態値そのものが異常
```

という場合と、

```text
状態値は正常だが、すでに失効、未更新、非同期、または本状態遷移には適用できない
```

という場合を区別できる。

価値はデータ量を増やすことではなく、**状態遷移コンテキストと判定意味を追加すること**にある。

従来の MES / SCADA データは、通常、設備状態、アラーム、イベント、生産結果を中心としている。PCN Trace はさらに、

> **システムが当時どの Target State へ進入しようとしていたのか、何を根拠に判定したのか、なぜその制御経路を選択したのか、そして最終的に状態遷移が完了したのか**

を記録する。

したがって、

> **PCN Trace は単なる状態履歴ではなく、状態遷移判定履歴である。**

これにより、後続の AI 分析は、単純な状態相関分析から、状態遷移条件、動的時系列有効性、制御経路を対象とした履歴比較へ進むことができる。

基本的な位置付けは、次の通りである。

```text
PCN Trace
→ 履歴集約
→ AI 補助分析
→ 改善候補
→ エンジニア確認
→ 限定試行
→ 効果確認
→ 状態遷移設計更新
```

AI は、次の作業を補助できる。

- 同種の PCN Trace を集約；
- 高頻度の C / A / E と S / D / B の組合せを識別；
- 異なる Target State における繰返し問題を比較；
- 状態値異常と状態の動的時系列有効性問題を区別；
- 手直し、回流、廃棄処理などの経路の長期変化を識別；
- 改善前後の判定結果を比較；
- 候補チェックポイントやエンジニアリングレポートを生成。

たとえば、長期間の PCN Trace に次の結果が繰り返し現れる場合、

```text
Target State：次生産工程

CAE-SDB Result：A-D

関連状態：
品質承認状態が非同期

Multipath Control：
待機 / 再確認
```

AI は、次のような候補提示を補助できる。

> 作業指示切替段階で品質承認状態の非同期が繰り返し発生しているため、品質システムと MES 間の承認状態同期メカニズムを優先的に確認することを推奨する。

この結果は、あくまでエンジニアリング分析上の候補である。

AI は、次の責務を負わない。

- PCN の変更；
- CAE-SDB ルールの変更；
- 制御境界の変更；
- Arbitration を迂回して現場制御を出力；
- エンジニアリング変更の自動承認。

最終的な状態定義、許可関係、制御境界、PCN ルール変更、限定試行、効果確認、正式採用については、企業既存のエンジニアリング管理プロセスで確認する必要がある。

この枠組みにおいて、製造 DX の重点は、単に「より多くのデータをシステムへ接続すること」ではなく、

> **データ、設備、人員、品質、権限、生産プロセス間の状態遷移条件を明示化・構造化し、追跡可能な履歴を形成すること**

にある。

## 8. 公開範囲

本稿は、製造 DX 状態遷移条件設計・履歴分析に関する公開説明事例である。

本稿で公開する内容は、次の事項に限る。

- Current State / Target State；
- 生産状態遷移における PCN の位置；
- 代表的な複数ソース状態；
- C / A / E 状態マッピング；
- S / D / B 判定；
- CAE-SDB Result；
- 時間情報 T；
- 代表的な Arbitration と Multipath Control；
- PCN Trace と履歴分析の価値。

本稿における時間情報 T および状態の動的時系列有効性に関する内容は、エンジニアリング判定原則を説明するためのものである。

具体的な状態有効時間、更新周期、同期ウィンドウ、バージョンルール、失効条件、リトライ回数、関連制御パラメータは、実際の生産システム、工程要求、プラットフォームアーキテクチャ、制御要求に応じて設計する必要があり、本稿では公開しない。

具体的なエンジニアリング実装は、プラットフォームアーキテクチャ、現場設備、品質要求、安全要求、権限体系、エンジニアリング納入仕様を組み合わせて設計する必要がある。

PCN は、安全 PLC、安全リレー、ハードウェア安全回路、企業既存の強制安全制御メカニズムを置き換えるものではない。

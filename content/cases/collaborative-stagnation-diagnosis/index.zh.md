## 为什么 MES 记录了状态，仍解释不了制造现场为什么停

> 应用层级：群控协同层 / MES-WCS 协同停滞诊断  
> 代表对象：制造现场协同停滞诊断模块

**建议引用：**

```text
全野南政 / Nansei Zenno，《MES / WCS 协同停滞诊断模块案例：为什么 MES 记录了状态，仍解释不了制造现场为什么停》，公开案例，Public Case Version 1.6，2026-09-20，https://zennns.com/zh/cases/collaborative-stagnation-diagnosis/
```

MES 可以记录任务、设备、工位、物料和生产实绩，WCS 可以记录搬送任务、车辆、路径、资源占用和调度结果。

但在多设备、多任务、多系统协同场景中，仍可能出现：

- 任务已经生成，但持续无法执行；
- 执行主体在线，工位也有需求，但补料或搬送没有连续推进；
- 单体设备没有明显故障，整体协同效率却持续下降；
- 多个系统都有状态记录，但仍然很难直接说明为什么整体停滞。

本案例关注的问题是：

> **当前系统为什么无法进入可持续协同执行状态？**

案例围绕“进入可持续协同执行状态”这一目标状态入口，说明如何把分散在 MES、WCS、搬送主体、资源和许可系统中的状态组织为 CAE-SDB 判定结果和群控协同分析结果，并继续进入控制仲裁、控制路径、执行结果和状态迁移判定履历。

案例按照统一九步工程顺序展开：

1. 当前状态
2. 目标状态 / 目标状态入口
3. PCN：相关状态获取与 C / A / E 状态映射
4. 前置判定与群控协同分析
5. 控制仲裁
6. 多路径控制
7. 当前入口控制结果
8. 控制路径执行 / 后续目标状态入口与执行结果
9. 状态迁移判定履历

## 案例对象

本案例对象为 MES / WCS 协同停滞诊断模块。

模块位于制造现场协同层，可汇总 MES、WCS、搬送系统、设备单元、站点、路径资源、许可系统和下游状态。

AGV / AMR 群控搬送可以作为代表场景，但本案例关注的是更一般的制造现场协同停滞问题。

![MES / WCS 协同停滞诊断模块示意图](/images/tpca/08-mes-wcs-collaborative-stagnation-module.png)

图：协同停滞诊断模块汇总 MES、WCS、搬送主体、站点、路径资源、许可和下游状态。

---

# 1. 当前状态

当前现场状态为：

```text
任务存在
执行主体在线
部分任务持续未执行
多个主体持续等待
协同执行受阻
```

同时还可以看到：

```text
工位有需求
部分路径仍可用
单体设备无重大报警
局部任务仍在执行
```

此时只能确认协同执行受阻，还不能直接认定已经形成群体停滞。

---

# 2. 目标状态 / 目标状态入口

本次目标状态为：

```text
可持续协同执行状态
```

对应的目标状态入口为：

```text
进入可持续协同执行状态
```

PCN 设置在当前协同状态和这一目标状态入口之间。

后续的状态映射、CAE-SDB 判定、群体停滞识别和控制处理，都围绕这个入口展开。

---

# 3. PCN：相关状态获取与 C / A / E 状态映射

PCN 取得与当前协同入口直接相关的状态，并按照其在本次状态迁移中的工程作用进行 C / A / E 状态映射。

| 代表状态 | 状态映射 |
|---|---|
| 任务状态、工位需求、目标站点信息 | C：条件状态 |
| 调度许可、资源锁、区域许可、安全许可 | A：许可状态 |
| 执行主体状态、路径状态、站点承接状态、下游状态 | E：执行链状态 |

本案例重点使用：

- 任务存在：C
- 资源锁状态：A
- 安全许可：A
- 执行主体在线：E 的相关状态
- 路径可用状态：E

群体未执行比例等群体层信息不直接等同于某个 CAE-SDB 判定结果，而用于后续群控协同分析。

---

# 4. 前置判定与群控协同分析

本案例假设当前出现以下状态：

```text
任务： 存在

执行主体： 在线

安全许可： 成立

资源锁接口： 已经建立

资源锁状态： 不同步

群体未执行比例： 达到停滞识别条件
```

资源锁在当前入口中属于 A，其问题发生在动态时序有效性，因此形成：

```text
CAE-SDB 结果：
A-D

资源锁状态不同步，
不能继续作为当前协同入口的有效许可依据
```

同时，群控协同层根据群体指标进行停滞识别和结构分型。

本案例中的分析结果为：

```text
群体未执行比例： 达到停滞识别条件

群体辅助执行比例： 呈现资源竞争型特征

群体能源补给比例： 未呈现能源偏在型特征

群体授权未成立比例： 本例已取得，未形成分配约束型主导特征

群体停滞识别： 成立

停滞结构分型： 资源竞争型
```

群体未执行比例用于确认群体停滞是否成立；群体辅助执行比例、群体能源补给比例以及可取得的群体授权未成立比例用于支持结构分型。

本公开案例不公开具体比例阈值和持续时间阈值。

因此，第 4 步保留两类结果：

- CAE-SDB：A-D
- 群控协同分析：群体停滞成立，资源竞争型

两类结果分别保留，并共同进入控制仲裁。

本案例不展开完整 CAE-SDB 九个坐标和全部停滞分型。详细定义可参见：

- [为什么是 CAE-SDB？——状态变量域与判定性质的双轴结构](/zh/notes/why-cae-sdb/)
- [为什么 MES / WCS 能记录，却不能解释停滞？](/zh/questions/why-mes-records-but-cannot-explain/)

---

# 5. 控制仲裁

本次控制仲裁的主要输入为：

```text
CAE-SDB 结果：
 A-D
资源锁状态不同步

群体停滞识别：
 成立

停滞结构分型：
 资源竞争型

关键安全许可：
 成立
```

分型依据包括：群体辅助执行比例呈现资源竞争型特征，群体能源补给比例未呈现能源偏在型特征，群体授权未成立比例未形成分配约束型主导特征。

控制仲裁结果为：

```text
优先处理资源锁不一致
同时进行路径协调和受影响任务重新分配
```

---

# 6. 多路径控制

根据控制仲裁结果，本次选择：

```text
资源释放
路径协调
任务重新分配
```

在本公开案例中，协同停滞诊断模块首先形成结构化控制结果、控制建议或协调请求。

实际项目中是否由模块直接下发控制指令，取决于既有 MES、WCS、调度系统和现场控制系统的接口及控制权限。

---

# 7. 当前入口控制结果

本次目标状态入口的控制结果为：

```text
暂不进入可持续协同执行状态
```

原因是资源锁状态仍然存在 A-D，同时群体停滞已经被识别为资源竞争型。

后续处理包括资源释放、路径协调和任务重新分配。

---

# 8. 控制路径执行 / 后续目标状态入口与执行结果

本案例中的多路径控制属于当前协同入口下的协调处理，由具有相应权限的既有系统执行。

假设处理完成后：

```text
资源锁： 恢复一致

关键路径： 恢复可用

受影响任务： 重新分配完成

群体未执行比例： 回到停滞识别条件以下
```

则本次执行结果可以记录为：

```text
相关资源与路径关系已恢复，
受影响任务重新进入可执行状态
```

如果后续控制选择备用路径、回退路径、异常分流等新的目标状态或目标路径，则形成新的目标状态入口，并由对应 PCN 重新执行前置判定。

---

# 9. 状态迁移判定履历

本次协同入口可以形成如下履历：

```text
PCN：
  协同执行入口 PCN

当前状态：
  协同执行受阻 / 多主体持续等待

目标状态：
  可持续协同执行状态

目标状态入口：
  进入可持续协同执行状态

主要状态：
  任务 = 存在
  执行主体 = 在线
  资源锁状态 = 不同步
  安全许可 = 成立

CAE-SDB 结果：
A-D

群体指标：
  群体未执行比例 = 达到停滞识别条件
  群体辅助执行比例 = 呈现资源竞争型特征
  群体能源补给比例 = 未呈现能源偏在型特征
  群体授权未成立比例 = 未形成分配约束型主导特征

群体停滞识别：
  成立

停滞结构分型：
  资源竞争型

控制仲裁结果：
  优先处理资源锁不一致，同时进行路径协调和任务重新分配

多路径控制：
 资源释放 + 路径协调 + 任务重新分配

当前入口控制结果：
  暂不进入可持续协同执行状态

执行结果：
  相关资源与路径关系已恢复，受影响任务重新进入可执行状态

时间信息：
  T

履历 ID：
  PCN-COLLAB-XXXX
```

如果后续形成新的目标状态入口，则由对应 PCN 建立新的状态迁移判定履历。

关于状态迁移判定履历的详细说明可参见：

[为什么状态迁移判定履历是一种新的工程数据？](/zh/notes/why-pcn-trace-is-engineering-data/)

## 案例总结

本案例中，MES、WCS、搬送主体和现场设备已经能够记录任务、主体、路径、资源和运行状态。

现场原本可以确认：

```text
任务存在
执行主体在线
多个主体持续等待
协同执行受阻
```

围绕“进入可持续协同执行状态”这一目标状态入口重新组织后，可以进一步明确：

```text
CAE-SDB 结果：
  A-D
  资源锁状态不同步

群体停滞识别：
  成立

停滞结构分型：
  资源竞争型
```

### 本案例带来的工程信息差异

| 原有现场能够确认 | 通过本案例进一步明确 |
|---|---|
| 任务已经生成 | 当前需要判断的是“能否进入可持续协同执行状态”这一明确目标状态入口 |
| 执行主体在线 | 主体在线只是相关状态之一，不能单独代表协同执行可以持续 |
| 多个主体持续等待 | 群体未执行比例已经达到停滞识别条件，可进一步确认群体停滞是否成立 |
| 资源锁存在异常或状态不一致 | 资源锁在当前入口中属于 A，并形成 **A-D：资源锁状态不同步** |
| 单体设备没有重大报警 | 协同问题仍可能发生在任务、许可、资源和执行链之间 |
| 路径、资源存在竞争现象 | 结合群体辅助执行、能源补给和授权未成立等指标，将停滞分型为 **资源竞争型** |
| 现场只能知道“整体卡住了” | 问题定位到当前协同入口中的许可状态动态失效，并伴随资源竞争型群体停滞 |
| 工程师需要继续跨系统判断如何处理 | 控制方向明确为“资源释放 + 路径协调 + 任务重新分配” |
| 控制动作执行后只能看新的运行状态 | 可以继续记录资源锁恢复、路径恢复、任务重新分配及群体未执行比例变化 |
| MES、WCS、车辆和设备分别保存日志 | 本次状态、判定、停滞分型、控制和执行结果被组织到同一次状态迁移判定履历中 |

本案例把“任务存在、主体在线，但系统仍然停滞”进一步定位为：当前协同入口中的资源锁状态存在 A-D，同时群体停滞表现为资源竞争型。

对应控制方向为资源释放、路径协调和任务重新分配，并继续记录处理后的资源、路径、任务和群体执行状态。

案例的重点不在增加更多任务、车辆或设备数据，而在于把已有状态放到同一个目标状态入口下判断，同时保留 CAE-SDB 结果和群控协同分析结果，再连接到控制处理和执行结果。

## 为什么 MES 记录了状态，仍解释不了制造现场为什么停

> 应用层级：群控协同层 / MES-WCS 协同停滞诊断  
> 代表对象：制造现场协同停滞诊断模块

**建议引用：**

```text
全野南政 / Nansei Zenno，《MES / WCS 协同停滞诊断模块案例：为什么 MES 记录了状态，仍解释不了制造现场为什么停》，公开案例，Public Case Version 1.6，2026-09-30，https://zennns.com/zh/cases/collaborative-stagnation-diagnosis/
```

MES 和 WCS 通常已经掌握大量运行信息。

例如某一时刻，系统可能同时显示：

```text
活动任务数：42
持续等待或未执行任务数：17

执行主体：在线
工位需求：存在
重大设备报警：无

可用路径：存在
共享资源：部分占用
```

从这些状态可以确认：任务仍然存在，执行主体在线，部分路径仍可使用，现场也没有出现一个足以解释整体停滞的单体重大故障。

但任务仍在持续积压，多个主体长时间处于等待，协同执行能力明显下降。

这时工程问题已经不是“有没有任务”或者“设备是不是在线”，而是：

> **为什么当前系统无法继续进入可持续协同执行状态？**

本案例围绕“进入可持续协同执行状态”这一 Target State Entry（目标状态入口），将 MES、WCS、执行主体、路径资源、许可和站点状态组织到同一次协同判定中。

与自动化执行单元不同，本案例还保留群控协同层的领域分析结果，用于识别群体停滞是否成立，以及当前停滞更接近哪一种结构类型。

案例仍按照统一九步工程顺序展开：

1. 当前状态
2. 目标状态 / 目标状态入口
3. PCN：相关状态获取与 C / A / E 状态映射
4. 前置判定与群控协同分析
5. 控制仲裁
6. 多路径控制
7. 当前入口控制结果
8. 控制路径执行 / 后续目标状态入口与执行结果
9. 状态迁移判定履历

基础概念可参见：

- [核心概念](/zh/concepts/)
- [TPCA / PCN 状态迁移前置控制架构｜白皮书](/zh/whitepaper/)

## 案例对象

本案例对象为 MES / WCS 协同停滞诊断模块。

模块位于制造现场协同层，可汇总：

- MES 任务和工位需求；
- WCS 调度和搬送任务；
- AGV / AMR 或其他执行主体状态；
- 路径和共享资源状态；
- 区域及安全许可；
- 站点承接状态；
- 下游状态；
- 群体运行指标。

AGV / AMR 群控搬送可以作为代表场景，但这里关注的是更一般的制造现场协同问题：**多个单体都没有明显故障时，为什么整体执行仍然无法持续。**

![MES / WCS 协同停滞诊断模块示意图](/images/tpca/08-mes-wcs-collaborative-stagnation-module.png)

图：协同停滞诊断模块汇总 MES、WCS、搬送主体、站点、路径资源、许可和下游状态。

以下数量和状态组合用于说明公开案例中的一次示例运行关系，不代表特定真实项目数据。群体停滞阈值、持续时间窗口和完整结构分型规则不在本公开案例中展开。

---

# 1. 当前状态

当前系统并不是完全停止。

部分任务仍然执行，部分路径也可以使用，但整体协同过程已经出现持续受阻。

示例运行快照：

```text
活动任务数：42
已执行或正在推进：25
持续等待或未执行：17

执行主体：在线
工位需求：存在
重大设备报警：无

可用路径：存在
共享资源：部分占用
协同执行状态：受阻
```

现场能够观察到：

```text
任务存在
执行主体在线
部分任务持续未执行
多个主体持续等待
局部任务仍在执行
```

因此，这里不是简单的“全系统停止”。

当前能够确认的是：

```text
协同执行受阻
```

至于是否已经达到群体停滞条件，以及造成当前受阻的主要结构是什么，还需要继续判定。

---

# 2. 目标状态 / 目标状态入口

本案例不是判断某一台 AGV 能否移动，也不是判断单个设备能否启动。

当前关注的系统级目标状态为：

```text
可持续协同执行状态
```

对应的 Target State Entry（目标状态入口）为：

```text
进入可持续协同执行状态
```

这里所说的“可持续协同执行”，表示当前任务、执行主体、资源、许可、路径和站点关系能够支持系统继续推进，而不是仅有个别任务仍在运行。

PCN 设置在当前协同状态与这一目标状态入口之间。

后续的状态映射、CAE-SDB 判定、群体停滞识别、结构分型和控制处理，都围绕这个协同入口展开。

---

# 3. PCN：相关状态获取与 C / A / E 状态映射

PCN 从不同系统取得与当前协同入口直接相关的状态，并根据它们在本次状态迁移中的工程作用进行 C / A / E 状态映射。

| 代表状态 | 状态映射 |
|---|---|
| 任务状态、工位需求、目标站点信息 | C：条件状态 |
| 调度许可、资源锁、区域许可、安全许可 | A：许可状态 |
| 执行主体状态、路径状态、站点承接状态、下游状态 | E：执行链状态 |

本次示例重点关注：

```text
任务存在 → C

资源锁状态 → A
安全许可 → A

执行主体在线 → E 的相关状态
路径可用状态 → E
站点承接状态 → E
```

这里需要特别区分两类信息。

第一类是与具体 Target State Entry 直接相关、可以进入 CAE-SDB 判定的状态。

第二类是群控协同层通过多个任务和主体统计形成的群体信息，例如：

```text
群体未执行比例
群体辅助执行比例
群体能源补给比例
群体授权未成立比例
```

这些群体指标用于停滞识别和结构分型，不直接等同于某一个 CAE-SDB Result。

---

# 4. 前置判定与群控协同分析

在本次示例运行中，系统形成如下状态快照：

```text
活动任务数：42
持续等待或未执行任务数：17

执行主体：在线
安全许可：成立

资源锁接口：已建立
资源锁状态：不同步

可用路径：存在
工位需求：存在
```

从单体状态来看：

- 任务存在；
- 执行主体在线；
- 安全许可成立；
- 路径并非全部不可用；
- 工位仍有执行需求。

但资源锁状态没有保持一致。

在当前协同入口中，资源锁属于 A。

其接口本身已经存在，当前问题不是“没有资源锁结构”，而是运行中的锁状态发生不同步，不能继续作为当前入口的有效许可依据。

因此形成：

```text
CAE-SDB Result：

A-D

资源锁状态不同步，
不能继续作为当前协同入口的有效许可依据
```

与此同时，群控协同层继续观察多个任务和执行主体的整体运行状态。

本示例中：

```text
群体未执行比例：
达到停滞识别条件

群体辅助执行比例：
呈现资源竞争型特征

群体能源补给比例：
未呈现能源偏在型特征

群体授权未成立比例：
未形成分配约束型主导特征
```

由此形成另一类分析结果：

```text
群体停滞识别：
成立

停滞结构分型：
资源竞争型
```

这里得到的是两个不同层面的工程结果：

```text
目标状态入口层：
A-D
资源锁状态动态时序失效

群控协同层：
群体停滞成立
资源竞争型
```

CAE-SDB Result 不替代群体停滞识别和结构分型；群体指标也不需要强行映射成 CAE-SDB 坐标。

两类结果各自保留自己的工程语义，并共同进入后续控制仲裁。

具体群体比例阈值、持续时间窗口和完整分型规则属于内部工程实现范围，本公开案例不展开。

相关定义可参见：

- [为什么是 CAE-SDB？——状态变量域与判定性质的双轴结构](/zh/notes/why-cae-sdb/)
- [为什么 MES / WCS 能记录，却不能解释停滞？](/zh/questions/why-mes-records-but-cannot-explain/)

# 5. 控制仲裁

进入控制仲裁时，当前系统已经不仅知道“很多任务在 Waiting”。

它掌握的是：

```text
CAE-SDB Result：
A-D

资源锁状态：
不同步

群体停滞识别：
成立

停滞结构分型：
资源竞争型

安全许可：
成立
```

此时继续向系统投入更多任务，或者仅等待个别设备自行恢复，都不能直接解决当前协同关系。

当前控制优先级首先指向已经确认的资源锁不一致。

同时，资源竞争型群体特征说明还需要处理受到影响的路径和任务分配关系。

控制仲裁形成：

```text
优先处理：
资源锁状态不一致

同时处理：
受影响路径协调
受影响任务重新分配
```

最终控制方向为：

```text
资源释放
+
路径协调
+
任务重新分配
```

---

# 6. 多路径控制

本次协同入口形成以下 Multipath Control（多路径控制）：

```text
资源释放

路径协调

任务重新分配
```

与机器人抓取案例不同，这里的多路径控制不一定意味着某一台设备立即执行一个物理动作。

协同层首先形成的是结构化控制结果、协调请求或调度处理方向。

实际项目中：

- 哪一个系统执行资源释放；
- 哪一个调度系统重新分配任务；
- 是否自动修改路径；
- 哪些动作需要人工确认；

取决于既有 MES、WCS、调度系统和现场控制系统的接口、职责和控制权限。

TPCA / PCN 在这里不替代原有调度和执行系统的控制责任。

# 7. 当前入口控制结果

当前 Target State Entry 为：

```text
进入可持续协同执行状态
```

本次形成：

```text
当前入口：
暂不进入
```

原因并不是“系统完全没有任务”或“执行主体全部故障”。

当前能够明确的是：

```text
A-D：
资源锁状态不同步

+

群体停滞：
成立

+

停滞结构：
资源竞争型
```

系统需要先完成相应协调处理，再重新观察当前协同状态是否已经恢复到可以持续推进的条件。

---

# 8. 控制路径执行 / 后续目标状态入口与执行结果

由具备相应权限的既有系统执行协调处理。

处理过程中，工程状态逐步发生变化。

例如：

```text
资源锁状态：
不同步
    ↓
恢复一致

受阻共享资源：
占用关系重新整理

受影响路径：
重新协调

受影响任务：
重新分配
```

处理完成后的示例状态为：

```text
资源锁状态：恢复一致
关键路径：恢复可用
受影响任务：重新分配完成

持续等待或未执行任务：下降
群体未执行比例：回到停滞识别条件以下
```

这时可以记录本次协调处理的执行结果：

```text
执行结果：

资源锁关系恢复一致
关键路径恢复可用
受影响任务完成重新分配
群体未执行状态下降
```

这些结果成为新的工程状态事实。

当前系统是否重新进入“可持续协同执行状态”，需要基于更新后的状态再次进行当前入口判定。

如果控制处理形成备用路径、回退路径、异常分流等新的目标状态，则相应建立新的 Target State Entry，并由对应 PCN 独立完成前置判定。

# 9. 状态迁移判定履历

本次协同入口可以形成如下 PCN Trace：

```text
履历 ID：
PCN-COLLAB-XXXX

PCN：
协同执行入口 PCN

当前状态：
协同执行受阻 / 多主体持续等待

目标状态：
可持续协同执行状态

目标状态入口：
进入可持续协同执行状态

主要状态：
  活动任务数 = 42
  持续等待或未执行任务数 = 17
  执行主体 = 在线
  安全许可 = 成立
  资源锁接口 = 已建立
  资源锁状态 = 不同步
  可用路径 = 存在

CAE-SDB Result：
A-D

判定内容：
资源锁状态不同步，
不能继续作为当前入口的有效许可依据

群控协同分析：
  群体停滞 = 成立
  停滞结构 = 资源竞争型

控制仲裁结果：
优先处理资源锁不一致，
同时进行路径协调和任务重新分配

多路径控制：
资源释放
+
路径协调
+
任务重新分配

当前入口控制结果：
暂不进入可持续协同执行状态

执行结果：
资源锁关系恢复一致
关键路径恢复可用
受影响任务完成重新分配
群体未执行状态下降

时间信息：
T
```

这条履历把原本分散在 MES、WCS、执行主体、资源和许可系统中的状态，放到了同一次协同入口判定中。

其中同时保留两类不同信息：

```text
入口级判定：
A-D

群控协同分析：
群体停滞成立
资源竞争型
```

两类结果没有被混成同一种标签，但可以沿同一次状态迁移履历继续追踪到控制处理和执行结果。

如果后续形成新的 Target State Entry，则由对应 PCN 建立新的状态迁移判定履历。

关于 PCN Trace 的详细说明可参见：

[为什么状态迁移判定履历是一种新的工程数据？](/zh/notes/why-pcn-trace-is-engineering-data/)

## 案例总结

本次示例开始时，MES、WCS 和现场系统已经能够看到很多真实状态：

```text
任务存在
执行主体在线
工位有需求
部分路径可用
无重大单体设备报警

但：

多个任务持续未执行
多个主体持续等待
整体协同执行受阻
```

如果只查看各系统页面，能够得到很多正确但彼此分散的信息。

围绕：

```text
目标状态入口：
进入可持续协同执行状态
```

重新组织以后，工程关系进一步明确为：

```text
资源锁状态
    ↓
不同步
    ↓
A-D
```

与此同时，群体运行数据形成：

```text
群体停滞：
成立

停滞结构分型：
资源竞争型
```

最终形成的处理关系为：

```text
资源锁不同步
    ↓
A-D

同时：

群体停滞成立
+
资源竞争型
    ↓
控制仲裁
    ↓
资源释放
路径协调
任务重新分配
    ↓
资源与路径关系恢复
    ↓
群体未执行状态下降
```

### 本案例带来的工程信息差异

| 原有现场能够确认 | 通过本案例进一步明确 |
|---|---|
| 任务已经生成 | 当前关注的是系统能否进入“可持续协同执行状态” |
| 执行主体在线 | 主体在线不等于群体执行关系已经成立 |
| 多个主体持续 Waiting | 群体未执行状态已经达到停滞识别条件 |
| 资源锁存在状态不一致 | 当前资源锁属于 A，并形成 `A-D` |
| 单体设备没有重大报警 | 问题仍可能存在于资源、许可、路径和任务之间的协同关系 |
| 多条路径和资源存在竞争 | 群体分析进一步识别为资源竞争型 |
| 现场只能看到“整体卡住了” | 同时形成入口级 `A-D` 和群控层资源竞争型判断 |
| 工程师需要跨系统协调处理 | 控制方向明确为资源释放、路径协调和任务重新分配 |
| 处理以后只能重新观察系统状态 | 可以继续比较资源锁、任务、路径和群体未执行状态的变化 |
| 不同系统分别保存自己的日志 | 判定、分型、控制和执行结果进入同一次状态迁移判定履历 |

本案例最终把一个模糊的“系统整体越来越堵”，拆成了两个可以分别处理的工程事实：

> **当前协同入口中的许可状态存在 A-D。**

以及：

> **群控协同层已经形成资源竞争型群体停滞。**

这两个结果共同进入控制处理，又继续通过后续状态变化确认协调措施是否真正改善了当前协同状态。

## 为什么 MES 记录了状态，仍解释不了制造现场为什么停

> 应用层级：群控协同层 / MES-WCS 协同停滞诊断  
> 代表对象：制造现场协同停滞诊断模块

**建议引用：**

```text
全野南政 / Nansei Zenno，《MES / WCS 协同停滞诊断模块案例：为什么 MES 记录了状态，仍解释不了制造现场为什么停》，公开案例，Public Case Version 1.6，2026-09-20，https://zennns.com/zh/cases/collaborative-stagnation-diagnosis/
```

MES 可以记录任务、设备、工位、物料和生产实绩，WCS 可以记录搬送任务、车辆、路径、资源占用和调度结果。

但在多设备、多任务、多系统协同场景中，仍可能出现：

- 任务已经生成，但持续无法执行；
- 执行主体在线，工位也有需求，但补料或搬送没有连续推进；
- 单体设备没有明显故障，整体协同效率却持续下降；
- 多个系统都有状态记录，但难以直接说明“为什么整体停滞”。

本案例关注的问题是：

> **当前系统为什么无法进入可持续协同执行状态？**

本案例重点验证的不是“停滞是否存在”这一事实本身，而是：

> **能否把分散在 MES、WCS、搬送主体、资源和许可系统中的协同受阻状态，进一步组织为明确的目标状态入口、CAE-SDB 判定结果、群体停滞结构、控制方向、执行结果和状态迁移判定履历。**

案例按照统一九步工程顺序展开：

```text
1. 当前状态
2. 目标状态 / 目标状态入口
3. PCN：相关状态获取 + C / A / E 状态映射
4. 前置判定与群控协同分析
   ├─ S / D / B 判定 → CAE-SDB 结果 + T
   └─ 群体指标 → 群体停滞识别 → 停滞结构分型
5. 控制仲裁
6. 多路径控制
7. 当前入口控制结果
8. 控制路径执行 / 后续目标状态入口与执行结果
9. 状态迁移判定履历
```

基础概念可参见：

- [核心概念](/zh/concepts/)
- [TPCA / PCN 状态迁移前置控制架构｜白皮书](/zh/whitepaper/)

## 案例对象

本案例对象为 MES / WCS 协同停滞诊断模块。

模块位于制造现场协同层，可汇总 MES、WCS、搬送系统、设备单元、站点、路径资源、许可系统和下游状态。

AGV / AMR 群控搬送可以作为代表场景，但本案例关注的是更一般的制造现场协同停滞问题。

![MES / WCS 协同停滞诊断模块示意图](/images/tpca/08-mes-wcs-collaborative-stagnation-module.png)

图：协同停滞诊断模块汇总 MES、WCS、搬送主体、站点、路径资源、许可和下游状态。

---

# 1. 当前状态

现在现场是什么状态？

```text
当前状态：
任务存在
执行主体在线
部分任务持续未执行
多个主体持续等待
协同执行受阻
```

现场还可以看到：

```text
工位有需求
部分路径仍可用
单体设备无重大报警
局部任务仍在执行
```

此时只能确认协同执行受阻，还不能直接认定已经形成群体停滞。

---

# 2. 目标状态 / 目标状态入口

这次准备进入哪里？

```text
目标状态：
可持续协同执行状态

目标状态入口：
进入可持续协同执行状态
```

PCN 位于当前协同状态与目标状态入口之间：

```text
当前状态［协同执行受阻］
    ↓
PCN［进入可持续协同执行状态前的判定］
    ↓
目标状态入口［进入可持续协同执行状态］
    ↓
目标状态［可持续协同执行状态］
```

本案例后续的状态映射、CAE-SDB 判定、群体停滞识别和控制处理，均围绕这个目标状态入口展开。

---

# 3. PCN：相关状态获取与 C / A / E 状态映射

本次入口最关键的状态分别是什么？

PCN 取得与当前协同入口直接相关的状态，并按照其工程作用进行 C / A / E 状态映射。

| 代表状态 | 状态映射 |
|---|---|
| 任务状态、工位需求、目标站点信息 | C：条件状态 |
| 调度许可、资源锁、区域许可、安全许可 | A：许可状态 |
| 执行主体状态、路径状态、站点承接状态、下游状态 | E：执行链状态 |

本案例重点使用：

```text
任务存在 → C
资源锁状态 → A
安全许可 → A
执行主体在线 → E 的相关状态
路径可用状态 → E
```

群体未执行比例等群体层信息不直接等同于某一个 CAE-SDB 判定结果，而进入后续群控协同分析。

---

# 4. 前置判定与群控协同分析

本次实际出现了什么判定问题？

本案例假设当前出现：

```text
任务：
存在

执行主体：
在线

安全许可：
成立

资源锁接口：
已经建立

资源锁状态：
不同步

群体未执行比例：
达到停滞识别条件
```

资源锁在当前入口中属于 A，其当前问题发生在动态时序有效性，因此形成：

```text
CAE-SDB 结果：
A-D

资源锁状态不同步，
不能继续作为当前协同入口的有效许可依据
```

同时，群控协同层形成：

```text
群体未执行比例：
达到停滞识别条件

群体停滞识别：
成立

停滞结构分型：
资源竞争型
```

因此，第 4 步得到两类结果：

```text
CAE-SDB：
A-D

群控协同分析：
群体停滞成立
资源竞争型
```

两类结果分别保留，并共同进入下一步控制仲裁。

本案例不展开完整 CAE-SDB 九个坐标和全部停滞分型。详细定义可参见：

- [为什么是 CAE-SDB？——状态变量域与判定性质的双轴结构](/zh/notes/why-cae-sdb/)
- [为什么 MES / WCS 能记录，却不能解释停滞？](/zh/questions/why-mes-records-but-cannot-explain/)

# 5. 控制仲裁

多个结果一起出现时，最终优先处理什么？

本次控制仲裁的主要输入为：

```text
CAE-SDB 结果：
A-D
资源锁状态不同步

群体停滞识别：
成立

停滞结构分型：
资源竞争型

关键安全许可：
成立
```

控制仲裁结果为：

```text
优先处理资源锁不一致
同时进行路径协调和受影响任务重新分配
```

---

# 6. 多路径控制

选择了什么路径？

本次形成：

```text
多路径控制：
资源释放
+
路径协调
+
任务重新分配
```

在本公开案例中，协同停滞诊断模块首先形成结构化控制结果、控制建议或协调请求。

实际项目中是否由模块直接下发控制指令，取决于既有 MES、WCS、调度系统和现场控制系统的接口及控制权限。

---

# 7. 当前入口控制结果

本次入口到底进不进？

```text
当前入口控制结果：
暂不进入可持续协同执行状态
```

原因是当前资源锁状态仍然存在 A-D，同时群体停滞已经被识别为资源竞争型。

已经确定的后续处理为：

```text
资源释放
路径协调
任务重新分配
```

---

# 8. 控制路径执行 / 后续目标状态入口与执行结果

实际执行以后发生了什么？

本案例中的多路径控制属于当前协同入口下的协调处理，由具有相应权限的既有系统执行。

```text
当前协同入口暂不进入
    ↓
资源释放
    ↓
路径协调
    ↓
任务重新分配
    ↓
形成新的协同运行状态
```

假设执行完成后：

```text
资源锁：
恢复一致

关键路径：
恢复可用

受影响任务：
重新分配完成

群体未执行比例：
回到停滞识别条件以下
```

则形成：

```text
执行结果：
相关资源与路径关系已恢复，
受影响任务重新进入可执行状态
```

如果后续控制选择的是备用路径、回退路径、异常分流等新的目标状态或目标路径，则需要形成新的目标状态入口，并由对应 PCN 重新进行前置判定。

---

# 9. 状态迁移判定履历

这次状态迁移最终记录成什么？

本次协同入口可以形成如下履历：

```text
PCN：
协同执行入口 PCN

当前状态：
协同执行受阻 / 多主体持续等待

目标状态：
可持续协同执行状态

目标状态入口：
进入可持续协同执行状态

主要状态：
  任务 = 存在
  执行主体 = 在线
  资源锁状态 = 不同步
  安全许可 = 成立

CAE-SDB 结果：
A-D

群体停滞识别：
成立

停滞结构分型：
资源竞争型

控制仲裁结果：
优先处理资源锁不一致，
同时进行路径协调和任务重新分配

多路径控制：
资源释放 + 路径协调 + 任务重新分配

当前入口控制结果：
暂不进入可持续协同执行状态

执行结果：
相关资源与路径关系已恢复，
受影响任务重新进入可执行状态

时间信息：
T

履历 ID：
PCN-COLLAB-XXXX
```

如果后续形成新的目标状态入口，则由对应 PCN 建立新的状态迁移判定履历。

关于状态迁移判定履历的详细说明可参见：

[为什么状态迁移判定履历是一种新的工程数据？](/zh/notes/why-pcn-trace-is-engineering-data/)

## 案例总结

本案例中，MES、WCS、搬送主体和现场设备原本已经能够记录任务、主体、路径、资源和运行状态。

但这些分散状态首先只能说明：

```text
任务存在
执行主体在线
多个主体持续等待
协同执行受阻
```

按照九步工程顺序重新组织后，本次问题被进一步明确为：

```text
目标状态入口：
进入可持续协同执行状态

CAE-SDB 结果：
A-D
资源锁状态不同步

群体停滞识别：
成立

停滞结构分型：
资源竞争型
```

由此，原本笼统的“系统整体在等待”被进一步定位为：

> **当前协同入口中的许可状态动态失效，并伴随资源竞争型群体停滞。**

这一判定结果继续进入控制仲裁，并形成：

```text
资源释放
+
路径协调
+
任务重新分配
```

执行后，资源锁恢复一致、关键路径恢复可用，受影响任务重新进入可执行状态。

因此，本案例展示的工程效果是：

- 将分散在不同系统中的状态组织到一次明确的目标状态入口；
- 将“协同受阻”进一步定位到具体 CAE-SDB 判定问题；
- 将群体现象进一步识别为明确的停滞结构类型；
- 将判定结果直接连接到控制方向和执行结果；
- 将本次状态、判定、控制和执行过程形成统一的状态迁移判定履历。

也就是说，原本只能观察到的：

> **“任务存在、主体在线，但系统仍然停滞”**

被进一步转换为：

> **“哪里没有成立、属于什么停滞结构、应该如何处理，以及处理后发生了什么”。**

这就是本案例所展示的主要工程效果。

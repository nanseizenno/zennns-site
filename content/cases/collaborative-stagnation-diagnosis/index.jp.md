## 1. 現場で発生する問題

MES は、タスク、設備、ステーション、材料、アラーム、生産数量、生産実績などを記録できる。

WCS は、搬送タスク、車両状態、経路状態、資源占有状態、スケジューリング結果などを記録できる。

設備側では、運転、待機、アラーム、インターロックなどの状態を記録できる。

HMI には、Ready、Waiting、Blocked、Pending などの運転状態が表示される。

一方、多設備、多タスク、多システムが連携する製造現場では、次のような状態が発生することがある。

* タスクは生成されているが、実行が長時間進まない。
* 車両はオンラインであり、ステーションにも要求があるが、補給が連続した実行につながらない。
* 個々の設備に明確な故障がなくても、システム全体のスループットが継続して低下する。
* MES、WCS、PLC、車両、ステーションに状態記録があっても、協調停滞がどこで発生しているかを短時間で特定できない。
* オーダ変更、資源競合、許可待ち、下流の受入待ち、手動確認、エネルギー補給などが重なり、複数システムのログと状態を照合する必要が生じる。

この場合に確認すべき対象は、

> **現在のシステムが、なぜ持続可能な協調実行状態へ移行できないのか。**

という状態遷移上の問題である。

TPCA / PCN では、これを明確な Target State Entry として扱う。

PCN は、「持続可能な協調実行状態」を Target State とし、今回の状態遷移に関係する複数ソース状態を取得する。

取得した状態は、状態遷移における機能役割に基づいて C / A / E へマッピングする。

```text
C：必要な条件が揃っているか。
A：移行が許可されているか。
E：移行後の実行チェーンが継続できるか。
```

続いて、関連状態に対して必要な S / D / B 判定を行う。

```text
S：判定に必要な構造が成立しているか。
D：現在の状態を本判定の根拠として使用できるか。
B：現在の状態が事前定義された制御境界に到達しているか。
```

さらに、複数の実行主体から得られる状態を集約し、群全体の指標を算出する。

これらの状態、CAE-SDB Result、時間情報 T、群全体の指標を用いて停滞を識別し、停滞構造を分析する。

基本的な処理関係は次の通りである。

```text
現在の協調状態
→ PCN
→ C / A / E Mapping
→ S / D / B Evaluation
→ CAE-SDB Result + T
→ 群全体の指標
→ 停滞識別・構造分析
→ Arbitration
→ Multipath Control
→ PCN Trace
```

## 2. モジュールの位置付けと PCN の配置位置

本事例の対象は、

> **MES / WCS 協調停滞診断モジュール**

である。

本モジュールは製造現場の協調層に配置し、MES、WCS、搬送システム、設備ユニット、ステーション、バッファ、経路資源、許可システム、現場の実行主体などから状態を取得する。

AGV / AMR 群制御搬送を代表的な適用場面とし、次のような協調システムにも適用できる。

* 無人フォークリフトおよび自動搬送システム
* 複数設備による協調生産
* ラインサイド供給およびバッファ制御
* ステーション待機および受入制御
* 経路資源の競合
* エリア許可および資源ロックの調整
* 臨時オーダおよび優先度切替
* エネルギー補給の集中による実行能力低下

![MES / WCS 協調停滞診断モジュール概念図](/images/tpca/08-mes-wcs-collaborative-stagnation-module.png)

図：MES / WCS 協調停滞診断モジュールは製造現場の協調層に配置し、MES、WCS、AGV / AMR、バッファ、加工設備、経路資源、自動扉、エレベータ、充電エリア、安全・許可システム、監視システムなどから複数ソース状態を取得する。

本事例における Current State は、例えば次のような状態である。

```text
タスクが存在
車両がオンライン
ステーションに要求が存在
Waiting / Blocked / Pending が継続
局所的な混雑または断続的な実行
システム全体のスループットが低下
```

Target State：

```text
持続可能な協調実行状態
```

この Target State では、タスク、実行主体、経路、資源、ステーション、下流受入、結果書戻しまでの一連の実行が継続できる状態を対象とする。

PCN は、この Target State Entry の前に配置する。

```text
Current State
      ↓
     PCN
      ↓
Target State
持続可能な協調実行状態
```

PCN は、この Target State Entry に対して複数ソース状態を取得し、C / A / E 状態マッピング、S / D / B 判定、停滞識別、構造分析、Arbitration、Multipath Control を行う。

その後、システムに過去と同じ状態内容が現れた場合も、その時点で新しい状態インスタンスが形成される。

## 3. 複数ソース状態と C / A / E 状態マッピング

協調停滞の判定では、タスク、実行主体、資源、経路、ステーション、許可、下流受入など、複数の対象に関係する状態を使用する。

代表的な信号源と状態を次に示す。

| 信号源                   | 代表的な状態                                               |
| --------------------- | ---------------------------------------------------- |
| MES                   | 作業指示、タスク、優先度、材料要求、ステーション要求、計画変更、手動確認、異常記録            |
| WCS / スケジューリングシステム    | タスクキュー、タスク割当結果、タスク状態、配車結果、資源ロック、経路割当、ステーション占有、バッファ状態 |
| AGV / AMR / 無人フォークリフト | オンライン状態、自動モード、位置、空荷 / 積載状態、バッテリ残量、タスク実行、待機、移動、アラーム状態 |
| 設備 / ステーション           | 受入可能状態、運転状態、待機状態、材料不足状態、完了状態、アラーム状態                  |
| 経路・設備資源               | 狭路、交差点、自動扉、エレベータ、エリア通行許可、バッファ、荷役位置の占有状態              |
| 安全・許可システム             | エリア許可、安全許可、上位システム許可、手動許可、ロック状態                       |
| 下流・書戻し経路              | 下流受入状態、結果書戻し状態、異常処理状態                                |

これらの状態は、「持続可能な協調実行状態」という Target State Entry における機能役割に基づいて C / A / E へマッピングする。

```text
C：必要な条件が揃っているか。
A：移行が許可されているか。
E：移行後の実行チェーンが継続できるか。
```

| 状態変数領域                       | 判定対象                                            | 本事例における代表的な状態                                               |
| ---------------------------- | ----------------------------------------------- | ----------------------------------------------------------- |
| C：Condition / 条件状態           | Target State へ入るために必要な事実条件が成立しているか              | タスク状態、材料要求、ステーション要求、目標ステーション情報、オーダ条件、工程条件                   |
| A：Authority / 許可状態           | 現在のタスク、実行主体または資源について Target State への移行が許可されているか | スケジューリング許可、資源ロック状態、エリア許可、安全許可、手動確認、上位システム許可                 |
| E：Execution Chain / 実行チェーン状態 | Target State へ入った後に後続の実行チェーンを継続できるか             | 実行主体の動作状態、経路通行状態、ステーション受入状態、バッファ状態、下流受入状態、エネルギー補給状態、結果書戻し状態 |

例えば、次のようにマッピングする。

```text
タスク状態 → C
エリア許可 → A
ステーション受入状態 → E
```

タスクの存在は C に関係する状態として扱う。

資源ロック、エリア許可、上位システム許可などは A に関係する状態として扱う。

実行主体、経路、ステーション、バッファ、エネルギー補給、下流受入などは E に関係する状態として整理する。

代表的な状態関係は次の通りである。

* 有効なタスクが存在し、資源ロックの解放待ちとなっている。
* 実行主体はオンラインであり、目標ステーションが受入待ちとなっている。
* 多数の実行主体がエネルギー補給中であり、実タスクを処理できる主体の比率が低下している。
* タスク、実行主体、経路の状態が取得されており、下流受入待ちが継続している。

CAE-SDB の構造については、以下を参照。

[なぜ CAE-SDB なのか ― 状態遷移における機能役割と状態検証の二軸構造](/jp/notes/why-cae-sdb/)

## 4. S / D / B 判定と群全体の状態

C / A / E 状態マッピングの後、PCN は関連状態に対して必要な S / D / B 判定を行う。

```text
S：判定に必要な構造が成立しているか。
D：現在の状態を本判定の根拠として使用できるか。
B：現在の状態が事前定義された制御境界に到達しているか。
```

| 判定性質                  | 判定対象                                                         | 本事例における代表項目                                                                       |
| --------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| S：Structure / 構造完全性   | 必要な対象、信号、インターフェース、マッピング関係、許可元、資源関係、実行チェーン境界が定義・接続され、観測可能であるか | MES-WCS 間のタスクマッピング、資源ロック元、ステーション受入インターフェース、経路資源関係、エネルギー補給状態インターフェース、結果書戻しインターフェース |
| D：Dynamics / 動的時系列有効性 | タスク、実行主体、ステーション、許可、経路、実行状態が現在も有効で、同期・安定し、本判定に使用できるか          | 作業指示変更の未同期、主体位置の遅延、ステーション状態の未更新、許可取消、経路占有状態の競合、実行フィードバックのタイムアウト                   |
| B：Boundary / 制御境界     | 関連状態と事前定義された制御境界との関係                                         | 待機時間、資源占有時間、ステーション容量、群全体の未実行率、エネルギー補給率、再試行回数、キュー長、負荷範囲                            |

例えば、実行主体の位置データに必要なインターフェースが定義・接続されている場合、S の判定対象となる構造を確認できる。

その位置情報が長時間更新されていない場合は、D によって現在の判定根拠としての有効性を評価する。

```text
主体位置データ
→ S：必要な構造を確認
→ D：更新状態・時刻を確認
```

また、群全体の未実行率を事前定義された閾値と比較する場合は、B の判定対象となる。

```text
群全体の未実行率：現在値

事前定義値：
X %

現在値：
X % を超過

→ B 判定
```

協調停滞の識別では、個別状態に加えて、複数の実行主体から集約した状態や指標を使用する。

代表的な指標は次の通りである。

* 群全体の未実行率
* 群全体の補助実行率
* 群全体のエネルギー補給率
* 群全体の許可未成立率
* 経路資源の占有状態
* ステーションの受入状態
* 重要タスクの継続未実行状態

これらの指標は、それぞれ現在の実行状態、資源利用状態、エネルギー補給状態、許可状態などを協調層で把握するために使用する。

例えば、群全体の未実行率に事前定義された境界値を設定している場合、現在値を B の判定対象として扱うことができる。

```text
群全体の未実行率
→ 事前定義された制御境界と比較
→ B 判定
```

さらに、各指標の値と継続時間を用いて、局所的な待機から協調層の継続停滞へ移行しているかを識別する。

![協調停滞識別と Multipath Control の処理フロー](/images/tpca/09-collaborative-stagnation-control-flow.png)

図：モジュールは複数ソース状態を取得し、C / A / E 状態マッピング、S / D / B 判定、群全体の指標算出を行う。これらの結果を用いて停滞識別と構造分析を行い、Arbitration、Multipath Control、PCN Trace へ展開する。

## 5. 停滞識別と構造分析

協調停滞の識別では、タスク、実行主体、実行状態、および群全体の指標について、現在値と継続時間を確認する。

例えば、次のような組合せを停滞識別に使用できる。

```text
有効なタスクが存在
        +
複数の自動運転主体が継続して有効実行へ移行しない
        +
群全体の未実行状態が事前定義された判定条件を継続
        ↓
協調停滞を識別
```

協調停滞を識別した後は、関連する状態、CAE-SDB Result、群全体の指標、タスク、許可、資源、実行チェーンの状態から停滞構造を分析する。

代表的な構造を次に示す。

### 分配制約型

代表的な状態：

* 有効なタスクが存在する。
* 複数の実行主体が長時間実行へ移行していない。
* タスク割当、許可、資源解放、資源ロックなどに関係する状態が実行開始条件を満たしていない。

### 資源競合型

代表的な状態：

* 実行主体が移動、迂回、待機または共有資源の取得処理を継続している。
* 経路、交差点、自動扉、エレベータ、ステーションなどの共有資源に利用競合が発生している。
* 補助的な実行が継続する一方で、有効タスクの進行率が低下している。

### エネルギー偏在型

代表的な状態：

* 多数の実行主体が同じ時間帯に充電またはその他のエネルギー補給状態へ移行している。
* 実タスクに割り当て可能な実行主体の比率が低下している。
* エネルギー補給状態の分布が協調実行能力に影響している。

### 未確定型

既存の状態、CAE-SDB Result、群全体の指標から安定した構造分析結果を形成できない場合は、未確定型として記録する。

この場合、対象時間帯の状態記録を強化し、後続の確認に使用する。

MES / WCS の診断画面では、これらの構造分析結果に加えて、関連する許可、ステーション受入、経路占有などの状態を表示できる。

## 6. CAE-SDB Result、時間情報 T、Arbitration、Multipath Control

PCN は、C / A / E にマッピングされた関連状態に対して必要な S / D / B 判定を行い、一つまたは複数の CAE-SDB Result を形成する。

状態および判定には、対応する時間情報 T を保持する。

時間情報 T は、例えば次の処理に使用する。

* 群全体の状態の継続時間確認
* 関連状態のタイムアウト、未更新状態の確認
* 状態の前後関係の確認
* PCN Trace における履歴追跡

代表的な CAE-SDB Result を次に示す。

| CAE-SDB Result | 本事例における代表的な状態                                                          |
| -------------- | ---------------------------------------------------------------------- |
| C-S            | タスク、対象、ステーション、必要条件に関係する状態マッピングが定義されていない                                |
| C-D            | 作業指示変更が同期されていない、タスク状態が更新されていない、要求状態が有効時間を超えている                         |
| C-B            | タスク待機時間、滞留量、継続未実行時間が事前定義された制御境界に到達している                                 |
| A-S            | スケジューリング許可、資源ロック、エリア許可、手動確認などの許可元が定義されていない、または観測できない                   |
| A-D            | 許可が更新されていない、取り消されている、または資源ロック状態が同期していない                                |
| A-B            | 許可待機時間、資源占有時間、許可範囲が事前定義された制御境界に到達している                                  |
| E-S            | 経路、ステーション、バッファ、下流、エネルギー補給、結果書戻しなどの実行チェーン構造が定義されていない                    |
| E-D            | 経路状態が競合している、ステーション状態が更新されていない、実行主体のフィードバックがタイムアウトしている、実行チェーン状態が同期していない |
| E-B            | 経路待機時間、バッファ占有率、群全体のエネルギー補給率、下流受入能力などが事前定義された制御境界に到達している                |

同一の協調停滞事象について、複数の CAE-SDB Result が同時に形成される場合がある。

停滞識別と構造分析によって得られた情報は、CAE-SDB Result および時間情報 T とともに Arbitration で処理する。

```text
CAE-SDB Result + T
        +
群全体の状態・指標
        +
停滞識別・構造分析
        ↓
Arbitration
        ↓
Multipath Control
```

Arbitration は、今回の Target State Entry に関する判定結果と事前定義された制御制約に基づき、制御上の優先関係を処理する。

代表的な Multipath Control は次の通りである。

* 通常実行の継続
* 待機
* タスク再割当
* 資源解放
* 経路または通行権の調整
* 流量制限
* バッファ分流
* 下流調整
* エネルギー補給方針の調整
* 縮退実行
* 手動確認
* 移行禁止
* 異常隔離
* 強化記録

Multipath Control は、現在の Target State Entry に対する制御結果として、次に進む Target State または目標実行経路を決定する。

処理関係は次のように整理できる。

```text
現在の協調状態
→ C / A / E Mapping
→ S / D / B Evaluation
→ CAE-SDB Result + T
→ 群全体の状態・指標
→ 停滞識別・構造分析
→ Arbitration
→ Multipath Control
```

## 7. PCN Trace と協調停滞の振り返り

PCN は、今回の Target State Entry に関する判定、Arbitration、Multipath Control、実行結果を PCN Trace として記録する。

代表的な記録内容は次の通りである。

* Current State
* Target State
* 関連する実行主体およびタスク
* 主要な入力状態
* 時間情報 T
* C / A / E 状態マッピング
* S / D / B 判定
* CAE-SDB Result
* 群全体の状態または指標
* 停滞識別結果
* 構造分析結果
* Arbitration Result
* Multipath Control
* 実行結果
* Trace ID

これらの記録は、例えば次の用途に使用できる。

* 頻発する停滞入口の抽出
* 協調停滞構造の比較
* 許可および資源ロックに関する振り返り
* 経路およびステーション協調状態の分析
* エネルギー補給分布の分析
* Multipath Control の実行結果比較
* MES / WCS 診断画面への表示
* 後続のエンジニアリング改善

> **PCN Trace は、今回の Target State Entry に使用した状態、停滞識別と構造分析の結果、Arbitration の結果、選択された Multipath Control、および実行結果を一連の履歴として記録する。**

時間情報 T により、同じ状態内容が異なる時点で発生した場合も、それぞれの状態インスタンスと判定履歴を区別できる。

## 8. モジュールの位置付けと公開範囲

MES / WCS 協調停滞診断モジュールは、タスク、スケジューリング、資源、経路、ステーション、許可、実行主体、下流システムなどに分散した状態を、協調停滞の判定と後続制御に使用できる形で整理する。

現場での確認手順は、例えば次のように構造化できる。

```text
現在の協調状態
→ PCN
→ C / A / E Mapping
→ S / D / B Evaluation
→ CAE-SDB Result + T
→ 群全体の状態・指標
→ 停滞識別・構造分析
→ Arbitration
→ Multipath Control
→ PCN Trace
```

これにより MES / WCS では、発生した状態の記録に加え、現在の Target State Entry に関する判定根拠、停滞構造、選択された制御経路を関連付けて表示できる。

本稿で公開する内容は、次の範囲である。

* モジュールの位置付け
* 複数ソース状態
* C / A / E 状態マッピング
* S / D / B 判定
* 群全体の状態および指標
* 停滞識別
* 構造分析
* CAE-SDB Result
* 時間情報 T
* Arbitration
* Multipath Control
* PCN Trace

具体的な閾値、継続時間ウィンドウ、制御優先度、資源解放ルール、経路調整方針、インターフェースパラメータ、内部実行機構については、実際の MES / WCS プラットフォーム、対象設備、安全要求、エンジニアリング仕様に基づいて定める。

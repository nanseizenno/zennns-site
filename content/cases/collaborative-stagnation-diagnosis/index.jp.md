## MES に状態が記録されていても、なぜ製造現場の停滞を説明できないのか

> 適用階層：群制御・協調層 / MES-WCS 協調停滞診断  
> 代表対象：製造現場の協調停滞診断モジュール

**推奨引用：**

全野南政 / Nansei Zenno，  
『MES / WCS 協調停滞診断モジュール事例：MES に状態が記録されていても、なぜ製造現場の停滞を説明できないのか』，  
公開事例，Public Case Version 1.7，2026-10-01，  
https://zennns.com/jp/cases/collaborative-stagnation-diagnosis/

MES と WCS は、通常すでに多くの運転情報を持っている。

ある時点で、稼働中タスクが 42 件、そのうち 17 件が継続待機または未実行になっているとする。実行主体はオンラインで、ステーション要求も存在し、一部の経路は利用可能である。共有資源は一部占有されているが、全体停止を直接説明できるような単体設備の重大アラームは発生していない。

それでもタスクは滞留し続け、複数主体が長時間待機し、協調実行能力が低下している。

確認すべきなのは、タスクの有無や設備のオンライン状態だけではない。

> **現在のシステムが、なぜ継続可能な協調実行状態へ移行できないのか。**

本事例では、「継続可能な協調実行状態への移行」を目標状態入口（Target State Entry）とし、MES、WCS、実行主体、経路資源、許可、ステーション状態を同一の協調判定に関連付ける。

自動化実行ユニットの事例と異なり、本事例では群制御・協調層に固有の分析結果も扱う。群全体として停滞が成立しているか、また現在の停滞がどの構造に該当するかを、CAE-SDB 判定とは別の分析結果として保持する。

事例は、共通の9ステップの分析手順に沿って説明する。

1. 現在状態
2. 目標状態 / 目標状態入口
3. PCN：関連状態取得と C / A / E 状態マッピング
4. 前制御判定と群制御・協調分析
5. 制御調停
6. 複数経路制御
7. 現在の入口に対する制御結果
8. 制御経路の実行 / 後続の目標状態入口と実行結果
9. 状態遷移判定履歴

## 事例対象

本事例の対象は、MES / WCS 協調停滞診断モジュールである。

本モジュールは製造現場の協調層に位置し、MES のタスクとステーション要求、WCS のスケジューリングと搬送タスク、AGV / AMR などの実行主体状態、経路と共有資源状態、区域許可・安全許可、ステーション受入状態、下流状態、群全体の運転指標を扱う。

AGV / AMR の群制御搬送は代表的な適用場面の一つだが、本事例の対象は、より一般的な製造現場における協調停滞である。複数の単体設備に明確な故障がなくても、全体の実行が継続できない状態を扱う。

![MES / WCS 協調停滞診断モジュールの構成イメージ](/images/tpca/08-mes-wcs-collaborative-stagnation-module.jp.png)

図：協調停滞診断モジュールは、MES、WCS、搬送主体、ステーション、経路資源、許可状態、下流状態を取得し、同一の協調状態遷移に関連付ける。

以下の数量と状態の組合せは、本公開事例の運転状態を説明するための例示値であり、特定の実案件データではない。群全体の停滞判定に用いる具体的な閾値、継続時間窓、完全な構造分類ルールは、本公開事例では扱わない。

---

# 1. 現在状態

現在、システムは完全に停止しているわけではない。

稼働中タスク 42 件のうち、25 件は実行済みまたは進行中で、17 件は継続待機または未実行となっている。実行主体はオンラインで、ステーション要求も存在する。重大な設備アラームは発生しておらず、一部の経路も利用可能である。

一方、複数の主体が継続して待機し、一部のタスクが長時間未実行のまま残っている。

現在確認できるのは、全システム停止ではなく、**協調実行が継続的に阻害されている状態**である。

群全体として停滞が成立しているか、また現在の阻害がどのような構造から生じているかは、次の段階で判定する。

---

# 2. 目標状態 / 目標状態入口

本事例で扱うのは、ある1台の AGV が移動できるか、単体設備が起動できるかという問題ではない。

システムレベルの目標状態は「継続可能な協調実行状態」である。

対応する目標状態入口（Target State Entry）は、「継続可能な協調実行状態への移行」とする。

ここでいう継続可能な協調実行とは、現在のタスク、実行主体、資源、許可、経路、ステーションの関係が、システム全体として次の処理を継続できる状態を意味する。個別タスクが一部動いているだけでは、協調実行状態が成立しているとは判断しない。

PCN は、現在の協調状態とこの目標状態入口の間に配置される。

以降の状態マッピング、CAE-SDB 判定、群全体の停滞判定、構造分類、制御処理は、すべてこの協調入口を基準として行う。

---

# 3. PCN：関連状態取得と C / A / E 状態マッピング

PCN は、現在の協調入口に直接関係する状態を各システムから取得し、今回の状態遷移で担うエンジニアリング上の役割に基づいて C / A / E 状態マッピングを行う。

| 代表状態 | 状態マッピング |
|---|---|
| タスク状態、ステーション要求、目標ステーション情報 | C：条件状態 |
| スケジューリング許可、資源ロック、区域許可、安全許可 | A：許可状態 |
| 実行主体状態、搬送経路状態、ステーション受入状態、下流状態 | E：実行チェーン状態 |

本事例では、タスク存在を C、資源ロック状態と安全許可を A、実行主体オンライン、搬送経路利用可能状態、ステーション受入状態を E に関係する状態として扱う。

ここでは、入口に直接関係する状態と、群全体の状態を集約した分析情報を分けて扱う。

前者は、具体的な目標状態入口に対する CAE-SDB 判定へ入る。後者には、群全体の未実行率、補助実行率、エネルギー補給率、許可未成立率などがあり、停滞判定と構造分類に使用する。

群指標そのものを、単独の CAE-SDB 判定結果として扱うことはしない。

---

# 4. 前制御判定と群制御・協調分析

今回の例では、タスクが存在し、実行主体はオンライン、安全許可も成立している。一部の経路は利用可能で、ステーションにも実行要求がある。

一方、資源ロック状態はシステム間で同期していない。

現在の協調入口では、資源ロックは A：Authority / 許可状態に対応する。

資源ロック用インターフェース自体は確立されている。したがって、問題は構造の欠落ではなく、運転中のロック状態がシステム間で一致しておらず、現在の入口に対する有効な許可根拠として使用できないことにある。

このため、CAE-SDB 判定結果は `A-D` となる。

判定内容は、「資源ロック状態がシステム間で同期しておらず、現在の協調入口に対する有効な許可根拠として使用できない」である。

同時に、群制御・協調層では、複数のタスクと実行主体の運転状態を集約して分析する。

本事例では、群全体の未実行率が停滞判定条件を満たし、群全体の補助実行率は資源競合型の特徴を示している。一方、エネルギー補給率に偏りはなく、許可未成立率にも割当制約型を主要因と判断する特徴は認められない。

この結果から、群全体の停滞判定は「成立」、停滞構造分類は「資源競合型」とする。

ここでは、入口レベルの `A-D` と、群制御・協調層における「停滞成立 / 資源競合型」を別の分析結果として保持する。

CAE-SDB 判定結果は、群全体の停滞判定や構造分類を代替しない。群指標を CAE-SDB 座標へ無理に対応付ける必要もない。

両者は、それぞれのエンジニアリング上の意味を保持したまま制御調停へ入力する。

本公開事例では、具体的な比率閾値、継続時間窓、完全な構造分類ルールまでは扱わない。

関連定義については、以下を参照できる。

# 5. 制御調停

制御調停の時点では、資源ロック状態に `A-D` があり、群全体の停滞判定は成立、停滞構造は資源競合型となっている。安全許可は成立している。

この状態でタスクを追加投入したり、個々の設備の自然復旧を待ったりしても、現在の協調関係が改善するとは限らない。

優先して扱う対象は、確認済みの資源ロック状態の不整合である。同時に、資源競合型の特徴が確認されているため、影響経路とタスク割当ても調整する。

制御調停では、資源ロック状態の不整合解消を優先し、影響経路の調整と影響タスクの再割当てを同時に行う方針とする。

---

# 6. 複数経路制御

制御調停の結果に基づき、今回の協調入口では次の処理を複数経路制御として構成する。

- 資源解放
- 搬送経路調整
- タスク再割当て

ロボット把持事例と異なり、ここでいう複数経路制御は、必ずしも1台の設備が直ちに物理動作を行うことを意味しない。

協調層では、資源解放、経路調整、タスク再割当てなどの調整処理を制御結果として整理する。

実際のプロジェクトで、どのシステムが資源解放を実行するか、どのスケジューリングシステムがタスクを再割当てするか、経路変更を自動実行するか、人による確認を必要とするかは、既存の MES、WCS、スケジューリングシステム、現場制御システムのインターフェース、責任分担、制御権限によって決まる。

TPCA / PCN は、既存のスケジューリングや実行システムの制御責任を代替しない。

---

# 7. 現在の入口に対する制御結果

現在の目標状態入口は「継続可能な協調実行状態への移行」である。

今回の入口に対する制御結果は、「現時点では移行しない」となる。

資源ロック状態に `A-D` があり、同時に群全体の停滞が資源競合型として判定されているため、必要な調整処理を先に行う。

調整後、協調状態が継続可能な条件へ回復したかを、更新後の状態に基づいてあらためて判定する。

---

# 8. 制御経路の実行 / 後続の目標状態入口と実行結果

選択された調整処理は、対応する制御権限を持つ既存システムが実行する。

処理が進むと、資源ロック状態はシステム間で再同期され、共有資源の占有関係が再整理される。影響経路は再調整され、影響タスクも再割当てされる。

本事例では、処理完了後に、資源ロック状態が再同期し、主要搬送経路が利用可能状態へ復帰し、影響タスクの再割当てが完了したものとする。継続待機または未実行タスクは減少し、群全体の未実行率も停滞判定条件を下回る。

実行結果として、資源ロック関係の再同期、主要搬送経路の復帰、影響タスクの再割当て完了、群全体の未実行状態の減少を記録する。

これらは、次の判定に使用する新しいエンジニアリング状態事実となる。

現在のシステムが再び「継続可能な協調実行状態」へ移行できるかどうかは、更新後の状態に基づいて同じ入口で再判定する。

代替搬送経路、退避経路、異常系への分岐など、別の目標状態または目標実行経路が選択された場合は、新しい目標状態入口を設定し、対応する PCN が独立して前制御判定を行う。

---

# 9. 状態遷移判定履歴

今回の協調入口については、次のような PCN Trace（状態遷移判定履歴）を記録できる。

| 項目 | 記録内容 |
|---|---|
| 履歴 ID | PCN-COLLAB-XXXX |
| PCN | 協調実行入口 PCN |
| 現在状態 | 協調実行阻害 / 複数主体が継続待機 |
| 目標状態 | 継続可能な協調実行状態 |
| 目標状態入口 | 継続可能な協調実行状態への移行 |
| 稼働中タスク数 | 42 |
| 継続待機または未実行タスク数 | 17 |
| 実行主体 | オンライン |
| 安全許可 | 成立 |
| 資源ロック用インターフェース | 確立済み |
| 資源ロック状態 | システム間で非同期 |
| 利用可能な経路 | あり |
| CAE-SDB 判定結果 | A-D |
| 判定内容 | 資源ロック状態がシステム間で同期しておらず、現在の協調入口に対する有効な許可根拠として使用できない |

| 停滞構造分類 | 資源競合型 |

| 複数経路制御 | 資源解放、搬送経路調整、タスク再割当て |
| 現在の入口に対する制御結果 | 現時点では継続可能な協調実行状態へ移行しない |
| 実行結果 | 資源ロック関係が再同期し、主要搬送経路が利用可能状態へ復帰、影響タスクの再割当てが完了し、群全体の未実行状態が減少 |
| 時間情報 | T |

この履歴では、もともと MES、WCS、実行主体、資源、許可システムに分散していた状態を、同じ協調入口の判定に関連付けている。

また、入口レベルの `A-D` と、群制御・協調層の「群全体の停滞判定 = 成立 / 停滞構造分類 = 資源競合型」は、別の分析結果として保持する。

二つの結果を同じラベルへまとめず、それぞれの意味を保持したまま、同じ状態遷移判定履歴の中で制御処理と実行結果まで追跡する。

後続処理によって新しい目標状態入口が成立した場合は、その入口を担当する PCN が新しい状態遷移判定履歴を記録する。

## 事例まとめ

本事例の開始時点では、タスクが存在し、実行主体はオンライン、ステーション要求もあり、一部経路は利用可能である。単体設備には重大アラームがない。

一方で、複数タスクが継続して未実行となり、複数主体が待機し、全体の協調実行が阻害されている。

各システムの画面を個別に確認すれば、それぞれが保持する局所的な状態情報は確認できる。ただし、それらは分散している。

「継続可能な協調実行状態への移行」という目標状態入口を基準に整理すると、資源ロック状態がシステム間で非同期となっており、入口レベルでは `A-D` が生成される。

同時に、群全体の運転データからは、停滞判定が成立し、停滞構造は資源競合型と判断される。

その結果、資源ロック状態の不整合解消を優先し、搬送経路調整とタスク再割当てを行う。処理後は、資源ロック関係が再同期し、主要搬送経路が利用可能状態へ復帰し、群全体の未実行状態が減少する。

### 本事例によって明確になるエンジニアリング情報

| 従来の現場情報から確認できること | 本事例によってさらに明確になること |
|---|---|
| タスクが生成されている | 「継続可能な協調実行状態へ移行できるか」という明確な目標状態入口を判定対象として設定できる |
| 実行主体がオンラインである | 主体がオンラインであることは関連状態の一つであり、協調実行全体の継続可能性を単独では示さない |
| 複数の実行主体が待機している | 群全体の未実行率を用いて、複数主体を含む停滞が成立しているかを判定できる |
| 資源ロックに不整合がある | 資源ロックを現在の入口における A として位置付け、`A-D` として整理できる |
| 単体設備に重大アラームがない | 協調上の問題は、単体設備故障がなくても、タスク、許可、共有資源、実行チェーン間の関係から発生し得る |
| 経路や共有資源に競合が見られる | 群全体の補助実行率、エネルギー補給率、許可未成立率などを用いて、停滞構造を資源競合型として整理できる |
| 現場では「全体が止まっている」としか見えない | 現在の協調入口における `A-D` と、群制御・協調層における資源競合型停滞を分けて説明できる |
| エンジニアが複数システムを確認しながら対処方法を判断する | 制御処理として資源解放、搬送経路調整、タスク再割当てを明示できる |
| 対応後は新しい運転状態だけが残る | 資源ロックの再同期、経路復旧、タスク再割当て、群全体の未実行状態の変化まで同じ工程履歴として確認できる |
| MES、WCS、搬送主体、設備がそれぞれログを保存している | 状態、CAE-SDB 判定、群全体の停滞判定、停滞構造分類、制御、実行結果を一件の状態遷移判定履歴として関連付けられる |

本事例では、分散した状態を一つの明確な目標状態入口へ関連付け、協調入口に関係する状態について CAE-SDB 判定を行い、群全体の停滞判定・構造分類を別の分析結果として保持したうえで、同じ制御判断へ接続している。

状態、判定、停滞構造、制御、実行結果を同じ状態遷移判定履歴として記録することで、MES、WCS、搬送主体、共有資源、許可システムに分散していた情報を、一連のエンジニアリング関係として追跡できる。

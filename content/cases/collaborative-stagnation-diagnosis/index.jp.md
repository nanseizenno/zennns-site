## なぜ MES に状態が記録されていても、製造現場の停滞理由を説明しにくいのか？

> 適用階層：群制御協調層 / MES-WCS 協調停滞診断

> 代表対象：製造現場協調停滞診断モジュール

**推奨引用形式：**
```text
全野南政 / Nansei Zenno，「MES / WCS 協調停滞診断モジュール事例：なぜ MES に状態が記録されていても、製造現場の停滞理由を説明しにくいのか」，公開事例，Public Case Version 1.6，2026-09-20，https://zennns.com/jp/cases/collaborative-stagnation-diagnosis/
```

MES では、タスク、設備、ステーション、材料、アラーム、生産数量、生産実績などを記録できる。

WCS では、搬送タスク、車両状態、経路状態、資源占有状態、スケジューリング結果などを記録できる。設備システムでは運転、待機、アラーム、インターロックなどを記録でき、HMI には Ready（準備完了）、Waiting（待機）、Blocked（阻害）、Pending（保留） などの運転状態が表示される。

しかし、多設備・多タスク・多システムが連携する製造現場では、次のような状態が発生することがある。

- タスクは生成されているが、実行が継続的に進まない。

- 搬送主体はオンラインで、ステーションにも要求があるが、補給や搬送が継続的な実行につながらない。

- 個々の設備に明確な故障がなくても、システム全体のスループット低下が続く。

- MES、WCS、PLC、搬送主体、ステーションに状態記録があっても、協調処理がどこで阻害されているかを短時間で特定しにくい。

- オーダ変更、資源競合、許可待ち、下流受入待ち、人による確認、エネルギー補給などが同時に群全体の実行へ影響する。

本事例で扱う中心的な問いは、次のとおりである。

> ********現在のシステムが、なぜ協調実行を継続できる状態へ移行できないのか。******

本事例では、共通の9ステップのエンジニアリング分析手順に沿って説明する。
```text
1. 現在状態
2. 目標状態 / 目標状態入口
3. PCN（前制御ノード）：関連状態取得 + C / A / E 状態マッピング
4. 前置判定と群制御協調分析
   ├─ S / D / B 判定
   │  → CAE-SDB 判定結果+ T（時間情報）
   └─ 群集約指標
      → 協調停滞の識別
      → 停滞構造の分類
5. 制御優先度調停
6. 複数経路制御
7. 現在の入口に対する制御結果
8. 制御経路の実行 / 後続 目標状態入口 と 実行結果
9. PCN Trace（PCN 状態遷移判定履歴）
```

この9ステップによって、

> ********現在の協調状態から協調実行を継続できる状態へ移行しようとする 1回の要求が、どのように状態整理、前置判定、群全体の停滞識別、停滞構造の分類、制御、実行、記録まで処理されるか******

を確認できる。

基本概念については、以下を参照。

- [Concepts｜基本概念](/jp/concepts/)

- [TPCA / PCN 状態遷移前制御アーキテクチャ｜ホワイトペーパー](/jp/whitepaper/)

## 事例対象

本事例では、********MES / WCS 協調停滞診断モジュール******を対象とする。

本モジュールは製造現場の協調層に配置し、MES、WCS、搬送システム、設備ユニット、ステーション、バッファ、経路資源、許可システム、現場の実行主体などから関連状態を取得する。

AGV / AMR の群制御搬送を代表的な適用場面とするほか、無人フォークリフトや自動搬送システム、複数設備による協調生産、ラインサイド供給とバッファ調整、ステーション待機と受入、経路資源競合、エリア許可と資源ロックの調整、エネルギー補給の集中による群全体の実行能力低下などにも適用できる。

本事例では、TPCA / PCN の共通工程に加えて、群制御協調層に固有の群集約指標、協調停滞の識別、停滞構造の分類を独立して保持し、その結果を CAE-SDB 判定結果 とともに後続の 制御優先度調停 へ接続する。

![MES / WCS 協調停滞診断モジュール概念図](/images/tpca/08-mes-wcs-collaborative-stagnation-module.png)

図：MES / WCS 協調停滞診断モジュールは製造現場の協調層に配置し、MES、WCS、AGV / AMR、バッファ、加工設備、経路資源、自動扉、エレベータ、充電エリア、安全・許可システム、監視システムなどから複数系統の状態を取得する。

## 1. 現在状態

本事例は、製造現場にタスクと実行主体が存在しているものの、協調実行が継続的に阻害されている状態から開始する。

現在状態 は、例えば次のように整理できる。
```text
現在状態：タスクが存在
  +
実行主体がオンライン
  +
一部タスクが継続的に未実行
  +
Waiting（待機） / Blocked（阻害） / Pending（保留） が継続
  +
協調実行が阻害されている
```

現場では、さらに次のような状態が同時に見えることがある。
```text
ステーションに要求がある
搬送主体は移動可能
一部の経路は利用可能
単体設備に重大なアラームはない
一部のタスクは実行されている
```

これらは、現在の協調実行が阻害されていることを示すが、この時点で群全体の協調停滞が成立していると直接判断するものではない。

本分析では、まず現在の協調状態を明確にし、どのタスク、実行主体、資源、許可、ステーションを同一の協調実行コンテキストとして扱うかを定める。

後続の関連状態取得、C / A / E 状態マッピング、S / D / B 判定、群集約指標の生成、協調停滞の識別は、この 現在状態 を今回の分析起点とする。

---

## 2. 目標状態 / 目標状態入口

今回の 目標状態は、
```text
【目標状態】協調実行を継続できる状態
```

とする。

対応する 目標状態入口は、
```text
【目標状態入口】協調実行を継続できる状態への移行
```

である。

この 目標状態 は、タスク、実行主体、経路、資源、許可、ステーション、下流受入、結果書戻しが、継続して接続できる協調実行関係を形成している状態を表す。

PCN は、現在の協調状態と 目標状態入口 の間に配置する。
```text
現在状態［協調実行が阻害されている］
    ↓
PCN［「協調実行を継続できる状態への移行」に対する前制御判定］
    ↓
目標状態入口［協調実行を継続できる状態への移行］
    ↓
目標状態［協調実行を継続できる状態］
```

本事例における C / A / E、S / D / B、協調停滞の識別、停滞構造の分類、制御優先度調停、複数経路制御 は、すべてこの明確な 目標状態入口 に対応付ける。

PCN と 目標状態入口 の関係については、以下を参照。

[なぜ PCN は TPCA の最小エンジニアリングノードなのか？](/jp/notes/pcn-minimum-engineering-unit/)

## 3. PCN：関連状態取得と C / A / E 状態マッピング

協調停滞では、複数のタスク、実行主体、資源、経路、ステーション、許可、下流受入などを確認する必要がある。

PCN は、「協調実行を継続できる状態への移行」に直接関係する複数系統の状態を取得する。

| 情報源 | 今回の協調実行入口に関係する主な状態 |

|---|---|

| MES | 作業指示、タスク、優先度、材料要求、ステーション要求、計画変更、人による確認、異常記録 |

| WCS / スケジューリングシステム | タスクキュー、タスク割当結果、タスク状態、配車結果、資源ロック、経路割当、ステーション占有、バッファ状態 |

| AGV / AMR / 無人フォークリフト | オンライン状態、自動モード、位置、空荷 / 積載状態、バッテリ残量、タスク実行、待機、移動、アラーム状態 |

| 設備 / ステーション | 受入可能状態、運転状態、待機状態、材料不足状態、完了状態、アラーム状態 |

| 経路・設備資源 | 狭隘通路、交差点、自動扉、エレベータ、エリア通行権、バッファ、荷役位置の占有状態 |

| 安全・許可システム | エリア許可、安全許可、上位システム許可、手動許可、ロック状態 |

| 下流・書戻し経路 | 下流受入状態、結果書戻し状態、異常処理状態 |

これらの状態を、今回の 目標状態入口 におけるエンジニアリング上の役割に基づいて C / A / E の状態変数領域へ整理する。
```text
C = Condition（条件状態）
A = Authority（許可状態）
E = 実行チェーン（実行チェーン状態）
```

本事例では、例えば次のように整理できる。

| 状態変数領域 | 今回の 目標状態入口 における主な状態 |

|---|---|

| C：Condition（条件状態） | タスク状態、材料要求、ステーション要求、目標ステーション情報、オーダ条件、工程条件 |

| A：Authority（許可状態） | スケジューリング許可、資源ロック、エリア許可、安全許可、人による確認、上位システム許可 |

| E：実行チェーン（実行チェーン状態） | 実行主体状態、経路通行状態、ステーション受入状態、バッファ状態、下流受入状態、結果書戻し状態 |

例えば、
```text
【タスク状態】C
【エリア許可】A
【ステーション受入状態】E
```

と整理できる。

実行主体がオンラインであること、タスクが存在すること、または特定設備が Ready であることは、いずれも今回の 目標状態入口 に関係する状態の一部にすぎない。

現在の協調実行を継続できるかどうかは、他の Condition、Authority、実行チェーン の状態と合わせて判定する必要がある。

エネルギー補給状態や群全体の未実行率など、群全体に関係する情報は、本事例では後続の群制御協調分析で扱う。

これらの群全体の情報について、個別の PCN で C / A / E における役割が明確に定義され、対応する S / D / B ルールが設定されている場合に限り、対応する CAE-SDB 判定結果 を形成する。

---

## 4. 前置判定と群制御協調分析

関連状態取得と C / A / E 状態マッピングの後、同じ 目標状態入口 に対して次の二つの処理を行う。
```text
A. S / D / B 判定
   → CAE-SDB 判定結果+ T（時間情報）

B. 群制御協調分析
   → 群集約指標
   → 協調停滞の識別
   → 停滞構造の分類
```

CAE-SDB 判定結果 と、協調停滞の識別結果・停滞構造の分類結果は、それぞれ独立して形成し、後続の 制御優先度調停への入力とする。

---

## 4.1 S / D / B 判定

PCN は、今回の 目標状態入口 に必要な関連状態に対して S / D / B 判定を行う。
```text
S = Structure（構造完全性）
D = Dynamics（動的時系列有効性）
B = Boundary（制御境界）
```

本事例における代表的な確認内容は次のとおりである。

| 判定特性 | 主な確認内容 |

|---|---|

| S：Structure（構造完全性） | 今回の協調実行入口に必要なタスク、実行主体、資源、許可、ステーション、下流受入、結果書戻しについて、必要なインターフェース、マッピング、情報源、対象関係が定義・接続され、観測可能であるか |

| D：Dynamics（動的時系列有効性） | 現在の状態を今回の協調実行入口の判定根拠として引き続き使用できるか。作業指示とタスクの同期、実行主体位置の更新、許可の撤回、資源ロックの更新、ステーション状態の更新、経路状態の同期、実行フィードバックの時系列有効性などを確認する |

| B：Boundary（制御境界） | 現在有効な状態の値または範囲が、待機時間、資源占有時間、ステーション容量、許可時間窓、資源利用範囲、再試行回数など、事前に定義した許容範囲または制御境界内にあるか |

C / A / E の状態変数領域と S / D / B の判定特性を組み合わせることで、9つの CAE-SDB 判定座標を構成できる。

|  | S：Structure | D：Dynamics | B：Boundary |

|---|---|---|---|

| C：Condition | C-S | C-D | C-B |

| A：Authority | A-S | A-D | A-B |

| E：実行チェーン | E-S | E-D | E-B |

本事例では、「協調実行を継続できる状態への移行」という 目標状態入口 に対して、代表的なエンジニアリング上の問題を次のように整理できる。

| 判定座標 | 本事例における代表的なエンジニアリング上の問題 |

|---|---|

| C-S | MES と WCS 間のタスク対応が未定義である。タスクと対象、ステーション、目的地、工程条件の関係が未設定である。今回の入口に必要なタスク項目や対象関係を取得できない |

| C-D | 作業指示の変更が現在タスクへ反映されていない。タスク状態が長時間更新されていない。ステーション要求や目的地情報が失効している。タスクと実際の実行対象の切替が同期していない |

| C-B | 現在有効なタスクの待機時間が許容範囲を超えている。タスク優先度、要求時間窓、計画偏差などが今回の入口に対して事前に定義した境界を超えている |

| A-S | スケジューリング許可、資源ロック、エリア許可、安全許可、人による確認、上位システム許可などの情報源が未定義である。許可インターフェースやマッピングが未設定である。重要な許可状態を現在の PCN から取得できない |

| A-D | 許可状態が長時間更新されていない。今回の入口判定中に許可が撤回された。資源ロック状態が同期していない。エリア許可や人による確認に更新遅延または失効がある |

| A-B | 現在有効な許可が適用範囲外にある。許可の有効時間窓が今回の入口条件を満たしていない。資源ロック占有時間または許可利用範囲が事前に定義した境界に達している |

| E-S | 現在の協調実行に必要な実行主体状態、経路資源関係、ステーション受入、バッファ、下流受入、結果書戻しなどのインターフェースまたは接続関係が未定義・未接続である |

| E-D | 実行主体の位置やタスク実行状態が更新されていない。経路資源状態が同期していない。ステーション受入状態や下流受入状態に遅延・失効がある。実行フィードバックまたは結果書戻しがタイムアウトしている |

| E-B | 現在有効な経路容量、ステーション容量、バッファ容量、下流受入能力、実行待機時間など、現在の 実行チェーン に関係する値が事前に定義した許容境界を超えている |

この 9つの判定座標は、今回の 目標状態入口 において発生し得る状態判定上の問題を整理するために使用する。

> ********1回の状態遷移前制御で、9つすべての CAE-SDB 判定結果 を形成する必要はない。******

今回の 目標状態入口 に対して対応する判定ルールが定義され、判定に必要な根拠を取得でき、実際に 判定 を行った場合に、その結果として該当する CAE-SDB 判定結果 を形成する。

例えば、
```text
資源ロックのインターフェース：接続済み
資源ロック状態：長時間未更新
```

という状態を考える。

この資源ロック状態が今回の 目標状態入口 で A：Authority（許可状態）にマッピングされ、対応する D 判定が定義され、実際にその判定を行った結果、現在の判定根拠として使用できないと確認された場合、
```text
A-D：
資源ロック状態を、今回の協調実行入口に対する
有効な許可状態として使用できない
```

という CAE-SDB 判定結果を形成できる。

また、
```text
下流ステーション：受入可能
状態更新：長時間なし
```

という状態が E：実行チェーン（実行チェーン状態）にマッピングされ、対応する D 判定が定義され、実際にその判定を行った場合は、
```text
E-D：
下流受入状態を、今回の協調実行入口に対する
有効な実行チェーン状態として使用できない
```

という CAE-SDB 判定結果 を形成できる。

さらに、
```text
ステーション受入状態：現在有効
ステーション容量：事前に定義した上限に到達
```

という状態が E にマッピングされ、対応する B 判定が定義され、実際にその判定を行った場合は、
```text
E-B：
現在有効なステーション受入能力が、
今回の協調実行入口に対する事前定義済みの制御境界に達している
```

という CAE-SDB 判定結果 を形成できる。

> ********特定の S / D / B 判定を行う必要があることは、その判定が今回の入口に対する評価ルールに含まれることを意味する。CAE-SDB 判定結果 は、対応する判定が実際に行われ、結果が得られた後に形成する。******

時間情報 T は、今回使用した状態および判定結果と関連付けて保持する。

C / A / E と S / D / B の二軸構造については、以下を参照。

[なぜ CAE-SDB なのか ― 状態変数領域と判定特性の二軸構造](/jp/notes/why-cae-sdb/)

## 4.2 群集約指標

単体状態だけでは、群全体の協調状態を把握しにくい場合がある。

そのため、群制御協調分析では、複数の実行主体、タスク、資源、許可などの状態を群全体の観点から集約する。

代表的な群集約指標には、次のようなものがある。
```text
群全体の未実行率
群全体の補助実行率
群全体のエネルギー補給率
群全体の許可未成立率
```

このうち「群全体の許可未成立率」は、群制御協調層で従来から使用している分析用語を引き継ぐ。

具体的なプロジェクトでは、対応する状態はスケジューリング上の許可、資源利用許可、その他 Authority の根拠となる外部観測可能な状態から取得できる。

必要に応じて、経路資源占有、ステーション受入、重要タスクの継続未実行などの群全体の状態も組み合わせて判断する。

これらの群集約指標は、現在の多主体システム全体の実行状態を記述するために使用し、群制御協調分析の結果として独立して保持する。

例えば、
```text
群全体の未実行率が停滞識別条件を満たす
```

という結果は、まず群集約指標が対応する停滞識別条件に到達したことを意味する。

その指標が今回の PCN で C / A / E のいずれかの状態変数領域に明確にマッピングされ、対応する S / D / B 判定が実際に行われた場合にのみ、C-B、A-B、E-B などの CAE-SDB 判定結果 を形成する。

---

## 4.3 協調停滞の識別

群集約指標を形成した後、現在の協調阻害状態が群全体として停滞識別条件に達しているかを判断する。

例えば、次のような関係で確認する。
```text
有効なタスクが存在
        +
複数の自動運転主体が有効な実行状態へ移行しない状態が継続
        +
群全体の未実行状態が事前に定義した判定条件に達する
        ↓
協調停滞の識別
```

判定条件を満たした場合は、
```text
【協調停滞の識別結果】成立
```

とする。

条件を満たしていない場合は、現在の運転事実を保持し、この時点で「群全体の協調停滞」という結論を先に付与しない。

---

## 4.4 停滞構造の分類

協調停滞の識別が成立した後、群集約指標、タスク、許可、資源、実行状態を組み合わせて、停滞構造を分類する。

ここでいう「停滞構造の分類」は、群制御協調層における群全体の停滞分析であり、S：Structure（構造完全性）とは別の処理層に属する。

代表的な分類には、次のものがある。

### 割当制約型

典型的には、有効なタスクが存在しているにもかかわらず、複数の実行主体が長時間実行へ移行できず、タスク割当、許可または資源解放が有効な実行関係を形成していない状態が含まれる。

### 資源競合型

典型的には、実行主体が移動、迂回、待機、共有資源の取得などを継続し、経路、交差点、自動扉、エレベータ、ステーションなどの共有資源に競合が発生し、補助的な実行が多い一方で有効タスクの進行が不足している状態が含まれる。

### エネルギー偏在型

典型的には、多数の実行主体が同じ時間帯に充電またはその他のエネルギー補給状態へ移行し、実タスクへ割り当て可能な主体の割合が低下し、エネルギー補給状態の分布が群全体の協調実行能力へ明確に影響している状態が含まれる。

### 未確定型

現在取得できている状態、群集約指標、その他の根拠だけでは信頼できる分類を形成できない場合は、未確定型として保持し、詳細記録または人による確認へ移行する。

![協調停滞の識別と複数経路制御の流れ](/images/tpca/09-collaborative-stagnation-control-flow.png)

図：関連状態取得と C / A / E 状態マッピングの後、一方では CAE-SDB 判定結果 を形成し、もう一方では群集約指標、協調停滞の識別、停滞構造の分類を形成する。両方の結果を後続の 制御優先度調停 へ入力する。

## 5. 制御優先度調停

1回の 目標状態入口 では、次のような複数の結果や制約が同時に存在する場合がある。
```text
CAE-SDB 判定結果
協調停滞の識別結果
停滞構造の分類結果
重要な許可
安全上の制約
その他の制御制約
```

例えば、本事例で次の状態が確認されたとする。
```text
【CAE-SDB 判定結果】
A-D
  資源ロック状態が同期していない
```

同時に、
```text
【群集約指標】
  群全体の未実行率が停滞識別条件を満たす

【協調停滞の識別結果】
  成立

【停滞構造の分類】
  資源競合型

【重要な許可】
  安全許可は成立
```

とする。

制御優先度調停では、次の情報をもとに、今回の 目標状態入口 に対する制御上の優先関係を処理する。

- CAE-SDB 判定結果

- 協調停滞の識別結果

- 停滞構造の分類結果

- 重要な許可

- 安全上の制約

- 今回の 目標状態入口 に適用する制御ルール

- 今回の入口で選択可能な制御経路

重要な A：Authority（許可状態）は、独立した必要制約となり得る。

例えば、重要な安全許可が成立していない場合は、今回の入口で「協調実行を継続できる状態」への移行許可を形成しない。

制御優先度調停 が扱うのは、

> ********複数の判定結果、群全体の協調停滞状態、制御制約が同時に存在するとき、制御上どの処理を優先するか******

である。

---

## 6. 複数経路制御

制御優先度調停 の結果に基づいて、PCN は今回の 目標状態入口 に対する 複数経路制御を形成する。

MES / WCS 協調停滞診断モジュールが形成できる代表的な制御経路には、次のようなものがある。
```text
通常実行の継続
待機
タスク再割当
資源解放
経路・通行権の調整
流量制限
バッファ振り分け
下流調整
エネルギー補給方針の調整
縮退実行
人による確認
移行禁止
異常隔離
詳細記録
```

例えば、本事例で、
```text
【協調停滞の識別結果】
  成立

【停滞構造の分類】
  資源競合型

【CAE-SDB 判定結果】
  A-D
  資源ロック状態が同期していない
```

ことが確認されたとする。

現在の制御ルールに基づき、制御優先度調停 の結果として、
```text
【複数経路制御】
  資源解放 + 経路調整 + タスク再割当
```

を形成できる。

本公開事例において、MES / WCS 協調停滞診断モジュールは、まず構造化された制御結果、制御提案、または調整要求を形成する。

実際のプロジェクトで、本モジュールが直接制御指令を発行するかどうかは、既存 MES / WCS、スケジューリングシステム、現場制御システムとのインターフェースおよび制御権限によって決まる。

また、特定の 複数経路制御 が新しい 目標状態 / 目標実行経路 に対応する場合は、その経路へ入る際に新しい状態遷移前判定を行う。

---

## 7. 現在の入口に対する制御結果

今回の代表状態を次のように整理する。
```text
【タスク】存在
【実行主体】オンライン
【資源ロック状態】同期していない
【安全許可】成立
【群全体の未実行率】停滞識別条件を満たす
【協調停滞の識別結果】成立
【停滞構造の分類】資源競合型
```

現在、
```text
【CAE-SDB 判定結果】
A-D
```

が形成されている。

制御優先度調停 により、今回の 複数経路制御 が、
```text
資源解放 + 経路調整 + タスク再割当
```

と決定されたとする。

この場合、今回の「協調実行を継続できる状態への移行」という 目標状態入口 に対する制御結果は、
```text
【現在の入口に対する制御結果】
協調実行を継続できる状態へは、現時点では移行しない
```

となる。

制御経路の選択はすでに 制御優先度調停 の段階で行われている。本ステップでは、今回の 目標状態入口 に対する具体的な制御結果を明確にする。

実際の制御経路が正常に実行されたかどうかは、次のステップで確認する。

---

## 8. 制御経路の実行 / 後続の目標状態入口と実行結果

今回決定された 複数経路制御 は、
```text
資源解放 + 経路調整 + タスク再割当
```

である。

MES / WCS 協調停滞診断では、複数経路制御 が形成された後、次の二つのエンジニアリング上のケースを区別する必要がある。

## 8.1 現在入口の中で行う調整処理または制御要求

複数経路制御 が、資源解放、経路調整、タスク再割当など、現在の協調入口の中で行う調整処理、制御提案、または制御要求を意味し、新しい 目標状態 / 目標実行経路 を構成しない場合は、対応する制御権限を持つ既存 MES、WCS、スケジューリングシステム、または現場制御システムが処理を実行する。

実行例を次に示す。
```text
現在の協調入口では移行しない
    ↓
【複数経路制御】資源解放 + 経路調整 + タスク再割当
    ↓
既存制御システムが異常占有または失効した資源ロックを処理
    ↓
経路と通行権を再調整
    ↓
影響を受けたタスクを再割当
    ↓
実行フィードバック
    ↓
新しい協調運転状態を形成
```

処理後、例えば次の状態になったとする。
```text
資源ロック：整合した状態へ回復
主要経路：利用可能
影響タスク：再割当完了
群全体の未実行率：停滞識別条件未満へ回復
```

この場合、
```text
【実行結果】
  関連する資源と経路の関係が回復し、影響を受けたタスクが再び実行可能となった
```

と整理できる。

このケースでは、実行フィードバック と 実行結果 を、現在の 目標状態入口 に対応する PCN Trace に引き続き関連付けることができる。

## 8.2 複数経路制御 が新しい 目標状態 / 目標実行経路 を指す場合

複数経路制御 が、新しい 目標状態 / 目標実行経路、例えば代替経路、戻し経路、異常系への分岐経路、その他の独立した入口判定を必要とする後続状態を選択した場合、その経路は「選択された」という理由だけで進入許可済みとはみなさない。

この場合、新しい状態遷移入口を形成する。
```text
元の 目標状態入口
    ↓
複数経路制御
    ↓
新しい 目標状態 / 目標実行経路 を選択
    ↓
対応する 目標状態入口
    ↓
対応 PCN が前制御判定を再実行
    ↓
当該入口で移行許可が形成された場合
    ↓
対応する経路を実行
    ↓
実行結果
```

つまり、

> ********複数経路制御 が候補経路を選択したことは、その経路がすでに進入条件を満たしたことを意味しない。******

システムが実際に新しい 目標状態 / 目標実行経路 へ入ろうとする時点で、その経路に対応する 目標状態入口 において、対応 PCN が当該入口の要求に基づき関連状態を改めて取得し、新しい C / A / E 状態マッピング、S / D / B 判定、制御優先度調停、複数経路制御 を実行する。

本事例の「資源解放 + 経路調整 + タスク再割当」は、現在入口の中で行う調整処理の例として扱い、新しい 目標状態入口 として固定しない。

実際のプロジェクトでは、特定の制御出力が新しい 目標状態 / 目標実行経路 を構成するかどうかは、その経路に独立した進入条件、許可、実行チェーン、前制御判定が必要かどうかに基づいて決める。

したがって、1回の処理では、次の関係を区別する。
```text
CAE-SDB 判定結果 + 協調停滞の識別 + 停滞構造の分類
        ↓
制御優先度調停
        ↓
複数経路制御
        ↓
現在の入口に対する制御結果
        ↓
        ├─ 現在入口の中で行う調整処理 / 制御要求
        │      ↓
        │   実行フィードバック
        │      ↓
        │   実行結果
        │
        └─ 新しい 目標状態 / 目標実行経路
               ↓
           新しい 目標状態入口
               ↓
           対応 PCN が再判定
               ↓
           経路実行
               ↓
           実行結果
```

各要素の役割は、次のように整理できる。
```text
制御優先度調停
  = 判定結果、群制御協調分析結果、制御制約の優先関係を処理する

複数経路制御
  = 確定した制御上選択可能な経路、調整方向、または後続候補経路を出力する

現在の入口に対する制御結果
  = 現在の 目標状態入口 をどのように扱うかを示す

実行結果
  = 実際の実行後に何が成立したかを示す
```

状態タイプの循環と実運転の状態インスタンスの関係については、以下を参照。

[TPCA における状態インスタンスの単方向性 ― 状態タイプの循環と実運転履歴の違い](/jp/notes/tpca-unidirectional-state-transition/)

## 9. PCN Trace（PCN 状態遷移判定履歴）

今回の状態遷移に対する制御処理が完了した後、PCN は、入力状態、判定、協調停滞の識別、停滞構造の分類、制御、実行結果を関連付けて PCN Trace として記録する。

例えば、今回の Trace は次のように整理できる。
```text
【PCN】協調実行入口 PCN

【現在状態】協調実行阻害 / 複数主体の Waiting が継続

【目標状態】協調実行を継続できる状態

【目標状態入口】協調実行を継続できる状態への移行

主な入力：

  Task = Available

  Agents = Online

  Resource Lock = Unsynchronized

  Safety Permission = TRUE

【CAE-SDB 判定結果】

A-D

資源ロック状態が同期していない

【群集約指標】

群全体の未実行率が停滞識別条件を満たす

【協調停滞の識別結果】

成立

【停滞構造の分類】

資源競合型

【重要な許可】

安全許可は成立

制御優先度調停結果：

資源解放、経路調整、タスク再割当を優先

【複数経路制御】

資源解放 + 経路調整 + タスク再割当

【現在の入口に対する制御結果】

協調実行を継続できる状態へは、現時点では移行しない

【実行結果】
関連する資源と経路の関係が回復し、影響を受けたタスクが再び実行可能となった

【時間情報】T

【Trace ID】PCN-COLLAB-XXXX
```

PCN Trace は、1回の 目標状態入口 を単位として、今回使用した状態、CAE-SDB 判定結果、群制御協調分析結果、制御優先度調停、複数経路制御、現在の入口に対する制御結果、実際の 実行結果 を関連付けて記録する。

複数経路制御 が、現在入口の中で行う調整処理、資源処理、制御提案、または制御要求のみを形成する場合、その 実行フィードバック と 実行結果 は現在の PCN Trace に引き続き関連付けることができる。

一方、複数経路制御 が新しい 目標状態 / 目標実行経路 を選択する場合は、新しい 目標状態入口 に対応する PCN が新しい PCN Trace を形成し、前の Trace と関連付ける。
```text
元の入口の PCN Trace
    ↓
Selected Next 目標状態入口
    ↓
次の入口に対応する PCN
    ↓
新しい PCN Trace
    ↓
実行結果
```

前の入口の 複数経路制御 は、次の候補となる状態遷移入口を選択できるが、次の入口自体の前制御判定を代替することはできない。

PCN Trace を継続して蓄積することで、例えば次の内容を分析できる。

- 協調阻害が頻発する 目標状態入口 の識別

- 協調停滞の識別結果の集計

- 停滞構造の分類比較

- タスク割当と資源ロックに関する問題の振り返り

- 経路とステーションの協調問題分析

- エネルギー補給分布の分析

- 頻発する CAE-SDB 判定結果 の集計

- 頻発する 複数経路制御 の集計

- 制御経路と 実行結果 の関係比較

- MES / WCS 診断画面への表示

- エンジニアリング変更前後の比較

さらに、長期的には次のような観点で比較できる。
```text
どの 目標状態入口 が繰り返し成立しないか
どの停滞構造が高頻度で発生しているか
どの CAE-SDB 判定結果 が特定の停滞構造と同時に発生しやすいか
どの 複数経路制御 が繰り返し選択されているか
制御選択と 実行結果 の間にどのような関係があるか
```

## 事例まとめ

MES、WCS、設備、搬送システムには、タスク、実行主体、経路、資源、ステーション、許可など、多くの状態が記録されている。本事例では、これらの分散した状態を、明確な目標状態入口を基準として9ステップのエンジニアリング分析手順に沿って整理した。

分析は、現在状態と目標状態を明確にするところから始まる。次に、PCN が今回の目標状態入口に関係する状態を取得し、C / A / E の状態変数領域へ整理する。その後、第4ステップで前置判定と群制御協調分析を行い、第5ステップ以降で制御優先度調停、複数経路制御、現在の入口に対する制御結果、実行結果、PCN Trace へつなげる。

この事例で重要なのは、第4ステップに二つの分析系統があることである。

CAE-SDB では、今回の目標状態入口に関係する状態について、C / A / E による状態遷移上の役割と、S / D / B による判定特性を組み合わせて構造化判定を行う。これにより、C-D、A-B、E-D などの CAE-SDB 判定結果を形成する。

一方、群制御協調分析では、群全体の未実行率、補助実行率、エネルギー補給率、許可未成立率などの群集約指標を用いて、協調停滞が成立しているかを確認し、成立している場合には停滞構造を分類する。

つまり、CAE-SDB は「今回の目標状態入口に関係する状態をどのように判定するか」を扱い、群制御協調分析は「多主体システム全体でどのような協調阻害が起きているか」を扱う。両者の役割は異なるが、結果は制御優先度調停で合流する。
```text
CAE-SDB 判定結果
        ＋
協調停滞の識別結果
        ＋
停滞構造の分類結果
        ＋
重要な許可・制御制約
        ↓
制御優先度調停
        ↓
複数経路制御
```

複数経路制御の後は、処理を二つに分けて考える。

資源解放、経路調整、タスク再割当などを、現在の目標状態入口に関係する調整処理として実行する場合は、既存の MES、WCS、スケジューリングシステム、または現場制御システムがその処理を実行し、実行結果を現在の PCN Trace に関連付ける。

一方、複数経路制御によって別の目標状態または目標実行経路が選択された場合は、その経路が選択されたことだけで移行許可が成立したとはみなさない。独立した進入条件、許可、実行チェーン、前制御判定が必要であれば、新しい目標状態入口として扱い、対応する PCN が改めて前制御判定を行う。

> **候補経路が選択されたことと、その経路への移行が許可されたことは別である。**

この関係を明確にすることで、群制御協調層に固有の停滞分析を保持しながら、TPCA / PCN の共通の9ステップのエンジニアリング分析手順に沿って、状態取得、判定、制御、実行、履歴記録までを一貫して扱うことができる。

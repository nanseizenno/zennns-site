## 1. 現場で発生する問題

MES は、タスク、設備、ステーション、材料、アラーム、生産数量、生産実績などを記録できる。

WCS は、搬送タスク、車両状態、経路状態、資源占有状態、スケジューリング結果などを記録できる。

設備側では、運転、待機、アラーム、インターロックなどの状態を記録できる。

HMI には、Ready、Waiting、Blocked、Pending などの運転状態が表示される。

多設備、多タスク、多システムが連携する製造現場では、次のような事象が発生することがある。

- タスクは生成されているが、実行が長時間進まない。
- 搬送主体はオンラインであり、ステーションにも要求があるが、連続実行へ移行しない。
- 個々の設備に明確な故障がなくても、システム全体のスループットが継続して低下する。
- MES、WCS、PLC、搬送主体、ステーションに状態記録があっても、協調停滞の構造を短時間で説明しにくい。
- オーダ変更、資源競合、許可待ち、下流受入待ち、手動確認、エネルギー補給などが重なり、複数システムの状態を横断して確認する必要が生じる。

この場合に確認する中心的な問いは、次のとおりである。

> **現在のシステムが、なぜ持続可能な協調実行状態へ進入できないのか。**

TPCA / PCN では、この問題を協調層における状態遷移として扱い、明確な Target State Entry（目標状態入口）を設定する。

本事例の基本的な処理関係は次のとおりである。

```text
Current State
→ Target State と Target State Entry を特定
→ PCN
→ 関連状態を取得
→ 群集約指標を生成
→ C / A / E 状態マッピング
→ S / D / B 判定
→ CAE-SDB Result + T
→ 停滞識別・構造分析
→ Arbitration
→ Multipath Control
→ 選択された制御経路
→ 実行結果
→ PCN Trace
```

群集約指標、停滞識別、構造分析は、本事例における群制御協調層固有の処理である。

## 2. モジュールの位置付けと PCN の配置位置

本事例の対象は、

> **MES / WCS 協調停滞診断モジュール**

である。

本モジュールは製造現場の協調層に配置し、MES、WCS、搬送システム、設備ユニット、ステーション、バッファ、経路資源、許可システム、現場の実行主体などから関連状態を取得する。

AGV / AMR 群制御搬送を代表的な適用場面とするが、対象は AGV / AMR に限定しない。例えば、次のような協調システムへ展開できる。

- 無人フォークリフトおよび自動搬送システム
- 複数設備による協調生産
- ラインサイド供給およびバッファ制御
- ステーション待機および受入制御
- 経路資源の競合
- エリア許可および資源ロックの調整
- 臨時オーダおよび優先度切替
- エネルギー補給の集中による実行能力低下

![MES / WCS 協調停滞診断モジュール概念図](/images/tpca/08-mes-wcs-collaborative-stagnation-module.png)

図：MES / WCS 協調停滞診断モジュールは製造現場の協調層に配置し、MES、WCS、搬送主体、設備、経路資源、ステーション、バッファ、安全・許可システムなどから関連状態を取得する。

本事例における Current State（現在状態・現在段階・現在経路位置）は、例えば次のような状態である。

```text
タスクが存在
搬送主体がオンライン
ステーションに要求が存在
Waiting / Blocked / Pending が継続
局所的な混雑または断続的な実行
システム全体のスループットが低下
```

Target State（目標状態・目標実行経路・目標物理実行段階）は、

```text
持続可能な協調実行状態
```

とする。

本事例では、群全体が有効なタスクを継続して実行可能な協調状態へ入る位置を、協調層における 1 つの Target State Entry として設定する。

```text
Current State
現在の協調状態
      ↓
PCN（Pre-Control Node / 前制御ノード）
［協調層の Target State Entry に対する前置判定］
      ↓
Target State Entry（目標状態入口）
      ↓
Target State
持続可能な協調実行状態
```

PCN は、この Target State Entry に関係する状態を取得し、判定、制御優先度調停、複数経路制御、履歴記録を行う。

本モジュールは既存 MES / WCS のスケジューリング機能そのものを置き換えることを前提としない。PCN が Multipath Control を形成した後、実際の群制御処理は既存 WCS、スケジューリングシステム、または制御システムが、それぞれの制御権限とインターフェースに基づいて実行する。

## 3. 関連状態と C / A / E 状態マッピング

協調停滞の判定では、タスク、実行主体、資源、経路、ステーション、許可、下流受入など、複数の対象に関係する状態を使用する。

代表的な情報源と関連状態を次に示す。

| 情報源 | 代表的な関連状態 |
|---|---|
| MES | 作業指示、タスク、優先度、材料要求、ステーション要求、計画変更、手動確認、異常記録 |
| WCS / スケジューリングシステム | タスクキュー、タスク割当結果、タスク状態、配車結果、資源ロック、経路割当、ステーション占有、バッファ状態 |
| AGV / AMR / 無人フォークリフト | オンライン状態、自動モード、位置、空荷 / 積載状態、バッテリ残量、タスク実行、待機、移動、アラーム状態 |
| 設備 / ステーション | 受入可能状態、運転状態、待機状態、材料不足状態、完了状態、アラーム状態 |
| 経路・設備資源 | 狭路、交差点、自動扉、エレベータ、エリア通行許可、バッファ、荷役位置の占有状態 |
| 安全・許可システム | エリア許可、安全許可、上位システム許可、手動許可、ロック状態 |
| 下流・書き戻し経路 | 下流受入状態、結果書き戻し状態、異常処理状態 |

これらの関連状態を、今回の Target State Entry における役割に基づいて C / A / E の状態変数領域へマッピングする。

```text
C：
Target State へ進むための前提条件に関係する状態変数領域

A：
Target State への進入許可に関係する状態変数領域

E：
Target State へ進入した後に必要となる
実行チェーンに関係する状態変数領域
```

| 状態変数領域 | 本事例での役割 | 代表的な関連状態 |
|---|---|---|
| C：Condition / 条件状態 | Target State へ進むための前提条件に関係する状態を整理する | タスク状態、材料要求、ステーション要求、目標ステーション情報、オーダ条件、工程条件 |
| A：Authority / 許可状態 | Target State への進入許可に関係する状態を整理する | スケジューリング許可、資源ロック状態、エリア許可、安全許可、手動確認、上位システム許可 |
| E：Execution Chain / 実行チェーン状態 | Target State へ進入した後に必要となる実行チェーンに関係する状態を整理する | 実行主体の動作状態、経路通行状態、ステーション受入状態、バッファ状態、下流受入状態、エネルギー補給状態、結果書き戻し状態 |

例えば、

```text
タスク状態 → C
エリア許可 → A
ステーション受入状態 → E
```

と整理できる。

タスクが存在していても資源ロックが成立していない場合、C と A は異なる状態変数領域として扱う。

また、実行主体がオンラインであっても、経路、ステーション、バッファ、下流受入などの実行チェーンが継続できなければ E に関係する状態として判定対象となる。

CAE-SDB の二軸構造については、以下を参照。

[なぜ CAE-SDB なのか ― 状態変数領域と判定特性の二軸構造](/jp/notes/why-cae-sdb/)

## 4. 群集約指標と S / D / B 判定

群制御協調層では、個々の主体状態だけでは群全体の停滞を把握しにくい場合がある。

そのため、本事例では関連状態から必要な群集約指標を生成する。

代表的な群集約指標は次のとおりである。

- 群全体の未実行率
- 群全体の補助実行率
- 群全体のエネルギー補給率
- 群全体の許可未成立率
- 経路資源の占有状態
- ステーションの受入状態
- 重要タスクの継続未実行状態

ここで、

> **群全体の未実行率**は、有効な実行要求が存在する中で、実行へ進んでいない主体の状態を群単位で把握するための指標である。

> **群全体の補助実行率**は、直接的なタスク実行ではなく、移動、迂回、待避、資源取得などの補助的な実行状態にある主体の分布を把握するための指標である。

群集約指標の具体的な算出式、分母定義、閾値は、対象システムに応じた内部実装範囲とする。

これらの群集約指標は、必要に応じて関連状態として扱い、今回の Target State Entry における役割に基づいて C / A / E の状態変数領域へ整理する。

その上で、PCN は個別の関連状態および群集約指標に対して S / D / B 判定を行う。

```text
S：
判定に必要な構造が定義・接続され、観測可能か。

D：
現在の状態を本判定の根拠として使用できるか。

B：
現在有効な状態が、事前に定義された許容範囲、
しきい値、または制御境界内にあるか。
```

| 判定特性 | 判定対象 | 本事例における代表項目 |
|---|---|---|
| S：Structure / 構造完全性 | 必要な対象、信号、インターフェース、マッピング関係、許可元、資源関係、実行チェーン境界が定義・接続され、観測可能であるか | MES-WCS 間のタスクマッピング、資源ロック元、ステーション受入インターフェース、経路資源関係、エネルギー補給状態インターフェース、結果書き戻しインターフェース |
| D：Dynamics / 動的時系列有効性 | タスク、実行主体、ステーション、許可、経路、実行状態が現在も有効で、同期・安定し、本判定に使用できるか | 作業指示変更の未同期、主体位置の遅延、ステーション状態の未更新、許可取消、経路占有状態の競合、実行フィードバックのタイムアウト |
| B：Boundary / 制御境界 | 現在有効な関連状態または群集約指標が、事前に定義された許容範囲、しきい値、または制御境界内にあるか | ステーション容量、群全体の未実行率、エネルギー補給率、再試行回数、キュー長、負荷範囲、資源利用範囲 |

D と B は次のように読み分ける。

```text
D：
関連状態そのものを、
今回の判定根拠として現在使用できるか。

B：
現在有効な状態の数量、比率、時間値、容量などが、
事前に定義された範囲内にあるか。
```

例えば、

```text
主体位置の状態が長時間更新されていない
→ D

待機時間は最新値として取得できているが、
事前定義された許容時間を超えている
→ B
```

と整理できる。

また、群全体の未実行率を事前定義された許容上限と比較する場合も B の判定対象となる。

```text
群全体の未実行率
→ 事前定義された許容上限と比較
→ 制御境界内 / 制御境界外を B 判定
```

## 5. 停滞識別と構造分析

CAE-SDB Result、時間情報 T、および群集約指標を用いて、協調停滞を識別する。

例えば、次のような状態関係を確認する。

```text
有効なタスクが存在
        +
複数の実行主体が有効な実行状態へ移行しない状態が継続
        +
群集約指標が事前定義された判定条件を満たす
        ↓
協調停滞を識別
```

協調停滞を識別した後は、関連状態、CAE-SDB Result、群集約指標、タスク、許可、資源、実行チェーンの状態から停滞構造を分析する。

本事例では、代表的な構造を次のように整理する。

### 分配制約型

代表的な状態：

- 有効なタスクが存在する。
- 複数の実行主体が長時間実行へ移行していない。
- タスク割当、許可、資源解放、資源ロックなどに関係する状態が実行開始条件を満たしていない。

### 資源競合型

代表的な状態：

- 実行主体が移動、迂回、待機または共有資源の取得処理を継続している。
- 経路、交差点、自動扉、エレベータ、ステーションなどの共有資源に利用競合が発生している。
- 補助的な実行が継続する一方で、有効タスクの進行率が低下している。

### エネルギー偏在型

代表的な状態：

- 多数の実行主体が同じ時間帯に充電またはその他のエネルギー補給状態へ移行している。
- 実タスクに割り当て可能な実行主体の比率が低下している。
- エネルギー補給状態の分布が協調実行能力に影響している。

### 未確定型

既存の関連状態、CAE-SDB Result、群集約指標から安定した構造分析結果を導出できない場合は、未確定型として記録する。

この場合は、対象時間帯に関係する状態記録を拡充し、その後のエンジニアリング確認に使用する。

```text
未確定型
→ 関連状態・群集約指標の記録を拡充
→ 後続分析
→ 新しい停滞パターンを確認
```

この4分類は、CAE-SDB の判定結果そのものではない。

CAE-SDB は関連状態を状態変数領域と判定特性の二軸で構造化し、停滞識別・構造分析は、それらの結果と群集約指標を用いて群制御協調層の現象を整理する。

## 6. Arbitration と Multipath Control

同一の協調停滞事象について、複数の CAE-SDB Result が同時に形成される場合がある。

また、停滞識別・構造分析によって、複数の制御候補が考えられる場合がある。

Arbitration（制御優先度調停）は、今回の Target State Entry に関する CAE-SDB Result、時間情報 T、群集約指標、停滞識別・構造分析の結果、および事前定義された制御制約に基づいて、制御上の優先関係を処理する。

```text
CAE-SDB Result + T
        +
群集約指標
        +
停滞識別・構造分析
        ↓
Arbitration
        ↓
Multipath Control
```

Multipath Control（複数経路制御）は、今回の Target State Entry に対して次に適用する制御処理を形成する。

代表例は次のとおりである。

- 通常実行の継続
- 待機
- タスク再割当要求
- 資源解放要求
- 経路または通行権の調整要求
- 流量制限
- バッファ振り分け
- 下流調整
- エネルギー補給方針の調整
- 縮退実行
- 手動確認
- 移行禁止
- 異常隔離
- 記録の拡充

例えば、資源競合型の停滞が確認された場合は、次のように整理できる。

```text
Arbitration Result：
資源競合に関係する判定結果を優先処理し、
現在の協調実行状態への進入を保留

Multipath Control：
資源解放要求 → タスク再割当要求
```

PCN は、今回の Target State Entry に対する判定、Arbitration、Multipath Control を形成する。

実際の資源解放、タスク再割当、経路変更などの群制御処理は、既存 WCS、Scheduler、または Control System が、それぞれのインターフェースと制御権限に基づいて実行する。

```text
PCN
→ 判定
→ Arbitration
→ Multipath Control / 制御要求
        ↓
既存 WCS / Scheduler / Control System
→ 実際の群制御処理
```

この役割分担により、PCN は既存 MES / WCS のスケジューリング機能を置き換えず、Target State Entry に対する前置判定と制御経路形成を担当する。

## 7. PCN Trace と協調停滞の振り返り

PCN は、今回の Target State Entry に関する入力、判定、Arbitration、Multipath Control、実行結果を PCN Trace（PCN 状態遷移判定履歴）として記録する。

代表的な記録内容は次のとおりである。

- PCN
- Current State
- Target State
- Target State Entry
- 関連状態
- 関連する実行主体およびタスク
- 時間情報 T
- C / A / E 状態マッピング
- S / D / B 判定
- CAE-SDB Result
- 群集約指標
- 停滞識別結果
- 構造分析結果
- Arbitration Result
- Multipath Control
- 実行結果
- Trace ID

例えば、資源競合型の協調停滞について、次のような PCN Trace を形成できる。

```text
PCN：
協調実行前 PCN

Current State：
有効タスク存在 / 複数主体待機

Target State：
持続可能な協調実行状態

Target State Entry：
協調実行状態への進入

時間情報 T：
判定時刻および関連状態の更新時刻

関連状態：
タスク存在
経路資源占有
ステーション受入
実行主体状態

群集約指標：
未実行率上昇
経路資源占有率上昇

CAE-SDB Result：
E-B + E-D

停滞識別結果：
協調停滞

構造分析結果：
資源競合型

Arbitration Result：
資源競合に関係する判定結果を優先処理し、
協調実行状態への進入を保留

Multipath Control：
資源解放要求 → タスク再割当要求

実行結果：
既存 WCS が資源解放およびタスク再割当を実行

Trace ID：
PCN-COLLAB-XXXX
```

PCN Trace を継続して蓄積することで、例えば次の内容を確認できる。

- 停滞が頻発する Target State Entry
- 協調停滞の構造分布
- 許可および資源ロックに関係する反復問題
- 経路およびステーション協調状態
- エネルギー補給分布
- Multipath Control と実行結果の関係
- エンジニアリング変更前後の判定結果
- 未確定型として記録された事象の後続分析

> **PCN Trace は、今回の Target State Entry に使用した関連状態、群集約指標、CAE-SDB Result、停滞識別・構造分析、Arbitration、Multipath Control、および実行結果を一連の履歴として関連付ける。**

## 8. モジュールの位置付けと公開範囲

MES / WCS 協調停滞診断モジュールは、タスク、スケジューリング、資源、経路、ステーション、許可、実行主体、下流システムなどに分散した状態を、明確な Target State Entry を中心として判定・制御・記録可能な形へ整理する。

本事例の工程関係は、次のようにまとめられる。

```text
Current State
→ Target State と Target State Entry を特定
→ PCN
→ 関連状態
→ 群集約指標
→ C / A / E 状態マッピング
→ S / D / B 判定
→ CAE-SDB Result + T
→ 停滞識別・構造分析
→ Arbitration
→ Multipath Control
→ 既存 WCS / Scheduler / Control System
→ 実行結果
→ PCN Trace
```

この構造により、MES / WCS では、単に Waiting、Blocked、Pending などの状態を表示するだけでなく、

```text
どの Target State Entry で
どの関連状態を使用し
どの判定結果が形成され
群全体ではどの停滞構造が確認され
どの制御経路が選択され
最終的にどのような実行結果となったか
```

を同じエンジニアリング文脈で確認できる。

本稿で公開する内容は、次の範囲である。

- モジュールの位置付け
- Current State / Target State / Target State Entry
- PCN の配置位置
- 関連状態
- C / A / E 状態マッピング
- S / D / B 判定
- 群集約指標の基本的な意味
- 停滞識別
- 構造分析
- CAE-SDB Result
- 時間情報 T
- Arbitration
- Multipath Control
- 既存 WCS / Scheduler との基本的な役割分担
- PCN Trace

具体的な算出式、閾値、継続時間ウィンドウ、再試行回数、完全な制御優先順位、資源解放ルール、経路調整方針、インターフェースパラメータ、内部実行機構、詳細な Trace Schema については、公開範囲に含めない。

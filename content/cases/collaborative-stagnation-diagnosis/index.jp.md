## MES に状態が記録されていても、なぜ製造現場の停滞を説明できないのか

> 適用階層：群制御・協調層 / MES-WCS 協調停滞診断
> 代表対象：製造現場の協調停滞診断モジュール

**推奨引用：**

```text
全野南政 / Nansei Zenno，
『MES / WCS 協調停滞診断モジュール事例：MES に状態が記録されていても、なぜ製造現場の停滞を説明できないのか』，
公開事例，Public Case Version 1.7，
2026-10-01，
https://zennns.com/jp/cases/collaborative-stagnation-diagnosis/
```

MES と WCS は、通常すでに多くの運転情報を持っている。

たとえば、ある時点でシステムが次のような状態を示しているとする。

```text
稼働中タスク数：42
継続待機または未実行タスク数：17
実行主体：オンライン
ステーション要求：あり
重大な設備アラーム：なし
利用可能な経路：あり
共有資源：一部占有
```

これらの状態から、タスクは存在し、実行主体はオンラインで、一部の経路も利用可能であり、全体停止を直接説明できるような単体設備の重大故障も発生していないことが分かる。

それでもタスクは滞留し続け、複数主体が長時間待機し、協調実行能力が低下している。

このときの工程上の問題は、「タスクがあるか」「設備がオンラインか」ではない。

> **なぜ現在のシステムは、継続可能な協調実行状態へ移行できないのか。**

という点である。

本事例では、「継続可能な協調実行状態への移行」を目標状態入口（Target State Entry）とし、MES、WCS、実行主体、経路資源、許可、ステーション状態を同一の協調判定に関連付ける。

自動化実行ユニットの事例と異なり、本事例では群制御・協調層に固有の分析結果も保持する。群全体として停滞が成立しているか、また現在の停滞がどの構造に近いかを、CAE-SDB 判定とは別の分析結果として扱う。

事例は、共通の9ステップの分析手順に沿って説明する。

1. 現在状態
2. 目標状態 / 目標状態入口
3. PCN：関連状態取得と C / A / E 状態マッピング
4. 前制御判定と群制御・協調分析
5. 制御調停
6. 複数経路制御
7. 現在の入口に対する制御結果
8. 制御経路の実行 / 後続の目標状態入口と実行結果
9. 状態遷移判定履歴

基礎概念については、以下を参照できる。

- [中核概念](/jp/concepts/)
- [TPCA / PCN 状態遷移前制御アーキテクチャ｜ホワイトペーパー](/jp/whitepaper/)

## 事例対象

本事例の対象は、MES / WCS 協調停滞診断モジュールである。

本モジュールは製造現場の協調層に位置し、次の情報を集約できる。

- MES のタスクとステーション要求
- WCS のスケジューリングと搬送タスク
- AGV / AMR などの実行主体状態
- 経路と共有資源状態
- 区域許可および安全許可
- ステーション受入状態
- 下流状態
- 群全体の運転指標

AGV / AMR の群制御搬送は代表的な適用場面の一つだが、本事例が対象とするのは、より一般的な製造現場における協調停滞である。**複数の単体設備に明確な故障がなくても、なぜ全体の実行が継続できないのか**を扱う。

![MES / WCS 協調停滞診断モジュールの構成イメージ](/images/tpca/08-mes-wcs-collaborative-stagnation-module.png)

図：協調停滞診断モジュールは、MES、WCS、搬送主体、ステーション、経路資源、許可状態、下流状態を取得し、同一の協調状態遷移に関連付ける。

以下の数量と状態の組合せは、本公開事例の運転状態を説明するために設定した例示値であり、特定の実案件データではない。群全体の停滞判定に用いる具体的な閾値、継続時間窓、完全な構造分類ルールは、本公開事例では扱わない。

---

# 1. 現在状態

現在、システムは完全に停止しているわけではない。

一部のタスクは実行され、一部の経路も利用可能だが、全体として協調実行が継続的に阻害されている。

例として、次の運転スナップショットを考える。

```text
稼働中タスク数：42
実行済みまたは進行中：25
継続待機または未実行：17
実行主体：オンライン
ステーション要求：あり
重大な設備アラーム：なし
利用可能な経路：あり
共有資源：一部占有
協調実行状態：阻害
```

現場では、次の状態が確認できる。

```text
タスクは存在
実行主体はオンライン
一部タスクは継続して未実行
複数主体が継続待機
一部タスクは実行継続中
```

したがって、ここで確認できるのは単純な「全システム停止」ではない。

現在明確に言えるのは、

```text
協調実行が阻害されている
```

ということである。

群全体として停滞が成立しているか、また現在の阻害がどのような構造によって生じているかは、さらに判定する必要がある。

---

# 2. 目標状態 / 目標状態入口

本事例で扱うのは、ある1台の AGV が移動できるか、単体設備が起動できるかという問題ではない。

現在のシステムレベルの目標状態は、

```text
継続可能な協調実行状態
```

である。

対応する目標状態入口（Target State Entry）は、

```text
継続可能な協調実行状態への移行
```

である。

ここでいう「継続可能な協調実行」とは、現在のタスク、実行主体、資源、許可、経路、ステーションの関係が、システム全体として次の処理を継続できる状態を意味する。個別タスクが一部動いているだけでは、ここでいう協調実行状態が成立しているとは判断しない。

PCN は、現在の協調状態とこの目標状態入口の間に配置される。

以降の状態マッピング、CAE-SDB 判定、群全体の停滞判定、構造分類、制御処理は、すべてこの協調入口を基準として行う。

---

# 3. PCN：関連状態取得と C / A / E 状態マッピング

PCN は、現在の協調入口に直接関係する状態を各システムから取得し、今回の状態遷移で担うエンジニアリング上の役割に基づいて C / A / E 状態マッピングを行う。

| 代表状態 | 状態マッピング |
|---|---|
| タスク状態、ステーション要求、目標ステーション情報 | C：条件状態 |
| スケジューリング許可、資源ロック、区域許可、安全許可 | A：許可状態 |
| 実行主体状態、搬送経路状態、ステーション受入状態、下流状態 | E：実行チェーン状態 |

本事例では、主に次の状態を扱う。

```text
タスク存在：C
資源ロック状態：A
安全許可：A
実行主体オンライン：E の関連状態
搬送経路利用可能状態：E
ステーション受入状態：E
```

ここでは、二種類の情報を分けて扱う必要がある。

一つは、具体的な目標状態入口に直接関係し、CAE-SDB 判定へ入る状態である。

もう一つは、複数タスクや複数主体の状態を集約して得られる群全体の情報である。

たとえば、

```text
群全体の未実行率
群全体の補助実行率
群全体のエネルギー補給率
群全体の許可未成立率
```

などがある。

これらの群指標は、停滞判定と構造分類に使用する。単独の CAE-SDB 判定結果として扱うものではない。

---

# 4. 前制御判定と群制御・協調分析

今回の例では、次の状態スナップショットが得られているものとする。

```text
稼働中タスク数：42
継続待機または未実行タスク数：17
実行主体：オンライン
安全許可：成立
資源ロック用インターフェース：確立済み
資源ロック状態：システム間で非同期
利用可能な経路：あり
ステーション要求：あり
```

単体状態だけを見ると、

- タスクは存在する
- 実行主体はオンライン
- 安全許可は成立している
- すべての経路が使用不能なわけではない
- ステーションには実行要求がある

という状態である。

一方、資源ロック状態はシステム間で同期していない。

現在の協調入口では、資源ロックは A：Authority / 許可状態に対応する。

資源ロック用インターフェース自体は確立されているため、問題は「資源ロック構造が存在しない」ことではない。運転中のロック状態がシステム間で一致しておらず、現在の入口に対する有効な許可根拠として使用できないことが問題である。

そのため、次の CAE-SDB 判定結果が生成される。

```text
CAE-SDB 判定結果：
  A-D
  資源ロック状態がシステム間で同期しておらず、
  現在の協調入口に対する有効な許可根拠として使用できない
```

同時に、群制御・協調層では、複数のタスクと実行主体の運転状態を集約して分析する。

本事例では、次のような結果になったものとする。

```text
群全体の未実行率：
  停滞判定条件を満たす

群全体の補助実行率：
  資源競合型の特徴を示す

群全体のエネルギー補給率：
  エネルギー補給への偏りは認められない

群全体の許可未成立率：
  割当制約型を主要因と判断する特徴は認められない
```

この結果から、群制御・協調層では次の分析結果を得る。

```text
群全体の停滞判定：
  成立

停滞構造分類：
  資源競合型
```

ここでは、二種類の分析結果を分けて保持する。

```text
目標状態入口レベル：
  A-D
  資源ロック状態の動的時系列有効性に問題あり

群制御・協調層：
  群全体の停滞判定 = 成立
  停滞構造分類 = 資源競合型
```

CAE-SDB 判定結果は、群全体の停滞判定や構造分類を代替しない。

同様に、群指標を無理に CAE-SDB 座標へ対応付ける必要もない。

両者はそれぞれのエンジニアリング上の意味を保持したまま、次の制御調停へ入力する。

本公開事例では、具体的な比率閾値、継続時間窓、完全な構造分類ルールまでは扱わない。

関連定義については、以下を参照できる。

- [なぜ CAE-SDB なのか？——目標状態入口前の二軸構造化分析法](/jp/notes/why-cae-sdb/)
- [なぜ MES / WCS は状態を記録できても、停滞の理由を説明できないのか？](/jp/questions/why-mes-records-but-cannot-explain/)

# 5. 制御調停

制御調停の段階では、単に「多くのタスクが Waiting している」という状態だけを見ているわけではない。

現在、次の情報が得られている。

```text
CAE-SDB 判定結果：
  A-D

資源ロック状態：
  システム間で非同期

群全体の停滞判定：
  成立

停滞構造分類：
  資源競合型

安全許可：
  成立
```

この状態で、さらにタスクを投入したり、個々の設備が自然に復旧するのを待ったりしても、現在の協調関係を直接改善できるとは限らない。

まず優先して扱うべきなのは、すでに確認されている資源ロック状態の不整合である。

同時に、資源競合型の特徴が確認されているため、影響を受けている経路やタスク割当ても調整する必要がある。

制御調停の結果は、次のようになる。

```text
優先処理：
  資源ロック状態の不整合解消

同時処理：
  影響経路の調整
  影響タスクの再割当て
```

---

# 6. 複数経路制御

今回の協調入口では、制御調停の結果に基づき、次の複数経路制御を構成する。

```text
資源解放
搬送経路調整
タスク再割当て
```

ロボット把持事例と異なり、ここでいう複数経路制御は、必ずしも1台の設備が直ちに物理動作を行うことを意味しない。

協調層では、まず資源解放、経路調整、タスク再割当てなどの調整処理を制御結果として整理する。

実際のプロジェクトでは、

- どのシステムが資源解放を実行するか
- どのスケジューリングシステムがタスクを再割当てするか
- 経路変更を自動実行するか
- どの処理に人による確認が必要か

は、既存の MES、WCS、スケジューリングシステム、現場制御システムのインターフェース、責任分担、制御権限によって決まる。

TPCA / PCN が、既存のスケジューリングや実行システムの制御責任を代替するわけではない。

---

# 7. 現在の入口に対する制御結果

現在の目標状態入口は、

```text
継続可能な協調実行状態への移行
```

である。

今回の入口に対する制御結果は、

```text
現時点では移行しない
```

となる。

理由は、現在の資源ロック状態に A-D が存在し、同時に群全体の停滞が資源競合型として判定されているためである。

まず必要な調整処理を行い、その後で、現在の協調状態が継続可能な条件へ回復したかをあらためて確認する。

---

# 8. 制御経路の実行 / 後続の目標状態入口と実行結果

選択された調整処理は、対応する制御権限を持つ既存システムが実行する。

処理が進むと、実際のエンジニアリング状態も変化する。

たとえば、

```text
資源ロック状態：
  システム間で非同期→ 再同期

共有資源：
  占有関係を再整理

影響経路：
  再調整

影響タスク：
  再割当て
```

といった変化が起こる。

本事例では、処理完了後に次の状態となったものとする。

```text
資源ロック状態：再同期
主要搬送経路：利用可能状態へ復帰
影響タスク：再割当て完了
継続待機または未実行タスク：減少
群全体の未実行率：停滞判定条件を下回る
```

この場合、実行結果は次のように整理できる。

```text
実行結果：
  資源ロック関係が再同期
  主要搬送経路が利用可能状態へ復帰
  影響タスクの再割当て完了
  群全体の未実行状態が減少
```

これらの結果は、新しいエンジニアリング状態事実となる。

現在のシステムが再び「継続可能な協調実行状態」へ移行できるかどうかは、更新後の状態に基づいて同じ入口であらためて判定する。

一方、代替搬送経路、退避経路、異常系への分岐など、別の目標状態または目標実行経路が選択された場合は、新しい目標状態入口を設定し、対応する PCN が独立して前制御判定を行う。

---

# 9. 状態遷移判定履歴

今回の協調入口については、次のような PCN Trace（状態遷移判定履歴）を記録できる。

```text
【履歴 ID】：
    PCN-COLLAB-XXXX
【PCN】：
    協調実行入口 PCN
【現在状態】：
    協調実行阻害 / 複数主体が継続待機
【目標状態】：
    継続可能な協調実行状態
【目標状態入口】：
    継続可能な協調実行状態への移行
【主要状態】：
    稼働中タスク数 = 42
    継続待機または未実行タスク数 = 17
    実行主体 = オンライン
    安全許可 = 成立
    資源ロック用インターフェース = 確立済み
    資源ロック状態 = システム間で非同期
    利用可能な経路 = あり
【CAE-SDB 判定結果】：
    A-D
【判定内容】：
    資源ロック状態がシステム間で同期しておらず、
    現在の協調入口に対する有効な許可根拠として使用できない
【群制御・協調分析】：
    群全体の停滞判定 = 成立
    停滞構造分類 = 資源競合型
【制御調停結果】：
    資源ロック状態の不整合を優先して解消
    搬送経路調整とタスク再割当てを同時に実施
【複数経路制御】：
    資源解放
【搬送経路調整】
    タスク再割当て
【現在の入口に対する制御結果】：
    現時点では継続可能な協調実行状態へ移行しない
【実行結果】：
    資源ロック関係が再同期
    主要搬送経路が利用可能状態へ復帰
    影響タスクの再割当て完了
    群全体の未実行状態が減少
【時間情報】：
    T
```

この履歴では、もともと MES、WCS、実行主体、資源、許可システムに分散していた状態を、同じ協調入口の判定に関連付けている。

同時に、次の二種類の情報を分けて保持する。

```text
入口レベル判定：
  A-D
群制御・協調分析：
  群全体の停滞判定 = 成立
  停滞構造分類 = 資源競合型
```

二つの結果を同じラベルへまとめることはしない。

それぞれの意味を保持したまま、同じ状態遷移判定履歴の中で、制御処理と実行結果まで追跡できる。

後続処理によって新しい目標状態入口が成立した場合は、その入口を担当する PCN が新しい状態遷移判定履歴を記録する。

PCN Trace の詳細については、以下を参照できる。

[なぜ PCN Trace は新しいエンジニアリングデータなのか？](/jp/notes/why-pcn-trace-is-engineering-data/)

## 事例まとめ

本事例の開始時点では、MES、WCS、搬送主体、現場設備から、すでに多くの実状態を確認できる。

```text
タスクは存在
実行主体はオンライン
ステーション要求あり
一部経路は利用可能
単体設備に重大アラームなし
一方で：
複数タスクが継続して未実行
複数主体が継続待機
全体の協調実行が阻害
```

各システムの画面を個別に確認すれば、それぞれが保持する局所的な状態情報を確認できる。

しかし、それらは分散している。

そこで、

```text
目標状態入口：
継続可能な協調実行状態への移行
```

を基準として整理すると、エンジニアリング上の関係をさらに明確にできる。

```text
資源ロック状態：
システム間で非同期
CAE-SDB 判定結果：
A-D
```

同時に、群全体の運転データから、

```text
群全体の停滞判定：
成立
停滞構造分類：
資源競合型
```

という結果も得られる。

最終的な処理関係は、

```text
資源ロック状態の不整合
A-D
群全体の停滞判定 = 成立
停滞構造分類 = 資源競合型
制御調停：
資源ロック状態の不整合を優先して解消
搬送経路調整
タスク再割当て
実行後：
資源ロック関係が再同期
主要搬送経路が利用可能状態へ復帰
群全体の未実行状態が減少
```

と整理できる。

### 本事例によって明確になるエンジニアリング情報

| 従来の現場情報から確認できること | 本事例によってさらに明確になること |
|---|---|
| タスクが生成されている | 「継続可能な協調実行状態へ移行できるか」という明確な目標状態入口を判定対象として設定できる |
| 実行主体がオンラインである | 主体がオンラインであることは関連状態の一つであり、協調実行全体の継続可能性を単独では示さない |
| 複数の実行主体が待機している | 群全体の未実行率を用いて、複数主体を含む停滞が成立しているかを判定できる |
| 資源ロックに不整合がある | 資源ロックを現在の入口における A として位置付け、`A-D` として整理できる |
| 単体設備に重大アラームがない | 協調上の問題は、単体設備故障がなくても、タスク、許可、共有資源、実行チェーン間の関係から発生し得る |
| 経路や共有資源に競合が見られる | 群全体の補助実行率、エネルギー補給比率、許可未成立比率などを用いて、停滞構造を資源競合型として整理できる |
| 現場では「全体が止まっている」としか見えない | 現在の協調入口における A-D と、群制御・協調層における資源競合型停滞を分けて説明できる |
| エンジニアが複数システムを確認しながら対処方法を判断する | 制御処理として「資源解放・搬送経路調整・タスク再割当て」を明示できる |
| 対応後は新しい運転状態だけが残る | 資源ロックの再同期、経路復旧、タスク再割当て、群全体未実行状態の変化まで同じ工程履歴として確認できる |
| MES、WCS、搬送主体、設備がそれぞれログを保存している | 状態、CAE-SDB 判定、群全体の停滞判定、停滞構造分類、制御、実行結果を一件の状態遷移判定履歴として関連付けられる |

本事例によって、従来の、

> **「タスクは存在し、実行主体もオンラインだが、システム全体が停滞している。」**

という現象を、

> **「現在の協調入口のどこが成立していないのか、群全体の停滞がどのような構造を持つのか、どの制御を適用したのか、その結果、協調状態がどのように変化したのか。」**

というエンジニアリング上の関係として説明できる。

本事例で示した主なエンジニアリング上の意味は、分散した状態を一つの明確な目標状態入口へ関連付けること、協調入口に関係する状態について具体的な CAE-SDB 判定結果を得ること、単体状態の判定と群全体の停滞構造を区別したまま同じ制御判断へ接続することにある。

また、群全体の現象を停滞構造として分類し、その結果を制御方向と実行結果へ接続できる。

状態、判定、停滞構造、制御、実行結果の関係を、同じ状態遷移判定履歴として記録することもできる。

本事例で追加される価値は、タスク数、車両状態、設備状態などのデータ項目を増やすことではない。

> **MES、WCS、搬送主体、共有資源、許可システムに分散していた情報を、「現在の入口がなぜ成立しないのか」「群全体の停滞がどのような構造を持つのか」「どの制御を適用したのか」「その結果、協調状態がどのように変化したのか」という一連のエンジニアリング上の関係として整理することにある。**

## 1. 現場問題

MES は、タスク、設備、ステーション、材料、アラーム、生産量、生産実績を記録できる。

WCS は、搬送タスク、車両状態、経路状態、資源占有、スケジューリング結果を記録できる。

設備システムは、運転、待機、アラーム、Interlock 状態を記録できる。

HMI でも、Ready、Waiting、Blocked、Pending などの運転状態を表示できる。

しかし、複数設備、複数タスク、複数システムが協調する環境では、依然として次のような問題が発生することがある。

- タスクはすでに生成されているが、実行が継続的に進まない；
- 車両はオンラインで、ステーションにも需要があるが、補給が連続した実行につながらない；
- 単体設備には明確な異常がないにもかかわらず、システム全体のスループットが継続的に低下する；
- MES、WCS、PLC、車両、ステーションのすべてに状態記録があるが、協調停滞が発生している位置を迅速に特定できない；
- オーダー変更、資源競合、許可待ち、下流閉塞、人による確認、エネルギー補給などが重なり、最終的には人が複数システムを横断してログと状態を照合しなければならない。

したがって、問題はすでに「システムにデータがあるかどうか」ではない。

より重要なのは、次の問いに答えることである。

> **なぜ現在のシステムは、継続可能な協調実行状態へ入ることができないのか？**

TPCA / PCN では、この問題を明確な Target State Entry の問題として扱う。

PCN は、「継続可能な協調実行状態」という Target State を中心として、本状態遷移に関係する複数ソース状態を集約し、次のように整理する。

- C：タスク、材料、ステーション、経路、現場条件が成立しているか；
- A：スケジューリング許可、資源ロック、エリア許可、安全許可、人による許可が成立しているか；
- E：主体、経路、バッファ、下流、エネルギー補給、結果書戻しが継続して接続可能か。

その後、さらに S / D / B 判定を行い、群体状態を組み合わせて停滞識別、構造分析、Arbitration、Multipath Control を行う。

したがって、システム出力は、

```text
Waiting
Blocked
Pending
```

だけに限定されず、さらに次のような構造を形成する。

```text
現在の協調状態
→ 停滞識別
→ 構造化判定
→ Arbitration
→ Multipath Control
→ PCN Trace
```

## 2. モジュールの位置付けと PCN の位置

本事例の対象は、

> **MES / WCS 協調停滞診断モジュール**

である。

このモジュールは製造現場の協調層に位置し、MES、WCS、搬送システム、設備ユニット、ステーション、バッファ、経路資源、許可システム、現場実行対象などと接続できる。

AGV / AMR 群制御搬送は代表的な適用場面の一つであるが、モジュール自体は AGV に限定されない。

代表的な適用対象には、次のようなものがある。

- 無人フォークリフトおよび自動搬送システム；
- 複数設備による協調生産；
- ラインサイド補給とバッファスケジューリング；
- 工程待ちとステーション受入；
- 経路資源競合；
- エリア許可と資源ロックの協調；
- 臨時オーダーと優先順位切替；
- エネルギー補給の集中による群体実行能力低下。

![MES / WCS 協調停滞診断モジュール概念図](/images/tpca/08-mes-wcs-collaborative-stagnation-module.png)

図：MES / WCS 協調停滞診断モジュールは製造現場の協調層に位置し、MES、WCS、AGV / AMR、バッファエリア、加工設備、経路資源、自動ドア、エレベーター、充電エリア、安全許可システム、監視システムなどの複数ソース状態を集約する。

本事例における現在の協調状態は、たとえば次のように表される。

```text
タスクが存在
車両がオンライン
ステーションに需要あり
システムが継続的に Waiting / Blocked / Pending
局所的な混雑または断続的な実行
全体スループットが低下
```

Target State：

```text
継続可能な協調実行状態
```

この Target State は、

> **タスク、主体、経路、資源、ステーション、下流、結果書戻しが、継続して接続可能な実行構造を形成している状態**

を表す。

したがって、PCN は「継続可能な協調実行状態」という Target State Entry の前に配置できる。

```text
現在の協調状態
        ↓
      PCN
        ↓
継続可能な協調実行状態
```

PCN は Target State へ進入する前に、複数ソース状態の集約、構造化判定、停滞識別、制御経路の選択を行う。

システムが後に、過去の正常運転段階と同じ、または類似した協調状態内容を再び形成した場合でも、TPCA では新しい状態インスタンスとして扱い、過去の状態インスタンスへ戻ったとはみなさない。

## 3. 複数ソース状態信号と C / A / E 状態マッピング

協調停滞は、単一設備の状態ではなく、複数のタスク、主体、資源、実行対象の組合せによって形成される状態である。

PCN は、現在の協調実行に直接関係する複数ソース状態を取得する必要がある。

| 信号源 | 代表的な信号 |
|---|---|
| MES | 作業指示、タスク、優先順位、材料需要、ステーション需要、計画変更、人による確認、異常記録 |
| WCS / スケジューリングシステム | タスクキュー、タスク割当結果、タスク状態、配車結果、資源ロック、経路割当、ステーション占有、バッファ状態 |
| AGV / AMR / 無人フォークリフト | オンライン状態、自動モード、位置、空荷 / 積載、バッテリー残量、タスク実行、待機、移動、アラーム状態 |
| 設備 / ステーション | 受入可能状態、運転状態、待機状態、材料不足状態、完了状態、アラーム状態 |
| 経路・設備資源 | 狭通路、交差点、自動ドア、エレベーター、エリア通行権、バッファエリア、荷役ポイント占有状態 |
| 安全・許可システム | エリア許可、安全許可、上位許可、人による許可、ロック状態 |
| 下流・書戻し経路 | 下流受入可能状態、結果書戻し状態、異常処理状態 |

これらの状態は PCN に入力された後、「継続可能な協調実行状態」という Target State に基づいて C / A / E へマッピングされる。

| 変数領域 | 判定対象 | 本事例における代表項目 |
|---|---|---|
| C：Condition | Target State へ入る前の事実条件が成立しているか | タスクが存在するか；材料が一致しているか；対象ステーションに需要があるか；ステーションが有効か；主体がスケジューリング可能な対象か；目標経路が存在するか |
| A：Authority | システムが現在のタスク、主体、資源の協調実行継続を許可しているか | スケジューリング許可；資源ロック解放；エリア許可；安全許可；人による確認；上位許可 |
| E：Execution Chain | Target State へ入った後、実行チェーンが継続して接続できるか | 主体が実行可能か；経路が通行可能か；ステーションが受入可能か；バッファが受入可能か；下流が継続可能か；エネルギー補給が実行能力に影響していないか；結果を書き戻せるか |

したがって、次の関係を区別する必要がある。

```text
タスクが存在 ≠ Target State が成立

車両がオンライン ≠ 実行チェーンが成立

単体 Ready ≠ 群体実行チェーンが継続して接続可能
```

たとえば、

- タスクは存在するが、資源ロックがまだ解放されていない場合、A は成立しない；
- 主体はオンラインだが、目標ステーションが受入できない場合、E は成立しない；
- 多数の主体が同時にエネルギー補給へ集中し、実行可能主体の比率が低下した場合、E に関係する群体実行能力が影響を受ける；
- タスク、主体、経路の記録がすべて存在していても、下流が長時間受入できない場合、Target State は成立しない。

## 4. S / D / B 判定と群体状態

C / A / E は、現在の問題がどの状態変数領域に関係するかを示す。

S / D / B は、それらの状態について、構造完全性、動的時系列有効性、制御境界をさらに判定するために使用する。

| 判定性質 | 判定対象 | 本事例における代表項目 |
|---|---|---|
| S：Structure | 必要な信号、インターフェース、マッピング関係、許可元、資源関係、実行チェーン境界が定義・接続され、観測可能になっているか | MES と WCS のタスクマッピング；資源ロック取得元；ステーション受入状態；経路資源；エネルギー補給状態；結果書戻し状態 |
| D：Dynamics | 現在のタスク、主体、ステーション、許可、経路、実行状態が今も有効で、同期され、タイムアウトしておらず、競合していないか | 作業指示変更が未同期；主体位置が遅延；ステーション状態が未更新；許可取消；経路占有競合；実行フィードバックタイムアウト |
| B：Boundary | 現在の協調状態が事前に定義された制御境界に入っているか | 待ち時間；資源占有時間；ステーション容量；群体未実行比率；エネルギー補給比率；リトライ回数；流量制限制御条件；再割当条件；復帰条件 |

単体状態だけでなく、群体レベルの運転特性も確認する必要がある。

代表的な群体状態または指標には、次のようなものがある。

- 群体未実行比率；
- 群体補助実行比率；
- 群体エネルギー補給比率；
- 群体許可未成立比率；
- 経路資源占有状態；
- ステーション受入状態；
- 重要タスクの継続未実行状態。

これらの群体状態は、

> **現在の問題が局所的な待機から、群体協調レベルの継続的な停滞へ発展しているか**

を判断するために使用する。

![協調停滞識別と Multipath Control のフロー](/images/tpca/09-collaborative-stagnation-control-flow.png)

図：モジュールは複数ソース状態の集約から開始し、C / A / E 状態マッピング、S / D / B 判定、群体状態計算、停滞識別、構造分析、Arbitration、Multipath Control、履歴記録を順に行う。

## 5. 停滞識別と構造分析

協調停滞診断では、単一の Waiting や Blocked を直接分類するのではなく、まずシステムが継続的な停滞状態へ入っているかを確認する必要がある。

たとえば、

```text
有効なタスクが存在
        +
複数の自動運転主体が継続的に有効実行へ入らない
        +
群体未実行状態が判定条件を継続して満たす
        ↓
群体協調停滞
```

群体協調停滞を確認した後、群体状態と関連する C / A / E 情報を組み合わせて、停滞構造を分析する。

代表的な構造には、次のようなものがある。

### 割当制約

代表的な状態：

- 有効なタスクが存在する；
- 複数の主体が長時間実行へ入らない；
- タスク割当、許可、資源解放が有効な実行関係を形成していない。

### 資源競合

代表的な状態：

- 主体が移動、迂回、待機、共有資源の競合を続けている；
- 経路、交差点、自動ドア、エレベーター、ステーション、その他の共有資源で競合が形成されている；
- 群体内では補助的な動作が多いが、有効タスクの進行が不足している。

### エネルギー偏在

代表的な状態：

- 多数の主体が充電またはその他のエネルギー補給状態へ集中している；
- 実タスクに使用可能な主体の比率が低下している；
- エネルギー補給の分布が全体の協調実行へ明確な影響を与えている。

### 未確定状態

現在の状態および群体指標だけでは信頼できる構造判断を形成できない場合、未確定状態として保持し、強化記録または人による確認へ進む。

具体的な MES / WCS 製品実装では、許可、ステーション受入、経路閉塞などの診断情報をさらに表示することもできるが、これらの情報は群体停滞識別および構造分析と整合している必要がある。

## 6. CAE-SDB Result、時間情報 T、Arbitration、Multipath Control

PCN は C / A / E 状態に対して S / D / B 判定を行った後、1 つまたは複数の CAE-SDB Result を形成し、本状態および判定に対応する時間情報 T を保持する。

時間情報 T は、次の用途に使用できる。

- 群体状態の継続時間を判断する；
- 関連状態がタイムアウトまたは未更新であるかを判断する；
- 状態間の前後関係を判断する；
- PCN Trace を形成する。

代表的な結果を以下に示す。

| 判定結果 | 本事例における代表的な問題 |
|---|---|
| C-S | タスク、対象、ステーション、経路に必要なマッピング関係が欠落 |
| C-D | 作業指示変更が未同期；タスク状態が未更新；需要がすでに失効 |
| C-B | タスク待ち、滞留、継続未実行が制御境界に到達 |
| A-S | スケジューリング許可、資源ロック、エリア許可、人による確認の取得元が未定義または観測不能 |
| A-D | 許可が未更新、繰り返し取消、または資源ロック状態が非同期 |
| A-B | 許可待ちまたは資源占有が制御境界に到達 |
| E-S | 経路、ステーション、バッファ、下流、エネルギー補給、書戻し経路の構造が欠落 |
| E-D | 経路状態が競合；ステーション状態が未更新；主体実行フィードバックがタイムアウト；実行チェーンが継続的に閉塞 |
| E-B | 経路待ち、ステーション容量、エネルギー補給、下流待ちが制御境界に到達 |

同一の協調停滞において、複数の判定結果が同時に存在することがある。

これらの判定結果は群体停滞状態とともに Arbitration へ入り、最終的な Multipath Control を形成する。

代表的な制御経路には、次のようなものがある。

- 正常実行を継続；
- 待機；
- タスク再割当；
- 資源解放；
- 経路または通行権の調整；
- 流量制限；
- バッファ分流；
- 下流調整；
- エネルギー補給戦略の調整；
- 縮退実行；
- 人による確認；
- 進入禁止；
- 異常隔離；
- 強化記録。

これらの制御経路は、システムが現在の協調状態から、それぞれ異なる後続の Target State または目標実行経路へ進むことを表す。

後続で過去の正常運転段階と同じ協調状態内容が再び形成された場合でも、TPCA では新しい状態インスタンスとして扱う。

したがって、現場で確認される結果は、

```text
Waiting
Blocked
Pending
```

だけに限定されず、さらに次のような構造として形成できる。

```text
現在の協調状態
→ 停滞識別
→ CAE-SDB Result + T
→ Arbitration
→ Multipath Control
```

## 7. PCN Trace と協調停滞の振り返り

PCN は判定結果および制御結果を形成すると同時に、対応する PCN Trace を生成できる。

代表的な記録内容には、次のものが含まれる。

- 現在の協調状態；
- 目標協調実行状態；
- 関連する主体とタスク；
- 主要入力状態；
- 時間情報 T；
- C / A / E 状態マッピング；
- S / D / B 判定；
- CAE-SDB Result；
- 群体状態または指標；
- 停滞識別結果；
- Arbitration Result；
- Multipath Control Result；
- 実行結果；
- Trace ID。

これらの記録は、次の用途に利用できる。

- 頻発する停滞入口の識別；
- 群体停滞構造の比較；
- 許可および資源ロック問題の振り返り；
- 経路とステーションの協調問題分析；
- エネルギー補給分布の分析；
- 制御経路の効果比較；
- MES / WCS 診断画面；
- 後続のエンジニアリング改善。

PCN Trace が記録するのは、単純な停止ログではない。

> **なぜシステムが特定の協調状態遷移において継続可能な協調実行状態へ入れなかったのか、そして最終的にどの制御経路を採用したのか。**

時間情報 T は、エンジニアリング上の状態内容が同じであっても、異なる時間位置で発生した協調状態インスタンスを区別するためにも使用できる。

## 8. モジュールの価値と公開範囲

MES / WCS 協調停滞診断モジュールの中核的な役割は、ログの量を増やすことではなく、従来タスク、スケジューリング、資源、経路、ステーション、許可、主体、下流システムなどに分散していた状態を、協調停滞の判定と制御に利用できるエンジニアリング構造として整理することである。

これにより、現場の処理プロセスを、

```text
システム停滞 → ログ確認 → スケジューリング確認 → 設備確認 → 複数システムを横断して確認
```

から、さらに次のような構造へ変換できる。

```text
協調状態異常
→ PCN 判定
→ 停滞識別
→ 構造分析
→ CAE-SDB Result + T
→ Arbitration
→ Multipath Control
→ PCN Trace
```

MES / WCS 製品にとって、これはシステムが単に、

> **何が起きたか。**

を記録するだけでなく、さらに、

> **なぜ現在の協調実行を継続できないのか、そして次にどの制御経路へ進むべきか。**

を説明できることを意味する。

本稿は公開事例であり、次の事項のみを説明する。

- モジュールの位置付け；
- 複数ソース状態；
- C / A / E 状態マッピング；
- S / D / B 判定；
- 群体状態と指標；
- 停滞識別；
- 構造分析；
- CAE-SDB Result；
- 時間情報 T；
- Arbitration；
- Multipath Control；
- PCN Trace。

具体的なしきい値、制御優先度、資源解放ルール、経路調整戦略、エネルギー補給戦略、インターフェースパラメータ、内部実行メカニズムなどについては、実際の MES / WCS プラットフォーム、現場対象、安全要求、エンジニアリング納入仕様に応じて決定する必要がある。

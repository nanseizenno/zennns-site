## 1. 現場で発生する問題

MES は、作業指示、タスク、設備、ステーション、材料、アラーム、生産量、生産実績などを記録できる。

WCS は、搬送タスク、車両状態、経路状態、リソース占有、スケジューリング結果などを記録できる。

設備システムは、運転、待機、アラーム、Interlock などの状態を記録できる。

HMI でも、Ready、Waiting、Blocked、Pending などの運転状態を表示できる。

しかし、複数設備、複数タスク、複数システムが連携する環境では、次のような問題が発生することがある。

- タスクは生成されているが、実行が継続的に進まない。
- 車両はオンラインで、ステーションにも需要があるが、補給が連続した実行につながらない。
- 単体設備には明確な異常がないにもかかわらず、システム全体のスループットが継続的に低下する。
- MES、WCS、PLC、車両、ステーションの各システムに状態記録があるが、協調停滞が発生している位置や要因を迅速に特定できない。
- オーダー変更、リソース競合、許可待ち、下流閉塞、人による確認、エネルギー補給などが重なり、最終的には複数システムを横断してログと状態を照合する必要がある。

したがって、問題は「システムにデータが存在するかどうか」ではない。

より重要なのは、次の問いである。

> **なぜ現在のシステムは、継続可能な協調実行状態へ移行できないのか。**

TPCA / PCN では、この問題を明確な Target State Entry に対する判定問題として扱う。

本事例では、

```text
Target State：　継続可能な協調実行状態
```

と定義する。

PCN は、本 Target State Entry に関係する複数ソース状態を取得し、そのエンジニアリング上の役割に基づいて C / A / E へ整理する。

- C：タスク、材料、ステーション、経路、現場条件などの事実条件が成立しているか。
- A：スケジューリング許可、リソースロック、エリア許可、安全許可、人による許可などが成立しているか。
- E：主体、経路、バッファ、下流、エネルギー補給、結果書戻しなどの実行チェーンを継続できるか。

その後、S / D / B 判定を行い、群全体の状態指標と組み合わせて停滞識別、構造分析、Arbitration、Multipath Control を行う。

したがって、システム出力は、

```text
Waiting
Blocked
Pending
```

だけに限定されない。

```text
Current State
→ 停滞識別
→ 構造化判定
→ Arbitration
→ Multipath Control
→ PCN Trace
```

という一連の判定・制御構造として扱う。

## 2. モジュールの位置付けと PCN の位置

本事例の対象は、

> **MES / WCS 協調停滞診断モジュール**

である。

本モジュールは製造現場の協調層に位置し、MES、WCS、搬送システム、設備ユニット、ステーション、バッファ、経路リソース、許可システム、現場実行対象などの状態を取得する。

AGV / AMR 群制御搬送は代表的な適用例の一つであるが、本モジュールの適用対象を AGV に限定するものではない。

代表的な適用対象には、次のようなものがある。

- 無人フォークリフトおよび自動搬送システム
- 複数設備による協調生産
- ラインサイド補給とバッファスケジューリング
- 工程待ちとステーション受入
- 経路リソース競合
- エリア許可とリソースロックの協調
- 臨時オーダーと優先順位切替
- エネルギー補給の集中によるシステム全体の実行能力低下

![MES / WCS 協調停滞診断モジュール概念図](/images/tpca/08-mes-wcs-collaborative-stagnation-module.png)

図：MES / WCS 協調停滞診断モジュールは製造現場の協調層に位置し、MES、WCS、AGV / AMR、バッファエリア、加工設備、経路リソース、自動ドア、エレベーター、充電エリア、安全許可システム、監視システムなどから複数ソース状態を取得する。

本事例における Current State は、例えば次のように表せる。

```text
タスクが存在
車両がオンライン
ステーションに需要あり
Waiting / Blocked / Pending が継続
局所的な混雑または断続的な実行
システム全体のスループットが低下
```

Target State：

```text
継続可能な協調実行状態
```

この Target State は、

> **タスク、主体、経路、リソース、ステーション、下流、結果書戻しが、後続処理を継続できる実行構造を形成している状態**

を示す。

PCN は、この Target State Entry の前に配置する。

```text
Current State
      ↓
     PCN
      ↓
Target State
```

PCN は Target State へ移行する前に、複数ソース状態の取得、構造化判定、停滞識別、制御経路選択を行う。

後続で過去の正常運転時と同一または類似した状態内容が再び形成された場合でも、TPCA では新しい状態インスタンスとして扱う。過去の状態インスタンスへ戻ったとはみなさない。

## 3. 複数ソース状態信号と C / A / E 状態マッピング

協調停滞は、単一設備の状態ではなく、複数のタスク、主体、リソース、ステーション、実行対象の関係によって形成される。

このため PCN は、現在の協調実行に直接関係する状態を複数の情報源から取得する。

| 信号源 | 代表的な状態 |
|---|---|
| MES | 作業指示、タスク、優先順位、材料需要、ステーション需要、計画変更、人による確認、異常記録 |
| WCS / スケジューリングシステム | タスクキュー、タスク割当結果、タスク状態、配車結果、リソースロック、経路割当、ステーション占有、バッファ状態 |
| AGV / AMR / 無人フォークリフト | オンライン状態、自動モード、位置、空荷 / 積載、バッテリー残量、タスク実行、待機、移動、アラーム状態 |
| 設備 / ステーション | 受入可能状態、運転状態、待機状態、材料不足状態、完了状態、アラーム状態 |
| 経路・設備リソース | 狭通路、交差点、自動ドア、エレベーター、エリア通行権、バッファエリア、荷役ポイント占有状態 |
| 安全・許可システム | エリア許可、安全許可、上位許可、人による許可、ロック状態 |
| 下流・書戻し経路 | 下流受入可能状態、結果書戻し状態、異常処理状態 |

これらの状態は、取得元ではなく、本 Target State Entry における役割に基づいて C / A / E へマッピングする。

| 状態変数領域 | 判定内容 | 本事例における代表項目 |
|---|---|---|
| C：Condition | Target State へ移行するために必要な事実条件が成立しているか | タスク存在、材料一致、対象ステーションに需要あり、ステーション有効、主体がスケジューリング対象、目標経路が存在 |
| A：Authority | 現在のタスク、主体、リソースについて協調実行を継続する許可が成立しているか | スケジューリング許可、リソースロック解放、エリア許可、安全許可、人による確認、上位許可 |
| E：Execution Chain | Target State へ移行した後、実行チェーンを継続できるか | 主体が実行可能、経路通行可能、ステーション受入可能、バッファ受入可能、下流処理可能、エネルギー補給による実行能力への影響が許容範囲、結果書戻し可能 |

したがって、次の関係は同義ではない。

```text
タスクが存在 ≠ Target State が成立

車両がオンライン ≠ Execution Chain が成立

単体 Ready ≠ システム全体の実行チェーンが継続可能
```

例えば、

- タスクは存在するが、リソースロックが解放されていない場合、A は成立しない。
- 主体はオンラインであっても、Target State で必要となるステーションが受入不能であれば、E は成立しない。
- 多数の主体が同時にエネルギー補給へ移行し、実行可能主体の比率が低下した場合、E に関係するシステム全体の実行能力が低下する。
- タスク、主体、経路の記録が存在していても、下流が長時間受入不能であれば、Target State は成立しない。

## 4. S / D / B 判定と群全体の状態

C / A / E は、対象状態が本 Target State Entry においてどの状態変数領域に属するかを示す。

S / D / B は、それらの状態に対して、構造完全性、動的時系列有効性、制御境界を判定するために使用する。

| 判定性質 | 判定内容 | 本事例における代表項目 |
|---|---|---|
| S：Structure | 必要な信号、インターフェース、マッピング関係、許可元、リソース関係、実行チェーン境界が定義・接続され、観測可能であるか | MES-WCS 間のタスクマッピング、リソースロック取得元、ステーション受入状態、経路リソース、エネルギー補給状態、結果書戻し状態 |
| D：Dynamics | 現在のタスク、主体、ステーション、許可、経路、実行状態が現在も有効で、同期され、タイムアウトしておらず、競合していないか | 作業指示変更未同期、主体位置遅延、ステーション状態未更新、許可取消、経路占有競合、実行フィードバックタイムアウト |
| B：Boundary | 現在の協調状態が事前に定義された制御境界に到達しているか | 待ち時間、リソース占有時間、ステーション容量、未実行主体比率、エネルギー補給主体比率、リトライ回数、流量制限条件、再割当条件、復帰条件 |

単体状態だけでなく、システム全体の運転状態も確認する必要がある。

代表的な状態または指標には、次のようなものがある。

- 未実行主体比率
- 補助動作主体比率
- エネルギー補給主体比率
- 許可未成立主体比率
- 経路リソース占有状態
- ステーション受入状態
- 重要タスクの継続未実行状態

これらの状態および指標は、

> **現在の問題が局所的な待機にとどまっているのか、それともシステム全体の協調停滞へ発展しているのか**

を判定するために使用する。

![協調停滞識別と Multipath Control のフロー](/images/tpca/09-collaborative-stagnation-control-flow.png)

図：モジュールは複数ソース状態を取得し、C / A / E 状態マッピング、S / D / B 判定、群全体の状態指標計算、停滞識別、構造分析、Arbitration、Multipath Control、履歴記録を順に行う。

## 5. 停滞識別と構造分析

協調停滞診断では、単一の Waiting や Blocked 状態を直接分類するのではなく、まずシステム全体が継続的な停滞状態にあるかを確認する。

例えば、

```text
有効なタスクが存在
        +
複数の自動運転主体が継続的に有効実行へ移行しない
        +
未実行主体の状態が判定条件を一定時間継続して満たす
        ↓
協調停滞
```

協調停滞を確認した後、群全体の状態指標と関連する C / A / E 情報を用いて停滞構造を分析する。

代表的な構造を以下に示す。

### 割当制約

代表的な状態：

- 有効なタスクが存在する。
- 複数の主体が長時間実行へ移行しない。
- タスク割当、許可、リソース解放が有効な実行関係を形成していない。

### リソース競合

代表的な状態：

- 主体が移動、迂回、待機、共有リソースの競合を繰り返している。
- 経路、交差点、自動ドア、エレベーター、ステーションなどの共有リソースで競合が発生している。
- 群全体では移動や待機などの補助動作が多い一方で、有効タスクの進行が不足している。

### エネルギー偏在

代表的な状態：

- 多数の主体が充電またはその他のエネルギー補給状態へ集中している。
- 実タスクに使用可能な主体の比率が低下している。
- エネルギー補給状態の偏りがシステム全体の協調実行能力に影響している。

### 未確定状態

現在取得できる状態および指標だけでは十分な根拠を持って停滞構造を特定できない場合は、未確定状態として扱う。

この場合は、強化記録または人による確認へ移行する。

具体的な MES / WCS 製品実装では、許可、ステーション受入、経路閉塞などの診断情報を追加表示できる。ただし、これらの情報は停滞識別結果および構造分析結果と整合している必要がある。

## 6. CAE-SDB Result、時間情報 T、Arbitration、Multipath Control

PCN は、C / A / E 状態に対して S / D / B 判定を行い、1 つまたは複数の CAE-SDB Result を形成する。

同時に、本状態および判定に対応する時間情報 T を保持する。

時間情報 T は、例えば次の用途に使用する。

- 協調状態の継続時間の判定
- 関連状態のタイムアウトまたは未更新判定
- 状態間の前後関係の確認
- PCN Trace の形成

代表的な CAE-SDB Result を以下に示す。

| 判定結果 | 本事例における代表的な状態 |
|---|---|
| C-S | タスク、対象、ステーション、経路に必要なマッピング関係が未定義 |
| C-D | 作業指示変更未同期、タスク状態未更新、需要状態失効 |
| C-B | タスク待ち、滞留、継続未実行が制御境界に到達 |
| A-S | スケジューリング許可、リソースロック、エリア許可、人による確認の取得元が未定義または観測不能 |
| A-D | 許可未更新、許可取消、リソースロック状態非同期 |
| A-B | 許可待ちまたはリソース占有が制御境界に到達 |
| E-S | 経路、ステーション、バッファ、下流、エネルギー補給、書戻し経路が未定義 |
| E-D | 経路状態競合、ステーション状態未更新、主体実行フィードバックタイムアウト、実行チェーン閉塞 |
| E-B | 経路待ち、ステーション容量、エネルギー補給、下流待ちが制御境界に到達 |

同一の Target State Entry に対して、複数の CAE-SDB Result が同時に成立する場合がある。

これらの判定結果と停滞識別結果を Arbitration に入力し、最終的な Multipath Control を形成する。

代表的な制御経路には、次のようなものがある。

- 正常実行継続
- 待機
- タスク再割当
- リソース解放
- 経路または通行権の調整
- 流量制限
- バッファ分流
- 下流調整
- エネルギー補給戦略の調整
- 縮退実行
- 人による確認
- 進入禁止
- 異常隔離
- 強化記録

これらの制御経路は、Current State から異なる後続の Target State または目標実行経路へ移行することを示す。

後続で過去の正常運転時と同一の状態内容が再び形成された場合でも、TPCA では新しい状態インスタンスとして扱う。

したがって、現場で確認される結果は、

```text
Waiting
Blocked
Pending
```

だけに限定されない。

```text
Current State
→ 停滞識別
→ CAE-SDB Result + T
→ Arbitration
→ Multipath Control
```

という構造として扱う。

## 7. PCN Trace と協調停滞の振り返り

PCN は判定結果および制御結果を形成すると同時に、対応する PCN Trace を生成する。

代表的な記録項目は次のとおりである。

- Current State
- Target State
- 関連主体およびタスク
- 主要入力状態
- 時間情報 T
- C / A / E 状態マッピング
- S / D / B 判定
- CAE-SDB Result
- 群全体の状態または指標
- 停滞識別結果
- Arbitration Result
- Multipath Control
- 実行結果
- Trace ID

これらの記録は、例えば次の用途に利用できる。

- 頻発する停滞入口の識別
- 停滞構造の比較
- 許可およびリソースロック問題の解析
- 経路とステーションの協調問題分析
- エネルギー補給状態の分析
- 制御経路の効果比較
- MES / WCS 診断画面
- 後続のエンジニアリング改善

PCN Trace の目的は、単純な停止ログを追加することではない。

記録の中心は、

> **なぜ今回の Target State Entry が成立しなかったのか。また、その結果としてどの制御経路が選択され、どの状態へ移行したのか。**

という状態遷移判定履歴である。

時間情報 T を保持することで、状態内容が同一であっても、異なる時間位置で形成された状態インスタンスを区別できる。

## 8. モジュールの位置付けと公開範囲

MES / WCS 協調停滞診断モジュールの中核的な役割は、ログの量を増やすことではない。

従来、タスク、スケジューリング、リソース、経路、ステーション、許可、主体、下流システムなどに分散していた状態を、Target State Entry を中心として、協調停滞の判定と制御に利用できるエンジニアリング構造へ整理することにある。

これにより、現場での確認プロセスを、

```text
システム停滞
→ ログ確認
→ スケジューリング確認
→ 設備確認
→ 複数システムを横断して確認
```

だけに依存する状態から、

```text
協調状態異常
→ PCN 判定
→ 停滞識別
→ 構造分析
→ CAE-SDB Result + T
→ Arbitration
→ Multipath Control
→ PCN Trace
```

という構造化された判定・制御プロセスへ展開できる。

MES / WCS 製品にとって、これは単に、

> **何が起きたか。**

を記録するだけではなく、

> **なぜ現在の協調実行を継続できないのか。また、次にどの制御経路へ移行すべきか。**

を説明するための構造を持つことを意味する。

本稿は公開説明用の事例である。

公開範囲は次のとおりである。

- モジュールの位置付け
- 複数ソース状態
- C / A / E 状態マッピング
- S / D / B 判定
- 群全体の状態および指標
- 停滞識別
- 構造分析
- CAE-SDB Result
- 時間情報 T
- Arbitration
- Multipath Control
- PCN Trace

具体的なしきい値、継続時間条件、制御優先度、リソース解放ルール、経路調整戦略、エネルギー補給戦略、インターフェースパラメータ、PCN Runtime の内部実行メカニズムなどについては、実際の MES / WCS プラットフォーム、現場対象、安全要求、制御仕様、エンジニアリング納入仕様に応じて別途設計する。

なお、PCN は既存の安全制御システム、安全 PLC、安全リレー、ハードウェア安全回路などを代替するものではない。安全許可は、既存安全制御システムから取得する A：Authority に関係する状態として扱う。

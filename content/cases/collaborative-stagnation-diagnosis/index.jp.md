## MES に状態が記録されていても、なぜ製造現場の停滞を説明できないのか

> 適用階層：群制御・協調層 / MES-WCS 協調停滞診断  
> 代表対象：製造現場協調停滞診断モジュール

**推奨引用：**

```text
全野南政 / Nansei Zenno，
『MES / WCS 協調停滞診断モジュール事例：MES に状態が記録されていても、なぜ製造現場の停滞を説明できないのか』，
公開事例，Public Case Version 1.6，
2026-09-20，
https://zennns.com/jp/cases/collaborative-stagnation-diagnosis/
```

MES は、タスク、設備、ステーション、材料、生産実績などを記録できる。WCS は、搬送タスク、搬送主体、経路、資源占有状態、スケジューリング結果などを管理・記録できる。

それでも、複数設備、複数タスク、複数システムが連携する製造現場では、タスクが生成されているにもかかわらず実行が進まない、実行主体はオンラインでステーションにも要求があるのに補給や搬送が継続しない、単体設備には明確な故障がないのにシステム全体の協調性能が低下し続ける、といった状況が発生する。

さらに、各システムに状態記録が存在していても、「なぜ全体として停滞しているのか」を直接説明できない場合がある。

本事例が対象とする工程問題は、次の問いである。

> **現在のシステムは、なぜ「継続可能な協調実行状態」へ進入できないのか。**

ここで確認するのは、「停滞が発生している」という現象そのものではない。

> **MES、WCS、搬送主体、共有資源、許可システムなどに分散している協調実行上の状態を、明確な目標状態入口、CAE-SDB 判定結果、群全体の停滞構造、制御方向、実行結果、状態遷移判定履歴として一連の工程関係に組織化できるか。**

という点を扱う。

本事例は、統一した9ステップの工程順序に沿って説明する。

```text
1. 現在状態

2. 目標状態 / 目標状態入口

3. PCN：
   関連状態取得
   + C / A / E 状態マッピング

4. 前制御判定と群制御・協調分析
   ├─ S / D / B 判定
   │  → CAE-SDB Result + T
   │
   └─ 群指標
      → 群全体の停滞判定
      → 停滞構造分類

5. 制御優先度調停

6. 複数経路制御

7. 現在の入口に対する制御結果

8. 制御経路の実行
   / 後続の目標状態入口
   / 実行結果

9. 状態遷移判定履歴
```

基礎概念については、以下を参照できる。

- [中核概念](/jp/concepts/)
- [TPCA / PCN 状態遷移前制御アーキテクチャ｜ホワイトペーパー](/jp/whitepaper/)

## 事例対象

本事例の対象は、MES / WCS 協調停滞診断モジュールである。

本モジュールは製造現場の協調層に位置し、MES、WCS、搬送システム、設備ユニット、ステーション、経路資源、許可システム、下流設備などから関連状態を取得する。

AGV / AMR の群制御搬送は代表的な適用場面の一つであるが、本事例が対象とするのは、より一般的な製造現場における協調停滞である。

![MES / WCS 協調停滞診断モジュールの構成イメージ](/images/tpca/08-mes-wcs-collaborative-stagnation-module.png)

図：協調停滞診断モジュールは、MES、WCS、搬送主体、ステーション、経路資源、許可状態、下流状態を取得し、同一の協調状態遷移に関連付ける。

---

# 1. 現在状態

現在、製造現場はどのような状態にあるか。

```text
現在状態：

タスクが存在する

実行主体はオンライン

一部のタスクが継続して未実行

複数の実行主体が待機を継続

協調実行が阻害されている
```

一方、現場では次の状態も確認できる。

```text
ステーションに要求が存在する

一部の搬送経路は利用可能

単体設備に重大アラームはない

一部のタスクは継続して実行中
```

この時点で確認できるのは、システム全体の協調実行が阻害されているという事実である。

この状態だけから、群全体として停滞が成立していると判断することはできない。

---

# 2. 目標状態 / 目標状態入口

今回、システムはどの状態へ進もうとしているか。

```text
目標状態：
継続可能な協調実行状態

目標状態入口：
継続可能な協調実行状態への進入
```

PCN は、現在の協調状態と目標状態入口の間に位置する。

```text
現在状態
［協調実行が阻害されている］
    ↓
PCN
［継続可能な協調実行状態への進入前判定］
    ↓
目標状態入口
［継続可能な協調実行状態への進入］
    ↓
目標状態
［継続可能な協調実行状態］
```

以降の状態マッピング、CAE-SDB 判定、群全体の停滞判定、制御処理は、すべてこの目標状態入口を基準として行う。

---

# 3. PCN：関連状態取得と C / A / E 状態マッピング

今回の目標状態入口に対して、どの状態が重要になるか。

PCN は、「継続可能な協調実行状態への進入」に直接関係する状態を取得し、それぞれの工程上の役割に基づいて C / A / E へマッピングする。

| 代表状態 | 状態マッピング |
|---|---|
| タスク状態、ステーション要求、目標ステーション情報 | C：条件状態 |
| スケジューリング許可、資源ロック、区域許可、安全許可 | A：許可状態 |
| 実行主体状態、搬送経路状態、ステーション受入状態、下流状態 | E：実行チェーン状態 |

本事例では、主に次の状態を使用する。

```text
タスク存在 → C

資源ロック状態 → A

安全許可 → A

実行主体オンライン → E の関連状態

搬送経路利用可能状態 → E
```

群全体の未実行比率など、複数主体を集約して得られる群指標は、単独の CAE-SDB Result には直接対応させない。

これらの情報は、後段の群制御・協調分析に用いる。

---

# 4. 前制御判定と群制御・協調分析

今回、どのような問題が発生しているか。

本事例では、次の状態を仮定する。

```text
タスク：
存在

実行主体：
オンライン

安全許可：
成立

資源ロック用インターフェース：
確立済み

資源ロック状態：
システム間で非同期

群全体未実行比率：
停滞判定条件に到達
```

資源ロックは、現在の目標状態入口において A：Authority に対応する。

今回の問題は、資源ロック状態そのものの有無ではなく、複数システム間でその状態が同期しておらず、現在の許可根拠として利用できない点にある。

したがって、次の CAE-SDB Result が形成される。

```text
CAE-SDB Result：
A-D

判定内容：
資源ロック状態がシステム間で同期しておらず、
現在の協調実行入口に対する
有効な許可根拠として使用できない
```

一方、群制御・協調層では、複数主体の状態を集約した群指標に基づき、群全体の停滞判定と停滞構造分類を行う。

```text
群全体未実行比率：
停滞判定条件に到達

群全体補助実行比率：
資源競合型の特徴を示す

群全体エネルギー補給比率：
エネルギー補給への偏りは認められない

群全体許可未成立比率：
本事例では取得済みであり、
割当制約型を主因とする特徴は認められない

群全体の停滞判定：
成立

停滞構造分類：
資源競合型
```

ここで、群全体未実行比率は、複数主体を含む停滞が成立しているかを確認するために使用する。

そのうえで、群全体補助実行比率、群全体エネルギー補給比率、取得可能な群全体許可未成立比率などを用いて、停滞構造をさらに分類する。

本公開事例では、これらの指標間の工程関係までを示し、具体的な比率閾値や継続時間閾値は公開しない。

したがって、第4ステップでは二種類の結果を形成する。

```text
CAE-SDB：

A-D
資源ロック状態の動的時系列有効性に問題あり


群制御・協調分析：

群全体の停滞判定 = 成立

停滞構造分類 = 資源競合型
```

この二種類の結果は統合せず、それぞれの意味を保持したまま、次の制御優先度調停へ入力する。

本事例では、CAE-SDB の9座標すべて、ならびに停滞構造分類の全パターンまでは扱わない。

詳細については、以下を参照できる。

- [なぜ CAE-SDB なのか？——目標状態入口前の二軸構造化分析法](/jp/notes/why-cae-sdb/)
- [なぜ MES / WCS は状態を記録できても、停滞の理由を説明できないのか？](/jp/questions/why-mes-records-but-cannot-explain/)

# 5. 制御優先度調停

複数の判定結果が同時に存在する場合、何を優先して処理するか。

今回の制御優先度調停には、主に次の情報を入力する。

```text
CAE-SDB Result：

A-D
資源ロック状態がシステム間で非同期


群全体の停滞判定：

成立


停滞構造分類の根拠：

群全体補助実行比率
→ 資源競合型の特徴

群全体エネルギー補給比率
→ エネルギー補給への偏りなし

群全体許可未成立比率
→ 割当制約型を主因とする特徴なし


停滞構造分類：

資源競合型


重要な安全許可：

成立
```

これらを踏まえ、今回の制御優先度調停では、まず資源ロック状態の不整合を解消し、そのうえで搬送経路と影響を受けているタスクの再調整を行う。

```text
制御優先度調停結果：

資源ロック状態の不整合を優先して解消

同時に、
搬送経路の調整
および
影響タスクの再割当て
を実施
```

---

# 6. 複数経路制御

どの制御処理が選択されたか。

今回の制御優先度調停結果から、次の複数経路制御を形成する。

```text
複数経路制御：

資源解放
+
搬送経路調整
+
タスク再割当て
```

本公開事例における協調停滞診断モジュールは、まず構造化された制御結果、制御提案、または協調要求を形成する。

実際のプロジェクトで、本モジュールが制御指令まで直接出力するかどうかは、既存の MES、WCS、スケジューリングシステム、現場制御システムとのインターフェース、および付与されている制御権限によって決まる。

---

# 7. 現在の入口に対する制御結果

今回、「継続可能な協調実行状態」へ進入するか。

```text
現在の入口に対する制御結果：

現時点では
継続可能な協調実行状態へ進入しない
```

現在の資源ロック状態には A-D が存在し、同時に群全体の停滞が資源競合型として判定されているためである。

今回の後続処理は、次のように確定する。

```text
資源解放

搬送経路調整

タスク再割当て
```

---

# 8. 制御経路の実行 / 後続の目標状態入口と実行結果

選択された制御処理を実行した後、何が起きるか。

本事例で選択された複数経路制御は、現在の協調状態を回復させるための調整処理であり、実行権限を持つ既存システムによって実施される。

```text
現在の協調実行入口には進入しない
    ↓
資源解放
    ↓
搬送経路調整
    ↓
タスク再割当て
    ↓
新たな協調運転状態を形成
```

これらの処理完了後、次の状態になったと仮定する。

```text
資源ロック状態：
システム間で再同期

主要搬送経路：
利用可能状態へ復帰

影響タスク：
再割当て完了

群全体未実行比率：
停滞判定条件を下回る
```

この場合、実行結果は次のように整理できる。

```text
実行結果：

共有資源と搬送経路の関係が回復し、
影響を受けていたタスクが
再び実行可能な状態へ移行
```

一方、後続制御として代替搬送経路、退避経路、異常品搬送経路など、別の目標状態または目標実行経路が選択された場合は、新たな目標状態入口を設定する。

その場合は、対応する PCN が当該入口について改めて前制御判定を行う。

## 事例まとめ

本事例では、MES、WCS、搬送主体、現場設備が、もともとタスク、実行主体、搬送経路、共有資源、運転状態などを記録している。

これらの情報から、まず確認できるのは次の状態である。

```text
タスクが存在する

実行主体はオンライン

複数の実行主体が待機を継続

協調実行が阻害されている
```

これを9ステップの工程順序に基づいて整理すると、今回の状態遷移は次のように明確化される。

```text
目標状態入口：

継続可能な協調実行状態への進入


CAE-SDB Result：

A-D

資源ロック状態が
システム間で同期していない


群全体の停滞判定：

成立


停滞構造分類の根拠：

群全体補助実行比率
→ 資源競合型の特徴

群全体エネルギー補給比率
→ エネルギー補給への偏りなし

群全体許可未成立比率
→ 割当制約型を主因とする特徴なし


停滞構造分類：

資源競合型
```

### 本事例によって明確になる工程情報

| 従来の現場情報から確認できること | 本事例によってさらに明確になること |
|---|---|
| タスクが生成されている | 「継続可能な協調実行状態へ進入できるか」という明確な目標状態入口を判定対象として設定できる |
| 実行主体がオンラインである | 主体がオンラインであることは関連状態の一つであり、協調実行全体の継続可能性を単独では示さない |
| 複数の実行主体が待機している | 群全体未実行比率を用いて、複数主体を含む停滞が成立しているかを判定できる |
| 資源ロックに不整合がある | 資源ロックを現在の入口における A として位置付け、**A-D：資源ロック状態の動的時系列有効性に問題あり** と整理できる |
| 単体設備に重大アラームがない | 協調上の問題は、単体設備故障がなくても、タスク、許可、共有資源、実行チェーン間の関係から発生し得る |
| 経路や共有資源に競合が見られる | 群全体補助実行比率、エネルギー補給比率、許可未成立比率などを組み合わせ、停滞構造を **資源競合型** として整理できる |
| 現場では「全体が止まっている」としか見えない | 「現在の協調実行入口における許可状態の動的時系列有効性に問題があり、同時に資源競合型の群停滞が発生している」と説明できる |
| エンジニアが複数システムを確認しながら対処方法を判断する必要がある | 制御方向を「資源解放 + 搬送経路調整 + タスク再割当て」として明示できる |
| 対応後は新しい運転状態だけが残る | 資源ロックの再同期、経路復旧、タスク再割当て、群全体未実行比率の変化まで同じ工程履歴として確認できる |
| MES、WCS、搬送主体、設備がそれぞれログを保存している | 状態、CAE-SDB 判定、群全体の停滞判定、停滞構造分類、制御、実行結果を一回の状態遷移判定履歴として関連付けられる |

これにより、従来の、

> **「タスクは存在し、実行主体もオンラインだが、システム全体が停滞している。」**

という現象は、

> **「現在の協調実行入口のどこが成立していないのか、群全体の停滞がどのような構造を持つのか、どの制御を行うべきか、そして処理後にどのような状態へ変化したのか。」**

という工程関係へ展開できる。

本事例で示した主な工程上の意味は、分散した状態を一つの明確な目標状態入口へ関連付けること、協調実行阻害を具体的な CAE-SDB 判定問題へ展開すること、単体状態の判定と群全体の停滞構造を区別したまま同じ制御判断へ接続することにある。

さらに、群全体の現象を停滞構造として分類し、その結果を制御方向と実行結果へ接続できる。

その一連の状態、判定、停滞構造、制御、実行結果を、同じ状態遷移判定履歴として記録することもできる。

本事例で追加される価値は、タスク数、車両状態、設備状態などのデータ項目を増やすことではない。

> **MES、WCS、搬送主体、共有資源、許可システムに分散していた情報を、「現在の入口がなぜ成立しないのか」「群全体の停滞がどのような構造を持つのか」「どの制御を適用したのか」「その結果、協調状態がどのように変化したのか」という一連の工程関係として組織化することにある。**

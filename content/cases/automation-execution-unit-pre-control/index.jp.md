## ロボットが Ready でも、なぜ把持段階へ移行できないのか？

> 適用階層：自動化実行ユニット層  
> 代表対象：画像認識を用いた搬送ラインのロボットユニット

**推奨引用：**

```text
全野南政 / Nansei Zenno，
『自動化実行ユニット前判定事例：ロボットが Ready でも、なぜ把持段階へ移行できないのか』，
公開事例，Public Case Version 1.6，
2026-10-02，
https://zennns.com/jp/cases/automation-execution-unit-pre-control/
```

画像認識を用いた搬送ラインのロボットユニットでは、現場で次のような状態が見られることがある。

```text
Robot Ready：成立
画像認識結果：正常
安全許可：成立
正常品搬送先の受入状態：成立

ロボット動作：未開始
```

個々のシステムだけを見ると、明確な異常は見当たらない。

それでも、ロボットは把持を開始しない。

Robot Ready、画像認識結果、安全許可、正常品搬送先の受入状態は、それぞれ異なる設備やシステムから取得される。これらの状態の組合せが、**現在この時点で把持段階への移行要件を満たしているか**は、同じ目標状態入口を基準として判定する必要がある。

本事例では、「把持段階への移行」を Target State Entry（目標状態入口）とし、共通の9ステップの分析手順に沿って、PCN が関連状態を取得し、CAE-SDB 判定結果を生成し、その後の制御調停、複数経路制御、後続状態遷移、状態遷移判定履歴へどのようにつなげるかを説明する。

9ステップは次のとおりである。

1. 現在状態
2. 目標状態 / 目標状態入口
3. PCN：関連状態取得と C / A / E 状態マッピング
4. S / D / B 判定と CAE-SDB 判定結果 + T
5. 制御調停
6. 複数経路制御
7. 現在の入口に対する制御結果
8. 後続の目標状態入口と実行結果
9. 状態遷移判定履歴

基礎概念については、以下を参照できる。

- [中核概念](/jp/concepts/)
- [TPCA / PCN 状態遷移前制御アーキテクチャ｜ホワイトペーパー](/jp/whitepaper/)

## 事例対象

本事例では、画像認識を用いた搬送ラインのロボットユニットを代表対象とし、PCN は PLC 内の制御ロジックとして実装されているものとする。

ユニットの主な構成は次のとおりである。

- 搬送コンベヤ
- ワーク検出
- 画像認識システム
- ロボット
- グリッパ / 真空吸着ハンド
- 安全システム
- 正常品搬送先
- 戻し搬送経路
- 上位システム

このうち、「把持段階への移行」に直接関係する状態は、画像認識、ロボット、安全、搬送、下流、上位システムから取得する。

![画像認識搬送ラインのロボットユニット前制御イメージ](/images/tpca/06-pcn-pick-flow.png)

図：PCN は、ロボットが把持段階へ移行する前に、現在の目標状態入口に関係する複数システムの状態を取得し、判定結果に基づいて制御経路を決定する。

以下の時刻と値は、本公開事例の動作関係を説明するために設定した例示値であり、特定の実案件で使用されているパラメータではない。

---

# 1. 現在状態 / 現在段階

現在のワークは画像認識を完了しているが、ロボットによる把持はまだ開始されていない。

現在状態は次のとおりである。

```text
認識完了 / 把持待ち
```

今回の例では、次の状態が取得されている。

```text
ワーク存在：成立
画像認識結果：正常
Robot Ready：成立
ロボット動作：未開始
```

ワークはすでに今回の把持フローに入り、画像認識システムも今回のワークに対応する認識結果を生成している。

この時点で、システムは「認識完了 / 把持待ち」から「把持段階」へ移行してよいかを判定する必要がある。

これが、今回の状態遷移の起点となる。

---

# 2. 目標状態 / 目標状態入口

今回の目標状態は、

```text
把持段階
```

である。

対応する目標状態入口は、

```text
把持段階への移行
```

である。

PCN は、現在状態とこの目標状態入口の間に配置される。

ロボットが実際に動作を開始する前に、PCN は今回の入口に必要な状態取得、状態マッピング、判定、制御を完了する。

![目標段階入口前における PCN の位置関係](/images/tpca/07-pcn-position-before-target-stage.png)

図：PCN は、把持動作が実際に開始される前に、「把持段階への移行」という目標状態入口について前制御判定を行う。

---

# 3. PCN：関連状態取得と C / A / E 状態マッピング

PCN は、「把持段階への移行」に直接関係する状態だけを取得し、それぞれが今回の状態遷移で担うエンジニアリング上の役割に基づいて、C / A / E 状態マッピングを行う。

| 代表状態 | 状態マッピング |
|---|---|
| ワーク存在、位置、姿勢、画像認識結果 | C：条件状態 |
| 安全許可、区域許可、上位システム許可 | A：許可状態 |
| Robot Ready、ロボット動作経路、グリッパ / 真空吸着状態、正常品搬送先の受入状態 | E：実行チェーン状態 |

今回の例で重点的に使用する状態は、次のとおりである。

- 画像認識結果：C
- 安全許可：A
- Robot Ready：E の関連入力
- 正常品搬送先の受入状態：E

ここで、`Robot Ready = 成立` は、現在の把持実行チェーンに関係する一つの状態である。

これだけで、

```text
把持段階への移行：許可
```

と判断することはできない。

画像認識結果が現在のワークに対応しているか、現在も有効か、必要な許可が成立しているか、さらに把持後の実行チェーンが継続できるかを確認する必要がある。

戻し搬送や異常系への分岐などの経路状態は、後続の制御経路を選択するために使用する情報であり、現在の把持入口における E の成立を直接代替するものではない。

---

# 4. S / D / B 判定と CAE-SDB 判定結果

今回の例では、PCN が把持入口で次の状態を取得したものとする。

```text
現在の判定時刻：10:32:21.850

Robot Ready：成立
安全許可：成立
正常品搬送先の受入状態：成立

画像認識結果：正常
画像認識結果の生成時刻：10:32:14.200
画像認識結果の有効時間窓：5.0 s
```

画像認識結果の生成から現在の判定時刻までに経過した時間は、

```text
10:32:21.850
-
10:32:14.200
=
7.650 s
```

である。

今回の例で設定した画像認識結果の有効時間窓は、

```text
5.0 s
```

である。

したがって、状態値そのものは、

```text
画像認識結果：正常
```

のままであっても、現在の把持入口に対する有効な判定根拠としては使用できない。

画像認識結果は、現在の把持入口で C にマッピングされている。

今回の問題は、この状態の動的時系列有効性にあるため、次の CAE-SDB 判定結果が生成される。

```text
CAE-SDB 判定結果：

C-D

画像認識結果が有効時間を超過しており、
現在の把持入口に対する有効な判定根拠として
使用できない
```

この区別は重要である。

現場で確認できる元の状態は、

```text
画像認識結果：正常
```

であっても、PCN が現在確認するのは、

```text
この正常結果を、今も今回の把持入口の判定に使用できるか
```

という問題である。

状態値が正常であることと、その状態を現在の判定根拠として使用できることは、別のエンジニアリング問題である。

今回の状態値、生成時刻、判定時刻、生成された C-D 判定結果は、時間情報 T と関連付けて保存する。

本事例では、現在の問題に直接関係する判定だけを扱い、CAE-SDB の全座標を逐一展開しない。

C / A / E と S / D / B の二軸関係については、以下を参照できる。

[なぜ CAE-SDB なのか？——目標状態入口前の二軸構造化分析法](/jp/notes/why-cae-sdb/)

---

# 5. 制御調停

現在の把持入口では、次の主要な判定情報が得られている。

```text
CAE-SDB 判定結果：
C-D

重要な安全許可：
成立

Robot Ready：
成立

正常品搬送先の受入状態：
現在の入口要件を満たす

戻し搬送経路：
利用可能
```

Robot Ready、安全許可、正常品搬送先の受入状態が成立していても、すでに失効した画像認識結果をそのまま使用して把持段階へ移行することはできない。

現在の把持動作に必要な位置・姿勢情報は、判定根拠としての有効性を失っている。

制御調停の結果は、次のようになる。

```text
現在の把持入口：
移行不可

後続制御方向：
戻し搬送を優先
```

ここで制御調停が扱うのは、複数の状態や判定結果が同時に存在する中で、今回の入口に対して最終的にどの制御結果を確定するかという問題である。

---

# 6. 複数経路制御

制御調停の結果に基づき、今回の複数経路制御では、後続候補経路として「戻し搬送」を選択する。

```text
複数経路制御：

後続候補経路
→ 戻し搬送
```

ここでいう「戻し搬送」は、現在の把持入口へは移行せず、ワークを別の搬送処理へ移すための後続候補経路を表す。

この時点では、まだワークが「戻し搬送経路への移行」を許可されたことを意味しない。

---

# 7. 現在の入口に対する制御結果

現在の Target State Entry（目標状態入口）は、

```text
把持段階への移行
```

である。

この入口に対する制御結果は、

```text
移行しない
```

となる。

したがって、今回の判定では、ロボットは失効した画像認識結果を使用して把持動作を実行しない。

同時に、次の判定対象として新しい目標状態と目標状態入口が設定される。

```text
目標状態：
戻し搬送状態

目標状態入口：
戻し搬送経路への移行
```

ここまでで、現在の「把持入口 PCN」が担当する責任範囲は完了する。

---

# 8. 後続の目標状態入口と実行結果

システムが戻し搬送経路へ進もうとすると、判定対象となるエンジニアリング対象が変わる。

新しい状態遷移は、次のとおりである。

```text
現在状態：
認識完了 / 把持待ち

目標状態：
戻し搬送状態

目標状態入口：
戻し搬送経路への移行
```

「戻し搬送経路への移行」は、新しい Target State Entry（目標状態入口）である。

したがって、この入口に対応する PCN が、戻し搬送入口に定義された関連状態と移行条件に基づいて、あらためて前制御判定を行う。

たとえば、戻し搬送入口では次のような状態を確認する可能性がある。

```text
戻し搬送コンベヤの準備状態
戻し搬送経路の利用可能状態
区域許可
ワーク現在位置
戻し搬送先の受入状態
```

これらの状態は、把持入口で「戻し搬送」を選択したからといって自動的に成立するものではない。

新しい戻し搬送入口で移行が許可された場合に、システムは実際の戻し搬送を実行し、対応する実行結果を得る。

```text
実行結果：

戻し搬送状態への移行完了
```

本公開事例では、戻し搬送入口に対する詳細な状態設定、CAE-SDB 判定、制御規則までは扱わない。

---

# 9. 状態遷移判定履歴

今回の把持入口については、次のような PCN Trace（状態遷移判定履歴）を記録できる。

```text
履歴 ID：
PCN-PICK-XXXX

PCN：
把持入口 PCN

現在状態：
認識完了 / 把持待ち

目標状態：
把持段階

目標状態入口：
把持段階への移行

判定時刻：
10:32:21.850

主要な関連状態：
  Robot Ready = 成立
  安全許可 = 成立
  正常品搬送先の受入状態 = 成立
  画像認識結果 = 正常
  画像認識結果の生成時刻 = 10:32:14.200

CAE-SDB 判定結果：
C-D

判定内容：
画像認識結果が 5.0 s の有効時間窓を超過

制御調停結果：
現在の把持入口への移行不可

複数経路制御：
後続候補経路として戻し搬送を選択

現在の入口に対する制御結果：
現在の把持入口には移行しない

後続の目標状態：
戻し搬送状態

後続の目標状態入口：
戻し搬送経路への移行

時間情報：
T
```

この履歴が保持するのは、単純な、

```text
ロボット未動作
```

という結果ではない。

一つの目標状態入口に対する1回の判定について、状態、判定、制御の関係をまとめて記録する。

その後、「戻し搬送経路への移行」を判定する場合には、戻し搬送入口に対応する PCN が、新しい状態遷移判定履歴を記録する。

PCN Trace の詳細については、以下を参照できる。

[なぜ PCN Trace は新しいエンジニアリングデータなのか？](/jp/notes/why-pcn-trace-is-engineering-data/)

## 事例まとめ

今回の例の開始時点では、現場で次の状態が確認できる。

```text
Robot Ready：成立
画像認識結果：正常
安全許可：成立
正常品搬送先の受入状態：成立
```

現在の状態値だけを見ると、

> **ロボットは Ready なのに、なぜ把持しないのか。**

という疑問が残る。

これらの状態を「把持段階への移行」という Target State Entry（目標状態入口）へ対応付けると、さらに次の情報が確認できる。

```text
画像認識結果：正常
画像認識結果の経過時間：7.650 s
許容される有効時間窓：5.0 s

CAE-SDB 判定結果：C-D
```

問題は、「ロボットが動作しない」という現象から、

> **現在の把持入口が依存する画像認識結果が、動的時系列上の有効性を失っている。**

という判定問題へ具体化される。

### 本事例によって明確になるエンジニアリング情報

| 従来の現場情報から確認できること | 本事例によってさらに明確になること |
|---|---|
| Robot Ready が成立している | Robot Ready は現在の把持実行チェーンに関係する状態の一つであり、それだけでは入口の成立を意味しない |
| 画像認識システムが正常な認識結果を出力している | 認識結果は正常でも、今回の入口で許容される有効時間を超えている |
| 安全許可が成立している | 重要な A は成立しているが、C や E の判定を代替するものではない |
| 正常品搬送先が受入可能である | 現在の実行チェーンに関係する状態が今回の入口要件を満たしている |
| 把持動作が開始されない | 現在の入口で `C-D` が生成されている |
| 現場で追加調査しなければ、なぜ把持できないか分からない | 問題が画像認識結果の動的時系列有効性にあることを特定できる |
| 次の処理を工程技術者がその都度判断する | 制御調停によって戻し搬送が後続候補経路として選択されている |
| 戻し搬送経路が利用可能である | 「戻し搬送を選択した」ことと「戻し搬送入口への移行が許可された」ことを分けて扱える |
| 各システムが個別に状態やログを保存している | 現在状態、時間、判定、制御、後続の目標状態入口を同一の PCN Trace に関連付けられる |

今回の PCN Trace からは、本周期について、

- Robot Ready が成立していたこと
- 安全許可が成立していたこと
- 正常品搬送先の受入状態が成立していたこと
- 画像認識結果は正常だったが、有効時間を超過していたこと
- CAE-SDB 判定結果が C-D であったこと
- 現在の把持入口へは移行しなかったこと
- 後続候補として戻し搬送が選択されたこと
- その後は新しい戻し搬送入口であらためて判定すること

を一つの状態遷移関係として確認できる。

この事例で得られるのは、設備状態を増やすことではない。

> **複数システムに分散していた状態を、「現在の入口がなぜ成立しないのか」「どの状態遷移上の役割に、どの判定上の問題が生じたのか」「どの制御経路を選択したのか」「次にどの目標状態入口を判定対象とするのか」という一連のエンジニアリング関係として整理することである。**

MES にはすでにタスクがあり、WCS にも搬送タスクが登録されている。

しかし、現場では実行が開始されていない。

確認を進めると、例えば次のような状態が見つかる場合がある。

- 目標ステーションが現在受入できない。
- 共有資源がまだ使用中である。
- 必要な許可が成立していない。
- 現在、適切な実行主体を割り当てられない。
- 下流状態が変化している。
- タスク生成後に現場条件が変化している。

タスクは存在していても、システムはまだ実行状態へ入っていない。

この問題では、まず次の二つを区別する必要がある。

> **「タスクが存在する」とは、システム内に実行対象が形成されていることを示す。**

> **「タスクを実行できる」とは、現在のシステムが Target State へ入るために必要な状態を満たしていることを示す。**

両者は同じではない。

---

## 1. タスクはまず「何を実行するか」を示す

製造システムや物流システムでは、タスクによって例えば次の内容を表す。

- 何を生産するか。
- 何を搬送するか。
- どこからどこへ搬送するか。
- どのステーションで処理するか。
- どの対象に対してどの操作を行うか。
- どの要求がシステムの処理待ちになっているか。

例えば、

```text
MES：生産タスク生成済み
WCS：搬送タスク作成済み
PLC：起動要求受信済み
```

という状態は、

> **システム内に処理すべき実行要求が存在する。**

ことを示す。

一方、タスクの存在だけでは、

> **そのタスクが現在の状態から実行へ移れるか。**

までは確定しない。

したがって、

```text
Task Exists ≠ Execution Ready
```

である。

タスクが形成されることと、そのタスクが実際の実行へ入ることは、異なる段階のエンジニアリング問題である。

---

## 2. タスク生成後も、実行前には現場状態を確認する必要がある

タスクが生成されても、現場の実行条件が自動的にそろうわけではない。

例えば、搬送タスクが存在していても、同時に次のような状態が発生する場合がある。

- 目標ステーションが一時的に受入できない。
- 共有エリアを別のタスクが使用している。
- 実行可能な主体を現在割り当てられない。
- 下流バッファが満杯である。
- 関連設備が状態切替中である。
- 待機中に、当初有効であった条件が変化している。

したがって、タスクが主として示すのは、

> **次に何を実行する必要があるか。**

である。

実際に Target State へ入る前には、現在の現場状態に基づいて、

> **今、このタスクを実行へ進められるか。**

を判定する必要がある。

このため、タスク数、タスク状態、実際の実行数が常に一対一で対応するとは限らない。

---

## 3. Pending は未実行状態を示すが、その理由までは示さない

実行できないタスクを、システムが次のような状態で表示する場合がある。

```text
Pending
Waiting
Queued
Blocked
```

これらは、

> **タスクが現在まだ実行へ入っていない。**

ことを示す。

一方、それだけでは、

> **なぜ実行へ入っていないのか。**

までは説明できない。

同じ Pending でも、例えば次のような状況があり得る。

- 必要な Condition が成立していない。
- 必要な Authority が成立していない。
- 実行資源が使用中である。
- 目標位置が現在受入できない。
- 関連状態が変化している。
- 他の対象の完了を待っている。

したがって、

> **Pending はタスクの現在状態を示すものであり、実行できない理由そのものではない。**

原因確認のために MES、WCS、PLC、設備画面などを横断して状態を照合する必要がある場合、タスク状態と実際の Target State Entry の判定関係が十分に明示されていない可能性がある。

---

## 4. 重要なのは、タスクが次にどの Target State へ入ろうとしているかである

すでに存在するタスクについて、さらに確認すべきなのは、

> **このタスクが現在どの Target State へ入ろうとしているか。**

である。

例えば、

```text
タスク生成済み → タスク配信
```

または、

```text
タスク割当済み → 搬送開始
```

あるいは、

```text
搬送完了 → 目標ステーション受入
```

は、それぞれ異なる Target State Entry である。

同じタスクであっても、Target State Entry が異なれば、今回の状態遷移に関係する状態も異なる。

そのため、「タスクが存在するか」だけでは Target State Entry の判定として不十分である。

さらに、

> **今回どの Target State へ入ろうとしているか。また、その進入を決める状態は何か。**

を明確にする必要がある。

TPCA / PCN が扱うのは、この状態遷移前のエンジニアリング問題である。

関連状態を C：Condition、A：Authority、E：Execution Chain にどのように整理するかについては、以下を参照。

## 5. タスク管理システムと実行システムでは、扱う対象が異なる

複雑な製造システムでは、一つのタスクが複数のシステムをまたぐ場合がある。

```text
MES
→ WCS
→ スケジューリングシステム
→ PLC
→ 設備または AGV / AMR
→ 目標ステーション
```

各システムが扱う対象は同じではない。

MES は、主にタスクや生産要求を扱う。

WCS は、主にスケジューリング、経路、資源を扱う。

設備制御システムは、現在の動作を実行できるかを扱う。

目標ステーションは、自身が現在受入可能かを扱う。

そのため、同じ時点で次のような表示になる場合がある。

```text
MES：タスク正常
WCS：Pending
設備：Ready
ステーション：現在受入不可
```

これらは、必ずしも相互に矛盾しているわけではない。

各システムが、それぞれの責任範囲から現在状態を表している。

さらに必要なのは、

> **同じ Target State Entry に対して、これらの分散した状態を共通のエンジニアリング判定として整理すること。**

である。

複雑なタスク実行でシステム横断の調査が必要になりやすいのは、このためである。

---

## 6. 「タスクが存在する」から「なぜ今は実行できないのか」へ

システムが現場に、

```text
Task Exists
Task Pending
```

とだけ表示している場合、現場は、

> **タスクがまだ実行されていない。**

ことを確認できる。

一方、さらに必要なのは、

> **なぜ現在は実行できないのか。**

という説明である。

この問いは、具体的な Target State Entry に戻して整理する必要がある。

- タスクは現在どの段階にあるか。
- 次にどの Target State へ入ろうとしているか。
- どの状態が今回の Target State Entry に関係するか。
- C：Condition は成立しているか。
- 必要な A：Authority は成立しているか。
- Target State へ入った後の E：Execution Chain は継続できるか。
- 今回の Target State Entry が成立しない理由は何か。

このように整理することで、「タスクが存在すること」と「現在実行できること」のエンジニアリング上の違いを明確にできる。

## エンジニアリング上の結論

タスクが存在することは、まず、

> **システム内に実行すべきタスクまたは要求が形成されている。**

ことを示す。

それだけでは、

> **そのタスクが現在の Target State Entry に対して実行可能である。**

ことまでは確定しない。

タスクが実際の実行へ入るには、Current State、Target State、および今回の Target State Entry に関係する Condition、Authority、Execution Chain の状態を確認する必要がある。

したがって、

> **「Task Exists」はタスク実行判定の出発点であり、最終的な実行可否の結論ではない。**

TPCA / PCN は、タスクを明確な Target State Entry に対応付け、

> **このタスクは次にどの Target State へ入ろうとしているのか。また、なぜ現在は実行できるのか、または実行できないのか。**

を判定可能なエンジニアリング対象として整理する。

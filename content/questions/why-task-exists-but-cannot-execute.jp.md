MES にはすでにタスクがあり、WCS にも搬送タスクが登録されている。

しかし、現場では実行が開始されていない。

確認を進めると、例えば次のような状態が見つかる場合がある。

- 目標ステーションが現在、受入可能な状態にない。
- 共有資源がまだ使用中である。
- 必要な許可が成立していない。
- 現在、適切な実行主体を割り当てることができない。
- 下流側の状態が変化している。
- タスク生成後に現場条件が変化している。

タスクは存在していても、システムはまだ実行段階へ移行していない。

この問題では、まず次の2つを区別する必要がある。

> **「タスクが存在する」とは、システム内に実行すべきタスクまたは要求が登録されていることを示す。**

> **「タスクを実行できる」とは、現在のシステムが Target State へ移行するために必要な状態を満たしていることを示す。**

両者は、異なる状態を示す。

---

## 1. タスクは「何を実行するか」を示す

製造システムや物流システムでは、タスクに例えば次の情報が含まれる。

- 何を生産するか。
- 何を搬送するか。
- どこからどこへ搬送するか。
- どのステーションで処理するか。
- どの対象に対してどの操作を行うか。
- どの要求がシステムの処理待ちになっているか。

例えば、

```text
MES：生産タスク生成済み
WCS：搬送タスク作成済み
PLC：起動要求受信済み
```

という状態は、次のことを示す。

> **システム内に処理すべき実行要求が存在する。**

タスクの存在だけでは、次の点までは確定しない。

> **システムが現在の状態から、そのタスクの実行段階へ移行できるか。**

したがって、

```text
Task Exists ≠ Execution Ready
```

である。

タスクの登録と、そのタスクの実行開始は、異なる段階のエンジニアリング問題である。

---

## 2. タスク生成後も、実行前には現場状態を確認する必要がある

タスクが生成されても、現場の実行条件が自動的にそろうわけではない。

例えば、搬送タスクが存在していても、同時に次のような状態が発生する場合がある。

- 目標ステーションが一時的に受入可能な状態にない。
- 共有エリアを別のタスクが使用している。
- 実行可能な主体を現在割り当てることができない。
- 下流バッファが満杯である。
- 関連設備が状態の切替中である。
- 待機中に、当初有効であった条件が変化している。

タスクが主として示すのは、次の内容である。

> **次に何を実行する必要があるか。**

実際に Target State へ移行する前には、現在の現場状態に基づいて、次の点を判定する必要がある。

> **現在、システムがこのタスクの実行段階へ移行できるか。**

このため、タスク数、タスク状態、実際の実行数が常に1対1で対応するとは限らない。

---

## 3. Pending は未実行状態を示すが、その理由までは示さない

実行できないタスクを、システムが次のような状態で表示する場合がある。

```text
Pending
Waiting
Queued
Blocked
```

これらは、次の状態を示す。

> **タスクの実行がまだ開始されていない。**

この表示だけでは、次の点までは説明できない。

> **なぜ実行が開始されていないのか。**

同じ Pending でも、例えば次のような状況があり得る。

- 必要な C：Condition が成立していない。
- 必要な A：Authority が成立していない。
- 実行資源が使用中である。
- 目標位置が現在、受入可能な状態にない。
- 関連する状態が変化している。
- 他の対象の完了を待っている。

したがって、

> **Pending はタスクの現在状態を示し、実行が開始されていない理由は個別に確認する必要がある。**

原因確認のために MES、WCS、PLC、設備画面などを横断して状態を照合する必要がある場合、タスク状態と実際の Target State Entry の判定関係が十分に明示されていない可能性がある。

---

## 4. タスクに対応する Target State を明確にする

すでに存在するタスクについて、さらに確認すべき点は次のとおりである。

> **このタスクに関して、システムが現在どの Target State へ移行しようとしているか。**

例えば、

```text
タスク生成済み → タスク配信
```

または、

```text
タスク割当済み → 搬送開始
```

あるいは、

```text
搬送完了 → 目標ステーション受入
```

は、それぞれ異なる Target State Entry である。

同じタスクであっても、Target State Entry が異なれば、今回の状態遷移に関係する状態も異なる。

Target State Entry における状態遷移を判定するには、タスクの存在に加えて、次の点を明確にする必要がある。

> **システムが今回どの Target State へ移行しようとしているか。また、その Target State Entry における状態遷移判定に関係する状態は何か。**

TPCA / PCN が扱うのは、この状態遷移前のエンジニアリング問題である。

関連状態を C：Condition、A：Authority、E：Execution Chain にどのように整理するかについては、以下を参照。

[Concepts｜中核概念](/jp/concepts/)

## 5. タスク管理システムと実行システムでは、扱う対象が異なる

複雑な製造システムでは、1つのタスクが複数のシステムをまたぐ場合がある。

```text
MES
→ WCS
→ スケジューリングシステム
→ PLC
→ 設備または AGV / AMR
→ 目標ステーション
```

各システムが扱う対象は同じではない。

MES は、主にタスクや生産要求を扱う。

WCS は、主にスケジューリング、経路、資源を扱う。

設備制御システムは、現在の動作を実行できるかを扱う。

目標ステーションは、自身が現在受入可能かを扱う。

そのため、同じ時点で次のような表示になる場合がある。

```text
MES：タスク正常
WCS：Pending
設備：Ready
ステーション：現在受入不可
```

これらの状態は、相互に矛盾せず同時に存在する場合がある。

各システムは、それぞれの責任範囲に基づいて現在状態を示している。

システム全体では、さらに次の整理が必要である。

> **同じ Target State Entry に対して、これらの分散した状態を共通のエンジニアリング判定関係として整理する。**

複雑なタスク実行でシステム横断の調査が必要になりやすいのは、このためである。

---

## 6. 「タスクが存在する」から「なぜ現在は実行できないのか」へ

システムが現場に、

```text
Task Exists
Task Pending
```

とだけ表示している場合、現場は次のことを確認できる。

> **タスクがまだ実行されていない。**

現場でさらに必要となるのは、次の説明である。

> **なぜ現在は実行できないのか。**

この問いは、具体的な Target State Entry に基づいて整理する必要がある。

- タスクは現在どの段階にあるか。
- システムは次にどの Target State へ移行しようとしているか。
- どの状態が今回の Target State Entry に関係するか。
- C：Condition は成立しているか。
- 必要な A：Authority は成立しているか。
- Target State への移行後に、E：Execution Chain は継続できるか。
- 今回の Target State Entry における状態遷移が成立しない理由は何か。

このように整理することで、「タスクが存在すること」と「現在実行できること」のエンジニアリング上の違いを明確にできる。

## エンジニアリング上の結論

タスクが存在することは、まず次の状態を示す。

> **システム内に実行すべきタスクまたは要求が登録されている。**

この情報だけでは、次の点までは確定しない。

> **そのタスクが現在の Target State Entry において実行可能である。**

タスクの実行を開始するには、Current State、Target State、および今回の Target State Entry に関係する C：Condition、A：Authority、E：Execution Chain の状態を確認する必要がある。

したがって、

> **「Task Exists」はタスク実行判定の出発点であり、最終的な実行可否は Target State Entry における状態遷移判定によって決まる。**

TPCA / PCN は、タスクを明確な Target State Entry に対応付け、次の内容を判定可能なエンジニアリング対象として整理する。

> **このタスクに関して、システムは次にどの Target State へ移行しようとしているのか。また、なぜ現在は移行できるのか、または移行できないのか。**

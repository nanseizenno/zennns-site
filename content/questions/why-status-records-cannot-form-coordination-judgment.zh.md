现场已经有很多状态。

MES 有任务和工单。

WCS 有调度、路径和资源状态。

PLC 有设备状态和 Interlock。

机器人有 Ready、模式和动作状态。

视觉系统有识别结果、位置和置信度。

安全系统有许可状态。

下游设备也有自己的 Ready、Waiting 和接收状态。

数据并不少。

但真正要回答：

> **当前系统为什么还不能进入下一状态？**

现场仍然经常需要重新查程序、看画面、对日志、问不同系统的负责人。

原因通常不是缺少状态，而是：

> **这些状态虽然都存在，却没有围绕同一个目标状态入口形成一次完整的状态迁移判断。**

---

## 1. 状态存在，不等于判断已经形成

不同系统按照各自职责保存状态，本身没有问题。

MES 关注任务、工单和生产过程。

WCS 关注调度、路径、资源和执行状态。

PLC 关注设备、动作和顺序控制。

机器人控制器关注模式、轨迹和动作状态。

视觉系统关注识别结果、位置和置信度。

安全系统关注安全许可和危险动作限制。

这些状态分别来看都可以是正确的。

例如：

```text
MES 任务 = 已生成
WCS 任务 = Pending
机器人 = Ready
目标站点 = Available
区域许可 = 未成立
```

每个状态都真实存在。

但这些状态本身并没有自动回答：

> **为什么当前任务还不能进入目标执行状态？**

因为真正需要判断的是这些状态之间的工程关系。

---

## 2. 状态迁移判断首先要明确“从哪里到哪里”

多个状态要形成共同判断，首先需要明确：

```text
当前状态
→ 目标状态
```

例如：

```text
任务已生成
→ 进入执行
```

或者：

```text
等待抓取
→ 进入抓取阶段
```

目标状态一旦明确，才可以继续判断：

- 本次迁移真正需要哪些状态；
- 哪些状态只是背景信息；
- 哪些状态属于必要条件；
- 哪些属于关键许可；
- 哪些决定进入以后执行链能否继续；
- 当前状态是否仍然有效；
- 不能进入时系统应该怎么处理。

因此，问题不在于状态字段数量够不够。

真正重要的是：

> **这些状态共同服务于哪一次状态迁移。**

---

## 3. PCN 把分散状态组织到同一个入口

PCN 设置在明确的状态迁移入口前。

它围绕本次状态迁移，从不同系统读取相关状态，并重新组织其工程含义。

基本关系为：

```text
当前状态
→ 目标状态
→ PCN
→ 多源状态信号
→ C/A/E 状态映射
→ S/D/B 判定
→ CAE-SDB 判定结果
→ 控制仲裁
→ 多路径控制
→ PCN Trace
```

这样以后，一个状态不再只是：

```text
Ready = TRUE
```

而会进一步明确：

> 这个 Ready 对本次状态迁移有什么作用？

同样，一个许可状态也不再只是：

```text
Permission = FALSE
```

而会进一步明确：

> 这个许可是否构成本次目标状态进入的必要约束？

状态开始从“各系统自己的记录”转化为“同一次状态迁移中的判定输入”。

---

## 4. 用 C / A / E 统一状态的工程含义

对于同一个状态迁移入口，可以把相关状态整理为三个变量域。

### C：Condition

表示进入目标状态前的事实条件。

例如：

- 工件是否存在；
- 任务是否存在；
- 识别结果是否有效；
- 物料是否满足；
- 目标站点是否具备基本条件；
- 必要参数是否完整。

### A：Authority

表示系统是否允许进入目标状态。

例如：

- 安全许可；
- 区域许可；
- 上位放行；
- 调度许可；
- 资源锁；
- 对方设备许可；
- 人工确认。

### E：Execution Chain

表示进入目标状态以后，整个执行链是否能够继续接续。

例如：

- 主体是否能够执行；
- 路径是否可通行；
- 下游是否能够承接；
- 回退路径是否存在；
- 异常路径是否可用；
- 结果是否能够回写。

这样，来自 MES、WCS、PLC、机器人、视觉、安全系统和下游设备的状态，开始获得共同的状态迁移语义。

---

## 5. 状态值正确，还不代表当前判断有效

即使状态已经被组织到同一个目标状态入口，也还需要判断这些状态现在是否可以作为本次迁移依据。

例如：

- 视觉结果已经超时；
- 下游 Ready 长时间没有刷新；
- 许可刚刚被撤销；
- WCS 和 PLC 的状态不同步；
- 资源锁存在冲突；
- 某个状态仍处于切换过程中。

因此，还需要从 S / D / B 三类性质进行判定：

- S：所需结构是否完整；
- D：当前状态是否仍然有效；
- B：当前状态是否进入控制边界。

这一步使系统不只知道：

> **有哪些状态。**

还能够继续判断：

> **这些状态当前是否足以支持本次状态迁移。**

---

## 6. 从“状态记录”到“状态迁移判断”

单纯记录状态，可以得到：

```text
任务 = Pending
机器人 = Ready
路径 = Blocked
站点 = Available
许可 = 未成立
```

完整的状态迁移判断则进一步回答：

```text
当前状态是什么
→ 目标状态是什么
→ 本次迁移需要哪些状态
→ 哪些属于 C / A / E
→ 当前 S / D / B 判定结果是什么
→ 形成了哪些 CAE-SDB 判定结果
→ 最终如何进行控制仲裁
→ 进入哪一条控制路径
→ 本次判定和执行结果如何记录
```

这就是：

> **“系统有状态”**

和：

> **“系统已经形成一次明确的状态迁移判断”**

之间的区别。

---

## 7. 为什么这属于状态迁移设计问题

如果每一次现场问题发生以后，都需要工程师重新决定：

- 哪些状态应该一起看；
- 哪个状态更重要；
- 哪个许可必须成立；
- 哪个 Ready 只是局部状态；
- 哪个状态已经失效；
- 不能进入以后应该等待、回流还是人工确认；

说明这些关系还没有完全进入状态迁移设计本身。

因此，真正需要沉淀的不是更多状态字段，而是：

> **一个明确状态迁移入口的判断结构。**

PCN 将这套结构固定到具体入口后，状态才开始具备：

- 明确的工程语义；
- 明确的判定位置；
- 明确的控制关系；
- 明确的履历对象。

这也是状态迁移设计从“状态很多”走向“判断明确”的关键变化。

---

## 工程结论

系统记录很多状态，并不代表已经形成明确的状态迁移判断。

真正缺少的通常不是更多数据，而是：

> **把分散在不同系统中的状态，围绕同一个目标状态入口组织成完整的判定、控制和履历结构。**

当相关状态被统一放回：

```text
当前状态
→ 目标状态
→ PCN
→ C/A/E 状态映射
→ S/D/B 判定
→ CAE-SDB 判定结果
→ 控制仲裁
→ 多路径控制
→ PCN Trace
```

系统才真正从：

> **“我知道各个系统现在是什么状态。”**

进一步走到：

> **“我知道这一次状态迁移为什么能够成立，或者为什么没有成立。”**

这就是 TPCA / PCN 在状态迁移设计中的工程意义。

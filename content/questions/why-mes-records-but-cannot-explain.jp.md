搬送システムの停滞が継続している。

MES にはタスク記録があり、WCS には車両状態やスケジューリング状態が記録されている。AGV / AMR に明確な故障はなく、画面上でも Waiting、Pending、Blocked、Idle などの状態を確認できる。

状態情報そのものは存在している。

一方、現場で確認したいのは、

> **現在、何が記録されているか。**

だけではない。

さらに、

> **なぜ協調処理がこの位置で進まなくなっているのか。**

を確認する必要がある。

調査を進めると、例えば次のような状態が確認される場合がある。

- タスクは生成されているが、まだ実行段階へ入っていない。
- 車両はオンラインであるが、関連資源が占有されたままである。
- 目標ステーションは存在するが、現在は受入できない。
- 必要な許可が成立していない。
- 関連状態が長時間更新されていない。
- 各システムを個別に見ると大きな異常はないが、協調処理が先へ進んでいない。

このような場合、問題は MES / WCS に状態記録がないことではない。

> **複数システムがそれぞれ状態を保持していても、それらの状態が同じ Target State Entry に対する一回の協調判定として整理されているとは限らない。**

---

## 1. MES / WCS はすでに多くの状態を保持している

MES では、一般に次のような情報を記録できる。

- 作業指示
- タスク
- ステーション要求
- 物料状態
- 生産計画
- 生産実績
- 異常履歴
- 時間履歴

WCS では、一般に次のような情報を記録できる。

- タスクキュー
- タスク割当
- 車両状態
- 経路状態
- ステーション状態
- 資源占有状態
- Waiting
- Pending
- Blocked

これらの情報により、例えば次の事項を確認できる。

> タスクはいつ生成されたか。

> タスクはどの主体へ割り当てられたか。

> 車両は現在どこにいるか。

> どのステーションが使用中か。

> どの経路が現在使用できないか。

> タスクは最終的に完了したか。

これらの状態記録は、製造現場のデジタル化における重要な基盤である。

一方、協調停滞が発生した場合は、さらに次の問いが必要になる。

> **なぜ現在のタスク、実行主体、経路、ステーションが、次の協調状態へ進んでいないのか。**

この問いは、単一の状態記録だけでは判断できない場合がある。

---

## 2. 協調停滞では単一の故障対象が存在しない場合がある

単体設備の故障では、対象が比較的明確な場合が多い。

例えば、

```text
サーボアラーム
センサ異常
シリンダタイムアウト
安全扉開
```

などである。

これに対して、協調停滞は複数の対象間で発生する場合がある。

```text
タスク
↕
実行主体
↕
経路・資源
↕
許可
↕
目標ステーション
↕
下流システム
```

各対象を個別に確認した場合、明確な故障が見つからないこともある。

例えば、

- タスクは存在するが、実行段階へ進めない。
- 車両は Idle であるが、目標エリアへの進入許可が成立していない。
- 経路にアラームはないが、関連資源が解放されていない。
- ステーションはオンラインであるが、現在は受入できない。
- 上流システムでは状態更新が完了しているが、下流システムでは関連状態が更新されていない。

現場では、最終的に次のような状態だけが見える場合がある。

```text
Waiting
Pending
Blocked
```

これらの状態は、処理が現在進行していないことを示す。

一方、それだけでは、

> **なぜ次の状態へ進んでいないのか。**

までは特定できない。

---

## 3. 状態記録と状態遷移判定は異なる

MES、WCS、PLC、設備コントローラ、搬送システムが、それぞれ自システムの状態を保持することは通常のシステム構成である。

これらの状態は、それぞれのシステム内部で次の用途に使用される。

- タスク管理
- スケジューリング
- 制御
- 監視
- アラーム
- 履歴記録

一回の状態遷移が複数システムの状態に依存する場合、これらの状態を同じ画面に表示したり、同じデータベースに保存したりするだけでは、Target State Entry に対する判定関係までは自動的に形成されない。

例えば、

```text
Task = Pending
Vehicle = Waiting
Station = Available
```

という状態が記録されているとする。

各状態自体は正しくても、これだけでは次の事項は確定しない。

- Current State は何か。
- Target State は何か。
- 今回の Target State Entry に関係する状態はどれか。
- C：Condition に関係する状態は何か。
- A：Authority に関係する状態は何か。
- E：Execution Chain に関係する状態は何か。
- 関連状態に対してどの S / D / B Evaluation が必要か。
- CAE-SDB Result は何か。
- Arbitration の結果としてどの Multipath Control を形成するか。

したがって、

> **状態記録と状態遷移判定は、異なるエンジニアリング対象である。**

重要なのは、

> **複数の状態が、同じ Target State Entry に対する判定対象として整理されているか。**

という点である。

---

## 4. 判定対象を明確な Target State Entry に戻す

複数システムの状態を個別に確認する場合、現場の調査は次のようになりやすい。

```text
MES を確認
→ WCS を確認
→ 車両状態を確認
→ 経路状態を確認
→ ステーション状態を確認
→ PLC を確認
→ 時刻を照合
→ 状態間の関係を整理
```

このとき、最初に明確にすべき対象は、

> **現在、どの Target State へ進もうとしているか。**

である。

Target State が明確になれば、その Target State Entry に対して次の事項を整理できる。

- 今回の Target State Entry に直接関係する状態
- C にマッピングする状態
- A にマッピングする状態
- E にマッピングする状態
- 関連状態に必要な S / D / B Evaluation
- 状態および判定に対応する時間情報 T
- CAE-SDB Result
- Arbitration
- Multipath Control
- PCN Trace

TPCA / PCN が対象とするのは、この Target State Entry における状態遷移前判定である。

MES / WCS に新しい状態を追加すること自体が目的ではない。

既存の複数ソース状態を、明確な Target State Entry に対応付けて整理する。

基本概念については、以下を参照。

[Concepts｜中核概念](/jp/concepts/)

## 5. 停滞の記録から状態遷移の説明へ

従来の状態記録では、例えば次のような情報を確認できる。

```text
Task Pending
Vehicle Waiting
Path Blocked
```

これらは、現在のシステム状態を把握する上で重要である。

複雑な協調システムでは、さらに次の問いを扱う必要がある。

> **なぜ今回の Target State Entry が成立していないのか。**

同じ Target State Entry に関係する状態を整理すると、例えば次のような観点で判定できる。

- 現在は局所的な待機なのか、協調停滞として扱う状態なのか。
- 問題は C、A、E のどの状態変数領域に関係しているか。
- 関連状態に Structure、Dynamics、Boundary のどの判定が必要か。
- 状態がタイムアウト、未更新、非同期、競合などの状態になっていないか。
- Arbitration の結果として、現在の Target State Entry に対してどの Multipath Control を形成するか。

ここで必要なのは、アラームを増やすことではない。

> **複数システムに分散している状態を、同じ Target State Entry に対する判定関係として整理することである。**

具体的な適用例については、以下を参照。

[MES / WCS 協調停滞診断モジュール事例](/jp/cases/collaborative-stagnation-diagnosis/)

## エンジニアリング上の結論

MES / WCS は、タスク、車両、経路、資源、ステーション、運転状態など、多数の状態を記録できる。

一方、

> **複数システムがそれぞれ状態を記録していることと、それらが同じ Target State Entry に対する一回の協調判定として整理されていることは同じではない。**

複雑な協調システムでは、

> **現在どこで停止しているか。**

に加えて、

> **なぜ今回の Target State Entry が成立していないのか。**

を確認する必要がある。

TPCA / PCN は、分散している状態を明確な Target State Entry に対応付け、

```text
Current State
→ Target State
→ PCN
→ C / A / E Mapping
→ S / D / B Evaluation
→ CAE-SDB Result + T
→ Arbitration
→ Multipath Control
→ PCN Trace
```

という関係で状態遷移前判定を構成する。

これにより、状態記録から、今回の状態遷移に対する判定と制御の説明へ展開できる。

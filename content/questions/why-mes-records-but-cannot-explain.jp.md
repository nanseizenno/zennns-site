搬送システムが停滞している。

MES にはタスク記録があり、WCS には車両状態とスケジューリング状態が記録されている。AGV / AMR に明確な異常はなく、画面上でも Waiting、Pending、Blocked、Idle などの状態を確認できる。

状態データが不足しているわけではない。

しかし、現場で確認すべきなのは、

> **現在、どの状態が記録されているのか。**

だけではない。

さらに、

> **なぜ協調処理全体がここで停滞しているのか。**

を説明する必要がある。

関連状態を確認すると、例えば次のような状態が原因になる場合がある。

- タスクは生成されているが、実行には移行していない。
- 車両はオンラインであるが、関連リソースが占有されたままである。
- Target Station は存在するが、現在は受入不能である。
- 必要な Authority が成立していない。
- 関連状態が長時間更新されていない。
- 各システムを個別に確認すると明確な異常はないが、協調処理全体は進行していない。

したがって、問題は MES / WCS に状態記録が不足していることではない。

問題は、

> **複数のシステムがそれぞれ状態を保持していても、それらの状態が同一の Target State Entry を中心として、完全な協調判定を形成しているとは限らない。**

という点にある。

---

## 1. MES / WCS にはすでに多くの状態が存在する

MES では、一般的に次の情報を記録する。

- 作業指示
- タスク
- ステーション需要
- 材料状態
- 生産計画
- 生産実績
- 異常および時系列履歴

WCS では、一般的に次の情報を記録する。

- タスクキュー
- タスク割当
- 車両状態
- 経路状態
- ステーション状態
- リソース占有状態
- Waiting
- Pending
- Blocked

これらの情報から、次のような内容を確認できる。

> タスクはいつ生成されたか。

> タスクはどの実行主体へ割り当てられたか。

> 車両は現在どこにいるか。

> どのステーションが占有されているか。

> どの経路が現在使用できないか。

> タスクは最終的に完了したか。

これらの状態記録は、製造現場のデジタル化における重要な基盤である。

一方、協調停滞が発生した場合は、さらに別の問いに答える必要がある。

> **なぜ現在のタスク、実行主体、経路、ステーションは、次の状態へ進んでいないのか。**

この問いは、通常、単独の状態記録だけでは説明できない。

---

## 2. 協調停滞には単一の故障対象が存在しない場合がある

単体設備の故障は、比較的明確な対象として表れる場合が多い。

例えば、

```text
サーボアラーム
センサ異常
シリンダタイムアウト
安全扉開
```

などである。

一方、協調停滞は、複数の対象間の関係として発生する場合がある。

```text
タスク
↕
実行主体
↕
経路・リソース
↕
Authority
↕
Target Station
↕
下流システム
```

各対象を個別に確認した場合、明確な故障が存在しないこともある。

例えば、

- タスクは存在するが、現在は実行へ移行できない。
- 車両は待機可能な状態であるが、Target Area へ進入できない。
- 経路にアラームはないが、関連リソースが解放されていない。
- ステーションはオンラインであるが、現在は受入不能である。
- 上位システムでは必要な状態が成立しているが、下位システムの関連状態はまだ更新されていない。

現場では、最終的に次のような状態だけが表示される場合がある。

```text
Waiting
Pending
Blocked
```

これらは、システムが次へ進んでいないことを示す。

しかし、

> **なぜ次へ進んでいないのか。**

を直接示すものではない。

---

## 3. 状態記録と状態遷移判定は同一ではない

MES、WCS、PLC、設備コントローラ、搬送システムが、それぞれ自システムの状態を管理すること自体に問題はない。

これらの状態は、主に各システム内部の次の機能に使用される。

- タスク管理
- スケジューリング
- 制御
- 監視
- アラーム
- 履歴記録

一方、1 回の状態遷移が複数のシステムに依存する場合、関連状態を同一画面に表示したり、同一データベースへ格納したりするだけでは、統一的な状態遷移判定が形成されるとは限らない。

例えば、

```text
Task = Pending
Vehicle = Waiting
Station = Available
```

という各状態が、個別には正しい場合がある。

しかし、これらの記録だけでは、次の事項を確定できない。

- システムが現在どの Target State へ進もうとしているか。
- どの状態が本状態遷移の判定に使用されるか。
- 現在不足している Condition または Authority は何か。
- E：Execution Chain を継続できるか。
- 現在の状態が Waiting を継続すべき状態なのか、それとも別の処理経路へ移行すべき状態なのか。

したがって、

> **状態データと状態遷移判定は同一ではない。**

重要なのは、

> **関連状態が、同一の Target State Entry を中心として明確なエンジニアリング関係を形成しているか。**

という点である。

---

## 4. 判定対象を明確な Target State Entry に戻す

各システムの状態だけを起点として原因を確認する場合、現場での調査は次のようになりやすい。

```text
MES を確認
→ WCS を確認
→ 車両状態を確認
→ 経路状態を確認
→ ステーション状態を確認
→ PLC を確認
→ 時刻を照合
→ 人が総合判断
```

この前に、まず次の事項を明確にする必要がある。

> **システムは現在、どの Target State へ進もうとしているのか。**

Target State が明確になれば、さらに次の事項を判定できる。

- どの状態が本 Target State Entry に直接関係するか。
- どの Condition が必要か。
- どの Authority が必要な制約となるか。
- Target State へ進んだ後、E：Execution Chain を継続できるか。
- 現在使用している状態が、判定根拠として現在も有効か。
- なぜ今回の Target State Entry が成立していないのか。

TPCA / PCN が対象とするのは、このエンジニアリング上の位置である。

MES / WCS に状態項目を追加することが目的ではない。

> **明確な Target State Entry を中心として、既存の複数ソース状態に判定上の関係を与えること。**

が対象である。

関連概念については、以下を参照。

## 5. 停滞の記録から状態遷移の説明へ

従来の状態記録から、例えば次の情報を確認できる。

```text
Task Pending
Vehicle Waiting
Path Blocked
```

これらは、システムの現在状態を把握するうえで重要な情報である。

一方、複雑な協調システムでは、さらに次の問いに答える必要がある。

> **なぜ今回の Target State Entry が成立していないのか。**

同一の Target State Entry に関係する状態を統一的に整理することで、システムは例えば次の点を区別できる。

- 現在の状態が局所的な通常待機であるか、協調停滞として扱うべき状態であるか。
- 問題が主に C：Condition、A：Authority、E：Execution Chain のどこにあるか。
- 関連状態に失効、非同期、長時間未更新などの問題があるか。
- Waiting を継続すべきか、別の処理経路へ移行すべきか。

ここで重要なのは、アラーム項目を増やすことではない。

> **複数システムに分散している状態を、同一の協調状態遷移に対する説明可能な判定関係として整理することである。**

具体的な適用方法については、以下を参照。

[MES / WCS 協調停滞診断モジュール事例](/jp/cases/collaborative-stagnation-diagnosis/)

## エンジニアリング上の結論

MES / WCS は、タスク、車両、経路、リソース、ステーション、運転状態など、多くの情報を記録できる。

しかし、

> **複数のシステムがそれぞれ状態を記録していても、それらの状態が同一の Target State Entry を中心として完全な協調判定を形成しているとは限らない。**

したがって、複雑な協調システムでは、

> **システムは現在どこで停滞しているのか。**

だけでなく、

> **なぜ今回の Target State Entry が成立していないのか。**

を説明できる必要がある。

TPCA / PCN は、複数システムに分散していた状態遷移判定を明示化し、状態記録から状態遷移の説明へ展開することを対象とする。

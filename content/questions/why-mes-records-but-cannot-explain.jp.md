搬送システムの停滞が継続している。

MES にはタスクの記録があり、WCS には車両状態やスケジューリング状態が記録されている。AGV / AMR に明確な故障はなく、画面上でも Waiting、Pending、Blocked、Idle などの状態を確認できる。

現場には、停滞を調査するための状態情報がすでに存在している。

ここで確認したいのは、

> **どの目標状態入口で、どの状態関係によって協調処理が進んでいないか。**

という点である。

例えば、調査の結果として次のような状態が確認されることがある。

- タスクは生成されているが、実行段階へ移行していない。
- 車両はオンラインであるが、関連資源が占有されたままである。
- 目標ステーションは存在するが、現在は受入可能な状態にない。
- 必要な許可が成立していない。
- 関連状態が長時間更新されていない。
- 各システムは個別に動作しているが、協調処理が先へ進んでいない。

このような停滞を説明するには、各システムに記録された状態を、同じ目標状態入口に対応付けて整理する必要がある。

---

## 1. MES / WCS が保持している情報

MES では、一般に次のような情報を記録できる。

- 作業指示
- タスク
- ステーション要求
- 材料・部品の状態
- 生産計画
- 生産実績
- 異常履歴
- 時間履歴

WCS では、一般に次のような情報を記録できる。

- タスクキュー
- タスク割当
- 車両状態
- 経路状態
- ステーション状態
- 資源占有状態
- Waiting
- Pending
- Blocked

これらの情報から、タスクの生成時刻、割当先、車両位置、経路状態、ステーション使用状況、タスク完了状況などを確認できる。

協調停滞を分析する際は、これらの記録を現在状態、目標状態、目標状態入口に対応付けて確認する。

例えば、

```text
現在状態： タスク割当済み / 車両待機中

目標状態： 搬送実行開始
```

と整理すると、確認対象は次のようになる。

> **搬送実行開始という目標状態入口に対して、タスク、車両、資源、許可、経路、ステーションがどのような状態にあるか。**

---

## 2. 協調停滞は複数の状態関係として現れる

協調停滞では、複数の対象が同じ状態遷移に関係する。

```text
タスク
↕
実行主体
↕
経路・資源
↕
許可
↕
目標ステーション
↕
下流システム
```

例えば、次のような状態が同時に存在する場合がある。

- タスクは存在している。
- 車両は Idle である。
- 目標エリアへの進入許可は成立していない。
- 経路にアラームはない。
- 関連資源は占有されたままである。
- ステーションはオンラインである。
- ステーションの受入条件は成立していない。

画面上では、

```text
Waiting
Pending
Blocked
```

のような運転状態として表示されることがある。

協調停滞の確認では、これらの表示状態と、今回の目標状態入口に関係するタスク、許可、資源、実行チェーンの状態を対応付ける。

確認対象は、

> **どの目標状態入口で、どの状態関係が現在の状態遷移を止めているか。**

である。

---

## 3. 目標状態入口を基準に状態を整理する

複数システムをまたぐ停滞では、現場の調査が次のようになることがある。

```text
MES を確認
→ WCS を確認
→ 車両状態を確認
→ 経路状態を確認
→ ステーション状態を確認
→ PLC を確認
→ 時刻を照合
→ 状態間の関係を整理
```

この調査を状態遷移の観点から整理する際は、まず現在状態と目標状態を明確にする。

例えば、

```text
現在状態： タスク割当済み / 車両待機

目標状態： 搬送実行開始
```

と定義する。

その上で、目標状態入口に関係する状態を整理する。

- 条件状態：タスク、搬送要求、対象情報など
- 許可状態：エリア許可、資源ロック、上位許可など
- 実行チェーン状態：車両、経路、ステーション、下流受入など

必要に応じて、構造完全性、動的時系列有効性、制御境界の判定を行い、CAE-SDB 判定結果として整理する。

基本的な処理関係は次の通りである。

```text
現在状態
→ 目標状態
→ 目標状態入口 / PCN
→ C / A / E 状態マッピング
→ S / D / B 判定
→ CAE-SDB 判定結果 + 時間情報 T
→ 制御優先度調停
→ 複数経路制御
→ PCN 状態遷移判定履歴
```

この構成により、MES / WCS、PLC、AGV / AMR、ステーションなどに分散している状態を、今回の状態遷移に対応する判定情報として扱うことができる。

## 4. 状態記録を協調停滞の説明につなげる

運転記録では、例えば次のような状態を確認できる。

```text
Task Pending
Vehicle Waiting
Path Blocked
```

目標状態入口を明確にすると、これらの記録を次の観点で整理できる。

- 現在は局所的な待機か。
- 協調停滞の判定条件に達しているか。
- 条件状態、許可状態、実行チェーン状態のどこに影響が出ているか。
- タイムアウト、未更新、非同期、競合などが発生しているか。
- 制御境界に達している状態があるか。
- どの CAE-SDB 判定結果が形成されたか。
- 制御優先度調停の結果として、どの制御経路を選択するか。

これにより、

```text
Waiting
Pending
Blocked
```

という運転状態を、

```text
どの目標状態入口で
どの状態関係に
どの判定結果が確認されたか
```

という形で説明できる。

具体的な適用例については、以下を参照。

[MES / WCS 協調停滞診断モジュール事例](/jp/cases/collaborative-stagnation-diagnosis/)

## エンジニアリング上の結論

MES / WCS は、タスク、車両、経路、資源、ステーション、運転状態など、多数の状態を記録できる。

協調停滞の説明では、それらの状態を同じ目標状態入口に対応付けて整理する。

TPCA / PCN では、

```text
現在状態
→ 目標状態
→ 目標状態入口 / PCN
→ C / A / E 状態マッピング
→ S / D / B 判定
→ CAE-SDB 判定結果 + 時間情報 T
→ 制御優先度調停
→ 複数経路制御
→ PCN 状態遷移判定履歴
```

という関係で状態遷移前判定を構成する。

これにより、MES / WCS が保持する状態記録を、

> **どの目標状態入口で、どの状態関係によって協調処理が進んでいないか。**

という説明へつなげることができる。

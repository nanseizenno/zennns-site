自動化ラインでは、設備やロボットが Ready を示していても、次の実行段階へ進まないことがある。

また、Waiting が継続していても、画面表示だけでは何を待っているのか分かりにくい場合がある。

例えば、ピックアップ動作の直前で停止しているユニットを確認すると、ロボットは Ready、PLC に明確な異常はないが、実際の動作は開始していないことがある。

このとき現場で確認したいのは、

> **設備が Ready かどうか。**

だけではなく、

> **現在、どの実行段階へ進もうとしており、その移行に関係するどの状態が判定に影響しているか。**

という点である。

---

## 1. Ready は局所的な運転状態を示す

Ready は、一般に設備、ロボット、機構、モジュールなどが、所定の動作や処理に対応可能であることを示す状態として使用される。

例えば Robot Ready は、ロボット側が所定の動作に対応可能な状態であることを示すために使用される。

一方、実際に次の実行段階へ進む際には、ロボット本体の状態に加えて、ワーク、許可、下流受入、関連設備、状態の有効性など、今回の移行に関係する複数の状態を確認することがある。

例えば、

```text
Current State：ピックアップ待ち
Target State：ピックアップ段階
```

であれば、Robot Ready は今回の移行に関係する状態の一つとして確認する。

さらに、目標実行段階へ進入した後に必要となる実行チェーンが継続できるかも、今回の移行判定に関係する。

---

## 2. Waiting は、まだ次の実行段階へ進んでいない状態を示す

Waiting は、自動化システムで一般的に使用される運転状態である。

例えば、

- ワーク待ち
- 許可待ち
- 下流受入待ち
- 資源解放待ち
- 他設備の完了待ち

など、さまざまな場面で使用される。

Waiting から確認できるのは、

> **現在の処理が、まだ次の実行段階へ進んでいない。**

という状態である。

現場で必要になるのは、さらに、

> **どの実行段階へ進もうとしているのか。**

> **その移行に関係するどの状態が、現在の判定に影響しているのか。**

を確認することである。

---

## 3. 状態が複数の設備やシステムに分散すると、確認範囲が広がる

自動化ユニットでは、1 回の実行段階への移行に、複数の設備やシステムが関係する場合がある。

例えば、

- PLC
- ロボット
- 画像認識システム
- 安全システム
- 上流・下流設備
- HMI
- 上位システム

などである。

この場合、Ready や Waiting の表示だけでは、今回の移行に関係する状態全体を把握できないことがある。

現場では、

```text
PLC を確認
→ ロボットを確認
→ 画像認識を確認
→ 安全状態を確認
→ 下流設備を確認
→ 時刻や更新状態を照合
```

という形で、複数の情報を確認することになる。

確認対象が広がるほど、今回の移行に関係する状態を同じ文脈で整理することが重要になる。

---

## 4. 確認の起点は Current State → Target State である

Ready や Waiting を確認するときは、最初に今回の状態遷移を明確にする。

```text
Current State → Target State
```

例えば、

```text
Current State：ピックアップ待ち
Target State：ピックアップ段階
```

と定める。

その上で、

- 今回の目標状態入口はどこか。
- どの状態が今回の移行に関係するか。
- どの関連状態が現在の移行判定に影響しているか。
- 各状態は現在の判定に使用できる状態か。
- 目標実行段階へ進入した後に必要な実行チェーンが継続できるか。

を確認する。

TPCA / PCN では、今回の状態遷移に対する目標状態入口を明確にし、その入口に関係する状態を前判定の対象として整理する。

---

## エンジニアリング上の結論

自動化ユニットで、

```text
Ready だが動作しない
Waiting が継続している
```

という状態が発生した場合、確認の起点は、

> **現在、どの状態からどの実行段階へ進もうとしているのか。**

である。

その上で、今回の目標状態入口に関係する状態をまとめて確認する。

これにより、Ready や Waiting の表示を、次の実行段階へ進むための具体的な状態遷移判定と対応付けて整理できる。

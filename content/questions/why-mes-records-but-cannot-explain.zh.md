搬送系统已经停了很久。

MES 上有任务记录，WCS 上有车辆和调度状态，AGV / AMR 没有明显故障，页面里也能看到 Waiting、Pending、Blocked、Idle。

数据都在。

但现场真正想知道的是：

> **为什么整个协同过程停在这里？**

继续排查后，可能发现任务已经生成，车辆也在线，但资源锁没有释放；或者区域许可没有成立；或者目标站点暂时不能承接；也可能是相关状态长期没有刷新。

问题并不是 MES / WCS 没有记录。

而是：

> **这些状态还没有围绕同一个目标协同状态形成一次完整的判定。**

---

## 1. MES / WCS 能记录很多状态

MES 通常可以记录：

- 工单；
- 任务；
- 工位需求；
- 物料状态；
- 生产计划；
- 生产实绩；
- 异常和时间履历。

WCS 通常可以记录：

- 任务队列；
- 任务分配；
- 车辆状态；
- 路径状态；
- 站点状态；
- 资源占用；
- Waiting；
- Pending；
- Blocked。

这些数据能够回答：

> 任务什么时候生成？

> 任务分配给谁？

> 车辆现在在哪里？

> 哪个站点正在占用？

> 哪条路径被锁定？

> 任务有没有完成？

这些都是制造现场数字化的重要基础。

但一次协同停滞真正需要回答的是：

> **为什么当前系统没有进入目标协同执行状态？**

这不是单个任务记录、单台车辆状态或单条报警能够独立回答的问题。

---

## 2. 协同停滞发生在多个系统之间

单设备故障通常有比较明确的对象。

例如：

```text
伺服报警
传感器异常
气缸超时
安全门打开
```

协同停滞则经常发生在多个对象之间：

```text
任务
↕
车辆
↕
路径
↕
资源锁
↕
区域许可
↕
站点
↕
下游
↕
结果回写
```

每个对象单独看都可能没有明显故障。

但连接起来以后，系统仍然无法持续推进。

例如：

- 任务存在，但没有主体真正进入执行；
- 车辆空闲，但调度许可没有成立；
- 任务已经释放，但目标站点不能承接；
- 站点可用，但共享路径资源仍被占用；
- 路径可用，但区域许可没有成立；
- 许可成立，但下游状态没有刷新；
- 任务执行完成，但结果无法正确回写。

所以：

> **Waiting、Pending、Blocked 只是运行表现，不等于协同停滞已经被解释。**

---

## 3. 需要把分散状态放回同一个目标状态入口

对于一次明确的目标协同状态，可以把相关状态重新组织为 C / A / E。

### C：Condition

表示进入目标协同状态前的事实条件是否成立。

例如：

- 任务是否存在；
- 任务目标是否明确；
- 物料是否满足要求；
- 目标站点是否有效；
- 必要数据是否完整。

### A：Authority

表示系统是否允许任务、主体或资源继续进入目标执行路径。

例如：

- 调度许可；
- 资源锁；
- 区域许可；
- 上位放行；
- 对方设备许可；
- 人工确认。

关键许可不成立时，即使任务存在、车辆在线，也不能继续进入目标执行状态。

### E：Execution Chain

表示进入目标执行路径以后，整个执行链是否能够继续接续。

例如：

- 主体是否能够执行；
- 路径是否可通行；
- 站点是否可承接；
- 下游是否能够继续；
- 能源补给是否影响执行能力；
- 结果是否能够回写。

这样，原来的：

```text
Task = Pending
Vehicle = Waiting
Path = Blocked
```

才能进一步展开为：

```text
条件问题
许可问题
执行链接续问题
```

---

## 4. 还需要判断这些状态是否完整、有效

知道问题位于 C、A 或 E 以后，还需要继续进行 S / D / B 判定。

### S：Structure

判断本次协同状态迁移所需要的信号、接口、映射关系、许可来源、资源关系和执行链边界是否已经定义、接入并可观测。

例如：

- 资源锁存在，但释放状态没有接入；
- 下游有承接状态，但 WCS 无法读取；
- 区域许可存在，但来源不明确；
- 结果回写链路没有纳入执行链判断。

### D：Dynamics

判断当前状态是否仍然有效、同步和可信。

例如：

- 任务状态长期未刷新；
- 车辆位置存在延迟；
- 资源锁状态没有更新；
- 路径状态与车辆位置不同步；
- 许可在执行前已经撤销。

### B：Boundary

判断当前协同状态是否已经进入预设控制边界。

例如：

- 等待时间持续扩大；
- 资源长期占用；
- 路径拥堵达到控制边界；
- 能源补给集中影响群体执行能力；
- 现有信息不足，需要进入人工复核或增强记录。

这些判定形成 CAE-SDB 判定结果，再进入后续控制仲裁。

---

## 5. 协同停滞还需要看群体状态

单个任务 Pending，不一定代表系统发生停滞。

一台车辆 Waiting，也可能只是正常等待。

一台车辆正在充电，同样没有问题。

真正需要关注的是：

> **这些状态是否在群体层面持续累积，并导致有效执行能力下降。**

因此，协同停滞诊断还可以结合群体状态，例如：

- 群体未执行状态；
- 群体辅助执行状态；
- 群体能源补给状态；
- 许可未成立状态；
- 路径资源占用状态；
- 站点承接状态；
- 关键任务持续未执行状态。

这些群体状态用于判断：

> **当前是正常局部等待，还是已经形成群体协同停滞。**

确认停滞以后，再结合 C / A / E 和 S / D / B 判定结果，对停滞结构进行分析，并形成后续控制路径。

## 6. 从“记录状态”走向“解释一次协同停滞”

如果系统只有：

```text
Task Pending
Vehicle Waiting
Path Blocked
Station Full
```

现场仍然需要人工把这些状态重新串起来。

如果把它们围绕一次明确的协同状态迁移组织起来，就可以形成：

```text
当前协同状态
→ 目标协同状态
→ PCN
→ 多源状态
→ C/A/E 状态映射
→ S/D/B 判定
→ CAE-SDB 判定结果
→ 群体停滞识别
→ 控制仲裁
→ 多路径控制
→ PCN Trace
```

系统就可以进一步回答：

- 当前停滞主要位于哪个变量域；
- 是否存在关键许可阻断；
- 是否存在执行链接续问题；
- 哪些状态已经失效或不同步；
- 当前是否已经进入控制边界；
- 下一步应继续等待、释放资源、调整任务、协调下游，还是进入其他处理路径；
- 这次停滞能否形成可追溯履历。

这时 MES / WCS 不只是记录：

> **系统停在这里。**

还可以进一步说明：

> **为什么这一次协同状态迁移没有成立。**

---

## 工程结论

MES / WCS 已经能够记录大量任务、车辆、路径、站点和运行状态。

问题不在于数据不足。

而在于：

> **多个系统分别拥有状态，并不代表这些状态已经围绕同一个目标协同状态形成完整判定。**

协同停滞往往同时涉及：

- C：任务、对象和现场条件；
- A：调度许可、资源锁、区域许可和上位放行；
- E：主体执行、路径、站点、下游承接和结果回写；

并进一步受到：

- S：结构完整性；
- D：动态时序有效性；
- B：控制边界；

影响。

TPCA / PCN 关注的是把这些原本分散的状态重新组织为一次明确的状态迁移判定。

这样，系统才能从：

> **“停了。”**

进一步走到：

> **“为什么停在这里，以及下一步应该怎么处理。”**

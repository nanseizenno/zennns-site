搬送系统已经停了很久。

MES 上有任务记录，WCS 上有车辆和调度状态，AGV / AMR 没有明显故障，页面里也能看到 Waiting、Pending、Blocked、Idle。

数据都在。

但现场真正想知道的不是： **现在记录了什么状态？**

而是： **为什么整个协同过程停在这里？**

继续排查以后，可能会发现：

- 任务已经生成，但没有真正进入执行；
- 车辆在线，但相关资源仍被占用；
- 目标站点存在，但当前不能承接；
- 某个许可没有成立；
- 某个状态长时间没有更新；
- 单个系统看起来正常，但多个系统之间没有继续推进。

问题并不是 MES / WCS 没有记录。

真正的问题是：

> **多个系统分别拥有状态，并不代表这些状态已经形成对一次协同过程的完整判断。**

---

## 1. MES / WCS 已经拥有大量状态

MES 通常可以记录：

- 工单；
- 任务；
- 工位需求；
- 物料状态；
- 生产计划；
- 生产实绩；
- 异常和时间履历。

WCS 通常可以记录：

- 任务队列；
- 任务分配；
- 车辆状态；
- 路径状态；
- 站点状态；
- 资源占用；
- Waiting；
- Pending；
- Blocked。

这些信息能够回答很多重要问题：

> 任务什么时候生成？

> 任务分配给谁？

> 车辆现在在哪里？

> 哪个站点正在占用？

> 哪条路径不可用？

> 任务最终有没有完成？

这些都是制造现场数字化的重要基础。

但是，当系统发生协同停滞时，还会出现另一类问题：

> **为什么当前任务、设备、路径和站点没有继续进入下一协同状态？**

这个问题通常无法由某一条状态记录单独回答。

---

## 2. 协同停滞往往不存在一个明确的故障对象

单设备故障通常比较容易找到对象。

例如：

```text
伺服报警
传感器异常
气缸超时
安全门打开
````

协同停滞则不同，它可能发生在：

```text
任务
↕
执行主体
↕
路径与资源
↕
许可
↕
目标站点
↕
下游系统
```

其中任何一个对象单独看，都可能没有明显故障。

例如：

* 任务存在，但还不能执行；
* 车辆空闲，但当前不能进入目标区域；
* 路径没有报警，但相关资源仍未释放；
* 站点在线，但当前不能承接；
* 上一个系统认为状态已经成立，下一个系统看到的状态却还没有更新。

于是现场看到的只是：

```text
Waiting
Pending
Blocked
```

但这些状态只说明： **系统没有继续推进。**

它们并没有直接解释： **为什么没有继续推进。**

---

## 3. 状态记录与协同判断不是同一件事

这是问题的关键。

MES、WCS、PLC、设备控制器和搬送系统可以分别拥有自己的状态。

但是这些状态通常首先服务于各自系统内部的：

* 任务管理；
* 调度；
* 控制；
* 监视；
* 报警；
* 履历记录。

当一次状态迁移同时依赖多个系统时，仅仅把这些状态放在同一个画面或数据库中，并不会自动形成统一判断。

例如：

```text
Task = Pending
Vehicle = Waiting
Station = Available
```

这三个状态都可能是真的。

但仍然不能仅据此判断：

* 当前准备进入哪个目标状态；
* 哪些状态真正参与这一次状态迁移；
* 当前缺少的究竟是什么；
* 系统是否应该继续等待；
* 是否需要改变执行路径。

因此：

> **State Data 不等于 State Transition Judgment。**

真正困难的地方，不是有没有状态，而是这些状态是否围绕同一个目标状态入口形成了可解释的关系。

---

## 4. 问题需要重新回到“准备进入什么状态”

如果只从各个系统自己的状态出发，现场很容易陷入这样的排查方式：

```text
查 MES
→ 查 WCS
→ 查车辆
→ 查路径
→ 查站点
→ 查 PLC
→ 对时间
→ 人工判断
```

真正需要先明确的是： **系统当前准备进入什么目标状态？**

只有目标状态明确以后，才能进一步判断：

* 哪些条件与这次进入有关；
* 哪些许可必须成立；
* 哪些执行环节必须能够继续接续；
* 当前使用的状态是否仍然有效；
* 为什么这一次状态迁移没有成立。

TPCA / PCN 关注的正是这一类问题。

它不是要求 MES / WCS 重新记录更多状态，而是把与一次明确目标状态进入有关的分散信息重新组织起来，使系统能够形成结构化的前置判断。

具体的 C / A / E、S / D / B、控制仲裁、PCN Trace 等结构，可参见：

[Concepts｜核心概念](/zh/concepts/)

## 5. 从“记录停滞”走向“解释停滞”

传统记录可能最终告诉现场：

```text
Task Pending
Vehicle Waiting
Path Blocked
```

这对于知道  **系统停在什么状态**  非常有价值。

但对于复杂协同系统，还需要继续回答： **这一次为什么停在这里？**

如果与一次目标状态迁移有关的状态能够被统一组织，系统就有机会进一步区分：

* 当前只是正常等待，还是已经形成协同停滞；
* 问题主要来自条件、许可还是执行链接续；
* 是否存在状态失效、不同步或长期未更新；
* 是否需要继续等待，还是进入其他处理路径。

这里的重点不是增加更多报警。

而是让原本分散在不同系统中的状态，能够围绕同一次协同状态迁移形成可以解释的判断结构。

具体的 MES / WCS 协同停滞诊断方式，可继续阅读：

[MES / WCS 协同停滞诊断模块案例](/zh/cases/collaborative-stagnation-diagnosis/)

## 工程结论

MES / WCS 已经能够记录大量任务、车辆、路径、资源、站点和运行状态。

但问题是：

> **多个系统分别记录了状态，但这些状态还没有围绕同一个目标状态形成完整的协同判断。**

因此，复杂协同系统真正需要解决的，不只是： **“系统现在停在哪里？”**

还包括： **“为什么这一次没有进入下一目标状态？”**

TPCA / PCN 关注的是将这类原本分散的状态迁移判断显式化，使系统能够从状态记录进一步走向状态迁移解释。

搬送系统已经停了很久。

MES 上有任务记录，WCS 上有车辆状态，AGV 没有明显故障。页面里 Waiting、Pending、Blocked、Idle 都有，日志也能导出来。

问题是：

> **所有系统都在记录“发生了什么”，却没有直接说明“为什么整个协同过程停在这里”。**

现场只能继续往下查。

先看 MES，任务存在。

再看 WCS，任务已经进入队列。

再看车辆，有的空闲，有的等待。

继续看路径、站点、资源锁、区域许可和下游状态，最后才发现：

> 不是任务没有生成，也不是车辆故障，而是某个交接区域的许可、资源和下游承接没有形成可持续执行关系。

类似问题在制造现场并不少见。

MES 能记录任务，WCS 能记录调度，AGV / AMR 能记录车辆状态，设备能记录报警，HMI 能显示当前画面。

但系统整体停滞时，现场仍然需要回答：

> 到底是任务条件没有成立？

> 许可没有成立？

> 执行链无法接续？

> 还是当前状态已经过期、不同步或长期滞留？

这就是“能记录”和“能解释停滞”之间的差别。

---

## 1. MES / WCS 已经记录了大量有价值的信息

MES 通常可以记录：

- 工单；
- 任务；
- 工位需求；
- 生产计划；
- 工序状态；
- 设备状态；
- 物料状态；
- 生产实绩；
- 异常和时间履历。

WCS 则可以记录：

- 任务池；
- 车辆状态；
- 路径状态；
- 调度结果；
- 执行状态；
- 站点状态；
- 资源占用；
- 任务完成与失败；
- Waiting；
- Pending；
- Blocked。

这些数据能够回答很多问题：

> 任务什么时候生成？

> 分配给谁？

> 车辆现在在哪里？

> 哪个站点满载？

> 哪条路径被占用？

> 任务有没有完成？

这些都是制造现场数字化的重要基础。

问题不在于 MES / WCS “没有数据”。

真正的问题是：

> **这些数据通常按照任务、车辆、设备、路径、站点和事件分别保存，而一次协同状态迁移为什么没有成立，还需要进一步组织。**

---

## 2. 记录状态，不等于解释协同停滞

例如系统里已经出现：

```text
Task = Pending
Vehicle = Waiting
Path = Blocked
Station = Full
```

这些状态都是真实的。

但它们仍然没有直接回答：

> 为什么当前任务没有进入有效执行？

因为同样一个 Pending，背后可能是完全不同的问题。

例如：

- 任务条件不完整；
- 任务还没有获得调度许可；
- 资源锁未释放；
- 区域进入许可未成立；
- 可用车辆比例下降；
- 路径持续被占用；
- 下游站点不能承接；
- 车辆集中进入能源补给；
- 状态长期未刷新；
- 当前数据不足以解释停滞。

因此：

> **Waiting、Pending、Blocked 是运行状态，不是协同停滞结构本身。**

只有把这些状态重新放回一个明确的协同执行入口，才能进一步判断它们之间是什么关系。

---

## 3. 协同停滞为什么比单设备故障更难解释

单设备故障通常有比较明确的对象。

例如：

```text
Servo Alarm
Sensor Error
Cylinder Timeout
Safety Door Open
```

设备、信号和位置都比较明确。

协同停滞则经常发生在多个对象之间。

例如：

```text
任务
↕
车辆
↕
路径
↕
区域许可
↕
站点
↕
下游工位
↕
结果回写
```

每个对象单独看都可能没有明显异常。

但连接起来以后，系统就是无法持续推进。

例如：

- 任务存在，但没有合适主体进入执行；
- 车辆空闲，但任务许可未释放；
- 任务已释放，但目标站点不可承接；
- 站点可承接，但共享路径资源仍被占用；
- 路径释放，但区域许可未成立；
- 许可成立，但下游状态没有刷新；
- 任务执行完成，但结果无法正确回写。

这种问题不是单点报警能够完整说明的。

它需要的是：

> **把多个系统的状态重新组织成一次协同状态迁移判定。**

---

## 4. 用 C / A / E 重新看协同停滞

对于一个明确的目标执行状态，可以把相关状态整理为三个变量域。

### C：Condition

表示任务、对象、工单、站点、物料和数据等进入目标执行状态前的条件是否成立。

例如：

- 任务是否存在；
- 任务目标是否明确；
- 工单是否已经下发；
- 物料状态是否满足；
- 目标站点是否可用；
- 缓存状态是否满足；
- 必要状态数据是否存在。

### A：Authority

表示系统是否允许任务或主体进入目标执行路径。

例如：

- 调度许可；
- 资源锁；
- 区域许可；
- 上位系统放行；
- 人工确认；
- 对方设备接收许可。

关键 A 不成立时，即使任务存在、车辆可用、局部路径可走，也不能直接进入目标执行状态。

### E：Execution Chain

表示进入目标执行路径以后，整个执行链能否继续接续。

例如：

- 主体是否能够持续执行；
- 路径是否可通行；
- 站点是否可承接；
- 下游是否可接收；
- 能源补给是否影响执行；
- 回退路径是否可用；
- 结果是否能够上传或回写。

这样，MES / WCS 页面上的 Waiting、Pending、Blocked 就不再只是状态名称，而可以进一步回到：

> **问题到底发生在条件、许可还是执行链。**

---

## 5. 还需要判断这些状态为什么不成立

知道问题位于 C、A 或 E 以后，还需要继续判断它的性质。

### S：Structure

关注完成协同执行所需要的状态、接口、许可来源、资源关系和执行链边界是否已经定义、接入并可观测。

例如：

- WCS 有 Waiting 状态，但没有接入区域许可；
- MES 有任务记录，但没有明确下游接收状态；
- 资源锁存在，但释放状态没有形成可追溯记录；
- 回写链路存在，但失败后的处理边界没有定义。

### D：Dynamics

关注运行中的状态是否仍然有效、同步和可信。

例如：

- 任务状态长期未刷新；
- 车辆状态延迟；
- 资源锁状态没有更新；
- 路径状态与车辆位置不同步；
- 许可在执行前被撤销；
- 多个系统之间时间状态不一致。

### B：Boundary

关注当前 C、A 或 E 状态是否已经达到预定义控制边界。

例如：

- 等待持续时间达到边界；
- 资源占用长期未释放；
- 局部拥堵达到处理边界；
- 能源补给比例达到需要调整的边界；
- 当前信息不足，需要进入增强记录或人工复核边界。

这些判定共同形成 CAE-SDB Result。

多个 Result 再经过 Arbitration，形成对应的诊断输出、控制建议或控制路径，并留下 PCN Trace。

## 6. 为什么协同停滞需要“群体视角”

单个任务或单台车辆的状态，并不一定能够说明整个系统是否发生协同停滞。

例如：

一台 AGV 在充电，很正常。

一台 AGV 在 Waiting，也很正常。

一个任务暂时 Pending，也可能只是正常调度过程。

真正需要关注的是：

> **这些状态是否在群体层面同时累积，并使有效执行能力持续下降。**

因此，协同停滞诊断还需要结合群体指标观察。

例如：

- 群体未执行比例；
- 群体辅助执行比例；
- 群体能源补给比例；
- 许可未成立比例；
- 路径资源占用情况；
- 站点不可承接情况；
- 关键任务持续时间。

这些指标不是为了替代 C / A / E 和 S / D / B。

它们的作用是：

> **把多个主体的状态聚合到协同层面，帮助判断系统是否已经从正常局部等待演变成结构性停滞。**

相关工程结构可参见：

[MES / WCS 协同停滞诊断模块案例](/zh/cases/collaborative-stagnation-diagnosis/)

## 7. 从“记录系统”进一步走向“解释系统”

如果 MES / WCS 只保存：

```text
Task Pending
Vehicle Waiting
Path Blocked
Station Full
```

现场仍然需要人工把这些状态重新串起来。

如果进一步形成：

```text
当前协同状态
→ 目标协同状态
→ 多源状态
→ C/A/E Mapping
→ S/D/B Evaluation
→ CAE-SDB Result
→ 群体指标
→ 停滞识别
→ Arbitration
→ 诊断 / 控制输出
→ PCN Trace
```

系统就能够进一步回答：

- 当前停滞主要位于哪个变量域；
- 是否存在关键许可未成立；
- 是否存在执行链接续问题；
- 哪些状态已经失效或不同步；
- 当前是否已经超过正常等待边界；
- 是否需要资源释放、路径复核、下游协调、任务调整或增强记录；
- 这次停滞以后能否被完整复盘。

这时 MES / WCS 的价值就不再只停留在：

> “我记录了系统停在这里。”

而可以继续向：

> **“我能说明这次协同停滞是怎样形成的。”**

发展。

## 8. 一个简单例子

假设 MES 已经生成补料任务。

WCS 中任务也已经存在。

现场出现：

```text
Task = Pending
AGV-01 = Idle
AGV-02 = Waiting
AGV-03 = Charging
Destination Station = Available
```

表面看，没有明显故障。

继续读取状态后发现：

```text
Shared Route Lock = occupied
Area Permission = not granted
```

从状态迁移结构看：

```text
C:
任务和目标条件成立

A:
共享资源许可 / 区域许可未成立

E:
车辆和目标站点具备执行基础
```

此时问题并不是“车辆为什么不走”这么简单。

真正没有成立的是：

> **任务进入目标执行路径所需要的关键许可。**

这次判定如果形成 PCN Trace，后续就可以继续比较：

- 同一资源锁是否反复造成停滞；
- 哪些区域许可长期成为瓶颈；
- 是否需要调整资源释放规则；
- 是否需要增加增强记录；
- 调整以后相同停滞是否减少。

这就是记录状态和解释停滞之间的区别。

## 工程结论

MES / WCS 能记录任务、车辆、路径、站点、状态和日志。

这些能力非常重要。

但：

> **记录系统发生了什么，不等于已经解释系统为什么无法继续进入目标执行状态。**

协同停滞往往分布在：

- C：任务和现场条件；
- A：调度许可、资源锁、区域许可和上位放行；
- E：主体执行、路径、站点、下游承接和回写链路；

并进一步受到：

- S：结构完整性；
- D：动态时序有效性；
- B：控制边界；

影响。

因此，更进一步的协同诊断需要把原本分散在 MES、WCS、AGV / AMR、站点和设备中的状态重新组织起来：

```text
C/A/E Mapping
→ S/D/B Evaluation
→ CAE-SDB Result
→ 群体指标与停滞识别
→ Arbitration
→ 诊断 / 控制输出
→ PCN Trace
```

这样，系统才能从：

> **“停了。”**

继续走到：

> **“为什么停在这里，以及下一步应该处理什么。”**

这就是 TPCA / PCN 在 MES / WCS 协同停滞诊断中关注的核心问题。

現場には、すでに多くの状態情報が存在している。

MES にはタスクと作業指示がある。

WCS にはスケジューリング、経路、資源の状態がある。

PLC には設備状態と Interlock がある。

ロボットには Ready、モード、動作状態がある。

画像認識システムには認識結果、位置、信頼度がある。

安全システムには許可状態がある。

下流設備にも、それぞれ Ready、Waiting、受入状態がある。

状態情報そのものは不足していない。

それでも現場では、次の問いが残る。

> **なぜ現在のシステムは、まだ次の状態へ進めないのか。**

実際の調査では、エンジニアがプログラム、画面、ログをあらためて確認し、複数システムの担当者と状態間の関係を確認する必要がある場合がある。

問題は、

> **状態が個別に存在していても、それらが同じ Target State Entry を中心として、一回の明確な状態遷移判定として整理されているとは限らない。**

という点にある。

---

## 1. 各システムが個別に状態を管理すること自体は問題ではない

複雑な自動化システムや製造システムでは、各システムがそれぞれの役割に応じて状態を管理する。

MES は、タスク、作業指示、生産プロセスを扱う。

WCS は、スケジューリング、経路、資源、実行状態を扱う。

PLC は、設備、動作、シーケンス制御を扱う。

ロボットコントローラは、モード、軌跡、動作状態を扱う。

画像認識システムは、認識結果、位置、信頼度を扱う。

安全システムは、安全許可や危険動作の制限を扱う。

これらのシステムは、それぞれがまず自らの機能を実行する必要がある。

そのため、同じ現場で次の状態が同時に存在することもある。

```text
MES Task = Released
WCS Task = Pending
Robot = Ready
Station = Available
Area Permission = False
```

これらの状態は、同時に成立し得る。

しかし、それだけでは、

> **なぜ今回の Target State Entry が成立していないのか。**

までは直接説明できない。

---

## 2. 状態値と状態遷移の判定関係は別のものである

状態記録が主に示すのは、

> **ある対象が現在どのような状態にあるか。**

である。

一方、状態遷移判定では、さらに、

> **その状態が、今回の Target State Entry に対してどのような意味を持つか。**

を確認する必要がある。

例えば、

```text
Robot Ready = TRUE
```

という状態は、ロボットが現在ある運転可能状態にあることを示す。

しかし、この状態だけでは次の内容は分からない。

- 現在、システムは何を実行しようとしているか。
- この Ready が今回の Target State Entry に直接関係するか。
- 他に必要な Condition が成立しているか。
- 今回の動作に必要な Authority が成立しているか。
- Target State へ入った後、Execution Chain が継続できるか。

したがって、

> **状態値が存在することと、それらの状態がどのような判定関係を形成するかは、別のエンジニアリング問題である。**

---

## 3. 共通の判定対象を形成するには Target State を明確にする必要がある

システムが次にどの状態へ入ろうとしているかが明確でなければ、どの状態が今回の判定に関係するかも明確にできない。

例えば、

```text
Current State：ピックアップ待ち
Target State：ピックアップ段階
```

という場合と、

```text
Current State：異常処理完了
Target State：自動運転への再投入
```

という場合では、Target State Entry に関係する Condition、Authority、Execution Chain の状態は同じではない。

そのため、既存システムに状態項目を追加し続けても、それだけで状態遷移判定が明確になるとは限らない。

より基本的な確認事項は、

> **これらの状態は、どの Target State Entry に対する判定に使用されるのか。**

である。

Current State と Target State が明確になって初めて、次の内容を整理できる。

- どの状態が今回の Target State Entry に直接関係するか。
- どの状態が今回の判定では背景情報となるか。
- どの状態が不足すると Target State へ進めないか。
- 状態値は存在していても、今回の判定時点では有効な根拠として使用できない状態があるか。

したがって、「状態情報が多いこと」と「状態遷移判定が明確であること」は同じではない。

---

## 4. 複数システムの協調では、この問題がさらに明確になる

単体設備の内部では、多くの状態関係をシーケンスプログラムや Interlock に直接組み込むことができる。

一方、システム規模が大きくなると、一回の Target State Entry が複数システムの状態に依存する場合がある。

```text
MES
↕
WCS
↕
PLC
↕
ロボット
↕
画像認識システム
↕
安全システム
↕
下流設備
```

この場合、各システムが扱うのは、状態遷移全体に関係する情報の一部である。

例えば、

- MES ではタスクが実行可能な状態になっている。
- WCS では資源解放を待っている。
- PLC では自設備の準備が完了している。
- ロボットは Ready を表示している。
- 安全システムではエリア許可がまだ成立していない。

これらの状態は、必ずしも相互に矛盾しているわけではない。

確認すべきなのは、

> **これらの状態が、同じ Target State Entry に対する共通のエンジニアリング関係として整理されているか。**

という点である。

整理されていなければ、現場では複数システムをまたいで状態間の関係を再構成する必要がある。

---

## 5. 状態値が正しくても、今回の状態遷移には使用できない場合がある

さらに分かりにくいのは、

> **状態値そのものは誤っていなくても、今回の Target State Entry の判定根拠としては使用できない場合がある。**

という問題である。

例えば、

- 検査結果が有効時間を超えている。
- Ready が長時間更新されていない。
- 上流と下流で状態更新時刻が一致していない。
- 許可がすでに取り消されている。
- 対象が切り替わった後も、以前の状態が保持されている。
- システムが状態切替中である。

このため、状態遷移設計では、

> **状態値が何であるか。**

だけでなく、

> **その状態が今回の Target State Entry とどのような関係にあり、現在も判定根拠として有効か。**

を確認する必要がある。

状態監視項目やログ項目を増やすだけでは、この関係が自動的に明確になるわけではない。

---

## 6. 重要なのは状態数ではなく、判定対象を明確にすることである

現場での調査が、例えば次のような手順を必要としている場合がある。

```text
MES を確認
→ WCS を確認
→ PLC を確認
→ ロボットを確認
→ 安全システムを確認
→ 時刻を照合
→ 状態間の関係を整理
```

この場合、複数システムの状態はすでに記録されていても、一回の Target State Entry に対する状態遷移判定関係を、人があらためて整理していることになる。

したがって、より重要な問いは、

> **さらにどの状態を記録するか。**

ではなく、

> **システムが現在どの Target State へ入ろうとしており、どの状態が今回の Target State Entry を共同で決定するのか。**

である。

TPCA / PCN が対象とするのは、このエンジニアリング問題である。

> **異なるシステムに分散している状態を、明確な Target State Entry を中心として整理し、状態遷移判定に必要な関係を明示する。**

これらの状態を、さらにどのように構造化判定、制御、履歴へつなげるかについては、以下を参照。

- [TPCA / PCN 状態遷移前制御アーキテクチャ｜ホワイトペーパー](/jp/whitepaper/)

## エンジニアリング上の結論

システムが多数の状態情報を持っていることと、明確な状態遷移判定が形成されていることは同じではない。

状態記録が主に示すのは、

> **各対象が現在どのような状態にあるか。**

である。

状態遷移設計では、さらに、

> **システムが現在どの Target State へ入ろうとしているか。それぞれの状態が今回の Target State Entry にどのように関係し、なぜ進入できるのか、または進入できないのか。**

を明確にする必要がある。

したがって、整理すべき対象は、個別に存在する状態を増やすことではなく、

> **明確な Target State Entry を中心として形成される状態間の関係である。**

TPCA / PCN は、このように分散している状態遷移判定を、明確なエンジニアリング設計対象として扱う。

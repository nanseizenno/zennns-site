現場には、すでに多くの状態情報が存在している。

MES にはタスクと作業指示がある。

WCS にはスケジューリング、経路、資源の状態がある。

PLC には設備状態とインターロックがある。

ロボットには Ready、モード、動作状態がある。

画像認識システムには認識結果、位置、信頼度がある。

安全システムには許可状態がある。

下流設備にも、それぞれ Ready、Waiting、受入状態がある。

状態情報そのものは不足していない。

それでも現場では、次の問いが残る。

> **なぜ現在のシステムは、まだ次の状態へ移行できないのか。**

実際の調査では、エンジニアがプログラム、画面、ログをあらためて確認し、複数システムの担当者と状態間の関係を確認する必要がある場合がある。

問題は、次の点にある。

> **状態が個別に存在していても、それらが同じ Target State Entry を中心として、1回の明確な状態遷移判定として整理されているとは限らない。**

---

## 1. 各システムはそれぞれの役割に応じて状態を管理する

複雑な自動化システムや製造システムでは、各システムがそれぞれの役割に応じて状態を管理する。

MES は、タスク、作業指示、生産プロセスを扱う。

WCS は、スケジューリング、経路、資源、実行状態を扱う。

PLC は、設備、動作、シーケンス制御を扱う。

ロボットコントローラは、モード、軌跡、動作状態を扱う。

画像認識システムは、認識結果、位置、信頼度を扱う。

安全システムは、安全許可や危険動作の制限を扱う。

各システムは、それぞれの機能を実行するために固有の状態情報を管理する必要がある。

そのため、同じ現場で次の状態が同時に存在することもある。

```text
MES Task = Released
WCS Task = Pending
Robot = Ready
Station = Available
Area Permission = False
```

これらの状態値は、同時に存在し得る。

これらの状態値だけでは、次の点まで直接説明できない。

> **今回の Target State Entry における状態遷移が成立しない理由は何か。**

---

## 2. 状態値と状態遷移の判定関係を区別する

状態記録が主に示すのは、次の内容である。

> **ある対象が現在どのような状態にあるか。**

状態遷移判定では、さらに次の点を確認する必要がある。

> **その状態が、今回の Target State Entry に対してどのような意味を持つか。**

例えば、

```text
Robot Ready = TRUE
```

という状態は、ロボットが現在、運転可能な状態にあることを示す。

この状態だけでは、次の内容は分からない。

- 現在、システムは何を実行しようとしているか。
- この Ready が今回の Target State Entry に直接関係するか。
- 他に必要な C：Condition が成立しているか。
- 今回の動作に必要な A：Authority が成立しているか。
- Target State への移行後に、E：Execution Chain が継続できるか。

したがって、

> **状態値を記録することと、その状態が今回の Target State Entry においてどのような判定上の役割を持つかを定義することは、異なるエンジニアリング課題である。**

---

## 3. 共通の判定対象を定義するには Target State を明確にする必要がある

システムが次にどの状態へ移行しようとしているかが明確でなければ、どの状態が今回の判定に関係するかも明確にできない。

例えば、

```text
Current State：ピックアップ待ち
Target State：ピックアップ段階
```

という場合と、

```text
Current State：異常処理完了
Target State：自動運転への再投入
```

という場合では、Target State Entry に関係する Condition、Authority、Execution Chain の状態は同じではない。

そのため、既存システムに状態項目を追加し続けても、それだけで状態遷移判定が明確になるとは限らない。

基本的な確認事項は、次のとおりである。

> **これらの状態は、どの Target State Entry に対する判定に使用されるのか。**

Current State と Target State が明確になることで、次の内容を整理できる。

- どの状態が今回の Target State Entry に直接関係するか。
- どの状態が今回の判定では背景情報となるか。
- Target State への移行に必要な状態は何か。
- 状態値は存在していても、今回の判定時点では有効な根拠として使用できない状態があるか。

状態情報の量と状態遷移判定の明確さは、それぞれ確認する必要がある。

---

## 4. 複数システムの協調では判定関係の整理が必要になる

単体設備の内部では、多くの状態関係をシーケンスプログラムやインターロックに直接組み込むことができる。

システム規模が大きくなると、1回の Target State Entry における状態遷移判定が、複数システムの状態に依存する場合がある。

```text
MES
↕
WCS
↕
PLC
↕
ロボット
↕
画像認識システム
↕
安全システム
↕
下流設備
```

この場合、各システムが扱うのは、状態遷移全体に関係する情報の一部である。

例えば、

- MES ではタスクが実行可能な状態になっている。
- WCS では資源解放を待っている。
- PLC では自設備の準備が完了している。
- ロボットは Ready を表示している。
- 安全システムではエリア許可がまだ成立していない。

これらの状態は、相互に矛盾せず同時に存在する場合がある。

確認すべき点は、次のとおりである。

> **これらの状態が、同じ Target State Entry に対する共通のエンジニアリング関係として整理されているか。**

整理されていない場合、現場では複数システムをまたいで状態間の関係を再構成する必要がある。

---

## 5. 状態値の正しさと判定時点での有効性を区別する

状態値が正しくても、次の状況が発生する場合がある。

> **その状態値を、今回の Target State Entry の判定根拠として使用できない。**

例えば、

- 検査結果が有効時間を超えている。
- Ready が長時間更新されていない。
- 上流と下流で状態更新時刻が一致していない。
- 許可がすでに取り消されている。
- 対象が切り替わった後も、以前の状態が保持されている。
- システムが状態の切替中である。

このため、状態遷移設計では、次の2点を確認する必要がある。

> **状態値が何であるか。**

> **その状態が今回の Target State Entry とどのような関係にあり、現在も判定根拠として有効か。**

この関係を明確にするには、状態監視項目やログ項目の追加に加え、Target State Entry との関係および判定時点での有効性を定義する必要がある。

---

## 6. 状態遷移判定の対象を明確にする

現場での調査が、例えば次のような手順を必要としている場合がある。

```text
MES を確認
→ WCS を確認
→ PLC を確認
→ ロボットを確認
→ 安全システムを確認
→ 時刻を照合
→ 状態間の関係を整理
```

この場合、複数システムの状態はすでに記録されていても、1回の Target State Entry に対する状態遷移の判定関係を、人があらためて整理していることになる。

現場で明確にすべき問いは、次の2点である。

> **追加して記録すべき状態は何か。**

> **システムが現在どの Target State へ移行しようとしており、どの状態が今回の Target State Entry における状態遷移判定に関係するのか。**

状態遷移判定を設計する上では、後者が中心となる。

TPCA / PCN が対象とするのは、このエンジニアリング問題である。

> **異なるシステムに分散している状態を、明確な Target State Entry を中心として整理し、状態遷移判定に必要な関係を明示する。**

これらの状態を、さらにどのように構造化判定、制御、履歴へつなげるかについては、以下を参照。

## エンジニアリング上の結論

多数の状態情報を保持しているシステムで状態遷移を明確に判定するには、各状態と Target State Entry との関係を定義する必要がある。

状態記録が主に示すのは、次の内容である。

> **各対象が現在どのような状態にあるか。**

状態遷移設計では、さらに次の内容を明確にする必要がある。

> **システムが現在どの Target State へ移行しようとしているか。それぞれの状態が今回の Target State Entry にどのように関係し、なぜ移行できるのか、またはなぜ移行できないのか。**

整理すべき対象は、次の状態間の関係である。

> **明確な Target State Entry を中心として整理される状態間の関係。**

TPCA / PCN は、このように分散している状態情報と判定関係を、明確なエンジニアリング設計対象として扱う。

多くの自動化プロジェクトでは、稼働開始後にシステム全体の運転ロジックを把握しているエンジニアが少数に限られる場合が多い。

設備は運転でき、PLC プログラムにはコメントがあり、HMI にも状態やアラームが表示される。

しかし、現場で次のような状態が発生すると、

- Ready は成立しているが、次の段階へ進まない。
- Waiting が長時間継続しているが、何を待っているのかを直接判断できない。
- 複数のシステムに明確な故障はないが、全体の処理が継続しない。
- 異常処理は完了しているが、システムが想定した後続の実行状態へ移行しない。

システム全体の関係を把握しているエンジニアによる確認が必要になる場合がある。

その理由の一つは、次のような重要な関係がシステム上で十分に整理されていないことにある。

> この Ready は、この設備自身の状態だけを示している。  
> ここでは、別システムからの許可も必要である。  
> この状態値は正常表示だが、今回の判定時点ではすでに有効ではない。  
> 下流設備はオンラインだが、現在は受入できない。  
> 異常は解除されているが、システムはまだ後続実行へ進める状態ではない。　

これらの判断には、設計・立上げ・保守で蓄積されたエンジニアリング知識が含まれている。

一方、その判断関係がプログラム、インターフェース、少数のエンジニアの経験に分散したままでは、後から同じ判断根拠を確認するために、複数の情報を再構成する必要がある。

---

## 1. プログラムが存在していても、状態遷移の判定関係が明確とは限らない

複雑な自動化システムには、すでに多くのプログラム、状態、制御機構が存在する。

例えば、次のようなものである。

- PLC シーケンスプログラム
- Interlock
- Handshake
- 設備 Ready
- アラーム
- 上下流インターフェース
- MES / WCS 状態
- 調整パラメータ
- 異常処理ロジック

これらは、それぞれシステム運転に必要な役割を持つ。

一方、一回の Target State Entry が成立するかを決める判定関係は、複数の場所に分散している場合がある。

- 一部は PLC プログラムに記述されている。
- 一部は上位システムから取得される。
- 一部は設備間インターフェースに定義されている。
- 一部は立上げ時の調整ルールやプロジェクト固有の運用として定着している。
- 一部はシステム全体を把握しているエンジニアが判断基準として保持している。

そのため、プログラムや文書が残っていても、新たに担当するエンジニアは、次の関係をあらためて確認する必要がある場合がある。

> **なぜこの状態では次へ進めるのか。なぜ別の状態では待機するのか。**

重要なのは、プログラムの有無だけではなく、Target State Entry に対する状態遷移判定が明確な関係として表されているかどうかである。

---

## 2. エンジニアリング経験そのものが問題なのではない

エンジニアリング経験は、複雑な設備や生産システムを設計、立上げ、保守する上で重要である。

設計、調整、現場対応を通じて蓄積された判断能力は、システムを安定して運転するための重要な要素である。

確認すべき点は、

> **その経験が、長期的に保持・再利用できるエンジニアリング定義へ移行されているか。**

である。

判断関係が個人の経験に残ったままの場合、例えば次のような状況が発生しやすい。

- 同種設備でも、設計担当者によって待機処理や異常処理の考え方が異なる。
- プロジェクト引継ぎ後、主要な状態遷移を理解するために大量のプログラムを再確認する必要がある。
- 同じ問題が別の生産ラインで発生した際、同じ判定関係を再度検討する必要がある。
- 現場問題を解決しても、プログラム変更結果だけが残り、そのときの判定根拠が残らない。
- システムの長期運用後、既存の制御条件が設定された理由を説明できる担当者が少なくなる。

長期的に引き継ぎにくいのは、プログラムそのものだけではない。

> **なぜこのように設計したのか。**

という判定根拠も、同時に残す必要がある。

---

## 3. 状態遷移判定は設計情報として残りにくい

複雑な自動化システムでは、多くのエンジニアリング判断が、最終的に次の問いへ集約される。

> **システムは現在の状態から Target State へ入れるか。**

例えば、ロボットがピックアップ段階へ入る場合、次のような状態が同時に関係することがある。

- ワーク状態
- 認識結果
- 設備状態
- 安全許可およびエリア許可
- 上位システム状態
- 下流受入状態
- 今回のピックアップに関係するその他の状態

これらの情報は、異なるコントローラ、異なるシステム、異なる責任範囲に分散している場合がある。

これらの関係が同じ Target State Entry を中心として整理されていない場合、システムが次へ進めるかどうかの確認は、システム全体の関係を理解しているエンジニアの判断に依存しやすくなる。

したがって、個人の経験として残りやすいのは、

> **一回の Target State Entry が、なぜ成立するのか、またはなぜ成立しないのか。**

という状態遷移判定である。

---

## 4. 状態遷移を明確な設計対象とする

少数のエンジニアへの長期的な依存を減らすためには、コメントを増やすことや、すべてのロジックを一つのプログラムへ集約することだけでは十分ではない。

重要なのは、

> **一回の明確な Target State Entry を、独立したエンジニアリング設計対象として扱うこと。**

である。

まず、次の関係を明確にする。

```text
Current State
→ Target State
```

その上で、今回の Target State Entry に対して次の事項を定義する。

- どの状態が今回の進入に直接関係するか。
- どの状態を C：Condition にマッピングするか。
- どの A：Authority が必要な許可となるか。
- Target State へ入った後の E：Execution Chain に関係する状態は何か。
- 今回の判定に使用する状態が現在も有効か。
- Target State Entry が成立しない場合、どのような判定結果と後続処理を形成するか。

このように整理することで、プログラム、インターフェース、個人の経験に分散していた判定関係を、同じ Target State Entry に対するエンジニアリング文脈で扱えるようになる。

TPCA / PCN が対象とするのは、この状態遷移前のエンジニアリング問題である。

C / A / E、S / D / B、Arbitration、Multipath Control などの詳細については、以下を参照。

## 5. 明示する効果は、まず保守と引継ぎに現れる

状態遷移判定を明確に表現すると、保守、引継ぎ、再利用の際に判定根拠を確認しやすくなる。

後続のエンジニアは、例えば次の事項を確認できる。

- なぜこの状態を Target State Entry の判定に使用しているのか。
- なぜこの許可が必要な制約となっているのか。
- なぜこの Waiting は正常な待機として扱われるのか。
- なぜこの状態の組合せでは次の実行へ進まないのか。
- 異常処理後、後続の Target State Entry で何を確認する必要があるのか。

これにより、プロジェクト引継ぎ時の確認を、

> 「以前このプロジェクトを担当した人に確認する。」

だけに依存するのではなく、

> **明確な状態遷移設計に基づいて、システムがそのように動作する理由を確認する。**

という形へ移行できる。

これは、設備の長期保守、生産ラインの横展開、チーム間連携、同種設備への再利用に直接関係する。

---

## 6. 「どう対処したか」だけでなく「なぜその設計なのか」を残す

個人の経験は、現場問題への対応に有効である。

一方、問題解決後にプログラム変更履歴だけが残る場合、新しい判定関係が再び暗黙化することがある。

状態遷移設計では、

> **今回どのように変更したか。**

だけでなく、

> **なぜこの状態では Target State Entry を許可し、別の状態では許可しないのか。**

という設計根拠も残す必要がある。

これらの判断を明示することで、エンジニアリング経験を、長期的に保守、再利用、引継ぎできる設計情報へ移行できる。

## エンジニアリング上の結論

状態遷移設計が長期にわたり個人の経験に依存する理由は、オートメーションシステムにプログラム、状態、アラームが不足しているからではない。

重要な点は、

> **Current State から Target State へ入れるかを決める状態、許可、Execution Chain、状態の有効性に関する判定が、複数のプログラム、システムインターフェース、エンジニアの経験に分散していることである。**

これらの判定が明確な Target State Entry を中心として整理されていない場合、システム規模が大きくなり、運用期間が長くなるほど、全体の関係を把握している少数の担当者への依存が大きくなりやすい。

したがって、明示すべき対象は、個別の信号や一つのプログラムだけではない。

より重要なのは、

> **システムが現在どの Target State へ入ろうとしており、その Target State Entry に対して、なぜ進入を許可できるのか、またはなぜ進入できないのか。**

という状態遷移判定である。

TPCA / PCN は、このような状態遷移判定を、個人の経験に依存した暗黙の判断から、明確なエンジニアリング設計対象へ移行するための構造として扱う。
